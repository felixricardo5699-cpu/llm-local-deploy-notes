# 多模态微调

> [!abstract] 一句话讲清楚
> 多模态微调是让模型学会"看特定类型的图，并按你的业务方式回答"。它比文本微调贵、坑更多，因为图像会占掉大量 token，而且一半以上的需求其实用"OCR + 文本模型"就能更便宜地解决。

## 为什么重要

- 你现在的位置：文本微调的全链路（数据 → 训练 → 评估 → 部署）走通了，需求里出现了图片：票据识别、报表问答、UI 理解、质检、看图客服。这时才需要这篇。
- 上游是 [[多模态模型原理]]（视觉编码器 + 连接层 + 语言模型的三段式结构），下游还是 [[合并导出与部署闭环]]，只是多了图像预处理这条路。
- 不懂会踩的坑：
  - 图片分辨率一压，小字全糊了，模型当然认不出——不是模型不行，是预处理错了。
  - 以为"冻结视觉编码器"一定是对的，结果业务是全新领域（如工业缺陷图），冻结后根本学不会。
  - 按文本微调的数据量标准准备数据，结果几千条图文对训出来还是不行。
- 一句话原则：**先问"这活能不能 OCR 完交给文本模型"，答案是否，再谈多模态微调。**

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| VLM | Vision-Language Model | 能同时看图和读文字的模型 | 和"扩散模型"完全不是一类，别和画图的搞混 |
| 视觉编码器 | Vision Encoder / ViT | 把图片切成小方块并编码成向量 | 通常冻结不训，但领域差异大时要解冻 |
| 投影层 / 连接层 | Projector / Connector | 把图片向量"翻译"成语言模型能懂的向量 | 多模态微调里最重要的可训练部分之一 |
| 图像 token | Image Tokens | 图片编码后占用的 token 数 | 一张图可能顶几百上千个文字 token，显存大头 |
| 图文对 | Image-Text Pair | 一条训练样本 = 一张图 + 一段问答 | 不是"图 + 一段描述"，要的是问答对 |
| 多图输入 | Multi-image | 一次输入多张图（对比、连续帧） | token 消耗成倍增长，容易 OOM |
| 分辨率策略 | Resolution Strategy | 图片怎么缩放/切块送给编码器 | 压太小丢字；原图太大爆显存 |
| 冻结 | Freeze | 训练时不更新某部分参数 | 冻结视觉编码器能省显存、防遗忘 |
| 解冻 | Unfreeze | 放开某部分参数让它学 | 数据量大/领域差异大才考虑 |
| OCR | Optical Character Recognition | 把图里的字识别成文本 | 很多"多模态需求"其实是 OCR + 文本模型 |
| Grounding | 视觉定位 | 让模型指出"这个东西在图里哪" | 需要框标注数据，比问答难 |
| 幻觉 | Hallucination | 图里没有的东西被模型说出来 | 多模态更严重，评估必须查 |

## 原理与机制

### 直觉版

多模态模型像一个**翻译 + 专家**的组合：

1. **视觉编码器**是"眼睛"，负责把图看成特征——它通常是现成的、很强的，不用重新教。
2. **投影层**是"翻译官"，把眼睛看到的东西翻译成语言模型能理解的语言。
3. **语言模型**是"大脑"，负责理解问题、组织回答。

微调的时候，多数做法是：**眼睛不动（冻结），翻译官和大脑稍微调一下（投影层 + LLM 部分 LoRA）**。

### 拆解版：图像是怎么变成一个"词"的

1. 图片被切成固定大小的小块（patch），比如 14×14 像素一块。
2. 视觉编码器把每个小块变成一个向量。
3. 投影层把这些向量映射到语言模型的词向量空间。
4. 于是图片变成了**一串"图像 token"**，和文字 token 拼在一起送进语言模型。
5. 模型像读文字一样"读"图，然后生成回答。

**这带来两个直接后果**：

- **显存开销大**：一张高分辨率图可能产生上千个图像 token，长度是文字的很多倍。所以多模态训练吃显存，主要吃在序列长度上。
- **分辨率决定信息量**：字小、图密、表格细的场景，图被压缩得太狠就"看不见"了。这是多模态效果差的头号原因之一，而且和训练无关。

### 为什么多模态比文本微调更难

| 维度 | 文本微调 | 多模态微调 |
|---|---|---|
| 数据构造 | 写问答对 | 还要管图片质量、分辨率、标注对齐 |
| 显存 | 主要看文本长度 | 图像 token 占比高，显存压力大 |
| 可训练部分 | 明确（LoRA） | 要决策：编码器/投影层/LLM 各放开多少 |
| 失败归因 | 相对清晰 | 可能是图的问题、预处理问题、模型问题，难定位 |
| 评估 | 文本比对/人工 | 还要判断"是不是看图答的"（防幻觉） |
| 部署 | 单模型 | 引擎要支持视觉输入，链路更长 |

## 从业务任务倒推方案

| 业务任务 | 典型输入 | 真需要多模态微调吗 | 建议方案 |
|---|---|---|---|
| 票据/合同/证件字段提取 | 扫描件 | 不一定 | **OCR + 文本模型 + 规则校验**，更便宜更可控 |
| 报表/图表问答 | 截图 | 是 | 多模态微调，数据要覆盖同类图表 |
| UI / 界面理解 | App 截图 | 是 | 多模态微调，注意分辨率和元素定位 |
| 工业质检 | 产品照片 | 是，且领域差异大 | 可能要解冻部分编码器，数据量要求高 |
| 看图客服 | 用户上传照片 | 视情况 | 先试试通用 VLM 零样本，不够再微调 |
| 视频内容理解 | 视频帧 | 是，但成本高 | 抽帧 + 多模态，或先用语音/文本链路 |

> 判断口诀：**"AI 能不能只靠文字把这件事做完？"** 能 → 别上多模态；不能 → 看差异是"认字"还是"理解图"，认字用 OCR，理解图才微调。

## 训练数据怎么构造

### 格式

主流框架多模态 SFT 的样本结构，一般是在 sharegpt 对话结构里，给每条样本挂一个图片路径：

```json
{"messages": [{"role": "user", "content": "<image>这张报表第三季度营收是多少？"}, {"role": "assistant", "content": "第三季度营收是 ……"}], "images": ["data/reports/q3.png"]}
```

- 对话里用 `<image>` 之类的占位符标出图片位置，具体写法**以你用的模型和框架文档为准**。
- `images` 字段的路径要和图片实际存放位置一致，路径错误是加载失败的第一大原因。

### 数据要求

1. **图片质量优先**：清晰、无遮挡、业务真实场景。手机翻拍的模糊图会教坏模型。
2. **分辨率要匹配业务**：文档类要高分辨率；场景类可以适当降。**先确定预处理管线，再生产数据**，否则数据白做。
3. **问答要"看图才能答"**：如果问题不看图也能猜出来，模型就会学会不看图。
4. **覆盖长尾**：不同光照、角度、版式、字体。只放"漂亮样本"，上线就崩。
5. **负样本**：图里没有答案时该说"图中未提供"，这类样本要专门加，否则模型会硬编。
6. **数据量**：图文对通常比文本少——几百到几千条就能看到效果，但**质量要求更高**。具体以实测为准。

### 图片预处理管线（容易被忽略，但决定成败）

| 步骤 | 做什么 | 错了会怎样 |
|---|---|---|
| 格式统一 | 统一转成模型支持的格式 | 部分图加载失败，被静默跳过 |
| 尺寸处理 | 按模型要求缩放/切块 | 太小丢字，太大 OOM |
| 方向校正 | 处理 EXIF 旋转 | 图是歪的，模型认不出 |
| 色彩/位深 | 统一 RGB | 灰度/CMYK 图异常 |
| 去重 | 相同图不同尺寸算重复 | 模型背图 |
| 隐私处理 | 人脸/证件打码 | 合规风险 |

## 视觉编码器到底冻不冻结

| 策略 | 显存 | 效果 | 什么时候用 |
|---|---|---|---|
| 全冻结（只训投影层 + LLM LoRA） | 最省 | 通用场景够用 | 默认首选，业务图和预训练分布接近 |
| 解冻投影层 + LLM LoRA | 中 | 最常用 | 绝大多数业务场景 |
| 解冻部分视觉编码器层 | 较高 | 领域差异大时有用 | 工业/医疗/遥感等特殊图像 |
| 全解冻 | 最高 | 理论上限高，但极易过拟合 | 数据量大、有专业团队才考虑 |

> 推荐路径：**先全冻结跑一版 baseline → 不够再解冻投影层 → 还不够再解冻编码器顶部几层**。每一步都用评估集验证，别一次全放开。

## 显存与数据量的量级参考

| 项目 | 量级参考 | 说明 |
|---|---|---|
| 7B 级 VLM 的 LoRA 微调 | 单卡 24GB 偏紧，常见要 40GB+ | 图像 token 让序列变长，比同规模文本微调更吃显存 |
| 图像 token 数量 | 一张图几百到上千 token | 高分辨率/多图时成倍增长 |
| 起步数据量 | 几百到两千条高质量图文对 | 比文本少，但每条成本高得多 |
| 多图/视频场景 | 显存和时间再翻倍 | 通常要减 batch、减帧数 |

> 这里全是量级，不是精确值。**不同模型、不同分辨率策略差很多，以实测为准**；实在吃不下就降分辨率、减图像 token、缩短回答长度。

## 决策点

- **岔路口 1：这个需求到底要不要多模态微调**
  - 判断依据：任务能不能拆成"OCR 取字 + 文本模型处理"？
  - 推荐：能拆就拆。OCR 链路便宜、可控、易排错；多模态是"图和语义强相关"才值得。
  - 代价：OCR 对复杂版面/图表/手写容易崩；多模态链路贵且难归因。

- **岔路口 2：视觉编码器冻不冻**
  - 推荐：默认全冻结，只训投影层 + LLM LoRA。
  - 代价：领域图像差异大时会欠拟合；解冻虽然提效果，但显存涨、掉通用能力的风险也涨。

- **岔路口 3：通用 VLM 零样本够不够**
  - 推荐：**先用最强可用的开源 VLM + 好 prompt 试 50 条真实样本**，再决定要不要微调。
  - 代价：零样本可能格式不稳；但先试一天，能省掉一周训练。

- **岔路口 4：图像分辨率怎么定**
  - 推荐：从"业务里最小但必须看清的字/元素"反推所需分辨率，再验证模型支持的上限。
  - 代价：分辨率高 → 显存和延迟都涨；低 → 关键信息丢失，怎么训都救不回来。

- **岔路口 5：评估怎么防"不看图瞎编"**
  - 推荐：评估集里放**对照题**——同一问题配无关图，正确行为是"图中没有相关信息"。
  - 代价：评估集制作麻烦；但没有这类题，你根本不知道模型是真看图还是在编。

## 参数与配置说明

| 参数 | 作用 | 调大 / 调小的影响 | 常见取值 |
|---|---|---|---|
| 图像分辨率 / `image_size` | 输入图片的尺寸 | 大 → 细节多但 token 多、显存涨；小 → 省但丢字 | 按业务最小可读尺寸定 |
| `max_pixels` / 最大像素数 | 限制单图 token 上限 | 大 → 吃显存；小 → 细节丢 | 由显存反推 |
| 每样本图片数 | 一次送几张图 | 多 → 能做对比但 token 翻倍 | 先单图，必要时多图 |
| 视觉编码器冻结策略 | 训不训视觉部分 | 解冻 → 效果上限高、显存高 | 默认冻结 |
| `freeze_vision_tower` | 同类开关的常见配置名 | 同上 | 以框架文档为准 |
| LLM 部分 LoRA rank | 语言部分的补丁宽度 | 大 → 表达强、显存涨 | 16~64 量级起步 |
| `cutoff_len` | 图文总序列长度上限 | 小 → 图或回答被截断；大 → OOM | 按 token 实测调 |
| batch size | 每步样本数 | 多模态通常只能开很小 | 1~2 起步 |
| 梯度检查点 | 重算激活省显存 | 开 → 必开选项之一 | 显存紧张时开 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 文档/票据上的小字永远认错 | 图片预处理时压得太小 | 提高分辨率或切块后分别识读；用 OCR 校验 |
| 模型答得挺顺但全是编的 | 训练数据里问题不看图也能答，模型学会忽略图 | 加"必须看图"的样本 + 无关图对照负样本 |
| 训练 loss 降了但效果没提升 | 只训了投影层，表达容量不够；或数据太单一 | 放开 LLM LoRA，扩数据多样性 |
| 训完通用看图能力变差 | 数据太窄 + 训练太猛，视觉-语言对齐被破坏 | 降 lr/epoch、混通用图文数据、冻结编码器 |
| 训练时大量样本被跳过 | 图片路径错、格式不支持、尺寸异常 | 训练前打印"成功加载条数"，逐条核对 |
| 多图/视频场景必 OOM | 图像 token 数量爆炸 | 减图数/帧数、降分辨率、缩回答长度、开梯度检查点 |
| 部署到推理引擎后不支持图片输入 | 选的引擎/模型格式不支持视觉输入 | 训练前就确认部署引擎支持该 VLM 架构 |
| 评估分数不错，客户说不准 | 评估集里没有"图里没答案"的题 | 补对照题，把"该拒答"也算对 |

## 自检问题参考答案

> [!success]- 1. 多模态模型的三部分是什么？微调通常动哪两个？
> 三部分是视觉编码器（眼睛，把图切成 patch 编码成向量）、投影层/连接层（翻译官，把图像向量映射到语言模型空间）、语言模型（大脑，理解问题组织回答）。
> 微调通常动投影层 + 语言模型的 LoRA，视觉编码器默认冻结——它通常已经很强，冻结能省显存、防遗忘。
> 只有领域图像差异很大时才考虑解冻。

> [!success]- 2. 为什么多模态微调比同规模文本微调更吃显存？
> 因为图像会变成大量图像 token：一张图可能几百到上千个 token，和文字拼在一起后序列长度成倍增长，而显存里的激活值和序列长度强相关。
> 所以同样 7B 模型，文本微调能开更大 batch，多模态通常只能开 1~2。
> 多图或视频帧还会再翻倍，通常要减图数、降分辨率、缩回答长度。

> [!success]- 3. "票据识别"需求怎么判断用 OCR 还是多模态？
> 先问"这活能不能只靠文字做完"。票据主要是认字和字段抽取，用 OCR + 文本模型 + 规则校验更便宜、可控、易排错，还能逐字段校验。
> 只有当版面理解、图表语义、判断画面内容是关键时，才值得上多模态。
> 口诀：认字用 OCR，理解图才微调。先拿 20 张真实图各跑一版做对比。

> [!success]- 4. 什么情况下才需要解冻视觉编码器？代价是什么？
> 只有领域图像和预训练分布差异很大时才需要：工业缺陷图、医疗影像、遥感、特殊仪器截图这类，冻结后模型根本"看不懂"这类视觉特征。
> 代价是显存明显上升、训练变慢、过拟合和掉通用看图能力的风险都涨。
> 推荐路径：先全冻结跑 baseline → 不够解冻投影层 → 还不够只解冻编码器顶部几层，每步都拿评估集验证。

> [!success]- 5. 图像分辨率为什么必须在造数据前定下来？
> 因为分辨率决定模型能看到多少信息，也决定预处理管线和 token 开销。
> 如果先做数据、后定分辨率，很可能发现数据是按小尺寸准备的、关键小字看不清，只能重做——图压太狠字就糊了，怎么训都救不回来，而且这属于预处理问题，和训练无关。
> 所以先按"业务里最小但必须看清的字"反推分辨率，再生产数据。

> [!success]- 6. 怎么设计评估题，才能发现模型其实没看图？
> 放对照题：同一个问题配一张无关图，正确行为是"图中没有相关信息、无法回答"。
> 再放"图里有答案但问题不看图也能猜出来"的陷阱题，看它是不是在硬编。如果模型不管配什么图都答得很顺，基本就是没看图。
> 这类负样本在训练数据里也要加，否则模型会学会忽略图、直接猜。

> [!success]- 7. 多模态数据量为什么可以少？为什么质量要求更高？
> 因为图文对里图片承载的信息密度高，几百到几千条就能让模型学到"这类图怎么答"，比纯文本样本的边际效用高。
> 但每条样本的处理成本（图片质量、分辨率、标注对齐）高得多，一条脏图会教坏模型，而且图像问题很难从 loss 上看出来。
> 所以量可以少，质检必须更严，宁少勿滥。

> [!success]- 8. 部署到推理引擎前，多模态链路要多确认哪两件事？
> 一是引擎是否支持该 VLM 架构和视觉输入（很多引擎只吃文本模型，或格式要求不同）。
> 二是图像预处理管线是否和服务端一致——分辨率策略、切块方式、模板里 `<image>` 占位符的写法。
> 这两件不对，模型效果再好也跑不对。所以训练前就确认部署引擎，别训完才发现不支持。

## 交付视角（对客户怎么讲）

- 客户会问："我要它看懂我们这些表格和单据，能做吗？"
  - 大白话：**"分两种情况：如果只是要把图里的字读出来，我们用识别 + 规则校验，又快又便宜；如果要理解图表含义、判断画面内容，才需要训一个看图模型，成本会高不少。先给我们 20 张真实图片，我们各跑一版给您对比。"**
- 报价要点：
  1. 多模态按"数据条数 × 图片复杂度"报价，别按文本单价套；
  2. 明确分辨率/拍摄要求的验收前提——**图拍不清楚属于数据问题，不算模型问题**；
  3. 部署环境和推理引擎要支持视觉输入，这部分要么客户提供，要么单列部署费。
- 预期管理：**"看图模型最容易出的问题是'看起来答得很像回事，其实是编的'。我们会专门做对照测试，把'图里没有答案时该说没有'也算进验收。"** 这句话能极大提升专业感，也避免后期扯皮。

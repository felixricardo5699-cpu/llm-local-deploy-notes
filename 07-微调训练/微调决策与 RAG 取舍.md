# 微调决策与 RAG 取舍

> [!abstract] 一句话讲清楚
> 微调不是"更好的方案"，只是四类需求里的一类解药。这篇给你一套判断框架：先把客户需求分成知识注入、格式风格、角色语气、能力补强四类，再分别对应 RAG、微调、Prompt、换模型/蒸馏，最后用成本表和三个反问确认。

## 为什么重要

- 这是整个微调领域的**第一道闸门**。判断错了，后面数据、训练、评估全白做，浪费的是几天时间和一张卡的租金。
- 它是**接单场景里最容易翻车的地方**：客户说"帮我微调一个懂我们公司的模型"，你吭哧训一周，发现他要的只是能查到内部文件——RAG 三天就能交付，还更好维护。
- 反过来的坑也有：明明是格式/风格问题，硬上 RAG，检索一堆资料给模型"看"，模型该不会输出 JSON 还是不会，成本反而更高。
- 位置：上游是 [[RAG 原理与全链路]] 与 [[提示词与上下文工程]]，下游决定你要不要读 [[训练数据工程]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 微调 | Fine-tuning, FT | 在基座模型上再训一轮，把私有数据"融进"模型权重 | 不等于"让模型知道更多知识"，SFT 主要学的是"怎么回答" |
| SFT | Supervised Fine-Tuning | 监督微调，用"问题→标准答案"对喂给模型学 | 最常见的一种微调，和"继续预训练"不是一回事 |
| RAG | Retrieval-Augmented Generation | 检索增强生成：先查资料，再让模型照着资料回答 | 知识在外部库里，不在权重里，所以能改能溯源 |
| 知识注入 | Knowledge Injection | 让模型"知道"某个事实/文档内容 | 首选 RAG，不是微调。微调注入知识会幻觉且难更新 |
| 格式对齐 | Format Alignment | 让模型稳定输出固定结构（JSON、表格、模板） | 微调最擅长的场景，比长 prompt 稳且省 token |
| 角色 / 语气 | Persona / Tone | 让模型说话像一个特定角色（客服、顾问、品牌口吻） | Prompt 能覆盖大半，微调负责"稳定性"和"省 token" |
| 能力补强 | Capability Uplift | 提升推理、代码、数学、长上下文等硬能力 | SFT 基本做不到，要换更强的基座或蒸馏 |
| 蒸馏 | Distillation | 用强模型的输出去训小模型，把小模型"教"到接近强模型 | 常见做法是先让强模型生成数据，再 SFT 小模型 |
| 继续预训练 | CPT, Continued Pre-Training | 用大量无标注语料继续训，学语言/领域分布 | 数据量要求是 SFT 的几十倍，个人接单极少做 |
| 灾难性遗忘 | Catastrophic Forgetting | 微调太猛，把基座原有的通用能力"洗掉" | 表现是闲聊、常识、指令遵循变差 |
| few-shot | 少样本提示 | 在 prompt 里放几个示例让模型照做 | 能解决 60%~80% 的格式需求，先试它，几乎零成本 |
| 验收用例集 | Acceptance Set | 出钱方认可的一组"答对才算过"的测试题 | 没有它，微调项目必扯皮 |

## 原理与机制

### 直觉版

把模型想象成一个刚招进来的实习生：

- **RAG** = 给他配了个可检索的资料柜。他不知道的，查一下就能答；资料更新了，换一下柜子里的文件就行。
- **微调（SFT）** = 带他做几天业务演练，把"我们公司的话术和格式"练成肌肉记忆。他说话的方式变了，但知识面不会因此扩大。
- **Prompt** = 当面交代一句"以后回答都按这个模板来"。一句话就管用，但他忙起来可能忘。
- **换模型/蒸馏** = 换一个更聪明的实习生，或者让老员工把经验总结成手册教新人。

### 拆解版：判断顺序不能反

1. **先分清需求类型**。绝大多数需求不是纯粹的某一类，要拆成"知识 + 格式 + 语气"的组合，分别给方案。
2. **从最便宜的方案试起**：Prompt / few-shot → RAG → 微调 → 换模型。便宜方案能解决 70% 的问题，剩下的才是微调的空间。
3. **微调只解决"行为"问题**：输出结构、话术、判别边界、特定任务的条件反射。它改变的是模型的"行为分布"，不是"知识库"。
4. **能力问题是硬门槛**：基座模型本身不会做的推理，SFT 数据里教几百遍也大概率学不会——它只是在模仿答案格式，换个题就露馅。

### 三个反问，问完基本就有答案

| 反问 | 如果答案是"能" | 如果答案是"不能" |
|---|---|---|
| 把全部相关资料塞进 prompt，模型能不能答对？ | 知识问题 → **RAG** | 继续问下一个 |
| 换一个更强的模型 + 好 prompt，能不能答对？ | 不用微调 → **换模型或加 Prompt** | 能力有缺口，微调也难补 → **降需求或蒸馏** |
| 问题是不是只在"格式/语气/稳定性"上？ | **Prompt 先上，不够再微调** | 大概率是知识或能力问题，回到上面 |

## 四类需求对照表

| 需求类型 | 典型说法 | 首选方案 | 次选方案 | 不推荐 | 原因 |
|---|---|---|---|---|---|
| 知识注入 | "要懂我们产品手册 / 内部制度 / 合同条款" | RAG | 长上下文 + 全文塞入 | 微调 | 知识会变、要溯源、要权限，微调全做不到 |
| 格式风格 | "必须输出固定 JSON / 固定报表 / 固定话术结构" | few-shot Prompt | SFT 微调 | RAG | 格式是行为，越稳定越该内化到权重里 |
| 角色语气 | "要像我们客服 / 要专业顾问口吻" | Prompt + 人设 | 轻量 LoRA | RAG | 语气和知识无关，检索帮不上忙 |
| 能力补强 | "数学不好 / 代码写不对 / 长文推理弱" | 换更强基座 | 蒸馏 + SFT | 纯 SFT | SFT 不创造能力，只会模仿格式 |
| 混合需求 | 既要查内部文档，又要固定话术 | RAG + 小 LoRA | 只做 RAG 先上线 | 只做微调 | 两件事分开解，各用各的工具 |

> 一句话记法：**知识进库，格式进权重，语气进 Prompt，能力进模型。**

## 成本对比：别只看训练那一天

| 维度 | RAG | LoRA 微调 | Prompt / few-shot | 换更大模型 |
|---|---|---|---|---|
| 前期时间 | 1~3 天（解析+切分+调检索） | 3~10 天（数据占 80%） | 半天 | 半天（换卡另算） |
| 硬件要求 | 只要能推理的机器 | 需要能训练的卡（量级见 MOC） | 无额外要求 | 推理显存更高或改用 API |
| 数据要求 | 文档即可，多多益善 | 几百~几千条高质量问答对 | 几条示例 | 无 |
| 知识更新 | 更新库即可，分钟级 | 要重新训，天级 | 改 prompt，分钟级 | 无 |
| 可溯源 | 强，能给出出处 | 弱，答错了看不出依据 | 中，看 prompt 里放没放资料 | 弱 |
| 幻觉控制 | 较好，有资料兜底 | 较差，知识被"焊死"在权重里 | 一般 | 看模型本身 |
| 格式稳定性 | 一般（靠 prompt 约束） | 强 | 中，长对话容易漂 | 中 |
| 维护成本 | 中，要维护解析和索引 | 高，每次迭代都要重训 | 低 | 低（外包给 API） |
| 效果上限 | 受检索质量限制 | 受数据质量和基座能力限制 | 受模型本身限制 | 最高 |
| 交付形态 | 一套服务 + 知识库 | 一个模型文件 / adapter | 一段配置 | 一个 API key |
| 适合报价 | 按知识库规模 + 部署人天 | 按数据条数 + 验收用例 | 按调试人天 | 按 token 或订阅 |

> 表里的天数、条数是**量级经验值**，不同项目差很多，别拿去当报价依据，以自己实测和历史工时为参考。

## 组合方案：真实项目里最常见的三种

| 方案 | 结构 | 适用 | 注意 |
|---|---|---|---|
| 纯 RAG | 检索 + 通用模型 | 客户要"问答准确、有出处" | 检索做不好，模型再好也白搭 |
| RAG + 轻 LoRA | 检索管知识，LoRA 管格式和话术 | 客服、坐席助手、内部问答 | 先上 RAG 验收，再加 LoRA 提稳定性 |
| 纯 LoRA | 无检索，模型内化话术 | 固定任务、离线场景、低延迟 | 知识一旦变就要重训，要提前说清楚 |
| 蒸馏 + LoRA | 强模型生成数据，训小模型 | 要私有化部署又要接近大模型效果 | 数据里会继承强模型的错误和风格 |

## 什么情况下微调才是对的

微调不是洪水猛兽，下面这些场景里它就是**正确答案**，而且 RAG 替代不了：

- **输出必须严格格式化**：每次都要吐出能被程序解析的 JSON / 固定字段，且调用量大到长 prompt 不划算。
- **话术必须一模一样**：品牌口径、合规话术、法律免责声明，不能每次"自由发挥"。
- **任务边界非常窄且重复**：把一段文本改写成固定风格、从工单里抽固定字段。
- **延迟和成本敏感**：每次请求少几百 token 的 prompt，长期算下来差距明显。
- **要私有化且不能联网**：没有 API 可用，又想要比开箱模型更贴合业务的行为。
- **基座已有能力、只差"用起来"**：模型明明会，但不用提示词就不做——微调能把它变成默认行为。

共同点：**这些需求都是"行为"问题，不是"知识"问题。**

## 三个真实需求的判断实录

**案例一：客户说"要一个懂我们产品手册的模型"**

- 拆解：手册内容相对固定、要回答"某个型号支不支持某功能"、还要求给出处。
- 判断：知识注入 → **RAG**。
- 结论：微调是错的。资料更新、可溯源、答错了要能查依据，这三条 RAG 完胜。
- 代价：要维护解析和索引；检索质量决定效果上限。

**案例二：客户说"客服回复太啰嗦，要按我们的话术来"**

- 拆解：不需要新知识，需要固定语气、固定结构、固定长度。
- 判断：角色语气 + 格式风格 → **先 Prompt + few-shot，不够再上小 LoRA**。
- 结论：先花半天改 prompt 验证；如果长对话里语气还是会漂，再训一版几百条的 LoRA。
- 代价：微调要标数据；但训好之后每次少几百 token 的说明，长期更省。

**案例三：客户说"我们的模型数学太差，微调一下"**

- 拆解：这是能力问题，不是知识或行为问题。
- 判断：**SFT 补不了推理能力。**
- 结论：换更强基座，或用强模型生成解题过程做蒸馏；继续在错误答案上 SFT，只会学得更像错误答案。
- 代价：换模型要更多显存；蒸馏要数据成本。**必须提前说清，别等训完才解释。**

## 为什么 RAG 应该先做（三个现实理由）

1. **可逆**：RAG 上线后不合适，改配置就能回退；微调上线后不合适，只能重训。
2. **可解释**：客户问"为什么这么答"，RAG 能给出资料出处；微调的答案是"模型觉得"。
3. **可分期交付**：RAG 一周能出一版，客户先看到东西；微调作为二期，风险和现金流都更好看。

> 反过来，如果 RAG 已经做得很好，客户还是不满意"格式不稳、话太啰嗦"，那就是微调的正确时机——**先让检索把知识兜住，再让微调管风格。**

## 决策点

- **岔路口 1：客户说"要懂我们行业"**
  - 判断依据：问一句"如果把你们的资料贴给它，它能答对吗？"
  - 推荐：能 → 做 RAG；不能 → 先换更强模型试。
  - 代价：RAG 要维护解析和索引；直接微调看着省事，但知识更新一次就要重训一次，后期维护是无底洞。

- **岔路口 2：只要输出格式稳定**
  - 判断依据：先用 few-shot 试 20 条真实输入，看格式稳定率。
  - 推荐：稳定率够 → 不微调；不够 → 上小规模 LoRA（几百条就够）。
  - 代价：微调要标数据、要训、要评估；好处是每次请求省掉几百 token 的格式说明，长期调用量大时反而更省。

- **岔路口 3：要"更像我们的人说话"**
  - 判断依据：看客户能不能接受"每次调用多花几百 token 的 prompt"，以及愿不愿意持续维护 prompt。
  - 推荐：先 Prompt + 人设；上线后发现语气不稳、长对话漂移，再补一个轻量 LoRA。
  - 代价：LoRA 会占用一点推理性能（可合并掉），且需要几十~几百条高质量对话样本。

- **岔路口 4：效果不够好，客户想"再训大一点"**
  - 判断依据：拿验收用例集跑一遍，错误是"不知道"还是"不会做"。
  - 推荐：不知道 → 补数据/RAG；不会做 → 换模型或蒸馏，不要加训练轮次硬怼。
  - 代价：换模型意味着显存和成本上升，必须提前和客户对账。

- **岔路口 5：预算只够做一件事**
  - 推荐：先做 RAG。它能立刻交付、能被验收、后续可扩展；微调可作为二期增值项。
  - 代价：先 RAG 可能拿不到"模型定制"的溢价，但翻车率低得多。

## 参数与配置说明

> 本篇是决策类笔记，这里的"参数"指的是**决策时要量化的几个变量**，不是训练超参。

| 变量 | 作用 | 调大 / 调小的影响 | 常见量级 |
|---|---|---|---|
| 知识更新频率 | 决定知识放库还是放权重 | 高频 → RAG；极低频且固定 → 可微调 | 每周更新 vs 一年一次 |
| 验收用例数 | 决定能不能验收、能不能证明有效 | 太少（<20）结论不可信；太多成本高 | 50~200 条 |
| 训练数据条数 | 决定微调可不可行 | 少于几百条只够学格式；上万条才有领域感 | 几百~几千 |
| 单次请求可接受 token 成本 | 决定用长 prompt 还是内化 | 对成本敏感 → 微调内化；不敏感 → prompt | 看调用量 |
| 推理延迟要求 | 决定能不能挂 RAG 检索 | 实时性极高 → 少检索、靠微调 | 秒级 vs 分钟级 |
| 硬件预算 | 决定能不能训练 | 没有训练卡 → RAG 或 API | 见 MOC 速查表 |
| 标注人力预算 | 决定数据质量上限 | 预算低 → 数据少而精，别贪多 | 每个项目 3~10 人天 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 微调完模型开始"编"公司制度 | 把知识当天赋塞进权重，模型只学会了"编的格式" | 知识类需求改 RAG；微调只负责"照着资料怎么答" |
| 客户资料更新一次就要重训一次，越维护越亏 | 选错了方案，把可更新内容放进权重 | 现在改：知识进库，只把格式/话术留在权重里 |
| few-shot 已经能过验收，还是训了一版 | 认为"微调=更高级"，忽视成本 | 交付前先算总成本，能 prompt 就不微调 |
| 训完通用能力变差，闲聊都答不好 | 灾难性遗忘，lr 太大 / epoch 太多 / 数据太窄 | 降 lr、减 epoch、混入 5%~20% 通用数据 |
| 效果不好就加数据、加轮次，越加越差 | 缺评估集，无法定位是知识问题还是能力问题 | 先建 50~200 条验收集，按错误类型分桶再决定动作 |
| 微调解决不了数学，硬说"再训训就好了" | SFT 只能模仿格式，不能补推理能力 | 换基座或蒸馏；向客户如实说明能力边界 |
| 客户以为微调后模型就"私有了" | 基座许可证仍有约束，权重是衍生物 | 提前核对 LICENSE 与商用条款，见 [[开源许可证与合规]] |

## 自检问题参考答案

> [!success]- 1. 微调和 RAG 各自改变模型的什么？
> RAG 改的是"模型答之前能看到什么"：知识放在外部库，先查再答，权重一点不变。
> 微调改的是"模型怎么回答"：把格式、话术、条件反射写进权重。
> 一句话记法——**知识进库，格式进权重**。所以知识会变、要溯源的需求走 RAG；只有行为要稳、要省 token 的需求才值得微调。

> [!success]- 2. "要懂公司制度"为什么推荐 RAG？
> 三个理由：制度会变，改库是分钟级、重训是天级；要溯源，RAG 能给出处，微调只能说"模型觉得"；内部制度还有权限边界，放库里能控制谁能查。
> 把制度焊进权重，模型学会的只是"编制度的格式"，答错了还查不出依据。
> 先问一句"把资料贴给它能不能答对"，能就做 RAG。

> [!success]- 3. 固定 JSON 和客服语气，方案为什么不同？
> JSON 是强约束，错一个字符就解析失败，调用量大时值得把格式内化——先 few-shot，不稳定再上几百条的小 LoRA。
> 语气是软约束，Prompt + 人设能覆盖大半，长对话漂移了再补轻量 LoRA。
> 根子在容错度：格式错就是事故，语气飘一点客户未必在意，先用零成本方案试。

> [!success]- 4. 三个反问分别筛掉哪类误判？
> 第一问"资料全塞 prompt 能不能答对"筛掉知识类的误微调；第二问"换更强模型 + 好 prompt 能不能答对"筛掉能力类硬上 SFT。
> 第三问"是不是只在格式/语气/稳定性上"筛掉本该用 Prompt 的伪微调需求。
> 三问都走完还是不行，才轮到微调——顺序别反，从最便宜的方案试起。

> [!success]- 5. 为什么 SFT 补不了能力，客户坚持怎么回？
> SFT 学的是"答案长什么样"——格式、话术、判别模式，不是推理过程。数据里教几百遍，模型只是模仿答案结构，换个题就露馅。
> 回客户时拿验收集分桶看：是"不知道"就补数据或上 RAG，是"不会做"就建议换基座或蒸馏。
> 把追加成本提前写进变更单，别承诺"再训训就好"。

> [!success]- 6. 成本表里哪两个维度最要命？
> **知识更新频率**和**维护成本**。这两栏签约时没人问，交付后天天找上门。
> 知识一周一变却选了微调，等于每次更新都重训一次，天级延迟加数据人力，越维护越亏。
> 表里"维护成本"一行写得很明白——RAG 是中、微调是高。签约前先问"这份资料多久改一次"，比问训练要多久重要得多。

> [!success]- 7. 预算只够做一件事，先做什么？
> 先做 RAG。它可逆、可解释、能分期交付，一周就能上线让客户先看到东西；微调上线后不合适只能重训。
> 对客户讲："先用检索把知识兜住、先验收；格式和话术不够稳，二期再训一版小模型，前面花的钱不白花。"
> 这样翻车率最低，也留住了后续复购。

> [!success]- 8. 组合 RAG + 微调，先交付哪一半？
> 先交付 RAG，验收通过再上 LoRA。知识对不对是可验证的（有没有出处、答没答对好判定），格式和话术是稳定性问题，前者不过关，微调再好也救不了。
> 另外 RAG 先上线还能攒出真实对话，正好当微调数据的来源。
> 顺序反了，等于在一个可能答错的模型上打磨话术。

## 交付视角（对客户怎么讲）

- 客户会问："你们能不能微调一个懂我们业务的模型？"
  - 大白话回答：**"模型不是靠'懂'来解决问题的，是靠'查得到'和'会按格式说'。我们先看看您的问题属于哪一类，能省的钱我不建议您花。"**
- 报价逻辑：RAG 按"知识库规模 + 部署人天"报；微调按"数据条数 + 训练轮次 + 验收用例"报，并明确写清三条边界：
  1. 微调不承诺通用能力提升，只承诺**验收用例通过率**；
  2. 知识类需求走 RAG，**不在微调合同里承诺"记住全部文档"**；
  3. 基座模型升级/许可证变化导致的返工，属于变更范围。
- 劝退话术：**"您这个需求用检索三天能上线，用微调要两周，而且以后资料一改就得重训。要不要先把检索这版跑起来，觉得不够我们再上微调？"** 这单可能少赚，但口碑和复购都在。

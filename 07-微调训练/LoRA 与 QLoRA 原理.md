# LoRA 与 QLoRA 原理

> [!abstract] 一句话讲清楚
> LoRA 的思路是"别改动原模型，只在旁边挂一小块可训练补丁"。它让 7B 模型的微调显存从几十 GB 降到十几 GB，是个人和小团队能玩得起微调的根本原因；QLoRA 再把冻结的基座压到 4bit，进一步把门槛压到单张消费级显卡。

## 为什么重要

- 这是整套微调技术的地基。不懂它，你就不知道为什么 24GB 卡能训 7B，也看不懂框架配置里 `r`、`alpha`、`target_modules` 到底在干什么。
- 上游是 [[Transformer 架构基础]] 和 [[参数量与显存估算]]；下游是 [[训练超参数]]（lr、batch 怎么配）和 [[合并导出与部署闭环]]（训完怎么合并）。
- 真实场景：客户预算只有一张 4090，要私有化一个 7B 客服模型。全参微调显存根本不够，LoRA/QLoRA 是唯一可行路线——而且训出来的 adapter 只有几十 MB，交付和迭代都轻。
- 反过来，LoRA 也有它的代价：效果上限不如全参、rank 选不好会欠拟合、adapter 合并进量化模型时会掉点。这些都要心里有数。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| LoRA | Low-Rank Adaptation | 冻结原权重，旁挂两个小矩阵，只训这两个小矩阵 | 它不是"小一号的模型"，是补丁 |
| QLoRA | Quantized LoRA | 基座压成 4bit 再挂 LoRA 训 | 省的是**基座权重显存**，训练时仍会反量化计算 |
| 秩 | rank, `r` | 补丁的"宽度"，决定能学多复杂的东西 | 不是越大越好，太大等于接近全参、失去省显存的优势 |
| 缩放系数 | alpha, `α` | 控制补丁输出的强度，常按 `α/r` 缩放 | 只改 alpha 不改 r 等于改学习率效果 |
| 目标模块 | target_modules | 决定补丁挂在哪些层上（q/k/v/o、MLP 等） | 名字写错会静默不训练，是最常见的坑 |
| 低秩分解 | Low-Rank Decomposition | 用两个瘦长矩阵相乘近似一个大矩阵 | 直觉：大改动可以用"两个方向的小组合"表达 |
| 适配器 | adapter | 训练产出的那堆小矩阵文件 | 几十 MB 级别，可单独存、单独换 |
| NF4 | 4-bit NormalFloat | QLoRA 用的 4bit 量化格式，按正态分布分桶 | 不是普通 int4，精度损失更小 |
| 双重量化 | Double Quantization | 把量化用的常数再量化一次 | 省的是"量化元数据"那点显存，积少成多 |
| 分页优化器 | paged optimizer | 显存吃紧时把优化器状态临时挪到内存 | 防 OOM 的保险，会拖慢速度 |
| 全参微调 | Full Fine-Tuning | 所有参数都训练 | 显存是 LoRA 的数倍，个人接单基本不碰 |
| 蒸馏 | Distillation | 用强模型的输出去训小模型 | 和 LoRA 是正交的：可以"蒸馏数据 + LoRA 微调" |
| 灾难性遗忘 | Catastrophic Forgetting | 微调太猛把通用能力洗掉 | LoRA 天然比全参轻，但训太狠一样会忘 |

## 原理与机制

### 直觉版

把基座模型想象成一本已经写好的教材。全参微调是**把整本书重写一遍**——成本高，还容易把原来的好内容改坏。

LoRA 是**在书页旁边贴便利贴**：原书一个字不动，只写一小叠补丁。用的时候把补丁和原文一起读（或干脆把补丁内容抄进书里，叫合并）。

因为补丁很小，写补丁的成本（显存、时间）只有重写整本书的零头。

### 拆解版：LoRA 到底在干什么

设某一层原来的权重矩阵是 `W`（形状很大，比如 4096×4096）。全参微调直接更新 `W`。

LoRA 把更新量改写成两个小矩阵相乘：

```text
W' = W + (α / r) · B · A
```

- `A`：降维矩阵，把 4096 维压到 r 维（r 通常 8~64）。
- `B`：升维矩阵，再升回 4096 维。
- `W` 被冻结（不计算梯度、不进优化器）；只有 `A` 和 `B` 是可训练参数。
- `α / r` 是缩放，保证换 r 的时候输出量级不会突然变化。

四个关键结论：

1. **可训练参数量骤降**。r=16 时，一个 4096×4096 层的补丁参数量大约是原来的 2×16/4096 ≈ 0.8%，全模型加起来通常不到 1%。
2. **显存省在"梯度 + 优化器状态"**，不是省在权重本身。
3. **推理时可以合并不增加延迟**：`W'` 直接算好存下来，部署时和普通模型一模一样。
4. **可以热插拔**：一个基座挂多个 adapter，按客户/场景切换（vLLM 支持动态加载，见 [[合并导出与部署闭环]]）。

### 为什么"低秩"就够了

研究者的观察是：**微调带来的权重变化，本身的有效自由度远小于参数总量**。模型不是要重新学一门语言，而是要把已有的能力"往某个方向拨一点"。

就像调音台上的旋钮：你不需要重新造一台音响，只需要拧几个旋钮。r 就是"允许你拧几个旋钮"。

**后果**：

- 任务越"窄"（改格式、改语气、固定问答），小 r 就够。
- 任务越"宽"（新领域对话、复杂任务），需要更大 r 和更多目标模块。
- r 太大时，LoRA 退化成"接近全参"，省显存的优势消失，还更容易过拟合。

### 显存到底省在哪

| 显存项 | 全参微调 | LoRA | QLoRA |
|---|---|---|---|
| 基座权重 | fp16/bf16，全额 | fp16/bf16，全额 | **4bit**，约 1/4 |
| 训练权重副本 | 有 | 无（冻结） | 无（冻结，反量化临时用） |
| 梯度 | 全部参数 | 只有 A/B | 只有 A/B |
| 优化器状态 | 全部参数（Adam 通常数倍于权重） | 只有 A/B | 只有 A/B |
| 激活值 | 和 batch、序列长度强相关 | 同左 | 同左 |
| 结论 | 显存最高 | 省 60%~80% 量级 | 再省一截，可上单张消费卡 |

> 上表只给结构性差异，具体数字取决于模型、序列长度、batch、是否开梯度检查点。**以实测为准，不要背别人的显存数字**。

### QLoRA 的三件套

QLoRA = 4bit 基座 + LoRA 补丁。它靠三个技巧把"4bit 量化"做成了能训练：

1. **NF4 量化**：按正态分布设计的分位点分桶，让 4bit 表示的权重误差更小。普通 int4 是均匀分桶，对正态分布的权重不友好。
2. **双重量化**：量化本身需要存"缩放常数"，这些常数再量化一次，进一步压缩。
3. **分页优化器**：显存峰值时把优化器状态临时换出到内存，避免 OOM 直接中断。

关键理解：**训练时前向/反向计算仍然会反量化回 bf16 参与计算**，所以 QLoRA 省的是"存权重"的显存，不是"算"的显存。速度会比纯 LoRA 慢一些，这是代价。

### 补丁文件里到底存了什么

训练完你会得到一个目录，通常只有两三个文件：

- `adapter_model.safetensors`：A、B 矩阵的实际数值，几十 MB 量级。
- `adapter_config.json`：r、alpha、target_modules、基座模型名——**没有它，补丁就是一堆无法解释的数字**。
- 可能还有 tokenizer 副本或 README。

**所以 adapter 和 config 必须成对保存。** 只拷权重文件，换台机器就加载不了；基座名字写在 config 里，是"这个补丁属于哪个模型"的唯一凭证。这点在 [[合并导出与部署闭环]] 会再强调一次。

### 一个容易搞错的点

LoRA 省钱不等于"可以随便训"。它降低的是**显存门槛**，不是**数据门槛**：数据烂、目标不清，LoRA 一样训不出东西。而且因为训得快、成本低，反而容易让人"多训几版碰运气"，最后没有一版能说清为什么好。

## 分类与对比

### LoRA 挂在哪：target_modules 的选择

| 策略 | 挂载范围 | 效果 | 显存 / 速度 | 什么时候用 |
|---|---|---|---|---|
| 只挂 q、v | 注意力里两个投影 | 最省，效果够改格式/语气 | 最好 | 快速试验、数据少 |
| 挂全部 attention（q/k/v/o） | 注意力四个投影 | 平衡，最常用 | 好 | 默认推荐 |
| attention + MLP 全部线性层 | 覆盖面最大 | 效果最接近全参 | 显存和参数量上升明显 | 数据多、任务复杂、效果不够时 |
| 只挂 MLP | 前馈层 | 对不同任务表现不一 | 中 | 需要实验验证，不建议盲选 |

> 记法：**要"改行为"（格式/语气）挂 attention 就够；要"学新任务"再扩到 MLP。**

### 全参 vs LoRA vs QLoRA vs 蒸馏

| 维度 | 全参微调 | LoRA | QLoRA | 蒸馏 |
|---|---|---|---|---|
| 训练显存 | 最高 | 中 | 最低 | 取决于学生模型规模 |
| 训练速度 | 慢 | 较快 | 较慢（反量化开销） | 看数据量 |
| 可训练参数 | 100% | 通常不到 1% | 通常不到 1% | 学生模型 100%（常用 LoRA 实现） |
| 效果上限 | 最高 | 略低 | 略低，且受量化影响 | 接近教师模型在该任务上的水平 |
| 交付体积 | 整个模型 | 几十 MB 补丁 | 几十 MB 补丁 | 学生模型完整权重 |
| 多任务切换 | 一次一模型 | 可热插拔 | 可热插拔 | 一次一模型 |
| 适合谁 | 有卡有数据的大团队 | 绝大多数接单场景 | 单卡、低预算 | 想把大模型能力压到小模型上 |
| 主要风险 | 显存不够、遗忘严重 | rank/模块选错效果平 | 量化+训练双重掉点 | 继承教师的错误与风格 |

## 决策点

- **岔路口 1：显存不够怎么办**
  - 条件：跑全参直接 OOM。
  - 推荐顺序：**先 LoRA（降 r、缩 target_modules、开梯度检查点）→ 还不够再 QLoRA**。
  - 代价：QLoRA 训练更慢，且量化基座上的效果要额外验证；能上 fp16 LoRA 就别急着量化。

- **岔路口 2：rank 选多大**
  - 推荐：格式/语气类 8~16；领域对话类 16~32；复杂任务 32~64 起试；数据很少时从小开始。
  - 代价：r 太小欠拟合（loss 降不下去、效果平）；r 太大显存涨、易过拟合、优势消失。**先小后大，用评估集说话。**

- **岔路口 3：alpha 怎么配**
  - 推荐：常用 `alpha = 2 × r` 或 `alpha = r`，只调一个变量做对比。
  - 代价：alpha 偏大相当于放大学习率，容易训飞；偏小则补丁"没存在感"。改了 alpha 就要重新调 lr。

- **岔路口 4：target_modules 扩不扩**
  - 推荐：先全 attention；效果不够、数据上千条，再扩到 MLP。
  - 代价：扩到 MLP 后可训练参数和显存明显上升，训练时间变长；而且不一定有效，要拿评估集对比。

- **岔路口 5：要不要"蒸馏 + LoRA"**
  - 条件：想在本地跑小模型，又要接近大模型效果。
  - 推荐：用更强模型生成高质量数据 → 学生模型 LoRA 微调。
  - 代价：数据成本高、会继承教师的错误；许可证要核对（教师模型的输出能不能用于训练）。

## 参数与配置说明

| 参数 | 作用 | 调大 / 调小的影响 | 常见取值 |
|---|---|---|---|
| `r`（rank） | 补丁的秩，决定表达能力 | 大 → 表达强/显存涨/易过拟合；小 → 省/可能欠拟合 | 8 / 16 / 32 / 64 |
| `alpha` | 缩放强度 | 大 → 补丁影响大，相当于放大 lr；小 → 学不动 | 通常 16~32，常按 2r 配 |
| `lora_dropout` | 补丁上的 dropout | 大 → 抗过拟合但难收敛；小 → 收敛快 | 0~0.1，数据少时用 0.05 |
| `target_modules` | 补丁挂载位置 | 越多越强、越贵 | 全 attention 起步 |
| `bias` | 是否训练偏置项 | `none` 最常用；`all` 略涨参数量 | none / lora_only / all |
| `use_rslora` | 用 1/√r 替代 α/r 缩放 | 大 r 时更稳定 | 大 rank 场景可开 |
| 量化位宽 | QLoRA 基座精度 | 4bit 最省；8bit 更稳但更占显存 | 4bit（NF4）|
| 计算精度 | 训练时用 bf16/fp16 | bf16 数值更稳，老卡可能只支持 fp16 | bf16 优先 |

> 字段名在不同框架里略有差异，以框架文档为准；核心含义一致。

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 训练 loss 一直不降，像没训 | `target_modules` 名字和模型结构对不上，实际没挂上 | 训练前打印可训练参数占比，太小或为 0 就是没挂上 |
| loss 能降，但效果比预期差很多 | rank 太小 / 只挂了 q,v | 加 r、扩到全部 attention；用评估集验证再决定 |
| 训完风格全变了，闲聊也不会了 | lr 太大 / epoch 太多 / 数据太单一 | 降 lr、减 epoch、混 5%~20% 通用数据 |
| QLoRA 训完比 LoRA 差一截 | 4bit 基座本身掉点 + 补丁补偿不了 | 先确认 LoRA 全精度下的上限；必要时升 8bit 或换 LoRA |
| 合并后模型输出乱码/变差 | 合并精度不够（fp16 溢出）或 tokenizer 没跟着换 | 用 bf16 合并；合并后必须做同一组 prompt 的对比验证 |
| 一个基座挂多个 adapter 效果互相干扰 | 多补丁同时激活或加载顺序错了 | 明确每次只激活一个；用推理引擎的 adapter 管理接口 |
| 换 r 之后效果突然变差 | 忘了 alpha/r 缩放关系，相当于改了学习率 | 换 r 时按比例同步调 alpha，或固定 alpha/r 再调 |

## 自检问题参考答案

> [!success]- 1. LoRA 的更新公式是什么？每个符号什么意思？
> `W' = W + (α/r)·B·A`。W 是原来冻结的权重矩阵；A 是降维矩阵，把高维压到 r 维；B 是升维矩阵，再升回原来的维度。
> r 是秩，决定补丁的"宽度"；α 是缩放系数，`α/r` 保证换 r 时输出量级不突变。
> 全参微调直接改 W，LoRA 只训 A 和 B，W 一点都不动。

> [!success]- 2. LoRA 省显存省在哪几项？
> 省在梯度、优化器状态和训练权重副本：基座冻结，不存训练副本、不算梯度、不进 Adam 状态，只给 A/B 算。
> 但基座权重本身仍要以 fp16/bf16 全量加载在显存里，这一项没省，所以量级上是省 60%~80%，不是省到十分之一。
> 要把基座也压下去，得上 QLoRA 的 4bit。

> [!success]- 3. QLoRA 三件套各解决什么？省的是"存"还是"算"？
> NF4 用按正态分布设计的分位点分桶，让 4bit 表示的权重误差更小；双重量化把量化用的缩放常数再压一次；分页优化器在显存峰值时把优化器状态临时挪到内存防 OOM。
> 它省的是"存权重"的显存——前向/反向计算时仍要反量化回 bf16 参与计算。
> 所以"算"没省，速度比纯 LoRA 慢。

> [!success]- 4. `alpha/r` 缩放为什么重要？只改 alpha 会发生什么？
> 这个缩放让补丁输出量级不随 r 变化而突变，等于把"补丁宽度"和"补丁强度"解耦。
> 只改 alpha 不改 r，效果上相当于改学习率：alpha 调大，补丁影响变强、容易训飞；调小，补丁没存在感、学不动。
> 所以换 r 时要按比例同步调 alpha，或者固定 alpha/r 再动别的变量。

> [!success]- 5. target_modules 扩到全部线性层的代价和收益是什么？
> 收益是表达能力更强：只挂 q、v 最省但只够改格式语气；扩到全部 attention 是平衡点，最常用；再扩到 MLP 全线性层，效果最接近全参，适合数据多、任务复杂的场景。
> 代价是可训练参数量和显存上升、训练变慢，而且不一定有效，容易过拟合。
> 记法：改行为挂 attention 就够，学新任务再扩到 MLP。

> [!success]- 6. 为什么 LoRA 能热插拔，全参微调不行？
> 因为补丁和基座是分开的两份文件：基座不动，adapter 只有几十 MB，推理引擎可以按请求动态加载、按客户或场景切换。
> 全参微调产出的是一个完整模型，一个模型只能对应一套权重，想换场景就得换整个模型或者重新加载几 GB 权重。
> 所以多客户托管用动态 adapter，客户自己部署就合并。

> [!success]- 7. 怎么用一行日志确认 LoRA 真的挂上了？
> 打印可训练参数占比：所有参数总数 vs 需要梯度的参数量，LoRA 正常应该在 1% 以内但明显大于 0。
> 如果这个数为 0 或者小得离谱，就是 target_modules 名字和模型结构对不上、根本没挂上，表现是 loss 平得像没训练。
> 这是"训了半天白训"的头号原因，训练前花十秒看一眼就能避免。

> [!success]- 8. 什么时候放弃 LoRA，改用蒸馏或换模型？
> 当错误是"能力不足"而不是"行为不对"时：数学、复杂推理、长文理解这类，LoRA 只是在模仿答案格式，换个题就废。
> 这时换更强的基座，或者用强模型生成解题过程做数据、蒸馏到小模型上。
> 另外显存够、数据量大、追求效果上限时可以考虑全参；LoRA 仍是不错的默认路线。

## 交付视角（对客户怎么讲）

- 客户会问："LoRA 是不是就是做了个缩水版模型？"
  - 大白话：**"不是。基座模型一点没动，我们只是在旁边加了一个几十 MB 的'习惯补丁'，需要的时候可以合进去，也可以单独拿掉。好处是成本低、能随时换回原版。"**
- 客户会问："为什么不用全参微调？效果不是更好吗？"
  - 大白话：**"全参效果上限是高一截，但显存和工期是几倍，您这个场景用不上。先用 LoRA 做到验收标准，不够我们再升级方案。"**
- 报价与承诺：
  1. 交付物写清是 **adapter + 合并后的模型文件**两种形态，合并不额外收费；
  2. 不承诺"超过原模型"，只承诺**验收用例通过率**；
  3. 基座升级需要重新适配，属于变更项；
  4. 明确说明 LoRA 不改变模型的知识边界，知识类需求走 RAG。

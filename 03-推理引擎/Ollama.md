# Ollama

> [!abstract] 一句话讲清楚
> Ollama 是把 llama.cpp 包装成"模型库 + 常驻服务 + 简单 API"的本地推理工具，让你一条命令就能跑起一个模型，并且把它变成局域网里可调用的接口。

## 为什么重要

- 它是绝大多数人**接触本地大模型的第一站**：装完就有模型可拉，不用碰 safetensors、不用手写量化转换脚本。
- 交付场景里，Ollama 是最省事的"单机演示版"方案：客户机器上一装，效果当场就有。
- 但它的上限最明显：并发弱、可调项少。**不懂它是什么，就会在需要生产服务时还拿它硬撑**，然后被"三个人用就卡"教育。
- 在技能栈里，它上游是 [[llama.cpp 与 GGUF]]（内部就跑在 llama.cpp 之上），下游是 [[OpenAI 兼容 API 规范]]（它暴露了兼容端点），再往上接 [[Dify 平台与工作流]] 这类应用。
- 学会它的真正价值不是"会装"，而是**知道它的边界在哪、什么时候必须换引擎**。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| Ollama | — | 本地模型运行与管理工具，自带服务端和命令行 | 不是新的推理内核，底层是 llama.cpp |
| 模型库 | Model Registry | 官方维护的模型清单，一条命令就能拉 | 里面是别人转好的 GGUF 变体，不等于原厂权重 |
| Modelfile | — | 描述"用哪个模型 + 什么系统提示 + 什么参数"的配置 | 像 Dockerfile 的定位，但简单得多 |
| ollama serve | — | 启动常驻服务，默认在本机端口提供 API | 默认只听本机，局域网访问要显式改绑定 |
| OLLAMA_HOST | — | 控制服务监听地址的环境变量 | 不设就是 127.0.0.1，客户在另一台机器就永远连不上 |
| OLLAMA_NUM_PARALLEL | — | 同时处理几路请求 | 每一路都要独立 KV Cache，调大直接吃显存 |
| OLLAMA_KEEP_ALIVE | — | 模型在显存里保留多久不卸载 | 调太短反复加载，调太长和别的进程抢显存 |
| num_ctx | — | 上下文窗口，一次能处理多少 token | 默认值偏小，长文档场景必须显式调大 |
| num_gpu | — | 有多少层放到显卡上 | 显存不够就调小，代价是速度掉到 CPU 水平 |
| 量化 tag | Quant Tag | 模型名后面的后缀，代表不同量化档位 | `:latest` 不等于原版，常见是 4bit 级别量化 |
| blob / 层缓存 | — | 模型文件在磁盘上的缓存结构 | 删模型不等于清干净，磁盘占用会一直涨 |
| OpenAI 兼容端点 | — | `/v1/chat/completions` 那套接口 | 能用不等于全功能一致，tools、json mode 有差异 |
| 内置模板 | Chat Template | 把 messages 拼成模型认识的提示词格式 | 模板不对时，模型会把指令当普通文本 |
| 冷启动 | Cold Start | 第一次请求要加载模型进显存 | 通常几秒到几十秒，和模型体积、磁盘速度有关 |
| 上下文截断 | Context Truncation | 提示词超过窗口后，前面部分被静默丢弃 | 不报错，只是"答非所问"，最容易被忽略 |
| 预热请求 | Warm-up | 服务起来后先发一个空请求把模型加载好 | 交付脚本里做一次，客户体验差别很大 |

## 原理与机制

### 直觉版

Ollama 像一家便利店：

- 货架上是官方挑好的商品（模型库里的 GGUF 变体）。
- 你写一张小纸条告诉店员怎么做（Modelfile：系统提示、温度、上下文）。
- 店里常驻一个收银台（`ollama serve`），谁来了都能点单（API 请求）。
- 但后厨只有一口锅（单推理进程），人一多就排队。

### 拆解版

1. **拉模型**：从 registry 下载 GGUF 变体到本地，按 blob 分块缓存。同一个基础模型的不同 tag 会共享大部分层，所以第二个 tag 常常下得很快。
2. **建模型**：`ollama create` 读 Modelfile，把基础模型 + 系统提示 + 参数组合成一个新的模型名。这一步本质是"生成一份新的元数据 + 复用已有权重"，不复制几个 G 的权重。
3. **跑服务**：`ollama serve` 把模型加载进显存，对外提供原生接口和 OpenAI 兼容接口。
4. **调度**：请求进来按 `OLLAMA_NUM_PARALLEL` 排队，排满就等；闲置超过 `OLLAMA_KEEP_ALIVE` 就把模型卸载释放显存。
5. **多模型切换**：同时驻留的模型数受 `OLLAMA_MAX_LOADED_MODELS` 限制，超了就卸载最久没用的。

### 一次请求的生命周期

1. 客户端发 HTTP 请求，带模型名、messages、参数。
2. 服务端把 messages 按内置对话模板拼成一段完整提示词。
3. 提示词 token 化，做 prefill（把整段算完、建 KV Cache）。
4. 进入 decode，一个 token 一个 token 生成，边生成边通过流式返回。
5. 达到停止条件（EOS、max_tokens、stop 词）后收尾。
6. 请求结束；如果显存紧张或空闲超时，模型可能被卸载。

**为什么要知道这个**：客户抱怨"答得慢"时，你能判断是卡在加载（冷启动）、卡在 prefill（提示词太长）、还是卡在 decode（模型太大/量化太保守）。三种原因的解法完全不同。

### 后果

- 因为只有一层简单调度，**低并发体验很顺，高并发排队明显**——这就是"演示很好、上线很虚"的根源。
- 因为参数藏在 Modelfile 和环境变量里，**不写进 Modelfile 的配置换台机器就丢了**——交付必须把配置文件一起给。
- 因为底层是 llama.cpp，**性能上限基本就是 llama.cpp 的上限**，换 Ollama 版本不会带来质变。
- 因为它帮你把模型格式统一成 GGUF，**换模型成本极低**——这也是它最大的产品价值。

## 完整流程：从零到可交付

`安装 → 拉模型 → 写 Modelfile 固化参数 → 起服务 → 压测 → 交付`

| 阶段 | 动作 | 为什么 |
|---|---|---|
| 1. 安装 | 装官方包，确认 `ollama -v` 能跑 | 版本行为有差异，交付要记录版本 |
| 2. 拉模型 | 按显存选参数档位，优先 4bit | 显存决定你能拉多大的模型 |
| 3. 固化参数 | 写 Modelfile：上下文、温度、系统提示 | 不固化的参数换机器就丢，现场必翻车 |
| 4. 起服务 | 设 `OLLAMA_HOST` 与并发相关变量再启动 | 默认只听本机、并发很低，是演示版配置 |
| 5. 压测 | 模拟真实并发与真实长度提示词 | 单人测出来好看，多人用才知道上限 |
| 6. 交付 | 打包 Modelfile、启动脚本、验收清单 | 客户要的是"能重复跑起来"，不是命令行历史 |

四段式的验收口径，交付时照着对：

- **输入**：客户的机器配置、使用人数、典型问题长度、期望响应时间。
- **动作**：拉模型 → 建 Modelfile → 起服务 → 压测 → 调参。
- **输出**：一个可重复启动的服务 + 配置文件 + 实测数据（首字延迟、单人速度、N 人并发时的排队情况）。
- **验收标准**：重启后能自动起来；局域网设备能访问；真实问题集上回答可用；并发人数场景下响应时间在客户可接受范围。

Modelfile 最少要固化这几个值：

```dockerfile
FROM qwen2.5:7b-instruct-q4_K_M
SYSTEM "你是一个企业知识库助手，只根据给定资料回答，不知道就说不知道。"
PARAMETER num_ctx 8192
PARAMETER temperature 0.3
```

> 这段的作用：把"用哪个模型、什么角色、多长上下文、多随机"四个决定写死。`ollama create my-assistant -f Modelfile` 之后，换机器只需要这一个文件。

启动服务时要把服务级配置设上，否则默认值只适合单人：

```bash
OLLAMA_HOST=0.0.0.0:11434 OLLAMA_NUM_PARALLEL=2 OLLAMA_KEEP_ALIVE=30m ollama serve
```

> 关键在三个值：对外监听、同时处理 2 路、闲置 30 分钟卸载。并发每加 1 都要多一份 KV Cache 显存。

## 分类与对比：Ollama 什么时候够用

| 场景 | 结论 | 说明 |
|---|---|---|
| 个人知识库问答、单人助手 | 够用 | 体验好、维护成本低 |
| 给客户现场演示 | 够用 | 装起来快、出效果快 |
| 内网 3~5 人轻量使用 | 勉强 | 要调并发，且要接受排队 |
| 对外提供 API / 10 人以上并发 | 不够 | 排队非常明显，该换 [[vLLM]] |
| 需要精细控制显存、批处理、KV Cache | 不够 | Ollama 基本不暴露这些旋钮 |
| 离线批处理跑几千条数据 | 勉强 | 能跑但没有动态批处理，效率低 |
| 多模型随时切换 | 很好 | 模型库 + 自动卸载，体验接近 App |
| 需要工具调用 / 结构化输出 | 一般 | 支持但受模板和底层能力限制，要实测 |

**和 llama.cpp 的关系**：Ollama ≈ llama.cpp + 模型仓库 + 服务封装。如果你需要调 `-ngl`、flash attention、KV Cache 类型这类参数，直接用 [[llama.cpp 与 GGUF]] 更顺手；如果只是"想跑起来"，用 Ollama。

## 并发不够时的三条路

| 方案 | 做法 | 适合 | 代价 |
|---|---|---|---|
| 调高内置并行 | 设 `OLLAMA_NUM_PARALLEL` | 2~4 人、机器显存宽裕 | 显存按倍增长，单请求速度下降 |
| 多实例 + 负载均衡 | 同一台或多台机器起多个 Ollama，前面挂反向代理 | 5~20 人、多台机器 | 部署复杂度上升，需要自己管分发 |
| 换 vLLM | 直接换生产引擎 | 长期使用、并发要求稳定 | 学习和适配成本，模型格式要换 |

判断标准很简单：**并发需求超过 4 路，或者客户明确要求 SLA，就别在 Ollama 上加补丁，直接换引擎。** 补丁方案的维护成本会慢慢超过换引擎的成本。

## 换引擎迁移清单

从 Ollama 迁到 vLLM 或别的引擎时，按这个清单逐项确认，别遗漏：

1. **模型格式**：GGUF 换 safetensors 系，要回到 HuggingFace 原模型或量化版本。
2. **API 地址**：应用层的 base_url 要改，别硬编码在代码里。
3. **模型名**：各家命名规则不同，配置文件要同步。
4. **上下文长度**：Ollama 的 num_ctx 对应 vLLM 的 max-model-len，语义不完全一致。
5. **采样参数默认值**：温度的默认值不同，可能影响输出风格。
6. **功能依赖**：tools、json mode、多模态、embeddings 是否都支持，逐项实测。
7. **流式行为**：有的引擎分块粒度不同，前端要能处理空 delta。
8. **鉴权**：从无到有，应用侧要加 API key。

## 决策点

- **岔路口 1：做演示还是做服务？** → 演示选 Ollama，服务选 vLLM → 代价：Ollama 省下的安装时间会在并发瓶颈上还回去。
- **岔路口 2：参数写在环境变量还是 Modelfile？** → 一律写 Modelfile + 启动脚本，环境变量只放服务级配置 → 代价：多维护两个文件，但换机器能复现。
- **岔路口 3：用官方 tag 还是自己转 GGUF？** → 常见模型直接用官方 tag；需要特定量化档位或微调模型时自己转 → 代价：自己转要过 [[llama.cpp 与 GGUF]] 那条工具链。
- **岔路口 4：开不开并行？** → 显存足够且确有并发才开，轻量场景 1~2 路 → 代价：每路独立 KV Cache，显存不够时会直接 OOM。
- **岔路口 5：模型常驻还是随用随加载？** → 高频使用设长 keep_alive；多人抢一台机器就设短 → 代价：反复加载带来冷启动等待。
- **岔路口 6：要不要做多模型路由？** → 模型种类多、但单模型并发低时适合；高并发场景别用一个大而全的实例 → 代价：显存要能同时放下多个模型，或者接受切换延迟。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| num_ctx | 上下文窗口 | 调大：能读长文，KV Cache 吃显存、首字变慢；调小：省显存但长文被截断 | 4K ~ 16K |
| num_gpu | 放显存的层数 | 调大：快；调小：能跑但慢，太小等于纯 CPU | 显卡够就全放 |
| OLLAMA_NUM_PARALLEL | 同时处理请求数 | 调大：并发上来，显存按倍涨；调小：排队 | 1 ~ 4 |
| OLLAMA_KEEP_ALIVE | 闲置卸载时间 | 调大：响应快、占显存；调小：省显存、冷启动慢 | 5m ~ 1h |
| OLLAMA_HOST | 监听地址 | 改成 0.0.0.0 才能被局域网访问 | 127.0.0.1 或 0.0.0.0 |
| OLLAMA_MAX_LOADED_MODELS | 同时驻留几个模型 | 调大：切换不等待，显存吃紧 | 1 ~ 2 |
| temperature | 采样随机性 | 调大：发散；调小：稳定，适合问答与工具调用 | 0.1 ~ 0.7 |
| top_p | 核采样范围 | 调小：更保守；调大：更丰富 | 0.8 ~ 0.95 |
| num_predict | 最大输出 token | 调大：回复完整但慢；调小：快但可能截断 | 512 ~ 4096 |
| stop | 停止词 | 用于截断多余输出 | 按场景 |
| num_thread | CPU 线程数 | 调大：CPU 段变快；过度会抢资源 | 物理核心数附近 |

## 参数调优的实操顺序

1. 先确认模型能稳稳跑起来，**不 OOM**。
2. 再按业务真实长度确定 num_ctx，别一次拉到最大。
3. 然后测单请求首字延迟和出字速度，作为基线。
4. 再逐步加并发路数，观察显存和排队时间。
5. 显存有富余就上 keep_alive 常驻，减少冷启动。
6. 最后才动采样参数（temperature/top_p），那是效果层不是性能层。

顺序错了的典型表现：一上来就调 temperature 想解决"答得慢"，白忙。

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 长文档问答总说"资料里没有"，但资料明明给了 | 默认 num_ctx 偏小，超出部分被静默截断 | 显式设 num_ctx，并检查提示词实际长度 |
| 客户在另一台电脑上打不开接口 | 服务默认只监听 127.0.0.1 | 设 `OLLAMA_HOST=0.0.0.0:11434`，同时放行防火墙 |
| 开了并行后显存爆了 | 每路请求都有独立 KV Cache | 先把 num_ctx 降下来，再逐路加并发 |
| 模型名一样，换台机器效果不一样 | 环境变量、Modelfile、模型 tag 不一致 | 交付物必须包含 Modelfile 与启动脚本 |
| 第一次请求特别慢，后面很快 | 冷启动要加载模型 | 用 keep_alive 常驻，或交付脚本里做预热请求 |
| 磁盘一直变小，删了模型也没释放 | blob 缓存与镜像层残留 | 用自带命令清理，别手删目录 |
| 用 OpenAI SDK 接 Ollama，工具调用不生效 | 兼容端点对 tools 的支持与主流程不同 | 涉及工具调用先自测，不行就换引擎或改原生接口 |
| 以为 `:latest` 就是原版模型 | tag 只是量化档位标识 | 需要什么量化就显式写 tag，并在模型卡确认 |
| 中文长句被截成半个词 | 分词器/停止词配置问题，或 max_predict 太小 | 调整输出长度，检查 stop 配置 |
| 服务跑着跑着自己退出 | 系统内存/显存不足被系统杀进程 | 看系统日志，降低显存占用，别在临界值上跑 |

## 与其他本地工具的分工

| 工具 | 和 Ollama 的关系 | 什么时候用 |
|---|---|---|
| Ollama | 本地引擎 + 模型管理 | 单人使用、演示、轻量内网 |
| LM Studio | 图形界面客户端，底层也是同一批 GGUF | 要交给非技术客户自己开箱用 |
| Open WebUI | 前端界面，后端可以接 Ollama | 要给客户一个"网页版 ChatGPT" |
| Dify | 应用编排平台，后端接 OpenAI 兼容接口 | 要做知识库、RAG、工作流 |
| 编码助手类客户端 | 前端工具，后端接兼容接口 | 本地代码补全、离线开发 |

> 记住一件事：Ollama 只是"后端之一"。客户看到的界面、登录、权限，往往不是它提供的，别把前端的活算到引擎头上。

## 多实例与反向代理

- 单实例并发到顶之后，最便宜的扩容方式是**多实例**：同一台机器起 2~4 个 Ollama，监听不同端口。
- 前提是显存能同时放下多个完整模型副本，通常只有 7B 级 4bit 这种小模型才划算。
- 多个实例前面挂反向代理（Nginx / Caddy / 任意负载均衡），按轮询分发请求。
- 好处：故障隔离，一个实例崩了不会全挂；升级可以一个一个来。
- 坏处：每个实例独立加载模型，显存翻倍；多轮对话需要会话粘性，否则上下文对不上。
- 判断口径：显存能稳稳放下几个副本就最多起几个实例，别指望靠"内存换显存"，一旦换出就是灾难性卡顿。

## 性能问题快速定位

| 症状 | 先查什么 | 常见原因 |
|---|---|---|
| 每个请求都慢，第一句尤其慢 | 服务日志的加载记录 | 模型没常驻，反复冷启动 |
| 长提示词慢、短提示词正常 | 提示词实际长度 | prefill 开销被长上下文放大 |
| 单人正常、多人排队 | 并发配置与显存余量 | 并行路数不足，或显存压着上限跑 |
| 速度突然掉一半 | 系统显存/内存占用 | 后台进程抢显存，部分计算回落到 CPU |
| 输出格式和预期不一样 | 对话模板 | 模板与模型不匹配，或系统提示被覆盖 |

## 一个真实的交付场景

需求：一家小公司，内网一台带显卡的工作站，5 个人要从内部 Wiki 查资料，希望"像 ChatGPT 一样"用。

- **第一版**：直接上 Ollama + Open WebUI，装完当天就能用。客户很满意。
- **一周后**：反馈"有人用的时候另一个人要等半分钟"。这是并发问题，不是模型问题。
- **根因**：默认并发低，且没做常驻，冷启动也占了一部分时间。
- **处理**：先把 keep_alive 调到 30 分钟消除冷启动；再把并发调到 2；同时把上下文从最大值降到业务真实长度，腾出 KV Cache 空间。
- **结果**：5 人日常使用基本可接受，高峰期仍有排队。
- **结论**：这个规模就是 Ollama 的天花板区间。要彻底解决得换 vLLM，但客户的机器显存一般、预算有限，所以交付时写了"并发上限说明"作为预期管理。

> 这类场景的关键不是调参，是**在交付前就把边界告诉客户**。边界说清楚了，小问题就不会变成索赔。

## 常见误解澄清

- **"Ollama 是新引擎"**：不是。它是 llama.cpp 的封装产品，性能瓶颈和 llama.cpp 一脉相承。
- **"模型越大效果一定越好"**：显存不够时上的大模型往往被降量化，效果可能还不如小一点的原版，要按实际任务测。
- **"num_ctx 拉满更保险"**：会让 KV Cache 吃掉显存，并发和速度双降。按业务真实长度设。
- **"并发数越高吞吐越高"**：并发之和显存成正比，超过显存会排队甚至 OOM，吞吐看的是整体而非单请求。
- **"Ollama 不能用于生产"**：单机、少人、轻量的生产场景完全可以用，关键是你有没有把边界写进交付文档。
- **"模型拉下来就完事"**：参数、系统提示、上下文全在 Modelfile 里，不固化等于每次交付都靠运气。
- **"API 兼容 OpenAI 就等于行为一致"**：只是接口形状一致，模板、默认值、功能支持都可能不同。
- **"换个快模型就能解决慢"**：先分清是冷启动、prefill 还是 decode 慢，三种原因解法完全不同。

## 版本与升级注意事项

- 升级 Ollama 等于升级底层 llama.cpp，**性能表现和默认参数可能变化**，升级前后各跑一次基线测试。
- 交付环境建议**锁版本**，并在文档里写清版本号；客户随手升级可能让验证过的参数失效。
- 模型 tag 指向的底层版本也可能更新，长期项目最好把模型文件本地留存，别依赖"再拉一次"。
- 升级前先备份 Modelfile 与启动脚本；升级后重点验证：并发是否正常、长上下文是否还稳、工具调用是否还可用。
- 遇到"升级后明显变慢"，先回退版本验证，再定位是参数默认值变了还是后端换了。

## 自检问题参考答案

> [!success]- 1. Ollama 和 llama.cpp 是什么关系？
> Ollama 是 llama.cpp 的封装产品：底层跑的就是 llama.cpp，上面加了模型库、Modelfile 和服务层。
> 所以它的性能上限基本就是 llama.cpp 的上限，换个 Ollama 版本不会带来质变。
> 反过来，想调 -ngl、KV Cache 类型这类底层参数，直接用「llama.cpp 与 GGUF」更顺手。
> 它真正不可替代的价值，是把模型格式统一成 GGUF、换模型成本极低。

> [!success]- 2. 默认配置为什么只能演示，不能接生产？
> 默认值全是"演示版配置"：只监听 127.0.0.1，别人连不上；并发很低，人一多就排队；模型按需加载，还有冷启动。
> 单人用确实很顺，但这三件事叠在一起，多人场景就是"等半分钟"。
> 要接生产，至少把 OLLAMA_HOST、OLLAMA_NUM_PARALLEL、OLLAMA_KEEP_ALIVE 调好并压测，再谈能不能用。

> [!success]- 3. 并发上调时，显存里多出来的是什么？
> 多出来的是每一路请求独立的 KV Cache，不是模型本身。
> 上下文越长、并发越高，这部分占用按倍增长，所以并发不是"开个参数"就能加。
> 正确顺序是先看显存余量，余量不够先降 num_ctx，再一路一路加。
> 顺序反了的表现不是变慢，是直接 OOM。

> [!success]- 4. 交付给客户时，除了模型还必须带上哪两个文件？
> Modelfile 和启动脚本。
> Modelfile 固化模型、系统提示、num_ctx、temperature；启动脚本里写 OLLAMA_HOST、并发、keep_alive 这些服务级变量。
> 少了这两个文件，换台机器参数就丢了，效果对不上，交付也无法复现。
> 客户要的是"能重复跑起来"，不是一段命令行历史。

> [!success]- 5. 上下文从 4K 调到 32K，会同时影响哪三件事？
> 一是 KV Cache 显存占用，二是首字延迟（prefill 变长），三是能同时跑的并发数。
> 上下文拉满等于用显存换"可能用不上的长度"，在显存紧的机器上非常致命。
> 所以按业务真实长度设 num_ctx，别为了"保险"拉到最大值。

> [!success]- 6. 什么信号出现时，该建议客户换 vLLM？
> 并发需求超过 4 路、客户明确要求 SLA、10 人以上同时用；
> 或者需要精细控制显存、批处理、KV Cache 这些 Ollama 基本不暴露的旋钮；
> 又或者加并发后只能在排队和 OOM 之间挣扎。
> 到了这个点，继续在 Ollama 上打补丁的维护成本会超过换引擎的成本。

> [!success]- 7. 局域网别人连不上，先查哪两个地方？
> 先查 OLLAMA_HOST：默认只监听 127.0.0.1，别的机器永远连不上，要设成 0.0.0.0。
> 再查防火墙是否放行端口，这是最常见的第二道墙。
> 顺手确认客户端填的是本机 IP 而不是 localhost，以及服务确实在跑。

> [!success]- 8. 冷启动慢和推理慢，怎么区分？
> 冷启动慢的特征是"第一个请求慢、后面正常"：模型要从磁盘加载进显存，服务日志里能看到加载记录，解法是 keep_alive 常驻或交付脚本里预热。
> 推理慢是每个请求都慢：卡在 prefill（提示词太长）就缩上下文，卡在 decode（模型太大、量化太保守）就量化或换小模型。
> 三种原因解法完全不同，先分类再动手。

> [!success]- 9. 客户强行要 10 人同时用，交付话术是什么？
> 别咬牙说能。直接讲清边界：Ollama 默认并发很低，10 人同时用会明显排队。
> 给两个选项：现在先做"5 人可用、高峰排队"的演示版，或者换 vLLM 做服务版，代价是显存和预算上涨。
> 把并发上限写进交付文档，比事后救火省事得多。

## 交付视角（对客户怎么讲）

- 对客户说人话：Ollama 相当于"本地版模型 App"，装好就能用；但它是给一个人用的，不是给一个团队用的。
- 报价时区分"演示版"和"服务版"：演示版用 Ollama 半天能交付；服务版要上 vLLM，工作量完全不同。提前讲清楚，避免后面扯皮。
- 每次交付把 Modelfile、启动脚本、验收清单打包，并当面跑一遍重启流程——这是"能复现"和"只有你会"的分界线。
- 客户问"能不能多几个人同时用"，别咬牙说能，直接讲清并发的限制和升级方案，比事后救火省事。
- 客户问"要不要买更好的模型服务"，用实测数据回答：单人延迟、N 人排队时间，比讲参数有说服力。
- 顺手教客户一个自查方法：任务管理器/活动监视器里看显存占用曲线，占满了就是瓶颈到了。

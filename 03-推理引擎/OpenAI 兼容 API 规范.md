# OpenAI 兼容 API 规范

> [!abstract] 一句话讲清楚
> 现在几乎所有的本地推理引擎都提供一套"长得像 OpenAI"的接口，客户端只要会调 OpenAI 就能接任何引擎——但"兼容"通常只兼容了主路径，细节差异才是交付时真正咬人的地方。

## 为什么重要

- 你在 [[Ollama]]、[[llama.cpp 与 GGUF]]、[[vLLM]]、[[SGLang 与 TensorRT-LLM]]、[[MLX 与 Apple 芯片推理]] 之间换引擎时，**应用代码不需要改**，这是交付时最大的自由度。
- 反过来，客户把云端 OpenAI 换成本地模型时，出问题的地方往往不是模型能力，而是接口细节：字段被忽略、结束原因不同、流式没有 [DONE]。
- 懂这套规范，你才能写"换引擎不改业务代码"的适配层，也才能在排错时判断问题在客户端还是在引擎。
- 上游是 [[模型获取与离线搬运]]、[[采样参数与解码策略]]，下游是 [[服务化与 API 鉴权]]、[[客户端 UI 工具]]、[[本地模型接入编码助手]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| OpenAI 兼容接口 | OpenAI-compatible API | 模仿 OpenAI 官方 API 的路径与字段，让客户端少改代码 | 兼容的是"形状"，不保证行为一致 |
| Chat Completions | /v1/chat/completions | 最常用的对话补全接口，输入消息列表、输出回复 | 很多老代码用 /v1/completions，那是文本补全，语义不同 |
| messages | — | 一次对话的消息数组，按顺序传给模型 | 顺序有语义，system 一般放第一条 |
| role | — | 消息角色：system / user / assistant / tool | 不同模型的对话模板对 role 支持有限，别乱用 |
| 会话模板 | Chat Template | 把消息数组拼成模型认识的一串文本 | 模板选错，效果会莫名其妙地差 |
| 流式 | streaming / SSE | 边生成边返回，不用等完整结果 | 流式和非流式的返回结构不同，要分别处理 |
| SSE | Server-Sent Events | 浏览器/HTTP 常见的流式协议，一行一条事件 | 不是 WebSocket，方向是单向的 |
| delta | — | 流式返回里"这一小段新增内容" | 最后一条可能是空 delta，只带结束原因 |
| finish_reason | — | 这次生成为什么结束 | 常见值：stop / length / tool_calls / content_filter |
| usage | — | 本次消耗的 token 统计 | 流式时不一定每条都有，可能只在最后一条 |
| tools / function calling | 工具调用 | 让模型返回结构化调用请求，由应用去执行 | 本地引擎支持程度差异很大，必须实测 |
| tool_calls | — | 模型发出的工具调用请求列表 | 需要应用执行完再用 role=tool 回传结果 |
| json mode | response_format | 要求输出是合法 JSON | 只保证格式合法，不保证字段符合你的 schema |
| 超时与重试 | — | 本地引擎更常见的失败模式 | 长上下文推理可能几十秒，别用云端默认超时 |

## 原理与机制

### 为什么会有"事实标准"

云端 API 是行业事实标准，所有客户端生态（聊天界面、插件、编码工具）都按它实现。本地引擎想被这些工具直接使用，最省事的办法就是**把自己伪装成 OpenAI**。

于是形成了现状：接口形状统一，实现细节各写各的。**兼容程度是选型时容易被忽略的维度**——有人只看模型跑不跑得动，结果接客户端时发现流式不支持、工具调用没有。

### 一次请求的生命周期

1. 客户端 POST `/v1/chat/completions`，带上模型名、消息数组、采样参数。
2. 引擎把消息数组按模型的**对话模板**拼成一串文本（这一步很关键，也很容易错）。
3. 引擎加载模型、做 prefill、开始 decode。
4. 非流式：全部生成完后一次性返回结构体。
5. 流式：每生成一小段就返回一条 SSE 事件，最后用结束标记收尾。
6. 客户端根据 `finish_reason` 判断是正常结束、被截断还是触发了工具调用。

**关键后果**：

- 你看到的所有"模型不听话"，有一半其实是第 2 步模板没拼对。
- `max_tokens` 之类参数如果客户端没显式传，**每个引擎的默认值不同**，会导致"同样的代码换个引擎，回答突然被截断"。
- 本地引擎的并发能力远小于云端，客户端要按"可能排队"来设计超时与重试。

### 流式返回长什么样

流式响应是若干条 `data:` 开头的行，每条是一段 JSON，里面 `choices[0].delta` 带着增量内容；最后一条通常是只带 `finish_reason` 的空增量，再跟一个结束标记。

客户端处理要点：

- 增量请**追加**，不要覆盖。
- 遇到 `finish_reason` 就准备收尾。
- 别依赖"一定有结束标记"，有的实现会直接断流，要做兜底。
- 流式场景下错误可能在流的中间才出现，别只检查 HTTP 状态码。

### 工具调用的往返

1. 客户端传 `tools`（工具定义），模型可能返回 `tool_calls`。
2. 应用执行这些调用，把结果作为 `role: tool` 的消息追加进 `messages`。
3. 再次请求，模型基于结果继续。
4. 结束条件是 `finish_reason` 不再是 `tool_calls`。

**坑在兼容性**：部分引擎对工具调用的支持是"表面支持"——字段能解析，但模型没有对应训练，返回质量很差；还有些版本干脆静默忽略 `tools`。

## 关键请求片段

最小非流式请求（意思是：一次最普通的对话，验证引擎是否通）：

```bash
curl http://127.0.0.1:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"本地模型名","messages":[{"role":"user","content":"你好"}]}'
```

流式请求与解析（意思是：加上 stream 开关，按行读、按 delta 追加）：

```python
resp = requests.post(url, json={"model": m, "messages": msgs,
                               "stream": True, "max_tokens": 512},
                     stream=True)
for line in resp.iter_lines():
    if line.startswith(b"data: "):
        payload = line[6:]
        if payload[:1] == b"[DONE]":
            break
        delta = json.loads(payload)["choices"][0]["delta"]
        print(delta.get("content", ""), end="", flush=True)
```

> 这段代码里两个细节最关键：`stream=True` 必须配 `iter_lines` 逐行读，以及要处理结束标记。不同引擎对结束标记的支持不一样，所以还应该加超时兜底。

## 分类与对比：引擎兼容矩阵

| 能力 | Ollama | llama.cpp server | vLLM | SGLang | MLX server |
|---|---|---|---|---|---|
| /v1/chat/completions | 支持 | 支持 | 支持 | 支持 | 支持 |
| 原生接口 | /api/chat 等 | /completion | /v1 为主 | /v1 为主 | /v1 为主 |
| 流式 SSE | 支持 | 支持 | 支持 | 支持 | 支持 |
| 流式带 usage | 常见在末条 | 看版本 | 通常支持 | 通常支持 | 看版本 |
| tools 工具调用 | 支持较好 | 支持较好 | 较完整 | 较强 | 有限 |
| json mode | 支持 | 支持 | 支持 | 强项 | 有限 |
| 模型名字段 | 必须是已拉取名字 | 看配置 | 与部署名一致 | 与部署名一致 | 与加载路径一致 |
| 默认 max_tokens | 默认不限制（受上下文限制） | 默认不限制 | 受 max-model-len 约束 | 受 context-length 约束 | 看实现 |
| 鉴权 | 默认无 | 可选 | 可选 api key | 可选 api key | 默认无 |
| 多并发 | 有限 | 有限 | 强 | 强 | 弱 |

> 读这张表的方式：**接口都能通，差异在细节行为**。做交付时按"客户要用的客户端需要哪几项能力"逐项实测，不要只看文档。

## 决策点

- **岔路口 1：直接用引擎原生接口还是 OpenAI 兼容层？** → 判断依据：应用是否会换引擎、是否需要多引擎共存 → 推荐：统一走兼容层，业务代码只认一套 → 代价：用不到引擎特有参数。
- **岔路口 2：流式还是非流式？** → 判断依据：交互式界面用流式，后端批处理用非流式 → 推荐：人看的用流式，机器处理的用非流式 → 代价：流式实现更复杂，要处理断流与错误。
- **岔路口 3：客户端默认超时设多少？** → 判断依据：上下文长度和本地硬件 → 推荐：按"最坏情况 + 余量"设，长上下文场景给足时间 → 代价：超时太长，故障发现慢。
- **岔路口 4：要不要自己写一层适配？** → 判断依据：是否用多引擎、是否需要统一错误码与重试 → 推荐：多引擎就写一层薄适配 → 代价：多一层代码要维护。
- **岔路口 5：要不要对外暴露这个接口？** → 判断依据：内部自用还是客户访问 → 推荐：对外必须先加鉴权、限流、日志 → 代价：多一层组件，但避免裸奔。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| model | 指定要用的模型 | 名字不匹配直接报错 | 与部署时注册的名字一致 |
| messages | 输入对话 | 越长越慢越吃显存 | 按模板要求组织 |
| temperature | 随机性 | 调大更发散；调小更稳定 | 0.2~0.8 |
| top_p | 采样范围 | 与温度配合，调小更保守 | 0.9 左右 |
| max_tokens | 单次输出上限 | 调大：可能被上下文截断；调小：回答不完整 | 显式指定 |
| stream | 是否流式 | 开：体验好；关：实现简单 | 交互式开 |
| stop | 停止词 | 噪声多、被截断 | 按业务定制 |
| tools | 工具定义 | 越多越吃 token，也越容易乱 | 精选，别一次给几十个 |
| response_format | 输出格式 | 强制 JSON 可能拖慢 | 需要结构化时开 |
| timeout | 客户端超时 | 见上 | 按最坏情况设置 |

## 响应结构速查

非流式响应的关键字段（意思是：客户端从这里取答案和结束原因）：

| 字段 | 含义 | 客户端要做什么 |
|---|---|---|
| choices[0].message.content | 文本答案 | 直接展示或入库 |
| choices[0].message.tool_calls | 工具调用请求 | 执行后以 role=tool 回传 |
| choices[0].finish_reason | 结束原因 | 区分 stop / length / tool_calls |
| usage | token 统计 | 记成本、算单价 |

流式响应里，上面这些内容出现在 `choices[0].delta` 与最后一条事件中，并且 **delta 里的 content 可能为空**，客户端必须容忍空增量，不能一遇到就报错。

## 错误码与失败模式

各家错误码并不统一，但大体落在下面几类，建议在适配层统一映射：

| 现象 | 常见状态码 | 真实原因 | 怎么处理 |
|---|---|---|---|
| 模型不存在 | 404 | 请求的 model 名与部署名不一致 | 对齐注册名 |
| 未授权 | 401 | 没带 key 或 key 错 | 检查请求头 |
| 参数非法 | 400 / 422 | 字段名错，或超出上下文限制 | 检查请求体与上下文预算 |
| 请求体过大 | 413 | 消息数组超过引擎上限 | 截断或拆分 |
| 限流 | 429 | 并发或配额超限 | 退避重试 |
| 服务过载 | 503 | 引擎排队过深或正在启动 | 降并发、等待、加副本 |
| 内部错误 | 500 | 模板 / 显存 / kernel 问题 | 看引擎日志，不是客户端问题 |
| 流中途断 | 200 之后断流 | 超时、引擎崩溃 | 客户端超时兜底 + 断点重试 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 换引擎后回答被截断 | 客户端没传 max_tokens，各引擎默认值不同 | 显式传，或统一在适配层写死默认 |
| 流式输出重复或乱序 | 把 delta 当完整内容覆盖而不是追加 | 增量追加，按 choices[0].index 处理 |
| 客户端卡住不结束 | 等不到结束标记，或引擎断流没兜底 | 加超时，同时处理异常断流 |
| 模型"不认识"工具调用 | 引擎对 tools 只是解析，模型本身没训练 | 选支持工具调用的模型，或自己写提示词约束 |
| system 提示好像没生效 | 对话模板没把 system 渲染进去 | 换支持的模板，或把约束写进用户消息 |
| JSON 输出时不时不合法 | 只开了提示词约束，没开强制格式 | 用引擎的 json mode / 结构化输出 |
| 同样的 seed 结果不同 | 不同引擎/不同后端不保证确定性 | 别把 seed 当可复现保证 |
| 换引擎后错误码对不上 | 各引擎错误码映射不统一 | 适配层统一错误语义，客户端只按类别处理 |
| 局域网客户端连不上 | 引擎默认只绑本机 | 显式绑定地址并加鉴权 |

## 交付视角（对客户怎么讲）

- 客户关心的是"我现有的系统能不能直接接"：能，接口层基本不用改，但要做一轮冒烟测试，重点测流式、超时、截断、工具调用。
- 讲清"兼容不等于一致"：名字一样、字段一样，行为可能不同，所以要有一份《兼容性验证清单》作为交付物。
- 交付文档里要写死：模型注册名、默认 max_tokens、超时建议、是否开启流式、是否支持工具调用。
- 如果客户要接自己的业务系统，建议加一层薄适配网关，后面换引擎时只改网关，不动业务代码。
- 报价里把"接口联调"和"兼容性测试"单列，这部分工作量经常被低估。

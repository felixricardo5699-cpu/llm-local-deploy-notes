# N卡 A卡 Mac 平台适配

> [!abstract] 一句话讲清楚
> 同一份模型代码，在 N 卡、A 卡、Mac 上能不能跑、跑多快，取决于底层走的硬件后端（CUDA / ROCm / Vulkan / Metal）和一条很长的版本兼容链——平台适配的本质就是把这根链子逐环对齐。

## 为什么重要

- 引擎选型再好，平台不支持也白搭：[[vLLM]] 基本只认 NVIDIA，Mac 上只能走 [[llama.cpp 与 GGUF]] 或 [[MLX 与 Apple 芯片推理]]。
- 客户环境是"历史遗留"的：可能是 A 卡工作站、可能是 Mac、可能是 Windows + WSL、也可能是云上虚拟化实例，你得能判断哪条路能通。
- 版本链错一环就报错，而且报错往往很含糊。懂这层结构，才能三下五除二把问题定位到"驱动"还是"框架"还是"引擎"。
- 上游是 [[参数量与显存估算]]，下游是 [[Windows 部署要点]]、[[Linux 部署要点]]、[[Mac 部署要点]]、[[容器化部署]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 硬件后端 | Backend | 引擎调用 GPU 的方式：CUDA / ROCm / Vulkan / Metal | 决定"能不能跑"，不是引擎自己的功能 |
| CUDA | — | NVIDIA 的 GPU 计算平台 | 版本分"驱动支持的最高版本"和"实际安装的运行时版本" |
| 驱动 | Driver | 操作系统和 GPU 之间的中间层 | 驱动太旧，新的 CUDA 运行时直接不可用 |
| CUDA 运行时 | CUDA Runtime | 程序运行时依赖的 CUDA 库 | 和驱动版本有兼容关系，不是越新越好 |
| cuDNN | — | NVIDIA 深度学习的算子加速库 | 缺失时常见现象是"能识别 GPU 但一跑就报算子错" |
| ROCm | — | AMD 的 GPU 计算平台，对标 CUDA | 支持型号有限，且在 Windows 上支持很受限 |
| HIP | — | AMD 用来把 CUDA 代码移植到 ROCm 的接口 | 不是所有 CUDA 程序都能无缝 HIP 化 |
| Vulkan | — | 跨平台图形/计算接口 | A 卡、集显、Windows 上常见的"能跑但慢"的路 |
| Metal | — | 苹果的 GPU 计算接口 | 只有 Apple 芯片的 Mac 才有完整加速 |
| 统一内存 | Unified Memory | CPU/GPU 共用内存（Mac 与部分平台） | 没有独立显存，调参逻辑完全不同 |
| 计算能力 | Compute Capability | NVIDIA 卡的代际编号 | 决定能跑哪些预编译 kernel、支持哪些精度 |
| 显存 | VRAM | 独显自己的内存 | Windows 上还会被桌面、共享机制吃掉一部分 |
| WSL2 | — | Windows 里的 Linux 子系统 | 可以跑 CUDA，但显存由 Windows 驱动统一管理，配置有坑 |
| 虚拟化直通 | Passthrough | 云主机/虚拟机把 GPU 直接给系统用 | 共享虚拟化 GPU 往往性能差且兼容性玄学 |
| 混合推理 | CPU+GPU offload | 一部分层放 GPU、一部分放 CPU | 是"装不下时的妥协"，不是性能优化 |
| 张量并行互联 | NVLink / PCIe | 多卡之间传数据的通道 | PCIe 带宽不够时多卡可能还不如单卡 |

## 原理与机制

### 四条后端路径

**CUDA（N 卡）**：生态最完整，所有主流引擎、所有量化、所有加速特性都优先支持。这也是"本地部署默认选 N 卡"的根本原因。

**ROCm（A 卡）**：能力接近 CUDA，但**型号支持清单窄、系统以 Linux 为主、生态轮子少**。装环境时经常遇到"框架装好了但 import 就报错"。

**Vulkan（跨平台兜底）**：A 卡 Windows、Intel 核显、各种奇怪显卡上，"能跑"的路。性能通常低于原生后端，量化支持也不全。

**Metal（Mac）**：配合统一内存，是 Mac 上唯一有实用意义的 GPU 路径（Apple 芯片）。

### 那条绕不开的兼容链

一个能跑起来的推理环境，依赖下面这条链的每一环对齐：

```
GPU 型号
  → 驱动版本（决定支持哪个 CUDA/ROCm 版本）
    → 计算运行时（CUDA / ROCm）
      → 深度学习框架（PyTorch 的 GPU 版 wheel）
        → 推理引擎（自己也要按对应 CUDA 版本编译）
          → 量化 kernel / 加速库
```

**任何一环跳版本，就可能出现"看起来都装了，跑起来就崩"。** 常见断点：

- 驱动比运行时旧 → 运行时初始化失败。
- 装了 CPU 版 PyTorch → 程序能跑，但只用 CPU，慢到离谱还不报错。
- 引擎是给旧 CUDA 编译的 → 在新环境里加载 kernel 失败。

**所以平台适配的第一步永远不是装引擎，是验证这条链**：

1. 驱动是否认得卡（`nvidia-smi` / `rocm-smi` 之类）。
2. 框架是否认到 GPU（`torch.cuda.is_available()` 这类检查）。
3. 一个最小矩阵乘能不能在 GPU 上跑。
4. 再上引擎，再上模型。

### 为什么 A 卡"性价比高"但本地部署仍以 N 卡为主

- 硬件券面参数不等于"能跑"：ROCm 支持清单之外，你就是在赌。
- 生态乘数效应：教程、轮子、量化 kernel、排错经验几乎都围绕 CUDA。
- Windows + A 卡是最麻烦的组合，很多方案要退回 Vulkan 或折腾 Linux。
- 结论：**给客户交付、团队长期维护，优先 N 卡；个人自用、愿意折腾，A 卡可以省预算**。

### Mac 的特殊性

- 没有"显存"这一层，内存就是上限，所以判断标准是"物理内存够不够 + 内存压力高不高"。
- 只有 Apple 芯片走 Metal；Intel Mac 基本只能 CPU 跑，别抱期待。
- 服务化和多并发能力弱，适合自用，不适合当团队服务。
- 详细内容见 [[MLX 与 Apple 芯片推理]] 与 [[Mac 部署要点]]。

### Windows 上的两个坑点

- **显存被系统占用**：桌面渲染、浏览器硬件加速都会吃掉一部分显存；核显机器还有"共享显存"的迷惑项，看到的数字不等于能用的数字。
- **WSL2 里的 CUDA**：能跑，但显存和主系统共享，且某些引擎/量化 kernel 在 WSL2 下兼容性一般，需要留退路。

## 平台对照表

| 维度 | N 卡（CUDA） | A 卡（ROCm / Vulkan） | Apple 芯片（Metal） | Intel 集显/独显（Vulkan 等） |
|---|---|---|---|---|
| 系统 | Win / Linux 都可 | Linux 好，Windows 受限 | macOS 原生 | Win / Linux |
| 引擎覆盖 | 最全（含 vLLM / TRT-LLM） | 中等（vLLM 支持有限） | 有限（llama.cpp / MLX） | 有限 |
| 量化支持 | 最全 | 较全（看后端） | GGUF / MLX 格式 | 较全（看后端） |
| 部署难度 | 低 | 中高 | 低 | 中 |
| 性能上限 | 高 | 中高（看型号） | 中（受内存带宽） | 低 |
| 多卡 | 成熟（NVLink/PCIe） | 一般 | 不支持 | 基本不支持 |
| 多人服务 | 适合 | 可做，看型号 | 不适合 | 不适合 |
| 典型用途 | 生产部署、批量服务 | 预算敏感、个人折腾 | 个人开发、内容创作 | 学习、demo |
| 建议 | 默认首选 | 查支持清单后再买 | 自用可以，服务别指望 | 只做入门体验 |

## 环境预检清单

上门或远程施工前，先按这张表把环境核一遍，比重装十遍环境都省时间：

| 检查项 | 怎么看 | 通过标准 | 不通过的典型表现 |
|---|---|---|---|
| 卡是否被系统识别 | nvidia-smi / rocm-smi / 系统信息 | 能看到型号与显存 | 命令不存在或列表为空 |
| 驱动版本 | 同上 | 满足框架与引擎的最低要求 | 装框架时报找不到 CUDA |
| 计算运行时版本 | 查 CUDA / ROCm 版本 | 与框架 wheel、引擎编译版本一致 | import 成功但 kernel 报错 |
| 框架是否真的用 GPU | 一行 GPU 可用性检查 | 可用且设备数正确 | 静默回落到 CPU，慢得离谱 |
| 最小 GPU 计算 | 一条小矩阵乘 | 快速返回、无报错 | 算子缺失、非法内存访问 |
| 显存实际可用 | 起服务前看剩余显存 | 比标称少 1~2G 属于正常 | 一加载模型就 OOM |
| 虚拟化情况 | 查实例类型是否直通 | 独占或直通 | 共享 GPU 驱动异常、性能玄学 |
| 多卡互联条件 | 查 NVLink / PCIe 拓扑 | 通道与并行策略匹配 | 多卡比单卡还慢 |
| 磁盘与内存 | 看剩余空间与物理内存 | 权重放得下、加载不 swap | 加载中途失败 |
| 路径与权限 | 模型目录、服务账户 | 无中文无空格、权限够 | 找不到模型文件 |

两条容易被跳过的提醒：

- **先确认"是不是根本没用到 GPU"**，再谈性能。很多"慢"的案子到这一步就终结了。
- **云端环境把直通情况问清楚**，共享虚拟化 GPU 上折腾半天，可能不如换实例类型。

## 混合 offload 什么时候才用

CPU+GPU 混合推理（[[llama.cpp 与 GGUF]] 里的常见手段）是"模型比显存大一点"时的兜底：

- **能用的边界**：只差几层还能忍；差一半时速度会掉到"演示可用、生产不可用"。
- **判断方法**：用不同 offload 层数各跑一次，看出字速度曲线，某一档骤降就说明越界了。
- **别把它当优化**：它的作用是让装不下的模型先跑起来，不是让模型更快。
- **交付时写清楚**：offload 比例决定了这台机器的速度下限，客户加内存或换卡会立刻改变表现。

## 完整流程：到一台陌生机器上怎么办

1. **摸底硬件**：卡型、显存、CPU、内存、系统版本、是否有虚拟化。
2. **验驱动**：装/升级到能支持目标 CUDA（或 ROCm）版本的驱动。
3. **验框架**：装 GPU 版框架，跑一行"能否识别 GPU"的检查，确认真的用了 GPU。
4. **验最小计算**：一条小矩阵乘，确认 kernel 能跑、不报错。
5. **选引擎**：按平台与场景选（见 [[推理引擎选型决策树]]），N 卡优先 vLLM，A 卡优先 llama.cpp/Ollama，Mac 优先 MLX/llama.cpp。
6. **跑小模型**：先用小模型验证链路，再上目标模型。
7. **测基线**：跑一次单请求与并发，记录指标（见 [[推理性能指标与调优]]）。
8. **写进交付文档**：驱动版本、CUDA 版本、框架 wheel 来源、引擎版本、启动参数。

## 决策点

- **岔路口 1：客户要买卡，推荐什么？** → 判断依据：是否要上 vLLM/多卡/生产 → 推荐：生产优先 N 卡；预算敏感且自用才考虑 A 卡 → 代价：N 卡贵，且供应紧张。
- **岔路口 2：A 卡要不要硬上 vLLM？** → 判断依据：型号是否在支持清单里、系统是否 Linux → 推荐：不在支持清单就用 llama.cpp 系或换 Ollama → 代价：放弃部分吞吐特性。
- **岔路口 3：Windows 还是 WSL2？** → 判断依据：引擎与量化 kernel 的兼容性 → 推荐：能上 Linux/WSL2 就上，原生 Windows 留作退路 → 代价：WSL2 有额外配置成本。
- **岔路口 4：Mac 上要不要自建服务给团队？** → 判断依据：并发需求与合规要求 → 推荐：能放服务器就放服务器，Mac 只做开发机 → 代价：多一台机器。
- **岔路口 5：装不下模型怎么办？** → 判断依据：是差一点还是差很多 → 推荐：差一点先量化/降上下文；差很多直接换卡，别用 CPU offload 硬撑 → 代价：offload 会慢到不可用。

## 参数与配置说明

| 项 | 作用 | 调大/调小的影响 | 常见建议 |
|---|---|---|---|
| 驱动版本 | 决定能用的运行时上限 | 太旧：新运行时不可用；太新：个别引擎 kernel 未适配 | 与引擎官方要求对齐 |
| CUDA / ROCm 版本 | 计算运行时 | 版本错配是最高频报错来源 | 与框架 wheel 和引擎编译版本一致 |
| 框架 wheel 来源 | 是否真的带 GPU 支持 | 装错成 CPU 版会"静默变慢" | 从官方索引装对应版本 |
| GPU 层数 offload | llama.cpp 把多少层放 GPU | 调大：快但可能 OOM；调小：安全但慢 | 从目标值往下试 |
| 显存上限/比例 | 允许占多少显存 | 过高：OOM；过低：浪费 | 留出桌面/其他进程余量 |
| WSL2 内存/显存配置 | 限制子系统资源 | 限制过严会导致 OOM 假象 | 按物理内存比例设置 |
| CUDA_VISIBLE_DEVICES | 指定用哪几张卡 | 数字写错就用不上卡 | 明确指定 |
| 精度设置 | FP16/BF16/FP8 等 | 降精度省显存；老卡可能不支持 | 按卡代际选 |
| PCIe 代际/通道 | 多卡通信 | 通道太少多卡收益暴跌 | 确认主板与插槽 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 装了框架但一直用 CPU 跑 | 装的是 CPU 版 wheel，或驱动不匹配导致回退 | 检查 GPU 是否可用，确认 wheel 来源 |
| nvidia-smi 正常，程序报 CUDA 初始化失败 | 驱动与运行时版本不匹配 | 按兼容表对齐，不盲目升最新 |
| A 卡装 vLLM 各种报错 | ROCm 支持型号/版本限制 | 先查支持清单，不行换 llama.cpp 系 |
| Windows 上可用显存比标称少 | 桌面渲染、共享内存机制占用 | 关掉占用、按实际可用值规划 |
| WSL2 里 OOM 但主系统内存还空 | 子系统资源限制过严 | 调整 WSL2 资源配置 |
| 多卡比单卡还慢 | PCIe 带宽不足或并行策略不当 | 先单卡调满，再评估互联条件 |
| 云主机跑不起来 | 共享虚拟化 GPU 不支持某些特性 | 选直通/独占实例，或换方案 |
| Mac 用 Intel 芯片想跑 Metal 加速 | Metal 完整加速只在 Apple 芯片 | 认命走 CPU 或换机器 |
| 模型装不下就用 offload 硬撑 | 一部分层走 CPU，速度骤降 | 量化/换小模型，offload 只当兜底 |

## 自检问题参考答案

> [!success]- 1. 依赖链上有哪几环？各环错了报什么？
> 六环：GPU 型号 → 驱动 → 计算运行时（CUDA / ROCm）→ 框架的 GPU 版 wheel → 引擎（按对应运行时版本编译）→ 量化与加速 kernel。
> 断点表现：驱动比运行时旧，运行时初始化直接失败；装了 CPU 版框架，静默回落到 CPU，慢但不报错；引擎按旧 CUDA 编译，kernel 加载失败。
> 所以验证顺序是驱动 → 框架 → 最小矩阵乘 → 引擎 → 模型，一环一环往上。

> [!success]- 2. A 卡参数不差，为什么还默认推 N 卡？
> 因为硬件参数不等于"能跑"：ROCm 支持型号清单窄、以 Linux 为主，清单外就是赌。
> 还有生态乘数效应：教程、轮子、量化 kernel、排错经验几乎都围着 CUDA 转。
> Windows 加 A 卡是最麻烦的组合，很多方案要退回 Vulkan 或去折腾 Linux。
> 结论：交付和长期维护优先 N 卡；个人自用、愿意折腾，A 卡可以省预算。

> [!success]- 3. 怎么区分"没用上 GPU"和"用了但慢"？
> 先跑框架的 GPU 可用性检查，看设备数对不对、是不是真的在用 GPU。
> 如果"能识别 GPU 但一跑就报算子错"，多半是 cuDNN 或 kernel 版本问题；如果跑得起来但慢到离谱、GPU 利用率几乎为零，基本就是静默回落到 CPU。
> 顺序不能反：先确认用没用上，再谈性能，很多"慢"的案子在第一步就终结了。

> [!success]- 4. Windows 上为什么可用显存少于标称？
> 桌面渲染、浏览器硬件加速都会长期吃掉一部分显存；核显机器还有"共享显存"这种迷惑项，看到的数字不等于能用的数字。
> 所以规划时按实际剩余显存算，起服务前先看一眼剩余量，留 1~2G 余量。
> 贴着标称值规划，最常见的结果就是一加载模型就 OOM。

> [!success]- 5. Mac 上判断跑不跑得动看什么？
> Mac 没有独立显存这一层，内存就是上限：看物理内存够不够、内存压力高不高、有没有开始 swap。
> 和 N 卡的区别是：N 卡看显存容量和显存带宽，Mac 看整块内存和内存带宽，而且并发和服务能力弱。
> 估算按可用内存的 60%~70% 选模型体量，还要给 KV Cache 单独留空间。

> [!success]- 6. 多卡什么时候反而更慢？
> 三种情况：卡间互联不够（PCIe 通道少、没有 NVLink 这类高速连接），TP 的通信开销吞掉收益；并行策略不当（卡数不能整除注意力头数，或者单卡明明放得下却强行切）；卡型或显存不一致导致负载不均。
> 对策是先单卡调满，再看互联条件决定要不要上多卡。
> 多卡的主要价值是"装得下"，不是"一定更快"。

> [!success]- 7. 拿到一台陌生机器，排查顺序是什么？
> 摸底硬件（卡型、显存、CPU、内存、系统版本、是否虚拟化）→ 验驱动（能否支持目标运行时）→ 验框架（GPU 是否真的可用）→ 验最小 GPU 计算（小矩阵乘）→ 按平台选引擎 → 先用小模型验证链路 → 测基线 → 把驱动/运行时/框架/引擎版本写进交付文档。
> 核心原则是"先确认链路通，再谈引擎和模型"，别一上来就怀疑模型。

## 交付视角（对客户怎么讲）

- 客户问"我这几张 A 卡能不能跑"：先查支持清单，再看系统，别先答应。给一个"能跑但慢/不能跑"的明确结论比模糊承诺值钱。
- 交付前必须做一次"环境预检"，把驱动、运行时、框架、引擎版本逐项记录，作为交付文档的一部分。
- 给客户推荐硬件时把"生态税"讲清楚：省下的卡钱，可能变成后面几周的折腾。
- 对 Mac 用户明确边界：开发机可以，服务端不要指望。
- 排错时先分三层：硬件/驱动层、框架层、引擎层，别一上来就怀疑模型。

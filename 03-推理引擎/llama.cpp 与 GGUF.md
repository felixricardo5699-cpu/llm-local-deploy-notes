# llama.cpp 与 GGUF

> [!abstract] 一句话讲清楚
> llama.cpp 是用 C/C++ 写的单机推理引擎，GGUF 是它专用的"模型集装箱"格式——两者合起来解决一件事：**用最少的依赖、尽量少的显存，在一台普通电脑上把模型跑起来**。

## 为什么重要

- **它是整个本地推理生态的地基**：Ollama、LM Studio、各种 Mac/Windows 客户端，底层基本都是 llama.cpp。
- **它是唯一把"显存不够怎么办"讲透的引擎**：GPU 层数 offload、KV Cache 量化、部分层跑 CPU，这些概念别的引擎都藏起来了。
- **它是老卡、核显、纯 CPU、AMD 卡的最后退路**：当 CUDA 生态走不通时，Vulkan/CPU 后端还能让模型跑起来。
- 上游是 [[量化技术]]、[[Attention 与 KV Cache]]；下游是 [[Ollama]] 与 [[推理性能指标与调优]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| llama.cpp | — | C/C++ 编写的推理引擎，跨平台、依赖少 | 不是"某个模型的客户端"，它支持大量模型结构 |
| GGUF | GPT-Generated Unified Format | 单文件模型格式：权重 + 词表 + 超参 + 模板都装在一个文件里 | 和 HuggingFace 的 safetensors 是两套格式，需要转换 |
| 量化类型 | Quant Type | 权重用几位存、怎么分块存，如 Q4_K_M | 名字相似类型差别不小，别只看数字 |
| imatrix | Importance Matrix | 用一段语料统计"哪些权重更重要"，让低比特量化更准 | 属于"校准"步骤，加了会更慢但质量更好 |
| GPU 层数 | n_gpu_layers | 有多少层模型放到显卡上算 | 不是"参数比例"，是"层的数量" |
| KV Cache | — | 缓存已算过的注意力结果，避免重复计算 | 上下文越长吃越多显存，和模型权重抢空间 |
| offload | — | 把一部分计算搬到 GPU，其余留 CPU | 部分 offload 是能跑大模型的唯一办法，但速度会掉台阶 |
| mmap | 内存映射 | 直接映射模型文件到内存，按需读取 | 冷启动/首次读取慢，但省内存、方便多进程共享 |
| KV Cache 量化 | -ctk / -ctv | 把 KV Cache 也用低位宽存 | 省显存，但可能影响长上下文稳定性 |
| 后端 backend | CUDA / Metal / Vulkan | 引擎用来调用不同硬件的计算接口 | 编译时选错后端，装完发现用的是 CPU |
| 张量分片 | tensor-split | 多卡时每张卡分多少比例 | 和"模型分片文件"不是一回事 |
| 上下文 | -c / n_ctx | 一次能处理多少 token | 调大线性吃 KV Cache 显存，是 OOM 的常见原因 |

## 原理与机制

### GGUF 里到底装了什么

GGUF 是一个"容器"：文件头 + 元数据区 + 张量数据区。

- **元数据**：模型架构参数（层数、头数、维度）、词表与分词规则、**对话模板**、BOS/EOS 之类的特殊 token。
- **张量数据**：量化后的权重，按张量逐个排列，每个张量旁边记着它的量化类型和形状。
- **为什么这么设计**：一个文件拿过去就能跑，不用再配 tokenizer.json、config.json 那一堆东西；可以用 mmap 直接内存映射，启动快、占用省。

**后果**：GGUF 是"自解释"的，所以 Ollama、LM Studio 这些工具都能直接吃；但一份 GGUF 只对应一种量化档位，想要别的档位得重新转/重新下。

### 量化格式怎么理解

- 不是"每个权重单独压到 4 位"，而是**按块（block）量化**：一组权重共享一个缩放因子（scale）。块越小越准，元数据越多。
- 常见档位从低到高：Q2_K、Q3_K_M、Q4_K_S、**Q4_K_M**、Q5_K_M、Q6_K、Q8_0。M 是"混合"——一部分张量用更高位宽保精度。
- 规律：**位宽越高，质量和显存越高，速度越慢**。Q4_K_M 是"质量/体积"的常见平衡点，低于 Q3 时复杂任务退化明显。
- IQ 系列（如 IQ4_XS）用 imatrix 做校准，在同样体积下通常比普通 K-quant 好一点，但转换更麻烦、有时速度略慢。

### GPU 层数 offload 到底在干什么

模型是**一层一层**串起来算的。llama.cpp 允许你说"前 N 层放显卡，剩下的留在内存用 CPU 算"。

- 每一层在显存里占的容量 ≈ 该层权重体积 + 该层的 KV Cache + 该层的计算缓冲。
- 所以 `-ngl` 不是"百分比"，而是很实的一层一层搬。**显存不够时，从最大值往下试，直到能稳定跑起来。**
- 全部 offload（`-ngl 99` 且层数放得下）速度最快；部分 offload 时，GPU 层算完要把结果传回 CPU，**速度会掉一个台阶**，不是线性变慢。

**后果**：24G 卡跑 32B 4bit 可以"全放"；16G 卡跑 32B 就要部分 offload，出字速度可能只剩全 GPU 方案的三分之一甚至更低。这是"能不能跑"和"值不值得用"的分界线。

### 上下文和显存的关系

KV Cache 占的显存可以用这个式子估：

> KV 显存 ≈ 2 × 层数 × KV 头数 × head_dim × 上下文长度 × 每元素字节数

- 前面的 `2` 是 K 和 V 两份，`2` 字节是 fp16。
- **GQA / MQA** 的模型 KV 头数很少，所以长上下文便宜；传统多头注意力的模型，长上下文非常吃显存。
- 举例感受一下量级：一个 7B~8B 级别、32 层左右、KV 头数为个位数的模型，fp16 KV 大约 **每 1K token 一百多 MB**；上下文开到 32K 就是几个 GB，比很多人想象的大得多。
- 把 KV Cache 也量化（`-ctk q8_0 -ctv q8_0`）能省一半左右，代价是长上下文质量可能有轻微损失。

## 工具链与关键命令

| 步骤 | 工具 | 干什么 |
|---|---|---|
| 转格式 | `convert_hf_to_gguf.py` | 把 HuggingFace safetensors 转成 GGUF（通常是 fp16 基础文件） |
| 量化 | `llama-quantize` | 把 fp16 GGUF 压成 Q4_K_M 等档位 |
| 校准（可选） | imatrix 流程 | 先统计重要性矩阵，再量化，低比特时质量更好 |
| 试跑 | `llama-cli` | 命令行单次对话，验证模板和输出是否正常 |
| 起服务 | `llama-server` | 提供 OpenAI 兼容 HTTP 服务 |
| 压测 | `llama-bench` | 测 prefill / decode 速度，用于对比参数 |

量化的关键一行（意思是：把 fp16 的 GGUF 按 Q4_K_M 规则压一遍）：

```bash
llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M
```

起服务的关键参数（意思是：把能放的层都放显卡、上下文 8K、开 flash attention、对局域网提供服务）：

```bash
llama-server -m model-Q4_K_M.gguf -ngl 99 -c 8192 -fa --host 0.0.0.0 --port 8080 --api-key local
```

> 这两行是最小可用集。真要调优，后面每个参数都对应一个显存/速度的取舍。

## 分类与对比：llama.cpp vs Ollama vs vLLM

| 维度 | llama.cpp | Ollama | vLLM |
|---|---|---|---|
| 定位 | 裸引擎，调参自由 | llama.cpp 的封装版 | 生产服务框架 |
| 模型格式 | GGUF | GGUF | safetensors 系 |
| 显存控制 | 逐层 offload，粒度最细 | 只能给个 num_gpu | 显存池化管理，粒度也不同 |
| 并发 | 弱，多路靠多进程/多实例 | 弱，靠内置并行 | 强，连续批处理 |
| 适合 | 单机自用、老卡、CPU、Mac | 快速上手、演示 | 多人服务 |
| 学习价值 | 最高（概念都能看见） | 中（封装掉了细节） | 高（但概念不同） |

## 决策点

- **岔路口 1：选哪个量化档位？** → 判断依据：显存预算 + 任务难度 → 推荐：默认 **Q4_K_M**，显存宽裕上 Q5/Q6，极度缺显存再考虑 Q3/IQ3 → 代价：Q3 以下复杂推理和代码任务会明显变差。
- **岔路口 2：显存不够时，降层数还是降量化？** → 推荐：先降上下文和并发，再降层数（保证质量），最后才降量化档位 → 代价：降层数速度掉台阶，降量化质量掉台阶，两个痛法不同。
- **岔路口 3：用不用 KV Cache 量化？** → 显存吃紧且上下文长时值得用 q8_0 → 代价：极长上下文下可能出现复读、注意力异常，交付前要验收。
- **岔路口 4：全 offload 还是接受部分 offload？** → 推荐：能全放就全放；差一两层就降上下文/降量化凑满；差很多层就说明这台机器不适合这个模型 → 代价：部分 offload 的"能跑"往往慢到没有交付价值。
- **岔路口 5：自己转 GGUF 还是用现成的？** → 通用模型直接用现成；微调模型、特殊量化档位必须自己转 → 代价：转换要吃 CPU 内存、耗时间，还要验证模板对不对。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| `-ngl` / n_gpu_layers | 放显存的层数 | 调大：快，显存吃紧；调小：能跑但慢 | 99（全放）或按显存逐层试 |
| `-c` / n_ctx | 上下文长度 | 调大：长文可用，KV Cache 线性吃显存 | 4K ~ 32K |
| `-fa` / flash attention | 用融合注意力算子 | 打开：长上下文更快、更省显存 | 开（除非后端不支持） |
| `-t` / threads | CPU 线程数 | 调大：CPU 段变快，但过度会抢资源 | 物理核心数附近 |
| `-b` / `-ub` | 批大小 / 微批 | 调大：prefill 更快，显存更高 | 默认附近，别乱拉满 |
| `-ctk` / `-ctv` | KV Cache 数据类型 | 降精度：省显存；过高上下文可能掉质量 | f16 或 q8_0 |
| `--mlock` | 锁内存，禁止换出 | 打开：更稳，但会占满内存 | 内存足够时开 |
| `--no-mmap` | 不用内存映射，整份读入 | 打开：启动慢、占内存，但某些机械盘/网络盘更稳 | 默认关 |
| `--tensor-split` | 多卡分配比例 | 调整各卡负载，防止一张卡先满 | 按显存比例 |
| `-np` | 并行请求数（server） | 调大：并发上来，KV Cache 翻倍 | 1 ~ 4 |
| `--api-key` | 服务鉴权 | 不设就是裸奔，局域网暴露风险 | 交付必设 |
| `--jinja` | 用模型自带对话模板 | 打开：模板更准确，工具调用更可靠 | 建议开 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| `-ngl 99` 之后直接 OOM | 全放之后 KV Cache 和计算缓冲没算进去 | 先把 `-c` 降下来；或按"显存 - 权重 - 1~2G 余量"算 KV 空间 |
| 以为 16G 卡能轻松跑 32B 4bit | 权重占了 18G 左右，根本放不下 | 32B 4bit 需要 24G 级别才舒服；16G 只能部分 offload，速度很难接受 |
| 输出的对话格式乱、把用户话当系统提示 | 模型缺对话模板，或者没开模板渲染 | 检查 GGUF 元数据里的模板，必要时用 `--jinja` 或手动指定模板 |
| 明明编了 CUDA 版，跑起来还是 CPU 速度 | 编译产物没带 GPU 后端，或驱动/运行时不对 | 看启动日志里的后端信息；确认用的是正确二进制 |
| 上下文开大后质量下降、开始复读 | KV Cache 量化 + 长上下文叠加导致注意力退化 | 先关 KV 量化验证；确认是显存换质量还是别的原因 |
| 多卡时一张卡先满、另一张闲着 | 默认均分，没有按显存比例调 | 用 `--tensor-split` 显式给比例 |
| 换了台机器同一模型速度差很多 | 后端不同（CUDA/Metal/Vulkan/CPU）、量化档位不同、内存带宽不同 | 固定后端与量化档位，用 `llama-bench` 对比而不是凭感觉 |
| 启动很快但第一句特别慢 | mmap 按需读文件，首次要真正从磁盘加载 | 交付时做一次预热请求；机械盘/网络盘考虑 `--no-mmap` |

## 输入 → 动作 → 输出 → 验收

用 llama.cpp 交付时，把每一步的"为什么"写清楚，现场就不会慌：

- **输入**：模型（HF 格式或现成 GGUF）、目标机器（卡型/显存/内存/系统）、业务上下文长度、并发人数。
- **动作 1 转格式**：HF 权重 → fp16 GGUF，验证词表与模板没丢。
- **动作 2 量化**：按显存选档位，压成 Q4_K_M 等目标档位。
- **动作 3 试跑**：命令行跑几条真实问题，确认输出正常、模板正确。
- **动作 4 定 offload**：从全放开始，OOM 就降上下文，再不行降层数。
- **动作 5 起服务**：`llama-server` + 鉴权 + 监听地址，压测并发。
- **输出**：一个可复现的启动脚本 + 量化好的模型文件 + 实测数据。
- **验收标准**：重启能起、模板正确、长上下文不崩、目标并发下延迟可接受。

## 一次推理的显存账本

拆开看，显存被五样东西占着，排 OOM 时按这个顺序对账：

| 占用项 | 量级感受 | 能不能调 |
|---|---|---|
| 模型权重 | 由参数量 × 每权重的比特数决定，是大头 | 换量化档位 |
| KV Cache | 由上下文长度 × 层数 × KV 头数决定 | 降上下文、KV 量化 |
| 计算缓冲 | 由批大小、上下文长度决定，通常较小 | 调低批大小 |
| 后端运行时开销 | 固定开销，各家实现不同 | 换后端 |
| 显存碎片/保留 | 通常几个百分点，但会让"够用"变成"差一点" | 留余量、必要时重启进程 |

**实操口径**：不要让权重 + KV 算出来正好等于显存。至少留 1~2G 给运行时和碎片，否则就是"能加载、一跑就爆"。

## 量化档位怎么选（实测法，不靠感觉）

1. 固定同一份提示词集（覆盖简单问答、长文总结、代码、多步推理四类）。
2. 每个候选档位跑同样的问题，记录输出质量（能不能完成任务）和速度。
3. 先排除质量明显不合格的档位，再在剩下的里选体积最小的。
4. 特别关注"长上下文 + 复杂任务"这两类，低比特翻车主要发生在它们身上。
5. 把结论写进交付文档：为什么选这个档位，而不是"默认就这样"。

> 经验值：Q4_K_M 在多数任务上是质量和体积的平衡点；需要更稳就上 Q5/Q6；Q3 以下只在显存极度受限时用，并且必须实测业务任务。

## 和 Ollama 的参数映射

从 Ollama 迁到原生 llama.cpp，或者反过来，对应关系是这样的：

| Ollama（Modelfile） | llama.cpp | 说明 |
|---|---|---|
| num_ctx | `-c` | 上下文长度，语义一致 |
| num_gpu | `-ngl` | 放显存的层数 |
| num_predict | `-n` | 最大输出 token |
| temperature | `--temp` | 采样温度 |
| top_p | `--top-p` | 核采样 |
| num_thread | `-t` | CPU 线程数 |
| 系统提示 | `--system-prompt` 或模板内 | 两边的注入方式不同，要验证 |
| OLLAMA_NUM_PARALLEL | `-np` | 并行请求数，llama.cpp 也有 |

> 这张表的意义：同一套调参思路可以平移，但**默认值不同**，别以为改了同样的数字行为就一样。

## 多卡、多实例与分片

- **多卡**：`--tensor-split` 控制每张卡分多少层/多少比例，目的是让两张卡同时满、而不是一张先爆。
- **多实例**：显存放得下多份权重时，起多个 `llama-server` 绑定不同端口再负载均衡，比硬提并发更稳。
- **多进程读同一份模型**：依靠内存映射可以让多个进程共享同份权重文件，但显存是各自独立的，别搞混。
- **判断**：卡多但显存小，分片能装下更大模型；卡少但单卡大，优先单卡全放，省掉通信开销。

## 常见误解澄清

- **"GGUF 只是另一种权重格式"**：它还包含词表、模板、超参，是自解释的整体，这点和 safetensors 差别很大。
- **"量化越低越快"**：低比特能省带宽，但反量化开销可能上升，实际速度要看后端实现，不是线性变快。
- **"层数全放就是最快"**：全放通常最快，但如果显存贴着上限，碎片和缓冲会导致抖动，反而更慢。
- **"上下文越长越强"**：长上下文能塞更多内容，但注意力成本上升、KV Cache 吃显存，还会稀释关键信息。
- **"llama.cpp 只能单机跑"**：它能起服务、支持并行请求，只是调度能力不适合高并发生产。
- **"编译一次到处能用"**：不同后端、不同指令集、不同显卡要对应编译产物，拷来拷去容易跑成 CPU。

## 一个真实的交付场景

需求：客户有一台旧工作站，显卡显存不大，想本地跑一个 32B 级模型做内部文档问答。

- **第一步估账**：32B 4bit 权重就十几 G，那张卡装不下全量，只能部分 offload。
- **实测**：部分 offload 后出字速度慢到不可接受，问答体验不如人工翻文档。
- **方案调整**：改用 14B 级 4bit 全放，上下文按业务真实长度给到 8K，速度回到可用区间。
- **结论**：不是"能不能跑"，而是"跑出来能不能用"。最终交付了 14B 方案 + 一份显存账本，说明为什么 32B 在这台机器上不成立。
- **教训**：先算显存账，再谈模型大小。客户不会因为你诚实而减少信任，反而会因为你提前识别风险而加信任。

## 自检问题参考答案

> [!success]- 1. GGUF 比 safetensors 方便在哪？
> 它把权重、词表、超参、对话模板、特殊 token 全装进一个文件，是自解释的"集装箱"。
> 拿过去就能跑，不用再配 tokenizer.json、config.json 那一堆文件，还能用 mmap 直接映射。
> 代价是一份 GGUF 只对应一种量化档位，换档位要重新转或重新下。
> 所以 Ollama、LM Studio 这类工具都能直接吃 GGUF。

> [!success]- 2. 为什么 `-ngl` 是层的数量，不是参数比例？
> 因为模型是一层一层串起来算的，这个参数说的是"前多少层放到显卡上"。
> 每一层在显存里占的是该层权重 + 该层 KV Cache + 该层计算缓冲，所以它是一层一层很实的搬迁。
> 显存不够时就从最大值往下试，直到能稳定跑起来；它跟"参数量占比"没有直接换算关系。

> [!success]- 3. 上下文从 4K 加到 32K，多出来的是什么？
> 多出来的是 KV Cache：它随上下文长度线性增长，和模型权重抢同一块显存。
> 量级上，7B~8B 级别、32 层左右、KV 头数为个位数的模型，fp16 KV 大约每 1K token 一百多 MB。
> 乘到 32K 就是几个 GB，比很多人想象的大得多，这正是长上下文机器容易 OOM 的原因。

> [!success]- 4. 部分 offload 为什么是"掉台阶"？
> 因为 GPU 层算完要把结果传回 CPU，再接着往下算，中间多了主机与显卡之间的来回搬运。
> 全放时这条数据通路不产生额外等待，一旦有层落在 CPU，每一步都要等搬运和 CPU 计算。
> 所以它不是按层数比例平滑变慢，而是一下掉一档；掉得多了，交付上就没有实用价值。

> [!success]- 5. 显存不够时调整顺序是什么？为什么先动上下文？
> 顺序：先降上下文、再降并发，然后才降层数，最后才降量化档位。
> 先动上下文是因为它不改模型质量、不动权重，只是把 KV Cache 的预留缩回来，代价最小。
> 降层数会掉速度台阶，降量化会掉质量，两者都是真的损失，所以要放到后面。

> [!success]- 6. GQA 模型为什么长上下文更便宜？
> 因为 KV Cache 的大小和 KV 头数成正比，GQA 让多个查询头共享一组 KV 头，KV 头数少了很多。
> 按公式看，层数、上下文、字节能省的不多，KV 头数却是成倍地降。
> 所以同样是 32K 上下文，GQA 模型的 KV 占用可能只有传统多头注意力的几分之一。
> 这也是选模型时"长上下文能力"要看结构、不只看上下文窗口标称值的原因。

> [!success]- 7. 自己转 GGUF 最容易错在哪？
> 最容易错在模板和词表：元数据里的对话模板丢了或不对，跑起来格式乱、把用户话当系统提示。
> 其次是量化档位选错和 imatrix 流程没走对，低比特下质量会明显退化。
> 对策是转换后马上用命令行试跑几条真实问题，确认模板、EOS、特殊 token 都正常，再进量化。

## 交付视角（对客户怎么讲）

- 客户问"我这个卡能跑多大模型"：先看显存，再按"权重 + KV Cache + 余量"三块算，通常给出的是保守量级，别拍胸脯。
- 客户问"为什么别人的 4060 能跑 32B"：能跑和能用是两件事，部分 offload 出来的速度拿来提问会让人失去耐心。
- 交付里要固化"模型文件 + 量化档位 + 启动参数"三件套，并在验收单上写清实测的上下文与并发上限。
- 如果客户机器是 AMD 或核显，别嫌麻烦，走 llama.cpp 的 Vulkan 路线往往比硬上 CUDA 生态更快交付。

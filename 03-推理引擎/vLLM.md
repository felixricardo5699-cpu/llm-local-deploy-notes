# vLLM

> [!abstract] 一句话讲清楚
> vLLM 是面向生产环境的 GPU 推理服务框架，它靠"显存分页管理 + 连续批处理"把一张卡上的并发吞吐拉到接近硬件上限，是目前自建大模型 API 的默认选择。

## 为什么重要

- 它是"演示"和"生产"之间的分水岭：[[Ollama]] 能让你一个人用得舒服，vLLM 能让十几个人同时用还不崩。
- 它把显存管理做成了一个体系（KV Cache 分块、内存池、前缀复用），**理解这套体系，才能理解为什么它会 OOM、为什么调两个参数吞吐就翻倍**。
- 做本地部署交付，客户只要提"多人用 / 对外 API / 稳定"，方案基本就落在 vLLM 上，绕不开。
- 上游是 [[Attention 与 KV Cache]] 与 [[Dense 与 MoE 架构]]，下游是 [[服务化与 API 鉴权]] 与 [[性能调优清单]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| vLLM | — | 高吞吐的 GPU 推理服务框架，自带 OpenAI 兼容 API | 不是"更快的 llama.cpp"，它面向的是服务端并发 |
| PagedAttention | 分页注意力 | 把 KV Cache 切成固定大小的块，按需分配、不连续存放 | 名字像算法，本质是显存管理机制 |
| KV Cache 块 | KV Block | 存放固定数量 token 的注意力缓存的最小单位 | 不是按"一条请求"分配，而是按块拼装 |
| 连续批处理 | Continuous Batching | 每生成一步就重排批次，算完的请求退出、新的插入 | 和"攒够一批一起跑"的静态批处理完全不同 |
| 前缀缓存 | Prefix Caching | 相同提示词前缀的 KV 结果直接复用 | 对系统提示、RAG 检索头、多轮对话收益很大 |
| gpu-memory-utilization | 显存利用率 | 启动时预占多大比例的显存 | 预占，不是"用多少占多少"，这是 OOM 的常见根因 |
| max-model-len | 最大模型长度 | 单条请求能处理的最大 token 数 | 直接决定 KV Cache 池的预留空间 |
| max-num-seqs | 最大并发序列数 | 同时处理多少条请求 | 和显存、上下文共同决定吞吐与延迟 |
| max-num-batched-tokens | 单步批 token 上限 | 一步最多算多少 token | 主要影响 prefill 的吞吐与尾延迟 |
| 张量并行 | Tensor Parallel, TP | 模型切到多张卡上同时算 | 卡数要能整除注意力头数，卡型最好一致 |
| safetensors | — | HuggingFace 的权重格式 | vLLM 吃的是这套，不是 GGUF，换引擎要换模型 |
| 量化格式 | AWQ / GPTQ / FP8 | 低比特权重格式 | 不是所有模型每个版本都支持，选型前查兼容表 |
| prefill / decode | 预填充 / 解码 | 一次性算提示词 / 逐 token 生成 | 两段瓶颈不同：前者靠算力，后者靠带宽 |
| 启动预热 | Warm-up | 启动时先跑几轮把显存和 kernel 准备到位 | 冷启动后第一批请求会明显更慢 |
| Prometheus 指标 | /metrics | 引擎暴露的吞吐、排队、显存指标 | 生产环境必须接，否则没法定位问题 |

## 原理与机制

### 直觉版

把显存想成一张餐桌：

- 传统做法：每来一桌客人，就按"最多可能来 10 人"预留整张桌子——**大部分位置空着不敢给别人用**。
- PagedAttention：改成"按人头分配椅子"，谁来给谁一把，中间可以拼桌。于是同样的桌子能坐更多人。
- 连续批处理：后厨不是等一桌菜全做完才接下一桌，而是每做好一道就换一道，**永远不让灶台闲着**。
- Prefix caching：客人点的都是同一份套餐，前菜直接提前备好，跳过重复劳动。

### PagedAttention：为什么它能让并发翻倍

传统 KV Cache 的浪费来自三块：

1. **预留浪费**：按最大可能长度预留，但用户实际只输入了几百 token。
2. **碎片浪费**：显存里东一块西一块，凑不出连续大块。
3. **共享浪费**：同一段系统提示，每个请求都各存一份。

PagedAttention 的做法是把 KV Cache 切成固定大小的块（block），用一张"块表"记录每条请求的 token 对应哪些块：

- 需要多少分配多少，**预留浪费基本消失**。
- 块可以在显存里不连续，**碎片问题消失**。
- 相同前缀的块可以共享，**共享浪费降低**。
- 后果：同样显存能装下更多请求、更长上下文；代价是多了块表管理和拷贝开销（通常很小）。

**一句话后果**：显存不再被"预留"吃掉，而是被"真实使用"吃掉。所以 vLLM 的 OOM 往往不是慢慢发生的，而是**启动阶段就把显存预占到顶**。

### 连续批处理：吞吐从哪来

- 静态批处理：攒满一批，全部算完再处理下一批。短请求要等长请求，**GPU 大量空转**。
- 连续批处理：每生成一个 token 就重排一次批次，算完的请求立刻退出，排队的立刻补位。
- 后果：**吞吐大幅上升**，尤其当请求长度差异大时；代价是单条请求的延迟会随并发波动，你没法承诺"固定 2 秒出首字"。
- 交付含义：对客户承诺延迟时要按"目标并发下的 P95"讲，而不是空载时的数字。

### Prefix Caching：省的是 prefill

- 原理：把请求开头的 token 序列的 KV 结果存起来，后续请求如果有相同前缀，直接命中，跳过重复计算。
- 什么场景收益大：**同一段长系统提示**（几千 token）、**RAG 检索头固定**、**多轮对话**（前面几轮都一样）。
- 什么场景没收益：每个请求前缀都不一样（比如把用户问题放最前面）、缓存被淘汰、前缀中间改了一个字。
- 后果：TTFT 明显下降、GPU 计算量下降；但如果提示词结构没设计好，等于白开。
- **实操建议**：把不变的内容（系统提示、工具定义、检索到的固定背景）放最前面，把变化内容放最后。

### gpu-memory-utilization：为什么它是 OOM 的第一嫌疑

- 这个参数不是"用到多少算多少"，而是启动时**按比例预占**：设 0.9 就先占 90%，再从里面切出一大块当 KV Cache 池。
- 预占的好处：KV Cache 池大小可预测，调度稳定。
- 坏处：**它不给你留后路**。系统、驱动、其他进程、模型加载峰值都需要显存，一旦算不准就 OOM。
- 常见取值 0.80 ~ 0.90。一张纯计算卡上可以高一点，桌面环境/多进程共用的机器上要低一点。
- 判断口径：先能稳定起来，再逐步往上调，别反过来。

### max-model-len：一个参数决定三件事

- 单请求能塞多长（业务上限）。
- KV Cache 池要为单条请求预留多少（显存）。
- 引擎内部的调度与 kernel 选择（性能）。

- 把它设成"模型的最大上下文"，等于告诉引擎"可能有人要这么长"，**显存要按这个上限准备**。
- 业务实际只要 8K，就不要设 128K。这是最容易被忽略的省钱操作。
- 后果：设小了长文档会被拒（返回错误或截断），设大了并发上不去甚至起不来。

### 张量并行：多卡怎么"变快"

- 把每一层的权重横切到多张卡，每张卡算一部分再合并。
- 好处：单卡装不下的模型可以装下；理论上算力叠加。
- 代价：卡之间要频繁通信，**卡间带宽差的机器可能比单卡还慢**。
- 经验：TP 卡数要能整除注意力头数；尽量同型号同显存；NVLink/高速互联比 PCIe 舒服很多。
- 后果：多卡不是"插上就翻倍"，多数情况下是"能装下大模型"，吞吐提升远小于卡数翻倍。

## 关键启动参数

一条最小可用的生产启动命令：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --gpu-memory-utilization 0.85 \
  --max-model-len 8192 \
  --max-num-seqs 16 \
  --api-key sk-local-xxx
```

> 这四行分别对应：模型从哪来、显存预占多少、单请求上限多长、同时处理几路、以及别裸奔的鉴权。**每个数字都是显存与体验的取舍**，不是抄来就行。

多卡时加一个参数即可（把模型切到两张卡上）：

```bash
--tensor-parallel-size 2
```

> 启动前先确认卡间互联和显存一致，否则并行度上去了速度反而掉。

## 完整流程：从模型到可服务 API

| 阶段 | 动作 | 为什么 |
|---|---|---|
| 1. 选模型 | 选 safetensors 格式、确认引擎支持该结构 | vLLM 对模型结构支持有清单，不是所有模型都能直接跑 |
| 2. 估显存 | 权重 + KV Cache 池 + 激活缓冲 + 余量 | 起不来的绝大多数原因是没算这笔账 |
| 3. 拉起服务 | 设 max-model-len、gpu-memory-utilization、并发上限 | 这三个决定"能起来"和"能服务" |
| 4. 单请求验证 | 先跑通一条，确认模板与输出正常 | 先证明功能，再谈性能 |
| 5. 并发压测 | 按目标并发、真实长度压一轮，看 TTFT 与吞吐 | 空载数字没有参考价值 |
| 6. 接上层 | 配 base_url 与 API key，验证工具调用等能力 | 上层依赖的功能要逐项测 |
| 7. 监控告警 | 接 /metrics，关注排队长度和显存 | 生产环境没有监控等于没有运维 |

## 内部能力对比：vLLM 的几个开关值不值得开

| 能力 | 默认状态 | 值不值得开 | 代价 |
|---|---|---|---|
| PagedAttention | 开 | 必开，这是它的核心 | 无，别关 |
| 连续批处理 | 开 | 必开 | 单请求延迟随并发波动 |
| Prefix Caching | 通常已启用 | 长系统提示/RAG 场景必须利用 | 结构设计不对就没收益 |
| 张量并行 | 关 | 模型装不下时开 | 通信开销，卡型要求 |
| 量化（AWQ/GPTQ/FP8） | 按模型 | 显存不够时开 | 质量与兼容性风险 |
| 投机解码 | 关 | 有匹配的草稿模型时值得试 | 收益依场景，配置复杂 |
| 最大并发拉满 | 按显存 | 不建议 | 尾延迟恶化，排队不可控 |

## 决策点

- **岔路口 1：用 vLLM 还是 Ollama？** → 判断依据：并发人数、是否需要稳定 SLA → 推荐：> 4 路并发或对外服务直接 vLLM → 代价：学习成本和"模型格式要换"的迁移成本。
- **岔路口 2：max-model-len 设多少？** → 判断依据：业务真实最长文档长度（不是模型上限） → 推荐：按 P95 长度再留 20% 余量 → 代价：设小了长文档请求会失败，要有明确的错误提示。
- **岔路口 3：gpu-memory-utilization 设多少？** → 判断依据：机器是否专用、有没有桌面环境 → 推荐：专用卡 0.90，混用机器 0.80 → 代价：设太高容易 OOM，设太低浪费显存、并发上不去。
- **岔路口 4：要不要上多卡？** → 判断依据：单卡能否装下 + 卡间互联 → 推荐：能单卡就单卡，装不下才 TP → 代价：多卡通信开销、故障面变大、成本翻倍。
- **岔路口 5：要不要量化？** → 判断依据：显存缺口大小、任务对质量的敏感度 → 推荐：先降上下文和并发，仍有缺口再考虑 FP8/AWQ → 代价：可能掉质量，还要确认引擎与模型版本兼容。
- **岔路口 6：自己起服务还是用容器？** → 推荐：交付用容器，把驱动、CUDA、引擎版本固定住 → 代价：镜像大、调试要走容器内。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| gpu-memory-utilization | 启动时预占显存比例 | 调大：KV 池更大、并发更高，但 OOM 风险上升；调小：安全但浪费 | 0.80 ~ 0.90 |
| max-model-len | 单请求最大 token 数 | 调大：长文档可用，KV 池要更多；调小：省显存、并发上去 | 4K ~ 32K，按业务 |
| max-num-seqs | 同时处理的序列数 | 调大：吞吐高，尾延迟差；调小：排队但单请求快 | 8 ~ 64，按压测 |
| max-num-batched-tokens | 单步批 token 上限 | 调大：prefill 吞吐高、首字延迟可能变差 | 默认附近调整 |
| tensor-parallel-size | 张量并行卡数 | 调大：能装大模型；通信成本上升 | 1/2/4/8 |
| dtype | 计算精度 | 降精度：省显存、快，但可能掉质量 | 按卡能力选 FP16/BF16/FP8 |
| quantization | 权重量化方式 | 低比特省显存，兼容性和质量要验证 | 按模型支持表 |
| enable-prefix-caching | 前缀缓存开关 | 打开：重复前缀场景收益大；关闭：省内存开销 | 长提示场景开 |
| enforce-eager | 禁用 CUDA Graph | 打开：兼容性好但慢；关闭：默认更快 | 兼容出错时才开 |
| api-key | 接口鉴权 | 不设就是裸奔 | 生产必设 |
| port / host | 监听地址 | 默认本地，对外要显式绑 | 0.0.0.0 视安全策略 |
| served-model-name | 对外模型名 | 用于上层固定模型名，换底模型不用改上层 | 自定义语义化名字 |

## 常见 OOM 与启动失败排查

| 现象 | 原因 | 对策 |
|---|---|---|
| 启动就报显存不足 | gpu-memory-utilization 太高，或 max-model-len 太大 | 先各降一档，能起来后再调 |
| 加载权重到一半失败 | 模型比显存大，或精度选错（FP16 当成能装） | 换量化或上多卡，别硬撑 |
| 能起来但跑几轮后 OOM | 并发把 KV 池占满后继续压，或系统其他进程抢显存 | 设并发上限，留 1~2G 余量 |
| 多卡启动卡住 |  TP 卡数不匹配、卡间通信异常、驱动版本不一致 | 先用 1 卡验证，再逐张加 |
| 启动很久没反应 | 模型下载/权重加载/图捕获慢，尤其首次启动 | 看日志阶段，别急着杀进程 |
| 报模型结构不支持 | 该模型版本还没被引擎支持 | 换官方支持的版本或换引擎 |
| 服务能起但请求全 500 | 模板/格式问题、鉴权配置错、模型名对不上 | 先看服务日志，再用最简请求验证 |

> OOM 排查的顺序固定：**先降 max-model-len → 再降并发 → 再降 gpu-memory-utilization → 最后才换量化**。因为前三个不改模型质量。

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 照抄网上的启动参数，机器上起不来 | 参数是按别人的卡和模型调的 | 按自己的显存账本重算三项：上下文、并发、显存比例 |
| 觉得"显存利用率设 1.0 能用满" | 预占到 100% 后系统和驱动没有余量 | 留 10%~20%，混合用途机器留更多 |
| 开了 prefix caching 却没变快 | 提示词前缀每次都不同，或结构把变量放最前 | 固定系统提示与背景资料在前，用户问题在后 |
| 单请求速度不如 Ollama 就否定 vLLM | vLLM 优势在多并发吞吐，不在单流极限 | 用目标并发压测再比较 |
| 并发拉满当"性能优化" | 队列变长，尾延迟恶化，用户体验更差 | 设上限并按 P95 延迟验收 |
| 用 OpenAI SDK 调通了就以为功能齐了 | tools、json、多模态等能力各家实现不同 | 按上层依赖清单逐项实测 |
| 多卡后速度没提升甚至变慢 | 卡间带宽不够，通信成了新瓶颈 | 评估互联，必要时回到单卡加大显存 |
| 升级引擎后性能变了 | 默认参数与调度策略随版本变化 | 锁版本 + 升级前后跑基线对比 |

## 自检问题参考答案

> [!success]- 1. PagedAttention 解决的是什么浪费？
> 它解决的是 KV Cache 的三块浪费：按最大长度预留、显存碎片、相同前缀各存一份。
> 做法是把 KV 切成固定大小的块，按需分配、不连续存放，相同前缀的块还能共享。
> 结果就是同样显存能装下更多请求和更长上下文，代价只是块表管理的小开销。

> [!success]- 2. gpu-memory-utilization 为什么是 OOM 第一嫌疑？
> 因为它不是"用多少占多少"，而是启动时按比例预占，再从里面切一大块当 KV 池。
> 好处是池子大小可预测、调度稳定；坏处是它不给系统、驱动和其他进程留后路。
> 常见取值 0.80~0.90，专用卡可以高一点，桌面环境或混合用途的机器要低一点。
> 所以 OOM 往往不是慢慢发生的，而是启动或压测阶段直接撞上预占上限。

> [!success]- 3. max-model-len 同时影响哪三件事？
> 单请求能塞多长（业务上限）、KV 池要为单条请求预留多少（显存）、以及引擎内部调度和 kernel 选择（性能）。
> 把它设成模型最大上下文，等于告诉引擎"可能有人要这么长"，显存就得按这个上限准备。
> 业务实际只要 8K 却设 128K，是最容易被忽略的显存浪费；设小了长文档会被拒或截断。

> [!success]- 4. 连续批处理提升的是吞吐还是延迟？
> 提升的是吞吐，不是单请求延迟。
> 静态批处理要等一桌菜全做完才接下一桌，短请求被长请求拖住，GPU 大量空转；连续批处理每生成一步就重排批次，算完的立刻退出、排队的立刻补位。
> 代价是单条请求延迟会随并发波动，所以对客户只能按"目标并发下的 P95"承诺，不能承诺固定首字时间。

> [!success]- 5. prefix caching 在什么提示词结构下收益最大？
> 同一段长系统提示、固定的 RAG 检索头、多轮对话前面几轮内容都一样，这类"长前缀、短变化"的结构收益最大。
> 反过来，把用户问题放最前面，或者前缀中间改一个字，缓存就命中不了，等于白开。
> 改法很直接：把不变的内容放最前，变化内容放最后。

> [!success]- 6. 多卡为什么不一定更快？
> 因为 TP 要每层切权重、卡间频繁通信，靠互联带宽换算力。
> 卡间带宽差的机器，通信可能成了新瓶颈，比单卡还慢。
> 判断依据：卡数能否整除注意力头数、卡型显存是否一致、有没有 NVLink 这类高速互联。
> 多数时候多卡的价值是"装得下大模型"，吞吐提升远小于卡数翻倍。

> [!success]- 7. OOM 排查为什么把"换量化"放最后？
> 因为前三步都不改模型质量：先降 max-model-len，再降并发，再降 gpu-memory-utilization。
> 这三步动的是显存账本和调度，不影响权重本身。
> 换量化是最后手段，因为它可能掉质量，还要确认引擎和模型版本兼容，代价最高。

> [!success]- 8. 给客户承诺延迟时要给什么数字？
> 给"条件下 + 分位"的数字：多少并发、多长上下文、什么模型、什么卡，以及 TTFT 和吞吐的 P95。
> 空载或单请求数字没有参考价值，因为连续批处理下延迟会随并发波动。
> 交付文档里必须写清这个前提，前提变了性能承诺就失效。

## 交付视角（对客户怎么讲）

- 客户问"为什么不能用 Ollama 那个"：Ollama 是给一个人用的，vLLM 是给一个团队用的，差别不在模型，在"同时来了十个人会怎样"。
- 讲显存时用"三块账"：权重、上下文缓存、运行余量。客户听得懂"这三块加起来超了"，听不懂术语。
- 报价里把"压测 + 参数固化 + 监控接入"单独列项，因为这三件事才是 vLLM 交付里真正花时间的部分。
- 交付文档必须写清前提：多少并发、多长上下文、什么模型、什么卡。前提变了，性能承诺就失效。
- 客户要"越快越好"时，先问是首字快还是整体快——这两个指标在 vLLM 里是要互相妥协的。
- 建议客户接监控，哪怕只看两个数：排队请求数和显存占用。出了问题这两个数能省半天排查。

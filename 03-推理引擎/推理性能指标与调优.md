# 推理性能指标与调优

> [!abstract] 一句话讲清楚
> 本地推理的调优不是"把参数都调大"，而是先分清你到底在优化首字延迟、出字速度还是并发吞吐——这三个目标互相打架，不先定目标，调什么都是白调。

## 为什么重要

- 客户说"太慢了"，你得先问清是"等首字久"、"出字卡"还是"人多就崩"，三种病的药完全不同。
- 大多数人调优的路径是错的：一上来加显卡、换引擎，其实可能是上下文设太大、并发参数默认太小。
- 知道指标怎么测，你才能在交付时给出**可验收的数字**，而不是"感觉快了"。
- 上游是 [[vLLM]]、[[Attention 与 KV Cache]]、[[参数量与显存估算]]，下游是 [[性能调优清单]]、[[排错方法论]]、[[部署检查清单]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 首字延迟 | TTFT | 从发请求到看见第一个字的时间 | 长上下文、冷启动时最明显 |
| 出字间隔 | TPOT / ITL | 第一个字之后，每个字的平均间隔 | 常被换算成"每秒多少字"来对客户讲 |
| 吞吐 | Throughput | 单位时间能处理多少 token 或多少请求 | 高吞吐不等于用户感受快 |
| QPS | 每秒请求数 | 每秒能完成多少个请求 | 要区分"接受"与"完成" |
| 并发 | Concurrency | 同时处理多少个请求 | 超过硬件能力后只会互相拖慢 |
| 尾延迟 | P95 / P99 | 最慢那 5% / 1% 请求的延迟 | 客户投诉往往来自尾延迟 |
| prefill | 预填充 | 把输入上下文一次性算完的阶段 | 计算密集，长上下文时是大头 |
| decode | 解码 | 一个字一个字往外吐的阶段 | 带宽密集，决定"出字快慢" |
| 计算密集 | compute-bound | 瓶颈在算力 | prefill 阶段通常是这样 |
| 带宽密集 | memory-bound | 瓶颈在搬运数据的速度 | decode 阶段通常是这样 |
| KV 缓存 | KV Cache | 存历史注意力的中间结果，避免重复计算 | 上下文越长占得越多，是显存大头 |
| 前缀缓存 | prefix caching | 复用公共前缀的 KV，跳过重复 prefill | 多轮、长系统提示收益大 |
| 批处理利用率 | Batch Utilization | 一次塞进 GPU 的请求是否够多 | 太小浪费算力，太大撑高尾延迟 |
| 冷启动 | Cold Start | 服务刚起、缓存空、模型刚加载 | 压测别把冷启动算进稳态 |
| 压测 | Benchmark / Load Test | 用模拟负载测出真实能力 | 必须用真实数据形态，不是随机字符串 |

## 原理与机制

### 两个阶段，两种瓶颈

**prefill 阶段**：把整段输入一次算完。矩阵乘很大，算力吃得满，属于**计算密集**。输入越长，这段越久，TTFT 越长。

**decode 阶段**：每次只生成一个 token，矩阵变成"矩阵 × 向量"，算力用不满，但要把权重全读一遍，属于**带宽密集**。所以出字速度基本由"模型大小 / 量化位宽 / 内存带宽"决定。

**后果**：

- 优化 TTFT 和优化 TPOT 是两件事。前者看上下文长度和 prefill 算力，后者看权重读取和带宽。
- 长上下文应用（RAG、代码库问答）首字慢是正常的，解决方向是前缀缓存、减少输入、或换更强的卡。
- 量化对 decode 的收益非常直接（每次读的字节少了），对质量有代价。

### 吞吐和延迟为什么打架

- 想让 GPU 别闲着，就要**一次多塞几个请求**（批处理），吞吐上去。
- 但请求多了，每个请求分到的时间片变少，单请求的尾延迟变差。
- 所以调优的本质是：**在可接受的尾延迟下，把批处理塞到最满**。
- 这就是为什么"跑单个请求很快"不能当服务能力吹——真实场景是并发的。

### 显存是所有指标的总闸门

- 显存 = 权重 + KV 缓存 + 临时开销。
- KV 缓存随上下文长度线性增长，随并发数线性增长。
- 显存不够时的表现不是"报错"，而是**OOM 崩掉**或**引擎保守降并发**，两种都会让你误判硬件。
- 所以调优第一步不是调参数，是算清楚"我还剩多少显存给 KV"。

## 完整流程：一次正经的性能评测

1. **定目标**：先写清楚验收指标——TTFT 目标、TPOT 目标、目标并发下的 P99 延迟、目标 QPS。
2. **固定条件**：模型、量化、上下文长度、输出长度、硬件、引擎版本全部写进文档。
3. **预热**：跑几轮把模型、缓存、编译都热起来，稳态数据才有意义。
4. **单请求基线**：测 1 个请求的 TTFT 与 TPOT，作为"理想情况"参考。
5. **固定并发爬坡**：1 / 2 / 4 / 8 / 16 并发逐级加压，记录 QPS、P99 延迟、显存占用。
6. **找拐点**：哪一级并发开始尾延迟陡增或吞吐不再上涨，那里就是这台机器的实际上限。
7. **用真实数据形态重测**：把压测输入换成业务真实提示（长短分布、共享前缀），结果往往差很多。
8. **记录并定档**：把推荐并发、推荐上下文、推荐量化档位写进交付文档。

**压测工具怎么选**：

- 引擎自带指标（如 vLLM 的 `/metrics`）能看排队、缓存命中、显存，优先用。
- 简单压测用并发脚本或现成压测工具即可，但**输入必须像真实业务**。
- 别直接引用网上别人的吞吐数字，模型、卡、长度、并发一个不同就没法比。

## 调优顺序：从便宜到贵

| 顺序 | 动作 | 预期收益 | 代价 / 风险 |
|---|---|---|---|
| 1 | 量化到 4bit / 8bit | decode 明显变快、显存大降 | 质量下降，需业务验证 |
| 2 | 收紧上下文长度 | KV 大降，并发能上去 | 长文场景不可行 |
| 3 | 调显存比例 / 并发参数 | 把闲置显存用起来 | 过大会 OOM 或抖动 |
| 4 | 开前缀缓存 | 多轮/RAG 场景 TTFT 大降 | 前缀不重复时没收益 |
| 5 | 调批处理上限 | 吞吐提升 | 尾延迟变差 |
| 6 | 多卡张量并行 | 能装更大模型 | 通信开销，不一定更快 |
| 7 | 换引擎（SGLang / TRT-LLM） | 特定场景再提一档 | 工程与维护成本 |
| 8 | 换硬件 | 全面提升 | 最贵 |

> 顺序原则：**先动零成本的配置，再动有质量代价的手段，最后动钱**。绝大多数"慢"的问题在第 2~4 步就解决了。

## 瓶颈定位表

| 现象 | 可能瓶颈 | 怎么验证 | 对策 |
|---|---|---|---|
| 首字很慢，后面出字正常 | prefill / 长上下文 | 缩短输入看 TTFT 是否明显下降 | 缩上下文、开前缀缓存、换更强卡 |
| 首字正常，出字很慢 | 带宽 / 模型太大 | 换更小或更低的量化版本对比 | 量化、换小模型、检查带宽 |
| 并发一上去就崩 | 显存不足 | 看显存占用与 OOM 日志 | 降并发、降上下文、降显存比例 |
| 吞吐上不去但延迟没恶化 | 批处理没塞满 | 看批大小与 GPU 利用率 | 提高并发上限、调批处理参数 |
| 延迟忽高忽低 | 资源争抢 / swap / 其他进程 | 看系统内存、其他 GPU 任务 | 隔离资源、别混跑 |
| 压测很高，真实业务很慢 | 输入分布不同 | 用真实提示重测 | 按真实形态重定档 |
| 大量请求排队超时 | 服务端并发上限太低 | 看排队指标 | 上调并发或加副本 |
| 长时间运行后变慢 | 缓存膨胀 / 内存泄漏 / 碎片 | 重启对比 | 加周期性重启或限上下文 |

## 指标换算与对客户表达

客户不爱听 TPOT，爱听"每秒几个字"和"等多久出第一句"。换算很简单：

- 每秒字数 ≈ 1000 / 单个 token 的毫秒间隔，但中文里 token 与字数的比例不固定，只能用于估算。
- "一句回答大概等多久" ≈ 首字延迟 + 输出长度 × 每 token 间隔。
- 报告里给出三个实测数：首字延迟、一句典型回答的总耗时、目标并发下还能保持这个体验的人数。

**常被忽略的区别**：技术指标里的 token 速度，和客户感知的"读完一段话"不是一回事。对客户永远用实测案例说明，别用理论值。

## 三种典型场景的基准怎么定

| 场景 | 主指标 | 定档方法 | 常见误区 |
|---|---|---|---|
| 个人聊天助手 | 首字延迟、出字是否顺畅 | 单请求测，用户能接受即可 | 拿并发吞吐当卖点 |
| 企业内部问答 | 目标并发下的 P99 | 按实际同时在用人数加压 | 用峰值人数定常驻资源 |
| 批量文档处理 | 总吞吐、任务总时长 | 固定并发跑批次算总耗时 | 用交互式指标衡量批处理 |

> 同一台机器，这三种场景的"合格线"完全不同。所以指标必须带场景，裸报一个 tokens/s 是没有意义的数字。

## 一页纸性能报告怎么写

交付时别甩一堆数字，给客户一页纸，按这个结构写，双方都省事：

- **硬件与软件清单**：卡型、显存、驱动、CUDA / ROCm、引擎版本、模型名与量化档位、上下文长度。
- **测试输入说明**：用的是什么提示词，长度分布如何，是否共享前缀——这一项不写清，数字就无法复现。
- **单请求基线**：首字延迟、出字速度，注明是热启动后的稳态值。
- **并发爬坡表**：并发 1/2/4/8… 对应的 QPS、P50、P99 延迟、显存占用。
- **推荐配置**：目标并发数、上下文上限、量化档位、显存比例，以及为什么选这个点。
- **已知边界**：超过多少并发会崩、多长的输入会变慢、什么情况下建议加卡。
- **复现命令**：启动命令与压测命令贴出来，让客户或后续维护者能自己重跑。

> 这份报告的价值不在数字好不好看，而在于"条件写清楚了"。以后客户说"变慢了"，你可以逐项对照，立刻知道是谁变了。

## 决策点

- **岔路口 1：先加卡还是先调参？** → 判断依据：是否已经把免费手段用完 → 推荐：先调参，有量化收益证据再加卡 → 代价：调参费时间，但省钱。
- **岔路口 2：为了吞吐牺牲多少尾延迟？** → 判断依据：业务是交互式还是批处理 → 推荐：交互式保尾延迟，批处理保吞吐 → 代价：不可能两头都最优。
- **岔路口 3：量化换性能，换多少？** → 判断依据：业务对错误率敏感度 → 推荐：先 8bit 稳，再试 4bit，用业务集验证 → 代价：4bit 在复杂推理/代码任务上可能明显掉点。
- **岔路口 4：要不要上多卡？** → 判断依据：单卡装不下才上，还是想更快 → 推荐：只有装不下才上；追求更快先调单卡 → 代价：多卡通信可能吞掉收益。
- **岔路口 5：指标怎么验收？** → 判断依据：合同是否需要量化承诺 → 推荐：用"目标并发下 P99 + 真实业务输入"来约定，不承诺单请求峰值 → 代价：需要更多测试工作量。

## 参数与配置说明（指标与参数速查）

| 项 | 作用 | 怎么调 / 怎么看 | 常见目标 |
|---|---|---|---|
| TTFT | 首字体验 | 降上下文、开前缀缓存 | 交互式场景尽量秒级以内（按硬件定） |
| TPOT | 出字体验 | 量化、小模型 | 交互式争取"读得舒服"的水平 |
| 吞吐 | 服务能力 | 提高并发、加大批处理 | 按成本模型定 |
| P99 延迟 | 稳定性 | 控并发、隔离资源 | 业务可接受的超时上限内 |
| 上下文长度 | KV 规模 | 收紧到业务真实需要 | 按业务真实值 |
| 最大并发 | 吞吐 vs 延迟 | 爬坡找拐点 | 取拐点前一级 |
| 显存比例 | 显存预占 | 0.8 左右起步，逐步试探 | 不 OOM 前提下尽量高 |
| 批处理上限 | 吞吐 | 与并发一起调 | 拐点处 |
| 量化位宽 | 速度/质量 | 8bit → 4bit 逐级验证 | 视任务而定 |
| 客户端超时 | 客户端等多久放弃 | 太短：长回答被误杀；太长：故障发现慢 | 按最坏情况 + 余量 |
| 服务副本数 | 横向扩展 | 加副本提吞吐，但每个副本都吃一份显存 | 单实例吃满再加 |
| 预热策略 | 首请求体验 | 不预热：第一个用户当小白鼠 | 启动后先跑一轮 |

> 参数的意义永远相对于目标：同一个"并发上限"，交互式场景该保守，批处理场景该激进。调参前先回到开头的三个目标，确认你优化的是哪一个。

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 拿单请求速度当服务能力 | 单请求根本没占满批处理 | 必须做并发压测 |
| 压测用随机短句，结论全错 | 输入分布和真实场景差太远 | 用真实提示词、真实长短分布 |
| 冷启动数据混进稳态 | 首轮加载模型、编译、缓存为空 | 先预热再采数据 |
| 只调大参数不测显存 | 以为配置越大越好 | 每改一次都记录显存与 OOM |
| 不同引擎比吞吐不看条件 | 模型、长度、并发、精度全不同 | 固定所有变量再比 |
| 把 GPU 利用率当瓶颈指标 | 带宽密集阶段利用率天然不高 | 看 decoding 阶段的 token 速度与带宽 |
| 忽略尾延迟 | 平均值好看，最慢请求体验差 | 看 P95/P99，不看平均 |
| 多卡一定更快 | 通信与切分开销可能超过收益 | 单卡先调满，再考虑多卡 |

## 自检问题参考答案

> [!success]- 1. TTFT 慢和 TPOT 慢分别从哪下手？
> TTFT 慢主要看 prefill 和排队：缩上下文、开前缀缓存、减少输入量，或者换更强的卡；先确认不是冷启动。
> TPOT 慢主要看 decode 的带宽：降量化位宽、换小模型、检查内存带宽有没有被别的进程抢。
> 两者的药完全不同，别混在一起调，否则改了也说不清是哪一项起的作用。

> [!success]- 2. 为什么 decode 是带宽瓶颈？
> 因为 decode 每步只生成一个 token，矩阵乘退化成"矩阵乘向量"，算力根本用不满。
> 但每生成一步都要把全部权重从显存里读一遍，所以卡住速度的是内存带宽，不是算力。
> 后果是出字快慢基本由模型大小、量化位宽、带宽决定；GPU 利用率在 decode 阶段天然不高，不能拿它当瓶颈指标。

> [!success]- 3. 吞吐和尾延迟为什么打架？怎么取舍？
> 想让 GPU 别闲着，就得一次多塞几个请求，吞吐才上得去；但请求一多，每个请求分到的时间片变少，单请求尤其尾延迟会变差。
> 取舍看业务：交互式场景保尾延迟、并发保守；批处理场景保吞吐、并发激进。
> 调优的本质就是"在可接受的尾延迟下，把批处理塞到最满"。

> [!success]- 4. 性能报告必须写清哪些固定条件？
> 模型名与量化档位、上下文长度与输出长度、硬件（卡型/显存/带宽）、引擎与驱动版本、并发级数、测试输入的真实形态，以及是否预热。
> 缺一项数字就不可复现，也就没法跟别人比、没法验收。
> 报告里还要贴复现命令，让客户以后能自己重跑。

> [!success]- 5. 显存不够，除了加卡还有哪三个免费动作？
> 一，收紧上下文长度，KV Cache 直接跟着降；二，调低并发和批处理上限，别把显存撑爆；三，调显存预占比例，从 0.8 左右往下试探。
> 这三个都不改模型质量、不花钱，应该先用完。
> 量化虽然也省显存，但有质量代价，不算"免费"。

> [!success]- 6. 怎么证明"慢"不是引擎的锅？
> 做单变量对照实验：同一模型、同一输入，先测单请求基线，再逐级加并发，记录 QPS 与 P99。
> 然后按瓶颈定位表排：首字慢就缩短输入看变化，出字慢就换低量化对比，并发一上去就崩就看显存和 OOM 日志，长跑变慢就重启对比。
> 条件固定、结果可复现，才能判断是引擎、模型、上下文还是硬件的问题。

> [!success]- 7. 验收指标怎么约定才不扯皮？
> 约定"目标并发下的 P99 + 真实业务输入形态 + 完整的模型/量化/上下文/硬件清单"，并把测试输入和复现命令写进报告。
> 不承诺单请求峰值，也不承诺"和云端一样快"，只承诺这个条件下实测到的数。
> 这样客户以后说"变慢了"，可以逐项对照，缺哪项都很清楚。

## 交付视角（对客户怎么讲）

- 先问清"你说的慢是哪种慢"，再谈优化，这一步能省掉一半返工。
- 给客户的验收指标要带条件：模型、量化、上下文长度、并发数、硬件型号，缺一个都可能扯皮。
- 优化路线图按"先免费后付费"报：先调参拿免费收益，再谈量化，最后才谈加卡。
- 交付文档里放一张"这台机器能扛多少并发、对应延迟多少"的爬坡曲线，比任何形容词都有说服力。
- 别承诺"和云端一样快"，讲清楚本地化的收益在数据不出门、可控、按需付费，不在速度。
- 客户如果只关心"能不能用"，把报告压缩成三个数：首字几秒、一句多久、几个人同时问，别用术语堆砌。

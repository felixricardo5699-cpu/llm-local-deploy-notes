# SGLang 与 TensorRT-LLM

> [!abstract] 一句话讲清楚
> 这两个引擎是"vLLM 还不够用"时才需要看的选项：SGLang 靠基数树前缀复用和结构化生成把多轮/RAG 场景的效率再压一档，TensorRT-LLM 靠提前把模型编译成引擎把极致性能榨出来——一个是"更聪明的调度"，一个是"更彻底的编译"。

## 为什么重要

- [[vLLM]] 能解决 80% 的生产场景。剩下 20% 是：**提示词前缀高度重复**、**需要严格结构化输出**、**模型和卡长期固定且要抠最后一点性能**。
- 不懂这两个引擎，你在这些场景里会以为"已经到极限了"，其实是没换工具。
- 反过来，**过早使用它们**也是常见错误：为了 5% 的性能提升付出几倍的部署和维护成本，交付性价比极低。
- 上游是 [[vLLM]] 与 [[Attention 与 KV Cache]]，下游是 [[Agent 与 Function Calling]]、[[性能调优清单]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| SGLang | — | 面向 LLM 服务的推理框架，前后端一体，强调前缀复用与结构化生成 | 不是"另一个 vLLM 克隆"，它的差异点在调度与编程接口 |
| RadixAttention | 基数树注意力 | 用一棵基数树管理所有请求的 KV 缓存前缀，自动发现并复用公共部分 | 和 vLLM 的 prefix caching 目标相同，实现与管理粒度不同 |
| 基数树 | Radix Tree | 按公共前缀组织字符串的树结构，相同前缀只存一份 | 树越深、共享越多的场景收益越大 |
| 结构化生成 | Structured Generation | 限定输出必须符合 JSON/正则/语法结构 | 不是提示词约束，是解码时直接限制可选 token |
| 前端 DSL | Frontend DSL | 用代码描述多步生成流程（如先思考再回答、并行采样） | 需要写代码，不是简单调 API |
| TensorRT-LLM | TRT-LLM | NVIDIA 官方的编译型推理方案，把模型编译成针对具体 GPU 的 engine | 编译产物与卡型强绑定，不是"拿来即跑" |
| engine | 引擎文件 | 编译后的推理程序与权重布局，运行时开销极低 | 换卡、换驱动版本可能就不能用 |
| in-flight batching | 在途批处理 | TRT-LLM 的连续批处理实现 | 概念和连续批处理一致，名字不同 |
| 编译成本 | — | 把模型转成 engine 的时间和工程投入 | 通常是小时级，且需要写配置、调并行策略 |
| 插件 | Plugin | TRT-LLM 对特殊算子/量化的扩展实现 | 版本匹配不对就编译失败 |
| 模型支持清单 | Support Matrix | 每个版本支持哪些模型结构与量化 | **选型前第一件事是查它**，别先安装 |
| 拆解式部署 | Disaggregated Serving | 把 prefill 和 decode 拆到不同实例 | 是两者都支持的能力，但对网络与运维要求高 |

## 原理与机制

### SGLang：把"重复的前缀"变成资产

**直觉版**：很多公司都在用同一份员工手册，每次问答都要把手册重读一遍。SGLang 的做法是——读过的部分留个书签，下次直接翻到那一页。

**拆解版**：

1. 所有请求的提示词前缀被组织成一棵基数树，公共前缀只保留一份 KV 缓存。
2. 新请求进来时，先在树里找最长匹配前缀，命中的部分直接跳过计算。
3. 不命中时才真正 prefill，算完把新节点挂到树上。
4. 调度器按树的引用情况决定淘汰哪些节点，把显存让给真正需要的请求。

**后果**：

- 多轮对话、Agent 反复调用同一套工具定义、RAG 用同一份长背景资料——这类场景的 prefill 成本几乎被消掉，TTFT 明显下降。
- 请求前缀差异大时，收益迅速归零，此时它和 vLLM 差别不大。
- 树的管理本身有开销，请求形态特别碎的时候可能不划算。

**另一条差异线是结构化生成**：解码时直接按语法/正则限制候选 token，输出天然合法 JSON。这比自己写重试逻辑靠谱得多，做 Agent 和工具调用的人会很有感觉。

### TensorRT-LLM：把"运行时决策"提前到编译期

**直觉版**：通用引擎像"现炒"，每次都要看菜单、备料、点火；TRT-LLM 像"预制菜工厂"，提前按你的锅、你的口味做好，上桌只负责加热。

**拆解版**：

1. 给定模型 + 目标 GPU + 精度 + 并行策略，编译出专门的 engine 文件。
2. 编译阶段就确定了算子融合、显存布局、kernel 选择、批处理形状。
3. 运行时几乎不做"运行时决策"，直接执行优化好的计划。
4. 需要变配置（更长上下文、更多卡、换精度）就要重新编译。

**后果**：

- 极致的延迟与吞吐，尤其在固定输入长度、固定并发形状的批处理场景。
- 灵活性差：模型、卡、驱动、上下文的组合一变，engine 可能要重做，交付周期变长。
- 运维成本高：客户环境升级驱动都可能让 engine 失效，必须有回退方案。

### 两者的共同点

- 都假设你有**明确的性能目标**和**稳定的部署环境**，不是"随便跑跑"的工具。
- 都需要 vLLM 级别的显存管理知识，才能配得对。
- 都不适合作为"第一次本地部署"的起点。

## 三引擎对比

| 维度 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 核心思路 | 通用高吞吐服务框架 | 前缀复用 + 结构化生成 | 编译期极致优化 |
| 上手成本 | 中 | 中 | 高 |
| 生态与资料 | 最丰富 | 中等 | 官方文档为主 |
| 多轮/长系统提示收益 | 有（prefix caching） | 更明显（基数树） | 有（in-flight batching + 复用） |
| 结构化输出 | 支持程度看版本 | 强项 | 支持，配置更繁琐 |
| 模型支持广度 | 广 | 较广 | 以主流模型为主 |
| 部署灵活性 | 高 | 高 | 低（绑定卡/驱动） |
| 换模型成本 | 低 | 低 | 高（重编译） |
| 典型场景 | 通用 API 服务 | RAG/Agent/多轮 | 固定模型的高性能服务 |
| 什么时候选 | 默认选择 | 前缀重复高的场景 | 极致性能且环境固定 |
| 部署复杂度 | 低 | 中 | 高 |
| 长期维护成本 | 低 | 中 | 高 |

## 什么时候值得上

**值得上 SGLang 的信号**：

- 系统提示几万 token，所有请求共用，每次都要 prefill 一遍。
- Agent 每轮都要带上一整套工具定义，请求之间高度相似。
- 需要强约束的 JSON 输出，不想靠提示词祈祷。
- vLLM 的 prefix caching 已经开了，但命中率始终上不去。

**值得上 TensorRT-LLM 的信号**：

- 模型长期固定，卡型固定，环境由你控制。
- vLLM 压到极限仍不满足指标，且指标直接关系到业务成本或合同。
- 有工程人力做编译、调优、版本管理，且能接受每次升级重新验证。
- 输入输出长度分布稳定，批处理形状可以专门优化。

**不值得上的信号（很常见）**：

- 只是"想试试更快的"，没有量化目标。
- 模型一周换一次，卡也不固定。
- 单机演示、少人使用——用 [[Ollama]] 或 [[llama.cpp 与 GGUF]] 就够，性能不是瓶颈。
- 团队里没人维护过编译型方案，出问题容易卡死交付。

## 部署形态：单机、多卡还是拆开

| 形态 | 适合什么 | 成本 | 坑 |
|---|---|---|---|
| 单机单卡 | 大多数团队 | 最低 | 显存和并发就是硬上限 |
| 单机多卡（TP） | 单卡装不下，或需要更高吞吐 | 通信与显存切分 | 卡间带宽差时收益打折 |
| 多机多卡 | 大模型、高并发生产 | 最高 | 网络、调度、故障处理都更复杂 |
| prefill/decode 拆解 | 长输入 + 短输出的极端形态 | 高 | 两套服务、多一跳网络 |
| 多副本 + 负载均衡 | 单实例扛不住多人 | 中 | 显存要成倍算，别只算单实例 |

**选择原则**：能单机就单机；单机装不下先量化降精度；还装不下才多卡；只有确实测出 prefill 拖住了全局，才考虑拆解。

> 一个经验：绝大多数"需要上 SGLang/TRT-LLM"的判断，其实先做完"提示词结构对齐 + vLLM 调参"再下结论，会少走很多弯路。

## 关键配置片段

SGLang 启动时的关键参数（意思是：启用前缀缓存、限制上下文、限制并发、绑定模型路径）：

```bash
python -m sglang.launch_server --model-path ./model \
  --context-length 8192 --mem-fraction-static 0.85 \
  --max-running-requests 16
```

> 三个数字对应三件事：业务上下文上限、显存预占比例、并发上限。`mem-fraction-static` 的作用类似 vLLM 的 gpu-memory-utilization，同样是 OOM 的第一嫌疑。

TensorRT-LLM 的关键动作不是"启动参数"，而是"编译时参数"（意思是：为目标卡和精度编译 engine，之后运行时几乎无调度开销）：

```bash
trtllm-build --checkpoint_dir ./ckpt --output_dir ./engine \
  --gemm_plugin auto --max_batch_size 16 --max_input_len 4096
```

> 注意这里的 `max_batch_size`/`max_input_len` 是**写进 engine 的硬约束**，改超了要么重编译要么报错——这就是"编译成本"的具体体现。

## 决策点

- **岔路口 1：先上哪个？** → 判断依据：是否有明确的前缀重复或性能缺口 → 推荐：先把 vLLM 调到位，再针对性上 SGLang → 代价：跳步会导致你在不熟悉的栈上排错。
- **岔路口 2：SGLang 还是优化提示词结构？** → 判断依据：能不能通过重排提示词让前缀自然对齐 → 推荐：先改提示词结构，零成本、立刻见效，再考虑换引擎 → 代价：结构改造受业务限制。
- **岔路口 3：要不要上 TensorRT-LLM？** → 判断依据：性能缺口是否影响合同/成本，环境能否锁定 → 推荐：有量化收益且环境可控才上 → 代价：编译与版本管理是长期负担。
- **岔路口 4：prefill/decode 拆开部署？** → 判断依据：长提示 + 短输出的业务形态 → 推荐：只有确实出现"prefill 拖死全局"时才考虑 → 代价：多一套服务、多一层网络与运维复杂度。
- **岔路口 5：客户现场用什么？** → 推荐：交付优先 vLLM（生态成熟、资料多、好交接）→ 代价：放弃最后几个百分点的性能，换来可维护性。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| context-length / max-input-len | 上下文上限 | 调大：长文可用，显存与编译约束变大；调小：省资源但截断 | 按业务真实长度 |
| mem-fraction-static / gpu-memory 比例 | 显存预占 | 调大：并发高，OOM 风险高；调小：安全但浪费 | 0.80 ~ 0.90 |
| max-running-requests / max-batch-size | 并发上限 | 调大：吞吐高、尾延迟差；调小：排队 | 8 ~ 32 |
| 张量并行（TP） | 多卡切分 | 调大：能装大模型；通信开销上升 | 1/2/4/8 |
| 精度（FP8/BF16 等） | 计算与权重精度 | 降精度：省显存、快；质量与兼容性要验证 | 按卡能力 |
| 前缀缓存相关开关 | 复用公共前缀 | 打开：重复前缀场景收益大；关闭：省管理开销 | 场景相关 |
| 结构化输出约束 | JSON/正则/语法限制 | 约束越严：越可控但生成越慢 | 按接口契约 |
| 编译并行策略 | TRT-LLM 编译期配置 | 调大：更贴合多卡；配置错则编译失败 | 与卡型匹配 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 看别人用 SGLang 很快，自己上了没变化 | 你的请求前缀本身就不重复，基数树没东西可复用 | 先统计前缀重复率，再决定是否值得 |
| TRT-LLM 编译出来的 engine 换个环境跑不了 | engine 与卡型、驱动、CUDA 版本绑定 | 把编译环境写进交付文档，或改用通用引擎 |
| 编译一小时，跑起来报错 | 模型结构/量化/并行配置与编译参数不匹配 | 用官方支持矩阵里的组合，别自由发挥 |
| 结构化输出开了，速度明显变慢 | 每个 token 都要做约束检查，候选 token 被大幅限制 | 只在确实需要严格格式的接口上开 |
| 以为"更高级的引擎一定更快" | 性能取决于场景匹配度，不是引擎档次 | 用自己的真实负载压测后再下结论 |
| 多卡部署后通信成瓶颈 | 卡间带宽不足，TP 开销吃掉收益 | 评估 NVLink/PCIe 条件，必要时单卡 |
| 版本没锁，升级后 engine 全失效 | 编译型方案对版本极敏感 | 锁死引擎/驱动/CUDA 版本组合，留回滚镜像 |
| 拿 vLLM 的调参经验直接套 | 显存管理机制与参数语义不同 | 参数逐个查文档、小步验证 |

## 交付视角（对客户怎么讲）

- 客户问"是不是用最好的引擎效果最好"：不是，是"最匹配的"。90% 的项目 vLLM 就够了，剩下 10% 要看数据。
- 讲 SGLang 的价值时说人话：你们每次提问都要把同一份长文档重读一遍，这个引擎能记住读过的部分，所以首字更快。
- 讲 TensorRT-LLM 的价值时要配一个明确的收益数字（压测得来），否则别推荐——它带来的是长期维护成本。
- 报价里把编译、版本锁定、回滚方案单独列出来，这是 TRT-LLM 项目最容易低估的部分。
- 如果客户模型还没定、卡还没买，先别聊这两个引擎，回去先把 vLLM 跑通再回来。

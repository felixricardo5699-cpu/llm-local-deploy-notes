# 高频咨询问题与话术

> [!abstract] 一句话讲清楚
> 客户/AI 咨询时反复出现的十几个问题，每个都给"一句话回答 + 技术依据 + 千万别说什么"。目标不是把客户说服，是**让客户觉得你靠谱、边界清楚**。

## 为什么重要

- **技术过关但话说不清，单子照样丢**：客户判断不了你的水平，只能听你怎么答。
- **一句过度承诺能毁掉整个项目**：说了"绝对安全""什么都能做"，后面所有意外都变成你的责任。
- **话术不是忽悠，是翻译**：把技术事实翻译成客户能听懂、能决策的语言。

这篇不教你包装，教你**在真实约束下把话说准**。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 咨询 | Inquiry | 客户带着模糊需求来问，还没到报价阶段 | 咨询阶段的目标是"判断能不能做"，不是成交 |
| 话术 | Script | 提前准备好的回答框架 | 不是背台词，是背"结构和边界" |
| 技术依据 | Technical Basis | 你回答背后的原理和数据 | 没有依据的回答，客户一追问就露馅 |
| 能力边界 | Scope Limit | 明确说清"能做什么、做不到什么" | 越早说清，后面越省事 |
| 私有化部署 | On-premise | 模型跑在客户自己的机器/内网里 | 不等于"绝对安全"，还要看日志和网络 |
| 幻觉 | Hallucination | 模型一本正经地编造不存在的内容 | 它不知道自己不知道，所以必须靠检索和评估兜 |
| 并发 | Concurrency | 同时处理请求的能力 | 客户问"能支持多少人"时，别直接换算出人数 |
| POC | Proof of Concept | 先做一个小规模验证，再决定是否采购 | 收费/免费都要提前约定范围 |
| TCO | Total Cost of Ownership | 总拥有成本：硬件 + 电 + 维护 + 你的服务费 | 客户常只看硬件，忽略后面几项 |
| 验收标准 | Acceptance Criteria | 双方约定的"做完"的定义 | 口头约定 = 没有约定 |

## 原理与机制

### 一次靠谱的咨询回答，结构是固定的

```mermaid
flowchart LR
  A["① 一句话结论<br/>能不能做"] --> B["② 技术依据<br/>为什么"]
  B --> C["③ 边界与代价<br/>什么情况下不行"]
  C --> D["④ 下一步动作<br/>需要客户提供什么"]
```

这四段少一段都会出问题：

- 少①，客户觉得你在绕；
- 少②，客户觉得你在吹；
- 少③，后面全是扯皮；
- 少④，谈话结束就没有下一步。

**核心原则：先给能不能，再给为什么，最后给条件。** 永远不要把"能不能"和"多少钱"混在一句话里说。

### 三类问题，三种答法

| 类型 | 客户真正在问 | 回答策略 |
|---|---|---|
| 能力类（"能不能跑""能支持多少人"） | 我的需求现实吗 | 先给结论 + 给判断依据 + 给降级方案 |
| 信任类（"会不会泄密""会不会胡说"） | 我能不能承担风险 | 讲清架构和边界，不承诺"绝对" |
| 商务类（"多少钱""多久"） | 值不值、稳不稳 | 先讲交付物和范围，再谈数字 |

## 高频问题库

### Q1 我的电脑能跑本地大模型吗？

- **一句话回答**：能，但要先看显卡显存——显存决定能跑多大、什么速度，不是看 CPU 或内存条大小。
- **技术依据**：模型权重要放进显存，显存不够就得降量化或换小模型；8G 显存和 24G 显存能跑的档位差好几级。Mac 另算，看统一内存。
- **千万别说什么**："能跑"就完了。一定要加一句"能跑到什么程度"——否则客户拿 8G 机器装完发现很慢，会认为你骗他。

### Q2 我这 8G 显存能跑 70B 吗？

- **一句话回答**：技术上能勉强塞进去（靠低量化和内存交换），但速度会慢到没法日常用，我不建议。
- **技术依据**：参数量越大，权重占用越高；低到极致的量化会明显掉质量，还要把部分权重放到内存里，生成速度断崖式下降。
- **千万别说什么**："能跑"然后收钱。客户要的是好用，不是"能启动"。正确做法是给替代方案：小一号的模型 + 更好的提示词/检索。

### Q3 做一套要多少钱？

- **一句话回答**：价格取决于三件事——硬件谁出、要不要接业务系统、要不要长期维护；范围不同差好几倍。
- **技术依据**：成本结构是"硬件 + 部署实施 + 应用集成 + 运维"。只做部署和做完整交付是两个量级的活。
- **千万别说什么**：直接报一个"两万块全包"。范围没定就报价，后面每加一个需求都是吵架。

### Q4 数据会不会泄密？安全吗？

- **一句话回答**：模型和对话都跑在你们自己的机器上，不往外发；但"安全"要靠网络隔离、鉴权和日志一起做，不是装个模型就安全。
- **技术依据**：本地部署去掉了"把数据传出去"这一环，但仍有内部人员访问、日志留存、端口暴露三类风险，需要配套控制。
- **千万别说什么**："绝对安全""100% 不会泄露"。这种话一出，以后任何一起内部误操作都算你的。

### Q5 跟 ChatGPT / 在线大模型比，差多少？

- **一句话回答**：顶级闭源模型在通用知识、复杂推理上更强；本地模型赢在私有数据、可控、离线、长期成本，两者不是替代关系。
- **技术依据**：模型规模、训练数据、算力都不同，所以通用能力有差距；但接上你们自己的文档和流程后，在具体业务上可以做得更准。
- **千万别说什么**："一模一样""比它还强"。客户一用就知道，信任直接归零。

### Q6 既然有免费的在线 AI，为什么要花钱做本地？

- **一句话回答**：免费的是"通用助手"，你们要的是"能处理内部资料、数据不出门、能接进自己系统"的东西。
- **技术依据**：在线服务的输入会离开内网，且不能深度接入客户业务数据；本地部署的价值在于数据可控 + 可定制 + 可集成。
- **千万别说什么**："免费的不好"。客户只是在做成本权衡，你要给的是"什么场景下本地更划算"。

### Q7 能不能训练一个我们公司专属的模型？

- **一句话回答**：可以，但先判断该不该——大部分"专属"需求其实靠知识库（RAG）就能解决，真需要微调的只有少数场景。
- **技术依据**：RAG 解决"知道公司的事"，微调改变"说话方式和任务格式"；前者便宜快、后者要数据和算力。
- **千万别说什么**："当然可以，我们有全套微调"。先问场景，否则做完发现不解决问题，还是你背锅。

### Q8 多久能交付？

- **一句话回答**：先分三段——摸底和试跑、正式部署、验收和培训；每段都有可见产出，具体天数要看机器和网络条件。
- **技术依据**：真正不可控的是客户环境（驱动、网络、权限），技术本身反而快；所以先做摸底再承诺时间。
- **千万别说什么**："两小时搞定"。环境问题一出现，这句话就是你信誉的终点。

### Q9 模型升级了怎么办？以后是不是要重新买？

- **一句话回答**：升级模型主要是换文件，服务架构不用变；但要重新做一次效果验证，这块工作量要提前算。
- **技术依据**：推理服务和模型文件是解耦的，换模型是"换权重 + 调参数"；但新模型的格式、上下文、显存需求可能变。
- **千万别说什么**："以后都不用管了"。任何升级都要验证和重新调参，这是长期服务，不是一次性买卖。

### Q10 能接我们现有的系统/微信/钉钉吗？

- **一句话回答**：只要是能发 HTTP 请求的系统，基本都能接；不能直接接的，我们做一个中间层。
- **技术依据**：本地服务对外暴露的是标准 API，绝大多数业务系统都能调用；难点在对方的权限和网络策略。
- **千万别说什么**："什么都能接"。有些老系统没有接口、有些平台不允许外部机器人，得先确认。

### Q11 为什么这么贵？能不能便宜点？

- **一句话回答**：贵在"出事有人管"——部署只是其中一部分，验收、文档、压测、后续调整才是大头。
- **技术依据**：一次性动手 vs 可持续运行的差别就在服务化、文档、维护上；砍价通常砍的就是这部分，风险也一起转移给客户。
- **千万别说什么**："那给你打个折吧"（没有交换条件的让价）。可以让范围，不能让责任。

### Q12 它答得不准 / 胡说八道怎么办？

- **一句话回答**：这是模型的固有特性，靠"给它资料 + 让它说不知道 + 定期评估"来压；我们交付时会把这套跑通。
- **技术依据**：模型是概率生成，不知道时也会编；RAG 能让答案有出处，提示词和评估能降低编造率，但不可能归零。
- **千万别说什么**："不会出错""准确率 100%"。任何模型都做不到，说这话等于给自己埋雷。

### Q13 我需要买什么硬件？要不要换服务器？

- **一句话回答**：先看要跑多大模型和多少人用，再倒推显存；很多情况现有机器够用，不够时我会给"够用"和"好用"两档配置。
- **技术依据**：显存决定模型档位，带宽决定生成速度，内存和磁盘决定稳定性；按需求倒推比按预算买东西靠谱。
- **千万别说什么**：直接推最贵的配置。客户会怀疑你在吃回扣；给两档配置和理由才专业。

### Q14 能支持多少人同时用？

- **一句话回答**：这个要看压测数据——不是按在线人数算，是按同时发起请求的数量算；我可以给你一个"多少人同时提问不出问题"的数字。
- **技术依据**：并发能力取决于显存、引擎并发参数和模型大小；单人用和十人同时用完全是两套配置。
- **千万别说什么**："随便多少人用"。这是最容易在交付第一周被打脸的一句。

### Q15 出了问题谁负责？能远程维护吗？

- **一句话回答**：交付内容里的故障我们负责，客户自己改配置/换硬件导致的不在范围内；远程维护需要你们开放一条通道。
- **技术依据**：责任边界要在合同里写明；远程维护依赖网络可达性和权限，客户内网需要专门开通道。
- **千万别说什么**："随叫随到"。没有 SLO 和范围的口头承诺，最后一定变成免费劳动力。

### Q16 能不能商用？版权归谁？

- **一句话回答**：取决于模型的许可证，开源模型不一定能随便商用；交付前我们会把许可证和商用条款核对清楚。
- **技术依据**：不同模型许可证差异很大，有的限制商用、有的有额外条款；以官方 LICENSE 和商用条款为准。
- **千万别说什么**："开源的随便用"。这是法律风险，不是技术问题，别替客户拍板。

## 决策点

- **岔路口 1：客户需求明显不现实（比如 8G 跑 70B 要好用）。**
  判断依据：技术硬约束。推荐：**当场给"能到什么程度" + 替代方案**，别为了成单硬接。代价：可能丢单，但避免交付灾难。
- **岔路口 2：客户预算砍半。**
  判断依据：砍的是价格还是范围。推荐：**降范围不降标准**——少做集成、少做培训，但验收和文档不砍。代价：项目变小，但可持续。
- **岔路口 3：客户拿在线服务价格压你。**
  判断依据：客户在意的是成本还是数据。推荐：**把比较维度从"每月多少钱"换成"数据在哪、能不能定制"**。代价：对价格极度敏感的客户确实留不住。
- **岔路口 4：客户要求承诺效果（比如准确率 90%）。**
  判断依据：能不能先做 POC 测。推荐：**先小样本试，用数据说话再谈承诺**。代价：多花一点前期时间，但避免后期扯皮。
- **岔路口 5：客户内部有人懂技术，问得很细。**
  判断依据：对方是真懂还是试探。推荐：**直接讲技术细节，承认不确定的地方**。代价：短时间显得不"神"，长期信任度更高。

## 关键参数（话术配置）

| 维度 | 说明 | 建议 | 常见错误 |
|---|---|---|---|
| 回答长度 | 一次说多少 | 先一句结论，客户追问再展开 | 一口气讲十分钟架构 |
| 承诺强度 | 敢说多满 | 只说能做到的，用"通常/大概" | "绝对""100%""随便" |
| 数字口径 | 报不报具体数字 | 给量级和条件，不编精确值 | 报"准确率 95%"却拿不出评估 |
| 边界说明 | 主动说限制吗 | 主动说，越早越好 | 等交付时才说"这个不支持" |
| 报价顺序 | 先说钱还是先说范围 | 先范围、再交付物、最后价格 | 一上来报价，客户只记住数字 |
| 下一步 | 每次沟通要落地什么 | 每次给一个具体动作 | 聊完说"再联系" |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 成单后客户满意度低 | 咨询阶段过度承诺 | 每次都主动说边界，宁可少说 |
| 客户反复问同样的问题 | 你上次回答太技术、没结论 | 第一句永远给"能不能" |
| 报价后客户消失 | 只报了数字，没说值在哪 | 报价前先讲范围、交付物、验收标准 |
| 被同行低价抢单 | 你在卖"装软件"，别人在卖"交付" | 强调验收、文档、压测、维护这些看不见的工作 |
| 客户拿"网上教程免费"说事 | 免费教程不含排错和责任 | 说清"教程教你跑通，我们负责它在你这儿稳定跑" |
| 一句话得罪人 | "你这配置太差了""这需求没意义" | 换成"这个配置跑 X 会比较吃力，建议 Y" |
| 售后变免费客服 | 没约定支持范围 | 合同里写清支持内容、响应时间、超出怎么算 |

## 交付视角（对客户怎么讲）

- 咨询的目标不是"说服"，是"判断 + 建立信任"。你说清做不到什么，客户反而更敢把项目给你。
- 每次沟通结束留一个**具体下一步**（发个配置单、约个实地看机器、给个 POC 范围），别停在"再联系"。
- 把技术词翻译成客户熟悉的说法：显存 → "能装多大的模型"；并发 → "几个人同时问不会卡"；RAG → "让它先查你们的资料再回答"。

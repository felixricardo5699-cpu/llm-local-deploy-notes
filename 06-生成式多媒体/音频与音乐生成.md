# 音频与音乐生成

> [!abstract] 一句话讲清楚
> "音频生成"不是一个模型，而是一族任务：**TTS 念稿、声音克隆、歌声转换、音乐生成、音效生成**——它们的技术路线、显存需求、许可证边界完全不同，混为一谈就会做错方案。

## 为什么重要

- **视频交付里音频是"最后一公里"。** 画面再好，配音机器味、口型不对、音乐侵权，项目照样不过。
- **客户需求很具体**："用我的声音做数字人口播""给这条 30 秒视频配个燃一点的音乐""把这个人的歌换成我唱"。每句话对应不同模型。
- **声音比图像更敏感。** 肖像权之外还有声音权，商用克隆必须拿到书面授权，否则风险远超技术风险。
- **门槛极低但质量分水岭很陡。** TTS 十几秒就能出结果，但"像真人"和"能交付"之间往往差着几轮调参。

## 核心名词全解

| 名词 | 人话解释 | 影响什么 |
|---|---|---|
| TTS（文本转语音） | 把文字念出来 | 口播、旁白、有声书 |
| 声音克隆 | 用几秒到几分钟音频模仿某个音色 | 数字人、个人 IP |
| 零样本克隆 | 不用训练，给参考音频直接模仿 | 上手最快，稳定性一般 |
| 少样本微调 | 用少量数据训练一个专属音色 | 更像，但要准备数据与训练时间 |
| 参考音频 | 用来"提示音色"的样本 | 质量直接决定像不像 |
| 韵律 / 语气 | 语速、停顿、轻重、情绪 | 决定"像人"还是"像播报" |
| 多音字 | 同一个字不同读法 | 中文 TTS 的头号坑 |
| SVC（歌声转换） | 把一段歌换成另一个音色唱 | 翻唱、虚拟歌手 |
| 音乐生成 | 用文字或旋律生成音乐 | 配乐、BGM、氛围音 |
| 音效生成 | 生成单个环境音/拟音 | 短视频、游戏 |
| 口型同步 | 让人物嘴型对上音频 | 数字人交付的刚需 |
| 采样率 | 每秒采样点数，决定频响 | 不匹配会变调、失真 |
| 响度标准化 | 统一音量到行业标准 | 避免忽大忽小、削波 |
| 声码器 | 把声学特征还原成波形 | 音质的关键一环 |

## 原理与机制

### 直觉版

TTS 像一个"极强的播音员"：它先理解这句话怎么断句、哪里重读，再把这些信息变成声音。声音克隆是给这个播音员一段你的录音，说"用这个嗓子念"——他听几秒就能模仿个七八成。音乐生成更像"哼一段给你听"：你描述风格和情绪，它从随机噪声里"长"出一段有结构的音乐。

### 拆解版：三条不同的技术路线

| 路线 | 做什么 | 代表（系列级） | 关键点 |
|---|---|---|---|
| 级联式 TTS | 文本→音素→声学特征→声码器→波形 | 传统引擎 | 可控、稳定、音质一般 |
| 端到端大模型 TTS | 文本 + 参考音频 → 直接出波形 | CosyVoice 类、Fish Speech 类、ChatTTS 类 | 自然度高、有随机性、要调 |
| 微调式克隆 | 在预训练模型上少量训练专属音色 | GPT-SoVITS 类 | 最像，但要数据与算力 |
| 音乐生成 | 文本/旋律 → 音频潜表示 → 波形 | MusicGen 类、ACE-Step 类、YuE 类 | 结构感与风格跟随是难点 |
| 歌声转换 | 原唱音频 → 换音色 | RVC 类 | 保留唱法，只换音色 |

为什么同样叫"音频生成"，显存要求差很多：

- **TTS 模型通常很小**，消费级显卡甚至 CPU 都能跑，显存不是瓶颈，速度与质量才是。
- **音乐生成模型更大**，因为要建模长时间结构，显存和时长直接相关；生成长曲一般靠分段再拼接。
- **微调式克隆要训练**，显存需求看训练脚本，通常比推理高一个档位。
- **口型同步、音频超分、降噪**这些配套模型体积不大，但常常是交付质量的关键。

### 后果：音频项目真正的瓶颈不是模型

- **参考音频质量 > 模型选择。** 一段有底噪、有混响、有背景音乐的样本，再好的克隆模型也救不回来。
- **文本规范化 > 参数调优。** 数字、单位、专有名词、多音字要先处理成正确的读法，否则听起来处处别扭。
- **分段合成 + 拼接 > 一次性长文本。** 长文本一次合成容易崩、难对齐，分段更可控。
- **后期混音 > 生成。** 响度、去齿音、加一点环境音，才是"能交付"的差别。

## 分类与对比

### 系列速查（系列级）

| 系列 | 类型 | 特点 | 显存感受 | 适合 |
|---|---|---|---|---|
| GPT-SoVITS 类 | 少样本克隆 TTS | 社区生态强，可训专属音色 | 很低 | 数字人、个人 IP 配音 |
| CosyVoice 类 | 零样本 TTS | 上手快，支持指令式语气控制 | 低 | 快速原型、多音色试听 |
| Fish Speech 类 | 零样本 TTS | 多语言，克隆效果不错 | 低 | 多语种口播 |
| ChatTTS 类 | 对话式 TTS | 口语感强、有停顿与语气词 | 低 | 聊天机器人、播客风 |
| RVC 类 | 歌声转换 | 保留唱法换音色，社区模型多 | 中 | 翻唱、虚拟歌手 |
| MusicGen 类 | 音乐生成 | 文本/旋律条件，结构中等 | 中 | BGM、氛围音乐 |
| ACE-Step 类 | 音乐生成 | 结构较完整，支持多种风格 | 中高 | 成段配乐 |
| YuE 类 | 歌曲生成 | 人声+伴奏一体，中文歌 | 高 | 原创歌曲 demo |
| 商用 API 类 | 云服务 | 效果稳、上限高 | 零 | 商用成片、质量兜底 |

### 四类任务对比

| 任务 | 输入 | 输出 | 可控性 | 主要风险 |
|---|---|---|---|---|
| TTS 念稿 | 文本 + 音色 | 语音 | 高 | 多音字、语气机械 |
| 声音克隆 | 文本 + 参考音频 | 语音 | 中 | 像不像、声音权 |
| 歌声转换 | 歌曲 + 目标音色 | 歌曲 | 中 | 走音、齿音、版权 |
| 音乐生成 | 文本描述/旋律 | 音乐 | 低到中 | 结构散、侵权风险 |

## 完整流程：三条典型交付链路

### 链路一：数字人口播

1. 写稿并做**文本规范化**：数字读法、单位、英文缩写、多音字标注。
2. 选音色：客户提供授权样本（30 秒~几分钟干净人声）→ 零样本试听 → 不够像再走微调。
3. 分段合成：按句子或短段落生成，逐段试听。
4. 拼接与对齐：调整段间停顿，整体语速统一。
5. 口型同步：把音频喂给口型模型，驱动人物视频；注意口型模型也吃显存。
6. 混音：降噪、去齿音、统一响度、加背景音乐。
7. 验收：客户试听 + 抽帧看口型。

### 链路二：视频配乐

1. 定情绪与节奏点（哪里起、哪里落、哪里卡点）。
2. 用音乐生成模型出 2~3 个候选，时长略长于目标。
3. 剪辑对齐：卡点、淡入淡出、段落拼接。
4. 与原声/旁白混音：音乐必须让位于人声。
5. 版权确认：用生成模型也要确认许可证与训练数据条款。

### 链路三：翻唱/虚拟歌手

1. 拿到授权与原始干声（或做音色分离）。
2. 用 SVC 模型换音色，保留唱法与节奏。
3. 修音：走音、齿音、气息。
4. 混音回原伴奏，检查是否违和。

> [!tip] 一条铁律
> **先有音频，再有画面。** 口播、数字人、MV 类项目都是音频定节奏，画面去对齐音频；反过来做会陷入无限重剪。

## 决策点

- **岔路口 1：TTS 就够，还是要克隆**
  条件：只要"好听的声音"、不要求特定人 → 直接用现成高质量音色；
  条件：客户要求"用我的声音" → 克隆（先零样本，不够像再微调）。
  推荐：**先用零样本试听**，让客户听过再决定要不要花时间做微调。

- **岔路口 2：零样本还是微调**
  条件：几十秒样本、快速上线 → 零样本；
  条件：长期使用、必须高度还原 → 微调，准备好 5~30 分钟干净音频与训练时间。
  代价：微调要环境、要数据清洗，交付周期至少多一天。

- **岔路口 3：本地还是 API**
  条件：声音敏感（客户自己的声音）、量大、长期 → 本地；
  条件：一次性、要求极高、不想折腾 → API。
  提醒：声音数据出境的风险比文本更高，能本地尽量本地。

- **岔路口 4：口型同步用什么方案**
  条件：正脸、口播为主 → 音频驱动口型模型；
  条件：侧脸、遮挡、大动作 → 效果普遍差，建议改分镜或人工后期。

- **岔路口 5：音乐用生成还是买版权库**
  推荐：**商用成片优先版权库**，生成音乐作为草稿与备用；生成音乐的版权状态在很多平台仍不明确，客户拿去投广告会有风险。

- **岔路口 6：歌声要不要碰**
  条件：版权清晰、有授权 → 可以；
  条件：客户想"翻唱某首歌发出去" → 先谈版权，技术不是问题。
  推荐：把授权确认做成流程里的强制关卡。

## 参数与配置说明

| 参数 | 典型范围 | 调法 |
|---|---|---|
| 语速 | 常规偏慢 | 口播宁慢勿快，后期可加速 |
| 随机性/温度 | 低到中 | 高随机更像人，但可能读错字 |
| 参考音频时长 | 几秒到几分钟 | 质量 > 时长，10~30 秒干净片段就够试 |
| 分段长度 | 一句话到一段 | 长句易崩，按标点切 |
| 采样率 | 常见 16k / 22k / 44.1k | 全链路统一，别混 |
| 响度 | 按平台标准统一 | 混音最后一步做 |
| 音乐时长 | 分段生成再拼 | 单次太长结构会散 |
| 生成步数 | 视模型 | 音乐生成步数对时间影响大 |

## 硬件与显存：音频其实不挑卡

和图像/视频比，音频生成的硬件压力小得多，但也别踩坑：

- **TTS 推理**：几 G 显存就够，甚至 CPU 可跑；小显存机器做配音完全可行。
- **克隆微调**：要训练，显存需求高一档；老卡训练慢，能租算力就租。
- **音乐/歌曲生成**：模型更大，时长与显存相关；24G 卡较舒服，小卡靠分段。
- **口型同步**：吃显存的是驱动视频那一侧，不是音频模型。
- **真正的瓶颈常常是 CPU 与 I/O**：长音频解码、批量转码、ffmpeg 处理，往往比推理更耗时。

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 克隆"完全不像" | 参考音频有底噪/混响/背景音乐，或时长太短 | 换干净干声，10~30 秒，同一语气 |
| 中文多音字总读错 | 文本没做规范化 | 用拼音/标注工具先处理，或换写法绕开 |
| 长文本合到一半崩了 | 一次生成太长，显存/上下文不够 | 分段合成，按句拼接 |
| 音频变调、声音发尖 | 采样率不匹配（生成 22k 当 44.1k 用） | 全链路统一采样率，转码时确认 |
| 爆音、削波、忽大忽小 | 没做响度归一化 | 统一响度、限幅器兜底 |
| 装好却跑不起来、报依赖冲突 | 音频栈依赖多（ffmpeg、声码器、推理框架），版本互相顶 | 用独立虚拟环境，按项目锁版本 |
| 模型放错目录，节点里看不见 | TTS 模型目录结构与图像模型不同，很多插件要求放插件自己的 models 下 | 看插件文档的目录约定，别套用图像模型的习惯 |
| 数字人成品嘴型对不上 | 音频有停顿、语速过快，或口型模型版本与驱动方式不匹配 | 放慢语速、加短停顿，按官方示例接线 |
| 客户声音被滥用风险 | 没做授权与用途约定 | 书面授权 + 交付说明，写明使用范围 |

## 交付视角（对客户怎么讲）

- **把"声音克隆"拆成授权 + 技术两件事讲。** 先要授权书，再谈效果；客户会觉得你专业，而不是"怎么这么麻烦"。
- **让客户听样本再定方案。** 零样本先出 3 条不同音色的试听，比讲一堆参数有用，也能避免做完才说"不像"。
- **明确"像"的预期。** 没微调的音色通常"七八成像"，一说客户就懂；承诺"一模一样"是给自己挖坑。
- **报价分三层**：基础 TTS（现成音色）、克隆（含样本处理）、微调（含训练与调优）。层次清楚，客户才知道加钱加在哪。
- **交付时给音频工程文件**：分段音频、拼接时间线、参数说明、授权文件。客户后续改稿不用全部重做。
- **版权提醒写进合同**：生成音乐的商用风险、翻唱的授权要求，提前写清，是保护双方。

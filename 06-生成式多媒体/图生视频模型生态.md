# 图生视频模型生态

> [!abstract] 一句话讲清楚
> 视频生成不是"图片生成加一个时间维"那么简单，它的显存由**分辨率 × 帧数**共同决定，而时长 = 帧数 ÷ 帧率；理解这个三角关系，比记住任何模型名都重要。

## 为什么重要

- **客户最想要视频，也最容易在这里翻车。** 一张图能出得漂亮，不代表能生成一条稳定、不闪烁、不崩坏的 5 秒视频。
- **显存是硬墙。** 图片模型 8G 能跑，视频模型 8G 往往只够玩具级分辨率与极短时长；报价前必须先算清楚能跑什么。
- **一次失败的视频比十张失败的图更贵。** 单条视频生成通常是分钟级甚至更久，重试成本极高，所以"首帧选图"和"参数固定"变得格外重要。
- **首尾帧与参考图控制是商用场景的核心。** 客户要的是"这条广告片按我的分镜走"，不是"随机抽一段好看的运动"。

## 核心名词全解

| 名词 | 人话解释 | 影响什么 |
|---|---|---|
| 文生视频（T2V） | 只给文字，生成视频 | 可控性最低，抽卡属性最强 |
| 图生视频（I2V） | 给一张图，让它动起来 | 主流交付方式，构图稳定 |
| 首帧 | 视频的起始画面 | I2V 的输入，决定全片基调 |
| 尾帧 | 视频的结束画面 | 首尾帧模式可锁定运动终点 |
| 关键帧 | 指定几个时间点的画面 | 高级控制，可做分镜衔接 |
| 参考图 | 提供身份/风格参考的图片 | 保持人物一致性的关键 |
| 帧率（fps） | 每秒多少张图 | 时长换算的分母 |
| 帧数 | 一条视频总共多少张 | 显存与耗时的直接变量 |
| 运动幅度（motion） | 画面动得多剧烈 | 太低像 PPT，太高会崩 |
| 运动质量 | 运动是否自然、物理是否合理 | 视频模型的真正分水岭 |
| 时序一致性 | 前后帧同一物体不跳变 | 闪烁、变形的根源 |
| 插帧 | 用算法补出中间帧 | 提升流畅度，不增生成成本 |
| 潜空间帧 | 压缩后进入模型的帧数 | 与显存直接相关 |
| 分段生成 | 把长视频切成多段 | 突破时长上限的通用做法 |

## 原理与机制

### 直觉版

图生视频模型像一个"看过大量视频的动画师"。你给他一张定妆照，他从这张图开始往后"脑补"下一秒、下下秒的画面。它的难点不在于"画得像"，而在于**每一帧之间要连得上**：光影要稳、物体不能闪、运动要符合物理。

### 拆解版：显存是怎么被吃掉的

- 图像模型处理的是"一个画面"的 token 集合；视频模型处理的是"一段时间内的画面"的 token 集合。
- 若分辨率翻倍，每帧 token 数大约变成四倍；若帧数翻倍，token 数再翻一倍。**两者相乘，就是显存爆炸的公式。**
- 所以想跑更长的视频，等比例降分辨率往往比硬扛分辨率更划算；反之想要清晰，就得砍时长。
- 中间还有 VAE 的时序处理、注意力计算、文本条件的中间激活，都是"帧数越多涨得越快"的部分。

### 后果：三角关系表

时长 = 帧数 ÷ 帧率。下表是量级参考（具体因模型而异，务必实测）：

| 分辨率档位 | 帧数 | 时长 @ 16fps | 显存感受 |
|---|---|---|---|
| 低（约 480p） | 49 左右 | 约 3 秒 | 8G 可尝试，速度慢 |
| 中（约 512~768） | 81 左右 | 约 5 秒 | 12~16G，需量化 |
| 中高（约 720p） | 81~121 | 5~8 秒 | 24G 起，分块可能闪烁 |
| 高（720p 以上） | 121~241 | 8~16 秒 | 单卡吃力，走分段 |
| 极高（1080p 以上） | — | — | 分段生成 + 超分，不做单次 |

一条铁律：**同一条视频，帧数减半比分辨率减半更省、也更不容易崩。** 先保证时长与运动稳定，再用插帧和超分补画质。

## 分类与对比

### 系列速查（系列级）

| 系列 | 类型 | 特点 | 显存感受 | 适合 |
|---|---|---|---|---|
| AnimateDiff 类 | 图加适配器 | 生态老、可控、插件多 | 很低到中 | 二次元短片、循环动画 |
| SVD 类 | I2V 元老 | 单图生成，稳但短 | 中 | 快速让图动起来 |
| LTX 类 | 轻量视频模型 | 速度相对快，显存友好 | 中 | 小显存试水 |
| CogVideo 类 | 开源 T2V/I2V | 时间长，质量中等 | 高 | 研究、Demo |
| HunyuanVideo 类 | 开源强模型 | 运动质量好，显存高 | 很高 | 24G 以上做品质片 |
| Wan 类 | 开源系列 | 覆盖 T2V/I2V、首尾帧能力 | 高 | 主流开源交付 |
| MiniMax 类（API） | 闭源云服务 | 效果好、上手快 | 零 | 质量兜底、无法本地时 |
| 商用闭源类（API） | 闭源云服务 | 运动与人像最自然 | 零 | 高要求成片 |

### 开源与 API 的取舍

| 维度 | 本地开源 | 云 API |
|---|---|---|
| 数据安全 | 全在内网 | 内容出境/出网 |
| 单条成本 | 显卡电费 + 时间 | 按条计费，价格透明 |
| 可控性 | 参数全开、可接控制网 | 只给有限接口 |
| 质量上限 | 受显存限制 | 通常更高 |
| 批量成本 | 边际成本低 | 量大后很贵 |

## 完整流程：从一张图到一条成片

1. **定分镜**：先确定每个镜头的时长与运动方式（推、拉、摇头、人物转身），别让模型自由发挥。
2. **出首帧**：用图像模型出高质量首帧，分辨率对齐视频模型能接受的范围。
3. **首帧试跑**：短帧数、低分辨率先跑一版，确认运动方向对、不崩。
4. **参数定版**：确定步数、CFG、motion 强度、种子，写进工作流。
5. **长视频拆分**：超过模型单次时长的部分，按镜头或按秒切段，每段用上一段的末帧当下一段首帧。
6. **插帧与超分**：生成的是"关键帧级"的流畅度，插帧补中间帧，超分补清晰度。
7. **拼音频**：配音、配乐、音效，对齐时长；口播类内容要先有音频再定视频节奏。
8. **质检**：逐段看有没有闪烁、变形、穿模、文字糊、色彩跳变。

> [!warning] 分段接缝是最容易翻车的地方
> 相邻两段如果首帧不是上一段的真实末帧，会出现"跳一下"。正确做法是把上一段导出的最后一帧当下一段的首帧，并把两段的提示词、种子、运动参数保持一致。

### 四种控制方式的对比

| 控制方式 | 你需要准备 | 可控程度 | 适用场景 | 成本 |
|---|---|---|---|---|
| 纯首帧 | 一张图 | 低，运动方向靠猜 | 氛围片、快速试稿 | 最低 |
| 首尾帧 | 两张图（起、止） | 中高，起点终点锁定 | 分镜明确的产品/人物镜头 | 中 |
| 关键帧序列 | 多张关键帧图 | 高，能指定中间状态 | 复杂运镜、转场 | 高 |
| 参考图 + 首帧 | 身份/风格参考 + 首帧 | 中，一致性优先 | 固定人物、固定产品 | 中高 |

一个实用建议：**先用纯首帧低成本试运动方向，方向对了再加尾帧锁死。** 反过来先做尾帧往往白做。

## 运动设计：让视频"看起来对"

视频崩坏通常不是画质问题，而是运动不合理。写提示词与选图时注意：

- **运动要"小"而"准"。** "人物缓缓转头"比"人物奔跑跳跃"成功率高一个量级。
- **给运动一个物理理由。** 风吹、车流、翻页、镜头推近，比"整体动起来"更容易被模型理解。
- **镜头运动用行业词。** 推、拉、摇、移、升降、环绕，这些词在训练语料里出现得多，模型更容易照做。
- **主体运动与镜头运动别同时堆。** 又要人跑、又要镜头环绕，崩的概率极高。
- **首帧要"留有运动空间"**：人物贴边、构图太满的图，动起来容易出画或穿模。
- **不要指望模型改画面内容。** I2V 是"让这张图动"，不是"按这张图重画一遍"；要改内容回去改首帧。

## 决策点

- **岔路口 1：8G 显存能不能做视频**
  推荐：**能做，但要降级**——低分辨率、约 3 秒、不开超分、不追求 720p。定位是"动起来看看效果"，不要承诺成片质量。
  更好的选择是 AnimateDiff 类轻量方案，小显存友好。

- **岔路口 2：12~16G**
  推荐：**LTX 类轻量模型或量化后的开源视频模型**，5 秒 512~768 档位，配分块 VAE 与分段。可用于内部试稿与短视频初稿。

- **岔路口 3：24G 及以上**
  推荐：**Wan 类 / HunyuanVideo 类等强模型**，720p 档位 5~8 秒，能出可交付素材；仍建议分段+插帧+超分链路。

- **岔路口 4：只用首帧，还是给首尾帧**
  条件：运动方向无所谓、要稳定 → 首帧即可；
  条件：必须落到特定构图/特定结尾 → 首尾帧模式。
  推荐：商用分镜一律用首尾帧，可控性提升明显，代价是多准备一张尾帧图。

- **岔路口 5：开源还是 API**
  条件：素材敏感、要批量、长期项目 → 本地开源；
  条件：要求最高、量小、赶时间 → API 兜底。
  推荐：**本地为主、API 补位**，报价时把 API 成本按条算进方案。

- **岔路口 6：帧率怎么选**
  推荐：生成端用 16fps 左右，后期插帧到 24/30fps；直接生成高帧率既慢又容易崩，性价比低。

- **岔路口 7：参考图要不要上**
  条件：有固定人物/产品 → 必须上参考图或先用图像模型锁死形象，否则一致性无解。

## 参数与配置说明

| 参数 | 典型范围 | 调法 |
|---|---|---|
| 分辨率 | 480p / 512~768 / 720p | 先低后高，定版再提 |
| 帧数 | 49 / 81 / 121 一类档位，常为 4n+1 或 8 的倍数 | 按模型要求取整，乱填会报维度错 |
| 帧率 | 生成端 16 左右 | 后期插帧提升观感 |
| 步数 | 常规 20~30；加速版更少 | 视频步数对耗时影响巨大，先砍步数 |
| CFG | 常规中低区间，视模型 | 过高会崩，过低会飘 |
| motion / 运动强度 | 中低起步 | 大幅运动最先崩 |
| 种子 | 固定 | 对比时只改一个变量 |
| 分块 VAE | 开/关 | 大分辨率必开，但可能导致帧间闪烁 |

## 显存不够时的降级顺序

瞎降参数只会白折腾，按这个顺序砍最不伤质量：

1. 先降**帧数**（保分辨率与运动质量）。
2. 再降**步数**（20 步降到 12 步以内，配加速方案）。
3. 然后开**分块 VAE**（注意闪烁）。
4. 再降**分辨率**（最后才动，画质损失最直观）。
5. 换**更轻的模型**（LTX 类等），放弃部分运动质量。
6. 换 **API** 兜底。

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 加载节点找不到视频模型 | 模型放错目录（应放 `diffusion_models` 或 `checkpoints`，视模型而定） | 查模型卡说明，按类型放，刷新节点 |
| 一跑就报维度/形状不匹配 | 帧数不满足模型的取整要求；分辨率不是 8/16 的倍数 | 按模型文档取帧数与尺寸 |
| 输出全黑或只有首帧 | 缺编码器/VAE，或条件图没接上 | 按官方模板核对接线，检查条件输入 |
| 视频闪烁、物体跳变 | 分块 VAE、分段接缝、运动过大 | 关分块对照、用真实末帧接续、降 motion |
| 自定义节点冲突导致导入失败 | 插件版本不匹配、依赖缺失、几个包抢同一模块 | 用干净环境，按工作流声明的版本装，隔离项目 |
| 显存够但内存爆了 | 视频解码/分块把系统内存吃满 | 加内存、降分辨率、减少并行任务 |
| 生成时长算出 5 秒，实际只有 3 秒 | 帧数 ÷ 帧率算错，或模型内部裁掉了首尾帧 | 生成后用播放器核对真实帧数与时长 |
| 换模型后同一工作流出废片 | 新旧模型参数含义不同（CFG/步数/帧数档位） | 换模型必须重跑最小验证，不要直接改文件名 |

## 交付视角（对客户怎么讲）

- **先讲"能做什么规格"，再谈效果。** 例如"本地方案支持 720p / 5 秒 / 首尾帧控制，单条生成约几分钟"，把预期钉死，别让客户想象成电影级。
- **分镜稿比提示词更重要。** 视频项目的沟通成本几乎全在分镜上，交付前先让客户确认逐镜头的运动描述。
- **说明不可控项。** 手指、文字、剧烈运动、多人物互动是当前视频模型的共同弱项，写进交付说明。
- **把链路拆开报价。** 首帧出图、视频生成、插帧超分、音频、剪辑是五件事，分开列价，客户才知道钱花在哪，也方便按需砍。
- **交付时给素材包而不只是成片。** 首帧图、分段视频、参数说明、工作流 JSON 一起给，客户后续自己微调不依赖你，这反而是专业度的体现。

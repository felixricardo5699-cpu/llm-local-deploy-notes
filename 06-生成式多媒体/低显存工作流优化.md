# 低显存工作流优化

> [!abstract] 一句话讲清楚
> 低显存优化的本质只有三招：**把权重变轻（量化）、把工作集拆小（分块/分段）、把不用的东西先挪走（卸载）**——剩下的都是这三招的组合与取舍。

## 为什么重要

- **客户绝大多数不是 4090。** "8G 显存能跑什么工作流"几乎是最常见的销售问题，答不上来就丢单。
- **显存决定"能做什么"，而不是"做得多快"。** 爆显存是硬失败，慢只是体验问题。
- **优化有画质与时间成本。** 乱开分块、乱用卸载，会得到"能跑但没法交付"的结果。
- **交付现场往往比实验室更紧。** 客户机器上还有浏览器、微信、WSL、其他服务在吃显存。

## 核心名词全解

| 名词 | 人话解释 | 影响什么 |
|---|---|---|
| 显存（VRAM） | 显卡上的专用内存 | 决定模型能不能装下 |
| 权重 | 模型参数占的空间 | 参数量 × 精度字节 |
| fp16 / bf16 | 半精度，主流推理精度 | 显存减半，几乎无损 |
| fp8 | 8 位精度，新卡支持更好 | 再减半，画质略降 |
| GGUF 量化 | 把权重压到 4~8 位的通用格式 | 省最多，速度可能更慢 |
| 分块（tiling） | 把大图切成小块逐块处理 | 省显存，可能有接缝 |
| 分块 VAE | VAE 解码时也分块 | 大图/高清必开 |
| 模型卸载 | 不用时把模型挪回内存 | 省显存，速度变慢 |
| 顺序卸载 | 按管道顺序加载/卸载 | 极省显存，最慢 |
| 注意力后端 | 优化注意力计算的实现 | 影响显存峰值与速度 |
| 分辨率 | 出图宽高 | 显存随面积增长 |
| 帧数 | 视频长度 | 显存随帧数线性增长 |
| 显存碎片 | 反复分配释放留下的空洞 | 明明够却 OOM |
| 共享显存 | Windows 把内存当显存用 | 看似够，实际慢到不可用 |

## 原理与机制

### 直觉版

想象一间小仓库（显存）要放一整套流水线设备（模型权重）和正在加工的零件（中间结果）。显存不够有三条路：**设备换小一号**（量化）、**一次只加工一小块**（分块/分段）、**用完的设备先搬出去**（卸载）。三条路可以同时用，但每条都有代价。

### 拆解版：显存都花在哪

- **权重**：最大头。参数越多、精度越高越吃。同样一个模型，fp8 大约是 fp16 的一半，4 位量化再减。
- **激活与中间结果**：分辨率越大、帧数越多、batch 越大，越大。**分辨率是平方增长**，宽高各翻倍，中间结果约四倍。
- **注意力峰值**：长序列/高分辨率时，注意力矩阵是显存尖峰的主要来源，优化后端能明显削峰。
- **上下文与碎片**：CUDA 上下文、缓存、反复分配释放留下的空洞；这也是"显存显示没满却 OOM"的原因之一。
- **视频的额外开销**：帧数线性叠加时间维，latent 体积按帧数增长；解码阶段还有一次性的大峰值。

### 为什么三招的代价不同

| 招数 | 省什么 | 代价 | 什么时候用 |
|---|---|---|---|
| 量化 | 权重空间 | 画质略降、格式兼容性 | 模型装不下时首选 |
| 分块 | 激活峰值 | 接缝、速度慢 | 大图、放大、解码 |
| 卸载 | 权重占用 | 极慢（频繁搬数据） | 实在装不下时兜底 |
| 降分辨率 | 全部 | 画质直接下降 | 视频、批量场景 |
| 降帧数 | 时间维 | 片段变短 | 视频首选 |
| 换轻模型 | 全部 | 上限下降 | 有"能用就行"的选项时 |

### 后果

- **先看瓶颈在哪：是"装不下"还是"算到一半爆"。** 装不下 → 量化/换模型；算到一半爆 → 分块/降分辨率/降帧数。
- **优化顺序错了会白折腾。** 8G 上跑 Flux 系 fp8，先降分辨率再谈分块，往往比反过来有效。
- **"能跑"不等于"能交付"。** 分块 VAE 的接缝、量化后的细节损失，验收时一眼看得出来。

## 8G / 12G 能跑什么

| 任务 | 8G | 12G | 说明 |
|---|---|---|---|
| SD1.5 系出图 | 很舒服 | 很舒服 | 老底模最省 |
| SDXL 系出图 | 可以（配合优化） | 舒服 | 1024 附近分辨率 |
| Flux 系（fp8/量化） | 勉强，需降分辨率 | 可以 | 12G 更稳 |
| Qwen-Image 类 | 吃力 | 勉强 | 建议量化版 |
| ControlNet 单控制 | 可以 | 可以 | 别多叠 |
| LoRA 叠加 | 可以 | 可以 | 开销小 |
| 高清放大（分块） | 可以 | 可以 | 必开分块 VAE |
| 图生视频（短片段） | 480p 级别短片段 | 480p~720p 短片段 | 帧数宁少勿多 |
| 比 AnimateDiff 更轻的视频方案 | 可以 | 舒服 | 老方案兼容性好 |
| 较重的视频模型（Wan/HunyuanVideo 类） | 基本不行 | 勉强（量化 + 低分辨率） | 建议租卡 |
| 音频 TTS | 轻松 | 轻松 | 甚至 CPU 可跑 |
| 音乐生成 | 可以 | 可以 | 时长别太长 |
| LoRA 训练 | 困难 | 小规模可以 | 建议租算力 |

> [!warning] 一句实话
> 很多"8G 能跑"的视频工作流，本质上靠的是**降分辨率 + 极短片段 + 量化**，成品只能当 demo。谈单时要提前说清上限。

## 低显存工作流设计原则

这十条是踩过坑之后总结的，按顺序用：

1. **先测基线，别拍脑袋。** 拿最小可跑配置跑一遍，记录"分辨率/帧数/步数/显存峰值"，再逐项加压找临界点。
2. **分清"装不下"还是"算不动"。** 装不下先量化；算到一半爆先分块、降分辨率。
3. **权重精度优先于降分辨率。** 同样省一半显存，fp8 通常比分辨率腰斩更保画质。
4. **视频先砍帧数，图像先砍步数。** 帧数减半显存直接减半，观感损失比分辨率小。
5. **能分段就分段。** 长视频拆成短片段，每段保存中间结果，最后拼接；这比一次生成稳得多。
6. **分块只在必要时开。** 分块 VAE 有接缝风险，先试整块跑不跑得动。
7. **卸载是最后的兜底。** 开了顺序卸载速度可能掉到几分之一，能加内存/换模型就先别开。
8. **一次只做一件事。** batch 固定为 1；多任务用队列串行，别并发跑两个工作流。
9. **中间结果落盘。** 每段视频、每张中间图都存下来，爆显存时不用从头再来。
10. **留出余量。** 显存占用稳定在 **80%~85%** 以内比较安全，贴着 100% 跑迟早爆。

## 完整流程：把一条工作流塞进小显存

1. **确认任务与目标**：分辨率、时长、质量要求、是否商用。
2. **选模型档位**：优先选有 fp8/量化版、社区支持好的系列。
3. **最小配置跑通**：最低分辨率 + 最少步数 + 单控制，确认链路没坏。
4. **逐步加压**：先加分辨率到目标，再加步数，再加控制与 LoRA。
5. **定位临界点**：记下每次显存峰值，找到"刚好不爆"的配置。
6. **加优化手段**：按"量化 → 降分辨率/帧数 → 分块 → 卸载"的顺序补。
7. **验证画质**：放大看细节、看接缝、看闪烁；不合格就回退一档。
8. **固化成模板**：把参数写进工作流 JSON，做成预设，交付时附参数说明。

## 优化手段对比

| 手段 | 大概能省 | 代价 | 推荐指数 |
|---|---|---|---|
| fp16→fp8 | 权重约减半 | 画质略降、部分卡不支持 | 高 |
| 4~8 位量化（GGUF 类） | 权重再降 | 兼容性与速度不稳 | 中高 |
| 降分辨率 1024→768 | 激活约减半 | 画质下降 | 高 |
| 帧数减半 | 视频显存约减半 | 片段变短 | 高 |
| 分块 VAE | 解码峰值大降 | 接缝 | 高（大图必开） |
| 顺序卸载 | 权重几乎不占卡 | 慢到几倍 | 低（兜底） |
| 换注意力后端 | 削峰 10%~30% | 版本兼容麻烦 | 中 |
| batch 降为 1 | 线性减少 | 吞吐下降 | 必做 |
| 换更轻模型 | 可能省一半以上 | 能力上限降 | 看需求 |

## 三个反直觉的点

- **显存峰值往往出现在解码或放大，而不是采样。** 采样跑得很欢，最后一步爆了，最常见。
- **降分辨率不一定提速。** 有的模型在小尺寸下反而效率低，得实测。
- **加内存条有时比换卡有用。** 卸载/共享显存能救急，虽然慢，但能让 8G 机器"跑起来"。

## 参数与配置说明

| 参数 | 小显存建议 | 说明 |
|---|---|---|
| 出图分辨率 | 768~1024 起步 | 别超目标，后期再放大 |
| 步数 | 20~25，配加速可更低 | 步数对显存影响小于分辨率 |
| batch size | 1 | 批量靠多跑几次 |
| 视频分辨率 | 480p 起步 | 720p 是 8G 的天花板 |
| 视频帧数 | 短片段优先 | 拼接优于长生成 |
| 分块尺寸 | 中等，别太小 | 太小接缝更多、速度更慢 |
| 卸载开关 | 默认关 | 不够再开 |
| 显存余量 | 留 15% | 防止碎片导致 OOM |

## 显存估算速算卡

不推公式，只记住几个量级：

| 项目 | 粗略体积 | 备注 |
|---|---|---|
| 权重 | 参数量 × 精度字节 | fp16 每 10 亿参数约 2GB，fp8 约 1GB，4 位再减半 |
| 图像 latent | 分辨率 ÷ 8 后的面积 × 通道数 | 面积翻倍约四倍 |
| 视频 latent | 图像 latent × 帧数 | 帧数翻倍约两倍 |
| 注意力峰值 | 随 token 数平方增长 | 高分辨率时最容易爆 |
| 解码峰值 | 与像素面积成正比 | 大图必开分块 |

一个实用的口算法：**先算权重够不够装，再按上一张成功图的分辨率试两倍面积。** 视频则按"每帧花多少显存"估，比按总时长估准。

## 不同场景的推荐配置

| 场景 | 卡 | 配置思路 |
|---|---|---|
| 电商产品图 | 8G | SDXL 系 1024、单控制网、分块放大 |
| 封面海报批量 | 8G | SD1.5 系 768、低步数、LoRA 统一风格 |
| 数字人短视频 | 8G | 480p 短片段、末帧续接、分段保存 |
| 商用成片 | 12G 以上 | 720p、fp16、少开卸载 |
| 原型验证 | 8G | 量化模型 + 降分辨率，先跑通再谈质量 |
| 训练 | 12G 以下不建议 | 租算力比自己慢慢跑划算 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 任务管理器显示显存没满，却报 OOM | 显存碎片、共享显存被算进来、其他程序占用 | 重启进程、关浏览器、降分辨率留余量 |
| 开着 WSL 或虚拟机，显存莫名少一截 | WSL 自己也吃显存，Windows 还会预留 | 关掉不用的环境，或直接在 Linux 下跑 |
| 开了 fp8 更快但画面糊 | 旧卡对低精度支持差，或模型本身不适合 | 回 fp16，或用官方 fp8 版本 |
| GGUF 量化版加载不了 | 节点/插件不支持该格式，或放错目录 | 装对应加载节点，按插件目录约定放 |
| 放大后出现网格状接缝 | 分块 VAE 分块尺寸太小、重叠不够 | 加大分块与重叠，或整块解码 |
| 开了卸载速度慢十倍 | 每步都在内存与显存之间搬模型 | 只在不爆的前提下开，或降分辨率 |
| 换注意力后端后报错/闪退 | 版本不匹配、与插件冲突 | 回默认后端，锁版本 |
| 两个工作流同时跑都爆 | 并发争抢显存 | 用队列串行，跑完再跑下一个 |
| 视频生成到解码阶段才爆 | 解码峰值远高于采样峰值 | 单独开分块 VAE，先存潜变量 |

## 交付视角（对客户怎么讲）

- **把"8G 能跑什么"说成一张表**，别只说"能跑"。客户要的是"我的活能不能干"，表里按任务列清楚，立刻建立信任。
- **明确上限，别承诺 demo 级效果。** 低显存视频就是"短片段、低分辨率、拼接"，提前说清楚，验收不扯皮。
- **给出升级路径**：现在 8G 能做什么，换 12G/24G 或租卡后能做什么，报价跟着算，客户会自己算账。
- **报价里体现"优化能力"**：低显存适配是一项实打实的技术服务，别当赠品送。
- **交付时附"配置卡"**：分辨率、帧数、步数、显存峰值、优化开关，客户换机器时直接照抄。

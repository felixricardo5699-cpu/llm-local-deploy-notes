# 部署检查清单

> [!abstract] 一句话讲清楚
> 一张能真打勾的出厂检验单：每次交付前从头过一遍，**每一条都写清楚"不通过会怎样"**，做完截图或打印签字，就是你的验收凭证。

## 怎么用这张清单

- 顺序不能跳：**前面的项不过，后面的项没有意义**（比如 GPU 没认到，压测就是浪费时间）。
- 标 🔴 的是**红线项**：不过就不能交付，别抱侥幸心理。
- 每一项都写"怎么验"和"不通过会怎样"，验收时按这个说法向客户解释。
- 全部过完，把这份清单和模型清单、压测结论一起归档——这就是你的交付证据。

## 核心名词全解（8 个就够看懂这张清单）

| 名词 | 英文/缩写 | 大白话解释 | 容易混淆/注意 |
|---|---|---|---|
| 红线项 | Red Line Item | 不过就不能交付的硬条件 | 其余项可带条件上线，红线不能让 |
| 冒烟测试 | Smoke Test | 只验"最基本功能通不通"的快速测试 | 通过不等于性能没问题 |
| 压测 | Load Test | 用模拟并发量探出服务上限 | 压测结论要写进确认单 |
| 常驻服务 | Daemon | 后台运行、开机自启、崩溃自恢复 | 前台窗口跑着不算 |
| 健康检查 | Health Check | 能区分"进程活着"和"能推理" | 只探端口会误报正常 |
| 鉴权 | Authentication | 谁能用、用哪个 Key、能不能吊销 | 只设一个密码发给所有人等于没有 |
| 交付物 | Deliverable | 服务 + 清单 + 使用说明 + 压测结论 | 少一样，后期就多一堆咨询 |
| 回滚 | Rollback | 出问题能退回上一个可用版本 | 没备份就没有回滚 |

## A. 交付前摸底（合同/报价前就该做）

- [ ] 🔴 **拿到硬件配置**：核型号、显存、内存、磁盘、系统。｜怎么验：让客户截图或用远程工具看。｜不通过会怎样：报了能做，现场发现跑不动，返工或退款。
- [ ] 🔴 **确认有没有外网**：能否下载、能否远程协助。｜怎么验：让客户访问一个外部地址试。｜不通过会怎样：模型搬不进去，工期翻倍。
- [ ] **确认使用者规模与场景**：几个人用、同时用还是轮流、问什么类型的问题。｜怎么验：让客户给个真实样例问题。｜不通过会怎样：选错模型档位，交付后天天被说"不够聪明"或"太慢"。
- [ ] **确认数据敏感等级与合规要求**：能否上传、能否记录日志、模型能否出内网。｜怎么验：书面确认。｜不通过会怎样：踩合规红线，项目被叫停。
- [ ] **确认交付边界**：交付什么、不交付什么、后续谁维护。｜怎么验：写进合同或确认单。｜不通过会怎样：客户无限追加"顺手帮我做个 XX"，尾款难收。

## B. 硬件与系统

- [ ] 🔴 **GPU 被系统识别**：能看到型号和显存。｜怎么验：跑显卡工具（如 `nvidia-smi`）。｜不通过会怎样：后面所有"显存不足/跑不起来"都从这里来。
- [ ] 🔴 **显存有余量**：模型权重的占用之外，还要给上下文和并发留空间。｜怎么验：加载后看显存占用曲线。｜不通过会怎样：聊几句就 OOM 或疯狂变慢。
- [ ] **内存充足**：系统不因内存不足杀进程。｜怎么验：加载模型后看剩余内存和交换分区。｜不通过会怎样：服务随机被系统杀掉，且日志里看不到明显原因。
- [ ] **磁盘空间足够**：模型放得下，且留出余量给日志和临时文件。｜怎么验：看剩余空间，建议是模型体积的两倍以上。｜不通过会怎样：运行中写日志失败、服务异常退出。
- [ ] **系统版本与驱动兼容**：太老或太新的组合都有风险。｜怎么验：对照官方支持列表。｜不通过会怎样：驱动装了也不生效，卡在环境层。
- [ ] **散热与电源策略合适**：不像笔记本一样会睡眠、会降频。｜怎么验：连续跑十几分钟，看是否降频/断线。｜不通过会怎样：用一段时间就变慢或失联，客户以为是你做得烂。

## C. 驱动与运行环境

- [ ] 🔴 **只有一套 GPU 驱动**：不存在开源/手动混装。｜怎么验：检查已安装驱动列表。｜不通过会怎样：随机报错，且报错信息指向不了真实原因。
- [ ] 🔴 **计算运行时可用**：引擎能真正调用 GPU 计算。｜怎么验：跑一个最小样例。｜不通过会怎样：能加载模型但速度像 CPU，或者直接报错。
- [ ] **环境可复现**：装在系统位置，不依赖某个临时终端的环境变量。｜怎么验：新开一个终端/重启后再验证一次。｜不通过会怎样：换个人、换台机器就装不出来。
- [ ] **Python/容器环境隔离**（如使用）：不同项目的依赖不互相污染。｜怎么验：看是否用虚拟环境/容器。｜不通过会怎样：装第二个项目时把第一个搞崩。
- [ ] **模型目录规划完成**：放在独立数据盘、路径纯英文。｜怎么验：看实际路径。｜不通过会怎样：C 盘/系统盘撑爆，或中文路径引发诡异报错。

## D. 模型

- [ ] 🔴 **模型与引擎格式匹配**：GGUF 给 llama.cpp 系，safetensors/AWQ 给 vLLM 类。｜怎么验：对文件扩展名和引擎文档。｜不通过会怎样：直接加载失败，白下载几十 GB。
- [ ] 🔴 **文件完整性已校验**：校验值一致、分片齐全。｜怎么验：算哈希，对比官方。｜不通过会怎样：加载报解析错误，或者加载成功但输出诡异，极难排查。
- [ ] **来源与版本已记录**：仓库地址、版本、量化等级、下载日期。｜怎么验：看模型清单。｜不通过会怎样：一周后没人能说清当时用的哪个版本。
- [ ] **许可证已确认**：客户商用是否允许。｜怎么验：看官方 LICENSE 与商用条款。｜不通过会怎样：客户上线后被追责，你是第一责任人。
- [ ] **加载成功且能出字**：不是"下完了"，是"能用了"。｜怎么验：起服务跑一句真实问题。｜不通过会怎样：把"下载完成"误当"部署完成"。

## E. 引擎与参数

- [ ] **关键参数已按场景设定**：上下文长度、显存占用、并发、输出上限。｜怎么验：对照参数表逐项确认。｜不通过会怎样：要么被截断，要么一次请求吃光显存。
- [ ] **上下文长度符合业务需求**：客户材料最长多少，上下文至少覆盖。｜怎么验：拿最长的真实材料试一次。｜不通过会怎样：长文档问答被悄悄截断，答案缺一半，客户还以为模型笨。
- [ ] **采样参数合理**：知识问答用低随机性，创作类可放开。｜怎么验：同一问题问三次看稳定性。｜不通过会怎样：同一个问题每次答案差异大，被认为"胡说八道"。
- [ ] **请求超时匹配回答长度**：客户端、反代、服务端三层都要够。｜怎么验：让它生成一篇长文看是否被掐断。｜不通过会怎样：长回答必断，客户体验极差。
- [ ] **并发上限与压测结论一致**：别设一个压测没验证过的数。｜怎么验：对照压测报告。｜不通过会怎样：上线后一忙就崩，而且崩得没有规律。

## F. 服务化

- [ ] 🔴 **常驻运行**：不是前台终端跑着。｜怎么验：关掉终端再访问。｜不通过会怎样：你电脑一关，服务就没了。
- [ ] 🔴 **开机自启**：重启机器后自动可用。｜怎么验：真的重启一次。｜不通过会怎样：客户断电/重启后服务消失，连夜找你。
- [ ] 🔴 **崩溃自动重启**：进程异常退出后能自己回来。｜怎么验：手动杀掉进程看是否拉起。｜不通过会怎样：小概率崩溃导致长时间不可用。
- [ ] **日志落盘且有轮转**：出问题能查，且不会撑爆磁盘。｜怎么验：查看日志文件，确认轮转配置。｜不通过会怎样：出事时没有证据，排错只能靠猜。
- [ ] **健康检查可用**：能区分"活着"和"能推理"。｜怎么验：加载过程中访问探活接口。｜不通过会怎样：监控永远显示正常，实际已经不能用。
- [ ] **运行用户非 root**：用专用普通用户。｜怎么验：看进程属主。｜不通过会怎样：一个漏洞就是整机权限，且模型文件权限混乱。

## G. 验证（功能）

- [ ] 🔴 **绕过 UI 直接调 API 成功**：返回标准结构、状态码正常。｜怎么验：命令行发一条请求。｜不通过会怎样：网页能聊但客户系统接不上。
- [ ] **多轮对话正常**：上下文能记住。｜怎么验：问一个需要前文的问题。｜不通过会怎样：接了知识库或客服后全是"断片"回答。
- [ ] **中文不乱码**：输入输出、日志都正常。｜怎么验：用中文提问并看日志。｜不通过会怎样：看着难受，且排查日志时更痛苦。
- [ ] **异常输入不崩**：空问题、超长问题、特殊字符。｜怎么验：逐个试。｜不通过会怎样：客户随便一操作就白屏，信任感归零。
- [ ] **错误信息可读**：缺 Key、路径错误、超限时有明确提示。｜怎么验：故意制造错误。｜不通过会怎样：客户以为"你做的系统坏了"，实际是一个参数没带。

## H. 网络与安全

- [ ] 🔴 **监听地址正确**：该对外开放的对外，不该的本机。｜怎么验：从另一台机器访问。｜不通过会怎样：要么连不上，要么把内部端口暴露出去。
- [ ] 🔴 **鉴权生效**：不带 Key / 错 Key 被拒绝。｜怎么验：命令行分别试两种。｜不通过会怎样：等于把模型免费送出去，还可能被刷爆。
- [ ] **端口与防火墙规则明确**：只开放必要端口。｜怎么验：列出对外端口清单。｜不通过会怎样：暴露面过大，安全审计过不了。
- [ ] **Key 管理有清单**：每个使用方一个 Key，能单独吊销。｜怎么验：查看 Key 清单。｜不通过会怎样：有人离职要停用时，只能全部重置，所有人一起断。
- [ ] **限流配置生效**：超频时返回明确错误而不是卡死。｜怎么验：快速连发请求。｜不通过会怎样：有人写了个循环，全公司都排队。
- [ ] **不默认开公网**：需要公网时有 VPN/HTTPS/额外防护。｜怎么验：看网络拓扑和配置。｜不通过会怎样：被扫描到就是一个公开接口。

## I. 性能与压测

- [ ] 🔴 **压测做过并留档**：知道多少并发会明显变慢。｜怎么验：看压测报告。｜不通过会怎样：上线即翻车，客户觉得你根本没测过。
- [ ] **压测结论能对上使用场景**：客户真实的并发量在安全范围内。｜怎么验：对照客户使用人数。｜不通过会怎样：承诺能支持 10 人，实际 5 人就排队。
- [ ] **首字延迟可接受**：不是"能答"，是"等得起"。｜怎么验：看 TTFT 指标。｜不通过会怎样：客户觉得"卡"，用两天就弃用。
- [ ] **长时间运行稳定**：连续跑一天不崩、不持续变慢。｜怎么验：挂机观察或看监控。｜不通过会怎样：内存/显存泄漏类问题交付后爆发。

## J. 交付物与交接

- [ ] **服务访问方式已交付**：地址、模型名、Key、示例代码。｜怎么验：客户照着做一遍。｜不通过会怎样：天天被问"怎么用"，你成了免费客服。
- [ ] **一页使用说明已交付**：怎么问、能问什么、不能问什么、出问题找谁。｜怎么验：客户自己读一遍能懂。｜不通过会怎样：客户拿它当搜索引擎用，效果不好就怪你。
- [ ] **限制与边界已书面说明**：并发上限、上下文限制、不支持的场景。｜怎么验：确认单上列清楚。｜不通过会怎样：预期错位，尾款和口碑一起受损。
- [ ] **备份与恢复方案**：配置、Key 清单、启动脚本有没有备份。｜怎么验：模拟一次重装/迁移。｜不通过会怎样：机器坏了要全部重做，且没人记得参数。
- [ ] **客户能独立完成一次完整使用**：当面或远程走一遍。｜怎么验：让客户自己操作。｜不通过会怎样：这不叫交付，叫"替客户用了一下"。

## 关键参数与配置说明表

| 参数 | 怎么定 | 常见取值思路 | 不通过会怎样 |
|---|---|---|---|
| 上下文长度 | 按客户最长的真实材料 + 余量 | 宁可留余量，别刚够 | 长文档被悄悄截断，答案缺一半 |
| 显存占用上限 | 权重之外的 KV Cache 和并发要留空间 | 加载后显存量出来，保留明显余量 | 聊几句就 OOM 或急剧变慢 |
| 并发上限 | 以压测结论为准，不拍脑袋 | 取压测安全值的保守侧 | 一忙就崩，且崩得没规律 |
| 请求超时 | 客户端、反代、服务端三层一致 | 从外到内逐层放大 | 长回答必断，客户体验极差 |
| 最大输出 token | 按业务问题的最长回答定 | 别默认无限 | 要么莫名截断，要么一次占满显存 |
| 日志与轮转 | 按磁盘容量反推保留天数 | 至少能覆盖一次故障窗口 | 出事没证据，或者日志撑爆磁盘 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 清单全打勾了，交付还是翻车 | 打勾是"我觉得过了"，不是"我验过了" | 每项都要有验证动作和记录，别凭印象 |
| 只在本机验证 | 客户和你在不同网络环境 | 每一项"访问类"检查都换一台机器做 |
| 跳过压测，直接上线 | 觉得"先跑起来再说" | 压测是交付前的最后一道闸，宁可当天晚交一小时 |
| 检查清单变成形式主义 | 每次都复制粘贴同一份 | 按客户类型裁剪，但红线项一条都不能删 |
| 交付后参数没人记得 | 没有归档 | 清单 + 日志 + 配置一起打包归档 |

## 自检问题

- [ ] 这份清单里，哪几项是"不过就不能交付"的红线？为什么？
- [ ] B 段和 C 段，为什么必须放在 D 段（模型）之前？
- [ ] "能通过 API 调通"为什么比"网页能聊"更重要？
- [ ] 压测这一项，最少要产出哪三个数字？
- [ ] 交付物里，哪一样最能减少你后期的咨询量？
- [ ] 客户环境和你环境不一样，哪几项要重做？

## 自检问题参考答案

> [!success]- 1. 这份清单里哪几项是"不过就不能交付"的红线？
> 红线集中在几类：GPU 与计算运行时可用、模型格式匹配且校验通过、服务常驻且开机自启、API 与鉴权可用、压测做过并留档。
> 因为这些一错就是"根本不能用"或"裸奔"，后面所有优化都没意义；标 🔴 就是提醒别抱侥幸上线。

> [!success]- 2. B 段和 C 段为什么必须放 D 段前？
> B 段是硬件与系统、C 段是驱动与运行环境，它们决定这台机器到底能不能把模型跑起来，是地基。
> 地基没过就去下载几十 GB 模型、调参数，等于在错误的机器上做无用功，报错还会指向模型，把人带偏。

> [!success]- 3. 能调 API 为什么比网页能聊重要？
> 网页能聊只证明有个界面能出字；客户真正要接的是业务系统、知识库、机器人，全都走 API。
> API 通了才说明地址、模型名、鉴权、返回结构都对；网页通而 API 不通，交付的就是个玩具。

> [!success]- 4. 压测这一项最少要产出哪三个数字？
> 首字延迟、生成速度，以及"从多少并发开始明显变慢或排队"的临界并发数。
> 三个数字合起来才能对客户承诺"几个人同时用不卡"，也才能反过来定并发上限和限流阈值。

> [!success]- 5. 交付物里哪一样最能减少后期的咨询量？
> 一页使用说明：怎么问、能问什么、不能问什么、出问题找谁、多久回复、支持到几点、怎么升级，再配几个真实示例。
> 它挡掉大半"怎么用、为什么这样答"的咨询，也是客户觉得你专业的直接证据。

> [!success]- 6. 客户环境和你环境不一样，哪几项要重做？
> 所有访问类和环境类的项：监听地址、防火墙端口、鉴权、客户端连通、开机自启、加载测试。
> 凡涉及网络、权限、硬件的都要在客户现场重验一遍，别拿自己机器上的结果替客户签字。

## 决策点：清单使用中的三个岔路口

- **现象**：客户催"先上线，检查后补"｜**判断依据**：红线项是否全过｜**推荐**：红线项必须过；非红线项可带条件上线并写进确认单｜**代价**：晚几小时交付，但避免上线即翻车。
- **现象**：机器配置刚好卡在模型下限｜**判断依据**：有没有并发和长上下文需求｜**推荐**：降一档模型或量化等级，别硬上｜**代价**：效果略降，换来稳定。
- **现象**：客户不愿做压测｜**判断依据**：是否多人同时使用｜**推荐**：做最低成本压测（小并发、十分钟、留三个数）｜**代价**：多花半小时，换来可承诺的并发边界。
- **现象**：清单全过、客户仍说不好用｜**判断依据**：问题在速度、效果还是用法｜**推荐**：拿客户真实问题复现，回看使用说明｜**代价**：多跑一次现场，但能把责任边界谈清。

## 交付视角（对客户怎么讲）

- 把这张清单当**专业感工具**：签合同前就发"验收我们会按这张表逐项过"，客户立刻知道你不是"装完就跑"的人。
- 客户问"这么多项要多久"：说"前面配置一天，后面验证和压测半天"，把时间花在能看见价值的地方。
- 客户想砍价时：指出清单里"压测、文档、验收"这三块是别人不做的，也是出问题时不扯皮的原因。

# 本地模型接入编码助手

> [!abstract] 一句话讲清楚
> Cline、Continue、Roo、Aider、DeepSeek Harness 这类"壳"自己不产模型，它们通过 OpenAI 兼容接口连你的本地推理服务。接不上的原因通常只有四类：**地址填错、上下文不够、工具调用不兼容、流式输出没对上**。这一篇就是讲怎么把这四件事按顺序排掉。

---

## 为什么重要

- "本地模型 + 编码助手"是企业客户接受度最高的场景之一：代码不出内网、不用按人头买订阅、可以按项目配机器。
- 但这是**兼容性坑最密集**的一类集成。模型明明能聊天，装进壳里就"只说不做"——大半是工具调用协议没对上，而不是模型不行。
- 客户会拿着"某某助手 + 某某模型"的教程来问你为什么不行。你必须能在十分钟内判断：是模型不支持、引擎没解析、还是壳的配置错了。
- 上游：[[推理引擎 MOC]] 提供的 OpenAI 兼容服务、[[OpenAI 兼容 API 规范]]；下游：[[工程化交付 MOC]] 的落地与运维。工具调用原理见 [[Agent 与 Function Calling]]，协议见 [[MCP 协议]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 壳 / 客户端 | Harness / Client | 提供界面和工具编排的那层软件，模型是插进去的 | 它不改模型能力，只决定"用起来顺不顺" |
| base_url | API 基地址 | 壳去哪里找模型服务，如 `http://IP:8000/v1` | 少 `/v1`、填 `localhost`、填成网页地址都是常见错 |
| API key | 访问密钥 | 服务的通行证，本地服务也常需要随便填一个 | 很多壳的 key 不能为空，乱填一个也行 |
| model id | 模型标识 | 服务端认识的模型名，不是文件名 | 填错就是 404 或"模型不存在" |
| OpenAI 兼容 | OpenAI-compatible | 服务端假装自己是 OpenAI 的接口格式 | "兼容"程度有差异，工具调用常不完全兼容 |
| 上下文长度 | Context Window | 模型一次能读多少 token | 写代码天然吃上下文，8K 基本不够用 |
| 工具调用 | Tool Calling | 模型输出"读文件/改文件/跑命令"的请求 | 编码助手的核心能力，不支持就退化成聊天 |
| 补全 / FIM | Fill-In-the-Middle | 光标前后文猜中间该写什么 | 和对话/Agent 模式是两套能力，别混 |
| Agent 模式 | Agent Mode | 模型自己多轮读文件、改文件、跑测试 | Cline/Roo 类工具的主打模式，最吃模型能力 |
| Plan / Act | 规划与执行 | 先只读地出方案，确认后再动手改 | 演示时用这个模式更安全 |
| diff 应用 | Diff Apply | 模型给出改动片段，客户端负责精确落盘 | 模型格式不稳会导致"改动对不上" |
| 上下文注入 | @ 引用 / Context | 手动把文件、文档、终端输出塞进对话 | 手动控上下文比自动塞更省 token |
| 压缩 | Compaction | 上下文快满时自动摘要压缩历史 | 压缩会丢细节，长任务容易前后不一致 |
| MCP | Model Context Protocol | 给壳挂外部工具的开放协议 | 壳支持 MCP 才算有扩展性 |

## 原理与机制

### 直觉：壳是"司机"，模型是"发动机"

发动机再好，装不进车里也开不走。壳负责三件事：

1. **界面与编辑器集成**：把代码、选中文本、终端输出组织成提示词。
2. **会话与工具编排**：管理多轮对话、执行模型要求的读文件/写文件/跑命令。
3. **模型调用**：拼请求、发 HTTP、解析流式响应。

你本地部署的模型服务只提供第 3 层要的那个接口。**壳和模型服务之间的兼容性，决定了体验的天花板。**

### 机制一：四种能力，要求完全不同

| 能力 | 原理 | 对模型的要求 | 常见表现 |
|---|---|---|---|
| 对话答疑 | 普通 chat completions | 基础指令遵循 | 一般模型都能用 |
| 行内补全 | FIM 或特殊提示格式 | 需要专门的补全训练 | 通用对话模型做补全往往很怪 |
| 单文件编辑 | 模型输出代码 + 壳做 diff | 代码能力 + 稳定格式 | 能用但不稳 |
| Agent 多文件操作 | 模型反复调工具（读/写/执行） | **工具调用 + 长上下文 + 多步一致性** | 最吃能力，小模型常崩 |

> [!important] 判断顺序
> 先测"对话答疑"能不能通，再测"单文件编辑"，最后才测"Agent 模式"。**一层一层往上测**，一次就上 Agent 模式，失败了你根本不知道是哪层的问题。

### 机制二：为什么编码场景特别吃上下文

一个中等大小的源码文件，几千 token 很正常。Agent 模式下一轮可能：

- 系统提示 + 工具定义：一两千 token
- 读 3~5 个相关文件：上万 token
- 历史对话 + 之前的工具结果：持续累积

所以 **8K 上下文做个补全还行，做 Agent 基本不够**；16K 勉强，32K 以上才舒服。上下文不够时的典型现象是：改到第三个文件时，它忘了第一个文件改了什么，或者开始重复读同一个文件。

### 机制三：工具调用兼容性——链路上有四个环节会断

这是本地模型接编码助手最核心的排错逻辑：

```mermaid
flowchart LR
  A["模型<br/>会输出工具调用标记吗"] --> B["推理引擎<br/>tool parser 能解析吗"]
  B --> C["API 响应<br/>tool_calls 字段格式对吗"]
  C --> D["壳<br/>能识别并执行吗"]
  D --> E["回填工具结果<br/>模型看得懂吗"]
```

四个环节任何一环不通，现象看起来都一样：**模型只回一段文字，不实际读写文件**。要逐个排除：

1. **模型层**：这个模型训练时见过工具调用格式吗？有些小模型、老模型、以及某些量化版本，确实不具备稳定的工具调用能力。
2. **引擎层**：推理引擎需要配置对应的 **tool call parser / chat template**。vLLM、llama.cpp、Ollama 等都需要模型自己声明的模板或手动指定解析器。**引擎不认识模型的输出标记，就会把它当成普通文本返回。**
3. **API 层**：兼容接口要把调用请求表达成标准的 `tool_calls` 字段，而不是塞在文本里。很多"半兼容"实现只支持 chat，不支持 tools。
4. **壳层**：客户端对返回格式的解析很严格，尤其**流式增量返回**时（`tool_calls` 分片到达）。有的壳只认完整返回。

> [!tip] 最快的定位方法
> 用 `curl` 直接打模型的 `/v1/chat/completions`，`tools` 里放一个最简单的函数（比如 `get_time`），看返回里有没有 `tool_calls`。
> - 没有 → 问题在模型/引擎层，别再去折腾壳。
> - 有 → 问题在壳的配置或解析，换客户端或看日志。

### 机制四：流式与"半截输出"

编码助手需要"边生成边显示"。流式响应下，工具调用通常也是分片到达的：先来函数名，再来参数的一段段字符串。壳需要把这些分片拼起来再执行。

如果服务端在流式模式下**不支持工具调用分片**，或者壳的实现不完善，就会出现：

- 界面上看到模型"说"它要读文件，但实际没读；
- 工具调用偶尔成功偶尔失败；
- 参数看起来被截断了。

排查办法：临时关掉流式（如果壳支持），看是否恢复正常。能恢复说明是流式兼容问题。

## 完整流程：从服务到好用的编码助手

1. **输入**：本地推理服务（vLLM / Ollama / llama.cpp 等）+ 目标模型。
   **动作**：确认三件事——服务地址、模型 id、支持的最大上下文；确认引擎是否配了 tool parser。
   **输出**：一份连接参数清单。**验收**：`curl` 一句聊天请求能返回正常内容。
2. **输入**：连接参数。
   **动作**：在壳里选"OpenAI 兼容"提供方，填 base_url、API key、model id。
   **输出**：配置完成。**验收**：壳里点"测试连接"通过。
3. **输入**：配好的壳。
   **动作**：**只做聊天**——问一个不涉及文件的问题。
   **输出**：能正常对话。**验收**：回答连贯，无乱码、无截断。这一步不过，后面全免谈。
4. **输入**：能对话的壳。
   **动作**：测单文件操作——让它读一个文件并总结。
   **输出**：真的调用了读取工具。**验收**：日志里能看到工具调用与执行。**这一步不过 = 工具调用链路断了，回到机制三。**
5. **输入**：工具能调。
   **动作**：测多文件小任务——"把 A 文件里的函数挪到 B 文件并更新引用"。
   **输出**：改动正确。**验收**：编译/测试通过，没有无关改动。
6. **输入**：小任务通过。
   **动作**：压长上下文——故意给它一个需要读 4~6 个文件的任务。
   **输出**：不丢前面的改动。**验收**：没有出现"忘了刚才改过什么"或重复读同一文件。
7. **输入**：稳定性问题清单。
   **动作**：调上下文上限、max_tokens、温度；必要时换更大模型或降低量化程度。
   **输出**：稳定可用。**验收**：连续做 5 个小任务，至少 4 个一次通过。

## 分类与对比：常见壳怎么选

| 工具 | 形态 | 强项 | 对本地模型的要求 | 注意 |
|---|---|---|---|---|
| Cline | 编辑器插件 | Agent 模式成熟，能读文件、跑命令、改多文件 | 工具调用 + 较长上下文 | 工具调用不稳时会显得"很笨" |
| Continue | 编辑器插件 | 可配置性强，补全与对话都能配，可指向任意 OpenAI 兼容地址 | 补全要 FIM 模型；对话要一般模型 | 配置文件字段多，首次配容易漏 |
| Roo Code | 编辑器插件 | 多模式切换（问答/写代码/架构），流程感强 | 工具调用 + 稳定指令遵循 | 模式多，配置项也多 |
| Aider | 命令行 | 直接在终端改仓库文件，Git 集成好 | 代码能力 + diff 格式稳定 | 依赖 git 流程，新手要先熟悉命令行 |
| DeepSeek Harness | 终端/Agent 运行环境 | 面向 Agent 型任务，能挂工具与 MCP | 工具调用 + 长上下文 + 稳定输出 | 终端类工具对模型纪律要求高，配置项以官方文档为准 |

> [!important] 怎么选
> **团队里人人有 IDE、想边写边用** → Cline / Continue / Roo；**喜欢命令行、强调按仓库批量改** → Aider 类；**要做 Agent 型自动化** → DeepSeek Harness 这类终端环境。别一次装三个，先用一个把工具调用跑通。

### 地址怎么填（最常见的三个错）

| 场景 | 引擎常见默认地址形态 | 填进壳里 | 常见错误 |
|---|---|---|---|
| vLLM | `http://IP:8000/v1` | base_url 填到 `/v1` | 少 `/v1` → 404 |
| Ollama | `http://IP:11434/v1` | base_url 填到 `/v1` | 用了 11434 但漏 `/v1` |
| llama.cpp server | `http://IP:8080/v1` | base_url 填到 `/v1` | 用了网页端口或路径 |

> [!warning] localhost 陷阱
> 壳跑在你自己电脑上、模型跑在服务器上时，`localhost` 指向的是**你自己的电脑**，不是服务器。一定填服务器的内网 IP。模型服务和壳在同一台机器上才用 `127.0.0.1`。

## 排错清单：症状 → 原因 → 对策

| 症状 | 最可能原因 | 对策 |
|---|---|---|
| 测试连接 404 | base_url 少了 `/v1`，或多了 `/chat/completions` | 只填到 `/v1` 为止，路径由壳自己拼 |
| 401 / 鉴权失败 | key 填了空值，或服务端要求认证格式 | 服务端没开鉴权时随便填个非空字符串；开了就填对的 |
| 连接超时 | IP/端口不通、防火墙、服务只监听 127.0.0.1 | 先 `curl` 测通；服务启动加 `--host 0.0.0.0` |
| 模型不存在 | model id 填的是文件名或显示名 | 调 `/v1/models` 看真实 id，照抄 |
| 能聊天但不能改文件 | 工具调用链路断（模型/引擎/API/壳） | 按机制三逐层排查，先 `curl` 看有没有 `tool_calls` |
| 模型"说"要读文件却没读 | 流式模式下工具调用不稳定，或壳解析失败 | 关流式试一次；看壳日志里的原始响应 |
| 改到一半忘了前面的改动 | 上下文不够或触发压缩 | 提高上下文上限、减少一次任务涉及的文件数 |
| 输出重复、乱码、停不下来 | 采样参数异常 / 量化质量差 / 模板错配 | 调温度与重复惩罚；换更高质量量化；确认 chat template |
| 一执行命令就卡住 | 命令在等交互输入，或壳的超时设置太短 | 命令加非交互参数；调大超时 |
| 同一个任务时好时坏 | 温度偏高、并发下显存压力、模型能力临界 | 固定低温、单任务串行、评估换更大模型 |

## 决策点

- **岔路口 1：本地模型做编码助手，选多大模型？**
  判断依据：任务是补全、单文件改、还是多文件 Agent。
  → **推荐**：只做补全和问答，小模型够；要做 Agent 连续改多文件，**明显要上更大模型**，并保证上下文足够。别指望 7B 4bit 稳定跑多文件。
- **岔路口 2：量化到什么程度？**
  判断依据：显存预算 vs 工具调用稳定性。
  → **推荐**：编码 Agent 场景尽量 4bit 起步、能 8bit 更好。**量化对"格式严格性"的伤害比对"知识"更大**，代码场景恰恰最在意格式。
- **岔路口 3：用插件式壳还是终端式壳？**
  判断依据：团队习惯、是否需要批量改仓库。
  → **推荐**：日常开发用插件式（看得见改动，容易回滚）；批量重构、自动化脚本用终端式。
- **岔路口 4：上下文给多少？**
  判断依据：模型支持上限、显存。
  → **推荐**：设到模型窗口的一半到八成，留余量给输出。**别设到满**，否则响应变慢、注意力变散。
- **岔路口 5：工具调用不兼容怎么办？**
  判断依据：是模型不支持，还是引擎没配解析器。
  → **推荐**：先换推理引擎配置（加 tool parser / 换 chat template），再考虑换模型。**引擎配置问题比模型问题更常见**。
- **岔路口 6：要不要开放执行命令？**
  判断依据：安全边界与客户要求。
  → **推荐**：默认只允许读 + 白名单命令，写文件和执行命令要确认。内网交付尤其要讲清楚这条，见 [[安全与合规]]。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| base_url | 服务地址 | 错一处就 404 | `http://内网IP:端口/v1` |
| model id | 模型标识 | 必须是服务端认的名字 | 用 `/v1/models` 查 |
| 上下文长度 | 一次能读多少 | 小→忘前文；满→慢且散 | 16K 起步，32K 更稳 |
| max_tokens（输出） | 单次输出上限 | 太小→写不完文件 | 2048~8192 |
| temperature | 随机性 | 高→乱改代码 | 0~0.2 |
| top_p | 采样范围 | 一般不动 | 0.9 左右 |
| 流式 | 边生成边显示 | 关掉可排查兼容问题 | 默认开 |
| 命令超时 | 执行上限 | 短→误判失败 | 按任务定 |
| 自动确认 | 是否每次操作都问 | 全自动方便但危险 | 演示/生产用确认模式 |

## 各类编码壳的配置速查与验收清单

客户端字段名各不相同，但要填的东西永远是那几样。

| 编码壳 | 添加入口 | 要填的字段 | 容易卡住的地方 |
|---|---|---|---|
| Cline | 设置里选 API Provider | OpenAI Compatible + Base URL / API Key / Model ID | 不同版本对 base_url 是否带 `/v1` 的写法有差异，按提示试 |
| Continue | 改配置文件里的 models 段 | provider 写 openai，apiBase 填到 `/v1`，model 填 id | 补全和对话是两段配置，要分别填 |
| Roo Code | 与 Cline 类似 | Provider / Base URL / Key / Model | 多模式共用一套配置，切模式后确认模型没变 |
| Aider | 命令行参数或环境变量 | 指定 OpenAI 兼容地址与模型名 | 要求仓库是 git 仓库，否则改动不好回滚 |
| DeepSeek Harness | 配置文件 / 环境变量 | 模型服务地址、key、模型名 | 以官方文档字段为准，版本之间字段可能变化 |

> [!note] 字段名以官方文档为准
> 上表只写"要填什么"，具体字段拼写每个版本都可能不一样。**交付文档里要写清你实际验证过的那一个版本怎么填**，并附截图。

### 上线前验收清单

- [ ] 纯对话能通，中文输出正常，无乱码。
- [ ] 让它读一个指定文件，日志里能看到工具调用与结果回填。
- [ ] 让它改一个文件里的一行，落盘内容正确、无无关改动。
- [ ] 跨两个文件的小任务能完成，引用关系更新正确。
- [ ] 连续做 5 个小任务，至少 4 个一次通过。
- [ ] 上下文接近上限时不会突然忘记前面的约束。
- [ ] 确认模式打开时，写文件和执行命令都会先询问。
- [ ] 确认本地链路不依赖公网（断外网仍可用）。
- [ ] 交付文档写清了地址、模型 id、上下文设置和常见故障处理。

### 什么情况下别用本地模型写代码

- **多文件大重构**：本地模型能力常在临界点上，返工成本比省下的钱高。
- **需要频繁查最新 API 文档**：模型知识有截止时间，又不能联网，容易给出过时写法。
- **团队没有 GPU 运维能力**：机器一出问题就停摆，维护成本会超过收益。
- **交付周期紧、要求一次成功**：先用成熟方案交付，本地化留作后续优化。

反过来，这些场景很适合本地模型：行内补全、测试生成、代码解释、小范围修改、完全离线环境。**把场景框对，客户满意度比堆参数高得多。**

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 照教程填了 `localhost`，怎么都不通 | 壳和模型不在同一台机器 | 填服务器内网 IP；同机才用 `127.0.0.1` |
| 以为"支持 OpenAI 兼容"就等于支持工具调用 | 兼容通常只保证 chat 部分 | 单独验证 tools 字段与 `tool_calls` 返回 |
| 换了个模型，工具调用突然全废 | 新模型的工具调用标记格式变了，引擎解析器没跟上 | 确认引擎对该模型配了正确的 tool parser / 模板 |
| 上下文设得很小，以为省钱，结果天天重跑 | 编码任务天然吃上下文，超了会忘前文 | 给足上下文，靠"少塞文件"省 token 而不是砍窗口 |
| 用通用对话模型做行内补全，效果很怪 | 补全需要 FIM 训练，普通 chat 模型不擅长 | 补全和对话分开配不同模型 |
| 开启了自动执行，模型把测试文件删了 | 没有确认环节、没有沙箱 | 用确认模式、限定目录、重要仓库先提交再让它动 |
| 客户端升级后连不上 | 配置字段/协议变化 | 锁版本、升级前备份配置 |
| 只看界面表现就断言"本地模型不行" | 没验证是否卡在工具调用链路 | 先用 `curl` 分离模型层与壳层 |

## 自检问题参考答案

> [!success]- 1. base_url 应该填到什么位置？为什么多填一段路径会 404？
> 只填到 `/v1` 为止，比如 `http://内网IP:8000/v1`；后面的 `/chat/completions` 由壳自己拼。多填一段就变成 `/v1/chat/completions/chat/completions`，直接 404；少 `/v1` 也是 404。
> 另外两个高频错：填成了网页地址；壳和模型不在同一台机器却写 `localhost`——它指的是**你自己这台电脑**。

> [!success]- 2. 工具调用从模型到壳，中间有哪四个环节可能断？
> ① **模型**：训练时见过工具调用标记吗，会不会稳定输出；② **推理引擎**：tool parser / chat template 认不认识这个模型的标记，不认识就当普通文本返回；③ **API 层**：有没有转成标准 `tool_calls` 字段，"半兼容"实现常常只支持 chat 不支持 tools；④ **壳**：能不能识别、执行、回填，流式分片时解析更严格。
> 任何一环断，现象都一样：模型只回一段文字，不真的读写文件。

> [!success]- 3. 怎么用一条 curl 在 1 分钟内判断是模型问题还是壳问题？
> 直接 `curl` 打模型的 `/v1/chat/completions`，`tools` 里放一个最简单的函数（比如 `get_time`），只看返回里有没有 `tool_calls`。
> **没有** → 问题在模型或引擎层，先别折腾壳；**有** → 问题在壳的配置或解析，去看壳日志或换客户端。这一刀把排查范围直接切成两半。

> [!success]- 4. 为什么编码 Agent 比普通问答更吃上下文？给一个量级感受。
> 因为每轮都在累积：系统提示加工具定义就一两千 token，读 3~5 个相关文件就上万 token，历史对话和之前的工具结果还持续往上叠。普通问答几千 token 就够，Agent 轻松上万。
> 量级参考：**8K 做补全还行、做 Agent 基本不够；16K 勉强；32K 以上才舒服**。不够的典型表现是改到第三个文件就忘了第一个改了什么。

> [!success]- 5. 量化对编码 Agent 的影响为什么比对知识问答更大？
> 因为代码场景要的是**严格格式**：diff 要能对上、JSON 和括号缩进不能错，而量化最先伤的就是这类精细格式能力，知识性问答反而还答得对。
> 所以 4bit 模型能聊天，但做多文件 Agent 会频繁"格式崩、改动对不上"，2bit/3bit 更明显。做法：编码场景尽量 4bit 起步，条件允许用 8bit。

> [!success]- 6. 流式输出会导致什么样的工具调用故障？怎么验证？
> 流式下工具调用是**分片到达**的：先来函数名，再一段段来参数字符串，壳要拼起来才能执行。服务端不支持分片、或壳的拼接实现不完善时，就会出现：界面显示模型"说"要读文件但其实没读、工具调用时好时坏、参数看起来被截断。
> 验证：临时关掉流式再跑一次，故障消失就说明是流式兼容问题。

> [!success]- 7. 哪些操作应该默认需要人工确认？
> 三类：**写文件/改代码**、**执行命令**（尤其是删除、装依赖、发网络请求）、**越过项目目录的操作**（git push、改系统配置）。这些误操作代价高且不一定可逆。
> 生产建议：开确认模式、限定可操作的目录、重要仓库先提交一次再让它动手；内网交付时把这条写进交付文档，客户会踏实很多。

> [!success]- 8. 16K 上下文能撑什么样的任务？32K 能撑什么？
> **16K 勉强**：读两三个短文件、单文件小改、带一点历史对话；**32K 以上**才能舒服地一次读 4~6 个相关文件、做跨文件的小重构、多轮 Agent 不丢前文。
> 但别设到满：设到模型窗口的一半到八成，留余量给输出，否则响应变慢、注意力被稀释。

## 交付视角（对客户怎么讲）

- **大白话解释**："我们让 AI 编辑器连上您机房里的模型。代码、文档、终端输出都不出内网。它能读您的项目、按您的要求改代码，但每次落盘前都会让您确认。"
- **客户最常问**："为什么它不如某某云端产品聪明？" 老实说：本地模型能力取决于参数量和量化程度，做补全和单文件修改足够，做复杂多文件重构会弱一些。**建议先小范围试点，用过再决定要不要加机器**。这话比吹效果好得多。
- **报价拆项**：推理服务部署（一次性）、客户端配置与模板（按人头/按套）、工具调用兼容性调优（按轮次，最费时间的一项）、培训（一次性）、机器与维护（按月）。**"兼容性调优"必须单列**，因为不同客户端组合的坑完全不一样，不单列会亏。

# 上下文窗口与位置编码

> [!abstract] 一句话讲清楚
> 上下文窗口 = 模型一次最多能"看见"多少 token。它受两件事约束：**显存**（KV Cache 随长度线性上涨）和**位置编码**（模型分得清"第几个字"的能力）。窗口写得大，不代表用得一样好。

## 为什么重要

- "支持 128K" 是现在最常见的卖点，也是最容易被误解的一句话。客户会默认以为"能塞 128K = 能理解 128K"，**实际是两回事**。
- 它直接决定两笔钱：
  - **显存钱**：上下文越长，KV Cache 越大，能跑的模型就越小、并发就越少。
  - **方案钱**：长上下文和 [[RAG 原理与全链路]] 是两条路线，成本和效果完全不同，选错了返工。
- 交付时几乎一定会遇到："客户丢一个 200 页 PDF 过来，说'让它全读一遍'"。你必须有判断和话术。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 上下文窗口 | Context Window | 一次性最多能塞进多少 token（输入 + 输出共用）。 | 不区分输入输出：输出也占额度，要留出空间。 |
| 上下文长度 | Context Length | 实际塞了多少 token。 | 和"窗口上限"是"实际值 vs 上限"，别混着说。 |
| 位置编码 | Positional Encoding | 告诉模型"这个 token 排在第几位"的机制。 | 注意力本身没有顺序概念，没有位置编码词序就乱。 |
| RoPE | Rotary Position Embedding | 目前主流的旋转位置编码：把位置信息"转"进向量里。 | 中文常叫"旋转位置编码"，是一类方法不是具体模型。 |
| 外推 | Extrapolation | 训练时只见过 8K，硬用到 32K。 | 粗暴外推会崩，需要专门方法。 |
| 内插 / 缩放 | Interpolation / Scaling | 把位置"压缩"到训练见过的范围里。 | 会牺牲分辨率，长距离区分度下降。 |
| 长度外推技术 | YaRN / NTK 等 | 一类让模型在更长文本上还能工作的技巧。 | 名字不用背，要记住"能做，但有损"。 |
| 滑动窗口注意力 | SWA | 只看最近 N 个 token，不回头看全部历史。 | 能压显存但会忘远处，常见于长上下文优化。 |
| 注意力稀释 | Lost in the Middle | 太长的输入里，中间部分容易被忽略。 | 这是实测常见的现象，不只是理论担忧。 |
| 上下文压缩/摘要 | Context Compression | 把长文本先压短再喂给模型。 | 属于工程手段，不在模型内部。 |
| 检索增强 | RAG | 先查资料再喂给模型少量相关片段，见 [[RAG 原理与全链路]]。 | 不是长上下文的替代品，是另一条更有性价比的路线。 |
| 上下文缓存 | Prompt Caching | 相同前缀只算一次，复用 KV。 | 能省首字时间，不省显存总量。 |

## 原理与机制

### 为什么模型需要"位置"这个概念

注意力机制本质是"所有 token 两两算相关性"，它**本身没有顺序**。如果不告诉它谁在前谁在后，"猫咬狗"和"狗咬猫"在它眼里是同一堆词。

所以要给每个 token 注入位置信息。历史上用过三种思路：

| 思路 | 做法 | 缺点 |
|---|---|---|
| 绝对位置编码 | 给第 1、2、3… 位各一个固定向量，加到 embedding 上 | 训练长度之外的位置没见过，无法外推 |
| 相对位置编码 | 只告诉模型"两个 token 隔了几个" | 实现复杂，扩展性一般 |
| **RoPE（旋转）** | 把位置"转"进 Q/K 的向量角度里，注意力分数天然带相对距离 | 主流方案，可外推性较好 |

### RoPE 在干什么（直觉版）

把每个 token 的 Q、K 向量想象成一根指针，位置越靠后，指针转的角度越大。计算相关性时看的是两个指针的**夹角差**——夹角差天然对应"相对距离"。

好处：

- 相对位置信息自然融入，不需要额外参数；
- 可以通过调"旋转速度"来实现长度扩展（这就是各种外推/内插方法的原理）；
- 工程实现干净，几乎所有现代开源模型都用它。

> [!tip] 类比
> 像钟表指针：位置 = 指针转到几点的方向。两只表看时间差，看的是夹角，不是绝对刻度。想表示更长的时间跨度，就把转速调慢（位置缩放），但刻度会变密、分辨率下降。

### "支持 128K"的三种成色

必须能分清这三种情况，这是本篇最有用的判断力：

| 成色 | 含义 | 实际表现 |
|---|---|---|
| **原生训练到 128K** | 训练数据里就有这么长的样本 | 长文理解最可靠，成本也最高 |
| **外推/插值扩展** | 原生长度较短，靠位置缩放等技术拉到 128K | 能跑，但**长距离检索和精确引用会掉**，需要实测 |
| **配置文件写着 128K** | 引擎允许填这个数，模型也勉强不崩 | 可能只是"能塞进去"，效果不能保证 |

判断方法：看模型卡/技术报告里**训练时的上下文长度**是多少，再看它是用什么方法扩展的。只写"支持 128K"而没有说明的，按第二种对待。

### 长度是怎么变成显存账单的

两笔额外开销，前面都讲过，这里串起来：

1. **KV Cache**：长度 × 并发，线性增长。见 [[Attention 与 KV Cache]]。
2. **注意力计算**：长度越长，需要算的两两关系越多，首字延迟明显上升（prefill 阶段）。

具体量级：

- 8K 以内，多数 24G 卡还能舒服；
- 32K 时，KV Cache 往往要占几 G，必须重新算账；
- 128K 时，KV Cache 可能到十几 G 甚至更多，单卡 + 高并发基本不现实。

**另一个隐形成本**：输入越长，prefill 越慢。客户感受是"**上传完文档后，等了很久才开始出字**"。这是长上下文最容易被投诉的点。

### 长上下文 ≠ 长文理解

业界反复观察到的现象（量级描述，不给具体分数）：

- **中间丢失**：把关键信息放在超长输入的中段，模型召回明显低于放在开头或结尾。所以重要信息应该放**开头或结尾**。
- **长文细节衰减**：文档越长，对具体细节的引用准确度越低。
- **干扰增加**：无关内容越多，越容易被带偏，占用了"有效注意力"。

结论：**窗口是容量，理解是另一回事。** 能塞 128K 不代表能准确回答第 200 页的表格。

## 分类与对比

### 长上下文 vs RAG

这是交付里最需要做的取舍：

| 维度 | 长上下文（整篇塞进去） | RAG（先检索再喂） |
|---|---|---|
| 实现复杂度 | 低（把文本拼进去） | 高（切分、向量库、检索、排序一套） |
| 显存/成本 | 随长度线性涨，越长越贵 | 基本恒定，只喂相关片段 |
| 首字延迟 | 明显变慢（prefill 长） | 快 |
| 准确度 | 全量信息都在，但可能"看不过来" | 依赖检索质量，检索错就答错 |
| 可追溯性 | 弱（说不清依据哪段） | 强（能给出引用来源） |
| 更新维护 | 每次重传全文 | 更新知识库即可 |
| 适合 | 一次性分析、合同比对、长报告总结 | 有稳定知识库、需要引用的问答 |

**经验判断**：

- **一次性、短周期任务** → 长上下文更快更省事；
- **长期、反复、需要引用** → RAG 更划算；
- **真实交付里大多是混合**：RAG 检索出候选片段，再把片段和问题一起喂给模型。

详见 [[RAG 原理与全链路]]。

### 常见"扩窗"手段对比

| 手段 | 省什么 | 代价 |
|---|---|---|
| 位置插值/外推（YaRN 类） | 让模型能处理更长输入 | 长距离精确性下降 |
| 滑动窗口注意力 | KV Cache 明显下降 | 会"忘"窗口外的内容 |
| KV Cache 量化 | KV 显存减半量级 | 精度损失 |
| 上下文压缩/摘要 | 输入的 token 数 | 信息丢失，需要策略 |
| Prompt Caching | 首字延迟（相同前缀复用） | 不省总显存 |

## 决策点

- **岔路口 1：客户说"要 128K 上下文"，先答应吗？**
  - 判断依据：问清楚**具体任务**——是一次性读长文，还是长期知识问答。
  - 推荐选择：先做一个小实测（拿客户真实的 10 份长文试）。**一次性任务 → 长上下文可行；长期知识库 → 推 RAG**。
  - 代价：答应得太快，要么硬件超预算，要么效果不达标。

- **岔路口 2：模型卡的上下文上限 vs 实际部署上限，怎么定？**
  - 判断依据：显存余量、并发数、业务真实需求。
  - 推荐选择：**按业务真实长度上浮 2~4 倍定上限**，别直接拉满模型最大值。留出余量给并发和输出。
  - 代价：定小了以后要调大，需要重新压测。

- **岔路口 3：长文效果不好，是模型不行还是用法不对？**
  - 判断依据：做对照实验——信息放开头 vs 中间 vs 结尾；整篇塞 vs 切片喂。
  - 推荐选择：先调**信息位置和输入组织**（把关键信息放两头、压缩无关内容），再考虑换模型。
  - 代价：调 prompt 和组织方式花时间，但比换硬件便宜太多。

- **岔路口 4：选模型时，"原生 32K + 质量好"和"扩展 128K + 质量一般"选哪个？**
  - 判断依据：任务是不是真的需要 100K 以上连续文本。
  - 推荐选择：**绝大多数业务选原生长度够用的那个 + RAG**。扩展窗口只在确实需要"通篇一次看"时才有意义。
  - 代价：确实有"整篇比对"类任务时，只能上长上下文。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| max_model_len / 上下文上限 | 引擎允许的单请求最大长度 | 调大 → KV 显存涨、prefill 变慢 | 4K / 8K / 32K，按业务定 |
| max_tokens（输出上限） | 回答最多生成多少 token | 影响耗时和费用，也占窗口 | 512 / 1024 / 4096 |
| RoPE scaling / 缩放因子 | 控制位置缩放的强度 | 调大 → 能处理更长，但分辨率下降 | 引擎里按模型卡推荐配置 |
| KV Cache 精度 | 缓存用 fp16 还是 int8 | 降精度省显存 | 长上下文场景建议开 |
| 滑动窗口大小 | 只回看多少 token | 调小省显存、忘得更多 | 模型内置参数，通常不可随意改 |
| 并发数 | 同时处理的请求 | 每请求一份 KV | 长上下文场景要压到很小 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 以为"支持 128K"就等于"能理解 128K" | 窗口是容量，理解质量是另一回事 | 用客户真实长文实测；重要信息放开头/结尾 |
| 开了长上下文后首字特别慢，客户投诉 | prefill 阶段处理长输入很吃时间 | 提前说明；能 RAG 就 RAG；用 Prompt Caching |
| 128K 窗口下并发一开就 OOM | KV Cache 随长度和并发相乘 | 长上下文场景必须限制并发 |
| 把 200 页 PDF 直接整篇塞进去，效果一般 | 中间信息丢失 + 无关内容干扰 | 先分段摘要或走 RAG，再喂关键片段 |
| 换了扩窗配置但没重新测召回 | 外推/缩放有损，长距离精确性下降 | 每次改窗口配置都跑一遍"针在草堆里"式测试 |
| 输出长度把窗口挤爆 | 输入 + 输出共用窗口 | max_tokens 要预留，别把输入塞到上限 |
| 以为"上下文越长越聪明" | 长上下文主要增加"可看的信息"，不增加推理能力 | 能力问题换模型，不是拉长窗口 |
| 在长对话里越聊越慢 | 历史全拼进输入，prefill 越来越大 | 做历史裁剪/摘要，或只带相关轮次 |

## 案例拆解：客户甩来一份 200 页 PDF，问"能不能直接塞进去"

这是最常遇到的场景，走一遍判断流程：

1. **算 token 量**：200 页中文文档，一页大约几百到一千字，整体通常在十几万到几十万 token 的量级（具体看排版和图）。**先看这个数有没有超过模型窗口**。
2. **看模型窗口**：不少开源模型的"宣称窗口"是 32K 或 128K 量级，但实际把整本书塞进去，效果往往明显下降（"支持"和"用得好"的差别）。
3. **算显存**：就算窗口够，十几万 token 的 KV Cache 也会把显存吃掉一大块，见 [[Attention 与 KV Cache]]。16G 卡基本别想，24G 也够呛。
4. **算延迟**：长输入意味着 prefill 要处理大量 token，第一个字出来的时间会很长，客户体感是"卡住了"。
5. **给结论**：**别直接塞**。正确做法是走 RAG——先检索出跟问题最相关的几段，再喂给模型，见 [[RAG 原理与全链路]]。

什么时候确实需要长上下文？

| 场景 | 是否适合长上下文 | 原因 |
|---|---|---|
| 通读合同找风险点 | 适合 | 需要全局对照，检索容易漏 |
| 200 页手册问答 | 不适合，用 RAG | 问题通常只涉及局部章节 |
| 一整个代码仓库分析 | 部分适合 | 依赖关系跨文件，检索会断链 |
| 长会议记录总结 | 适合 | 一次性摘要，不需要反复查 |

**一句话经验：需要"全局对照"的用长上下文，需要"精确查找"的用 RAG；两者经常要组合用。**

## 自检问题参考答案

> [!success]- 1. 用"钟表指针"怎么解释 RoPE？
> 把每个 token 的 Q、K 向量想成一根指针：位置越靠后，指针转过的角度越大。算相关性时看的是两个指针的**夹角差**，而夹角差天然对应"相对距离"。
> 所以位置信息不用额外加参数，直接"转"进了向量里；想让它表示更长的跨度，就把旋转速度调慢（位置缩放）——这正是各种长度扩展技巧的原理。
> 代价也在类比里：转速调慢后刻度变密，相邻位置的区分度下降，所以扩出来的长度是有损的。

> [!success]- 2. "原生训练长度"和"扩展支持长度"差在哪，为什么后者有损？
> **原生训练长度**是训练数据里真的出现过这么长的样本，模型见过长文的排布规律，长文理解最可靠，成本也最高。
> **扩展支持长度**是原生长度较短，靠位置插值、位置外推（YaRN 一类方法）把有效窗口拉到更长。位置缩放会把刻度压密，长距离的分辨率下降，于是"开头问、中间答"的检索和精确引用会明显变差。
> 判断方法：看模型卡或技术报告里训练时的上下文长度是多少、用什么方法扩展的；只写"支持 128K"却没说清来源的，按扩展版对待。

> [!success]- 3. 上下文变长会带来哪两笔成本？
> 第一笔是**显存**：KV Cache 随长度线性上涨，还和并发相乘。量级上 32K 往往要占几 G，128K 可能到十几 G 甚至更多，能跑的模型更小、并发更少。
> 第二笔是**首字延迟**：prefill 阶段要把整段输入先算完，输入越长，第一个字出来得越慢。客户感受就是"文档传完了，等了半天才开始回答"。
> 这两笔合起来，直接决定了硬件档位和体验上限，所以长上下文从来不是"免费的容量"。

> [!success]- 4. 长上下文和 RAG 怎么取舍？
> 长上下文的优势是实现简单（拼进去就行）、全量信息都在、可追溯性弱；劣势是成本随长度线性涨、首字慢、更新要重传全文。适合一次性分析、合同通读比对、长报告总结。
> RAG 的优势是成本基本恒定、首字快、能给出引用来源、知识库可更新；劣势是链路复杂、依赖检索质量，检索错就答错。适合有稳定知识库、需要引用的问答。
> 经验判断：一次性短周期任务用长上下文，长期反复且要引用用 RAG；真实交付里大多是混合——RAG 先检索候选片段，再和问题一起喂给模型。

> [!success]- 5. 什么是"中间丢失"，关键信息该怎么摆？
> 现象是：把关键信息放在超长输入的中段，模型召回明显低于放在开头或结尾。此外文档越长、对具体细节引用越不准，无关内容越多越容易被带偏。
> 实操结论：**重要信息放开头或结尾**，中间放辅助材料；无关内容先压缩掉，别一股脑全塞。
> 更稳的做法是分段摘要或先走 RAG 把相关段落捞出来再喂——不要假设"塞进去了它就都看懂了"。

> [!success]- 6. 客户问"能不能一次读 200 页 PDF"，怎么答？
> 先算账：200 页中文文档通常在十几万到几十万 token 量级，先看有没有超过窗口；再看 KV Cache 够不够（16G 卡基本别想，24G 也够呛）；最后算 prefill 延迟，几乎肯定很慢。
> 然后给两条方案：一是 **RAG**，检索出跟问题最相关的几段再喂，快、便宜、可引用，适合绝大多数问答；二是**长上下文**，只在需要全局对照时用（比如通读合同找风险点），并接受它慢和贵。
> 最佳答案通常是混合：RAG 找片段 + 少量长文做全局对照。

> [!success]- 7. 为什么输出长度也要算进上下文窗口？
> 因为窗口是**输入 + 输出共用**的额度，不是输入专属。模型生成的每一个 token 也要占这个窗口的位置。
> 所以 `max_tokens` 必须预留，别把输入塞到上限——否则回答生成到一半就撞墙，被截断或者直接报错。
> 交付文档里固定写清"最大上下文 / 最大输出 / 最大并发"三项，比只写"支持 128K"有意义得多。

> [!success]- 8. 至少说三种"扩窗"手段及各自代价。
> **位置插值/外推（YaRN 类）**：让模型能处理更长输入，代价是长距离精确性下降。
> **滑动窗口注意力**：KV Cache 明显下降，代价是会"忘"掉窗口外的内容。
> **KV Cache 量化和上下文压缩/摘要**：前者把 KV 显存压到减半量级但有精度损失，后者省输入 token 但会丢信息。
> 还有 **Prompt Caching**：相同前缀只算一次，省的是首字延迟，不省显存总量。

## 交付视角（对客户怎么讲）

- **客户问"这个模型支持多长上下文"**：别只报数字。说"**模型本身支持到某个长度，但你实际能用的长度由显存和并发决定。我建议按你的业务长度上浮一点来配。**"这样既不吹，也显得专业。
- **客户要"整库喂进去"**：先拆需求——"你是要它记住所有文档，还是要在这些文档里查答案？" 前者长上下文（贵、慢、难维护），后者 RAG（便宜、可引用、可更新）。这个岔路口直接决定报价量级。
- **客户投诉"读长文很慢"**：解释"**模型得先把整篇读完才能开始回答，读得越多等得越久**"，然后给方案：切片、摘要、只喂相关段落。
- **写进方案的表述**：固定写 `最大上下文 8K / 最大输出 1K / 最大并发 2`。这三项是交付边界，比"支持 128K"有意义得多。
- **别承诺**："128K 全文精确问答"这种承诺基本会翻车。承诺"在这个长度内、这类文档、这个准确率"才是可交付的。

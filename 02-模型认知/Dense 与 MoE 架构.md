# Dense 与 MoE 架构

> [!abstract] 一句话讲清楚
> Dense 模型每个 token 都要过全部参数，MoE 模型每次只"叫醒"一小部分专家。于是出现一个反直觉的现象：**MoE 的显存要按总参数装，速度却只按激活参数跑**——这是本地部署里最容易被误判的一笔账。

## 为什么重要

- 它是"**总参数 vs 激活参数**"这个混淆点的唯一解。看到新闻说"600B 模型"，再看到模型卡写"激活 30B"，普通人会以为 24G 显卡能跑。**不能**。
- 它直接影响三件事：
  1. **能不能跑**：取决于总参数（要全装进显存），不是激活参数。
  2. **跑多快**：主要取决于激活参数和带宽，MoE 通常快得多的。
  3. **怎么报价**：MoE 模型"看起来便宜（速度快）但很吃显存"，硬件成本结构不一样。
- 主流开源大模型已经出现明显的 MoE 化趋势，见 [[模型谱系 DeepSeek]]、[[模型谱系 Qwen]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 稠密模型 | Dense | 每个 token 计算时都要经过模型的**全部**参数。 | 大多数 7B/14B 都是稠密。简单、可预测。 |
| 混合专家 | MoE / Mixture of Experts | 把前馈网络拆成很多个"专家"，每个 token 只选几个专家算。 | 不是多个模型集成，是**同一个模型内部的路由**。 |
| 专家 | Expert | MoE 里一个独立的小前馈网络。 | 专家不是"法律专家/医学专家"，是训练自动分化出来的，不可解释。 |
| 路由 / 门控 | Router / Gate | 决定每个 token 该分给哪几个专家的小网络。 | 输出是"选谁 + 权重"，不是分类标签。 |
| 总参数量 | Total Params | 模型所有权重加起来的量。 | **显存按它算**。 |
| 激活参数量 | Active Params | 单个 token 前向时真正参与计算的参数量。 | **速度大致按它算**。 |
| 稀疏度 | Sparsity | 一次激活的专家占比，如 8 选 2 就是 1/4 稀疏。 | 稀疏度高不一定好，路由容易学不好。 |
| Top-k 路由 | Top-k Gating | 每个 token 选分数最高的 k 个专家。 | k 常见是 2 左右，不是越多越好。 |
| 负载不均衡 | Load Imbalance | 有的专家被挤爆、有的闲着。 | 会导致部分卡忙死、部分卡闲死，是 MoE 训练和推理的老问题。 |
| 专家并行 | Expert Parallelism | 把不同专家放到不同显卡上。 | 本地单卡部署基本用不上，但决定了 MoE 大模型为什么需要多卡。 |
| 容量因子 | Capacity Factor | 每个专家最多接多少 token 的上限。 | 设小了会丢 token，设大了浪费显存。 |

## 原理与机制

### 直觉：大医院分诊

- **Dense 模型**像只有一位全科医生：每个病人（token）都找他，他什么都会，但人一多就排队。他有多大本事，就要占多大诊室（参数全用）。
- **MoE 模型**像大医院：有几十个专科医生（专家），门口有个**分诊台**（路由）。每个病人只被分给其中 2 个医生。
  - 好处：单个病人等待时间短（只算 2 个专家），医院能雇很多医生（总参数大）。
  - 代价：**整栋楼得盖得下所有专科诊室**（总参数全要装进显存），哪怕今天只用了两个。

### MoE 里到底替换了什么

现代 MoE 基本只把**前馈网络（FFN）**换成多个专家，注意力部分还是共享的。

一层 MoE 的计算逻辑：

1. 每个 token 送进路由网络；
2. 路由算出"最该去的 k 个专家"和各自权重；
3. 这个 token 的向量被送进这 k 个专家，各自算一遍；
4. 结果按路由权重加权相加。

所以：

- **总参数量** = 共享部分（注意力等）+ 全部专家；
- **激活参数量** ≈ 共享部分 + k 个专家。

### 一个具体的算术（量级示意）

假设一个模型有 64 个专家层，每层 8 个专家、每次选 2 个：

- 如果所有专家都算进去，总参数可能是"几百 B"量级；
- 单 token 只激活 2/8 的专家，实际计算量对应的参数可能是"几十 B"量级。

于是你在模型卡上会看到类似这样的表述：**"总参数 XXX B，激活参数 YY B"**。这不是营销话术，是 MoE 的真实结构。

> [!warning] 本地部署的核心结论
> **显存按总参数算，速度按激活参数算。**
> - 24G 显卡装不下"总参数 100B+"的 MoE 权重（就算 4bit 也吃紧甚至装不下）；
> - 但如果装得下，它的出字速度可能接近一个"激活 10B~30B"的稠密模型。
> - 所以 MoE 是"**多卡/大显存 + 追速度**"的解法，不是"小显存跑大模型"的魔法。

### 为什么 MoE 省算力、不省显存

| 资源 | Dense | MoE | 结论 |
|---|---|---|---|
| 权重显存 | 按总参数 | 按总参数（**一样要全装**） | 不省 |
| 每 token 计算量 | 按全部参数 | 按激活参数 | **省很多** |
| KV Cache | 和结构有关，与 MoE 无直接关系 | 和结构有关 | 基本一样 |
| 通信成本 | 低 | 高（token 要路由到不同专家，多卡时跨卡） | 单卡省事，多卡复杂 |

### 路由是怎么学出来的

路由不是人工指定的规则，是训练时**和模型一起学**的：

- 路由器输出"每个专家给我这个 token 打几分"，取分数高的 k 个；
- 训练时为了让专家分工，会加"负载均衡"的辅助损失，防止所有 token 都挤到一个专家；
- 结果是专家会自动分化出某种分工，但**没人能准确解释每个专家到底负责什么**。

这带来一个工程事实：**MoE 的专家不能单独拿掉或替换**，它不是一个"专家库"，是一个耦合的整体。

## 分类与对比

### Dense vs MoE 总表

| 维度 | Dense 稠密 | MoE 稀疏 |
|---|---|---|
| 执行参数 | 全部 | 一小部分专家 |
| 总参数 vs 激活参数 | 相等 | 差距可达数倍到十倍量级 |
| 权重显存 | 按参数量线性 | 按**总**参数量线性 |
| 计算速度 | 参数量越大越慢 | 相对快（按激活量） |
| 部署复杂度 | 低，单卡友好 | 高，越大越需要多卡 |
| 量化友好度 | 好（常规量化） | 需要注意：专家参数少时对量化更敏感 |
| 可解释/可裁剪 | 结构规整 | 专家难以单独分析 |
| 典型适用 | 消费级显卡、单机部署、边缘 | 数据中心、多卡、追速度又追能力的场景 |

### 常见变体

| 变体 | 说明 | 备注 |
|---|---|---|
| 粗粒度专家（每层多个完整 FFN） | 最常见 | DeepSeek 系、Qwen 系部分型号都用这种 |
| 细粒度专家 + 共享专家 | 专家更多、每次激活更多小专家，另设始终激活的共享专家 | 目的是让共享知识不用重复存在每个专家里 |
| 逐层稀疏（部分层 MoE、部分层稠密） | 节省总参数 | 结构更复杂，看模型卡为准 |

具体型号的专家数量、激活数量一律**以官方模型卡为准**，不要背数字。

## 决策点

- **岔路口 1：小显存（8G~16G）该选 Dense 还是 MoE？**
  - 判断依据：显存能不能装下**总参数**。
  - 推荐选择：**Dense**。小显存下 MoE 大概率装不下，勉强装下也没有余量给 KV Cache。
  - 代价：同等速度下，能力上限比不过大 MoE，但这是硬件决定的。

- **岔路口 2：24G~48G 单卡，看到 MoE 要不要试？**
  - 判断依据：总参数量 × 量化字节数 + KV 余量 是否 ≤ 显存。
  - 推荐选择：**先算账再试**。总参数折算后如果占掉 80% 以上显存，单卡跑长上下文会很难受。
  - 代价：算错就白折腾一天。

- **岔路口 3：客户要"又聪明又快"，预算有限**
  - 判断依据：是单机交付还是集中式服务。
  - 推荐选择：单机交付 → 中等 Dense + 好量化；集中服务（有多卡）→ MoE 性价比更高。
  - 代价：MoE 在多卡下要处理专家并行和通信，工程复杂度和交付风险都高，报价要覆盖。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| num_experts | 每层专家总数 | 调大 → 总参数和显存涨，容量上限高 | 几十个量级（看模型） |
| top_k | 每个 token 激活几个专家 | 调大 → 算力涨、质量可能升；调小 → 省算力 | 常见 2 左右 |
| 专家中间维度 | 单个专家的大小 | 决定总参数和单专家计算量 | 比稠密 FFN 小很多 |
| capacity_factor | 每专家接单上限 | 太小丢 token、太大浪费 | 推理时通常可调，训练更敏感 |
| 共享专家数 | 始终激活的专家数量 | 提升通用知识，增加固定开销 | 0 或 1~2 |
| 量化档位 | MoE 权重压缩程度 | 压太狠，小专家更容易失真 | 建议比同规模 Dense 更保守 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 看到"激活 30B"就以为 24G 卡能跑 | 只算了激活参数，忘权重按总参数装 | 一律用**总参数**算权重显存 |
| 用 MoE 的"激活参数"去对比 Dense 的参数量 | 速度可以这么比，能力不能这么比 | 能力看总参数和训练数据，速度看激活参数 |
| 以为 MoE 是"多个模型投票" | 不是集成，是单模型内部路由 | 别按 ensemble 理解，显存和调度都不一样 |
| 量化 MoE 后发现质量掉得比 Dense 狠 | 每个专家参数少，低比特更容易伤到它 | 用更保守的量化档位，或选参数更多的专家结构 |
| 多卡部署 MoE 通信拖慢速度 | token 要跨卡路由到专家 | 评估互联带宽，必要时限制专家并行度 |
| 以为"专家多 = 某个专家专精某领域" | 专家分工不可解释 | 别拿专家做业务宣称，无法保证 |
| 小显存硬上量化 MoE，长上下文必崩 | 权重已占满，KV Cache 没地方 | 降低上下文、限制并发，或换 Dense |

## 案例拆解：总参数一样的两个模型，为什么一个更吃显存

假设有 A、B 两个模型，**总参数都在 100B 量级**，但 A 是稠密（Dense），B 是稀疏（MoE，比如每次只激活 10%~15% 的参数）。很多人第一反应是"总参数一样，显存应该一样"，对了一半。逐项拆：

| 项目 | A：Dense 100B | B：MoE 100B（约 12B 激活） | 结论 |
|---|---|---|---|
| 权重显存 | 100B × 每参数字节 | 100B × 每参数字节（**所有专家都要加载**） | 差不多，MoE 甚至略多（路由参数） |
| 单 token 计算量 | 按 100B 算 | 按 12B 激活算 | MoE 快好几倍 |
| 生成速度 | 慢 | 快 | MoE 的卖点 |
| 显存带宽压力 | 大 | 大（还是要读全部权重） | 两者都不轻松 |
| 上下文 KV Cache | 按层数和头数算 | 和专家数无关，只和注意力结构有关 | 大体相当 |

所以真实情况是：

- **MoE 省的是算力和时间，不省权重显存**。想在 24G 卡上跑总参数几百 B 的 MoE，一样跑不动，"激活参数只有 30B"救不了你。
- **MoE 对显存带宽更敏感**：每生成一个 token 都要把选中的专家从显存搬到计算单元，如果显存不够、要 offload 到内存，速度会掉得很难看。
- **批处理时 MoE 更划算**：不同请求可能激活不同专家，显存里的专家都能用上；而 Dense 模型算力是固定的。

给客户讲的一句话版本：**"MoE 是'知识很多、每次只用一部分'，所以它快；但知识本身还是要占地方，显存不能按激活参数打折。"**

## 三个常被问倒的问题

**问题一：MoE 的"激活参数"能不能当成模型大小？**

不能当"显存大小"，可以当"算力大小"。报硬件需求时按总参数算显存，报速度时按激活参数估。

**问题二：MoE 效果一定比同激活参数的 Dense 好？**

通常更好，因为它总知识量更大；但不绝对——路由没训好、专家利用率不均时会打折。**看评测不如看自己业务的实测**。

**问题三：MoE 微调是不是更难？**

是。MoE 的专家路由对数据分布敏感，微调容易把路由带偏（有的专家被冷落），所以微调成本比 Dense 高，小样本微调尤其要小心。这也是很多团队"用 MoE 的成品，微调用 Dense 的小模型"的原因。

## 自检问题参考答案

> [!success]- 1. 用"医院分诊"怎么讲清 MoE 的路由机制？
> **Dense 像只有一位全科医生**：每个病人（token）都找他，他什么都会，但人一多就排队；他有多大本事，就得占多大诊室（参数全用上）。
> **MoE 像大医院**：有几十个专科医生（专家），门口一个分诊台（路由）。分诊台给每个病人打分，只把他分给分数最高的 k 个医生，看完再按权重汇总结果。
> 好处是单个病人等待短（只算 k 个专家），医院还能雇很多医生（总参数大）；代价是**整栋楼得盖得下所有诊室**——所有专家权重都要装进显存，哪怕今天只用到两个。

> [!success]- 2. 总参数量和激活参数量分别决定什么？
> **总参数决定"能不能跑"**：权重显存按总参数算，所有专家都得加载进显存。
> **激活参数决定"跑多快"**：单个 token 前向时只算 k 个专家，计算量按激活部分算。
> 所以模型卡上"总参数几百 B、激活几十 B"不是营销话术，是真实结构；报硬件需求时按总参数，报速度时按激活参数，两者不能混用。

> [!success]- 3. 为什么 MoE 省算力却不省显存？
> 省算力是因为每个 token 只激活一小部分专家，计算量只跟激活参数走。
> 不省显存是因为**所有专家权重都必须加载**——路由可能把任何一个 token 分给任何一个专家，缺一个就出错，所以权重显存还是按总参数算。
> 另外 KV Cache 和专家数没直接关系，只看注意力的层数和头数，所以 MoE 在缓存这块也不占便宜。

> [!success]- 4. 有人问"480G 显存能跑多大 MoE"，先问什么？
> 先问**总参数是多少**，不是激活参数。然后按 `总参数 × 每参数字节 + KV 余量 + 框架开销 ≤ 显存` 去算。
> 量化档位可以放宽一点，但 MoE 对低比特更敏感，建议比同规模 Dense 更保守，别一上来就按最狠的档折算。
> 最后留出长上下文和并发的余量：权重占到 80% 以上，单卡跑长上下文会很难受，勉强能启动不等于能交付。

> [!success]- 5. MoE 量化为什么比 Dense 更需要小心？
> 因为 MoE 里每个专家都比稠密 FFN 小很多，参数越少，低比特量化越容易伤到它；路由那部分参数同样敏感，一压就可能选错专家。
> 表现是"同样量化档，MoE 掉质量比 Dense 狠"，尤其是细粒度专家结构。
> 对策是用更保守的量化档（比如高位混合量化），而且量化后一定要拿业务用例复测——只看困惑度会掩盖问题。

> [!success]- 6. 专家并行给多卡部署带来什么复杂度？
> 专家并行是把不同专家放到不同显卡上。每个 token 被路由到"别的卡上的专家"时，就得跨卡传数据，于是多了通信开销。
> 再加上负载不均衡——有的专家被挤爆、有的闲着——就会出现部分卡忙死、部分卡闲死的局面，整体速度被最慢的那张卡拖住。
> 本地单卡部署基本用不到专家并行，但这正是"MoE 大模型为什么需要多卡"的原因；交付时要评估互联带宽（PCIe 和高速互联差很多），必要时限制专家并行度。

> [!success]- 7. 小显存用户该选 Dense 还是 MoE？
> 8G~16G 选 **Dense**。原因是 MoE 的权重按总参数全装，小显存大概率装不下；就算勉强塞进权重，也没余量留给 KV Cache 和并发，长上下文一开就崩。
> 24G~48G 单卡看到 MoE 可以先算账：总参数折算后如果占掉 80% 以上显存，就要谨慎。
> 代价要认：同等速度下，Dense 的能力上限比不过大 MoE，但这是硬件决定的，不是选型技巧能绕过的。

> [!success]- 8. MoE 的"专家"是可插拔的知识库吗？
> 不是。专家是训练时随路由**自动分化**出来的，无人能准确解释某个专家到底负责什么；它不像人一样分"法律专家/医学专家"。
> 而且专家不能单独拿掉或替换——它不是一个专家库，而是一个耦合的整体，缺一个路由就会出错。
> 所以别拿"我们的专家专门处理你这类业务"对外宣称，无法验证；要提升特定业务能力，走微调或 RAG 链路更靠谱。

## 交付视角（对客户怎么讲）

- **客户看到"超大参数模型免费开源"很兴奋**：直接给一句话——"**总参数决定它要占多少显存，激活参数只决定它跑多快。你这个显存装不下它的总参数，就一切免谈。**"这句话能防止 90% 的无效折腾。
- **客户问"为什么 MoE 便宜"**：不是模型便宜，是**单位算力更划算**——同样硬件，它每次计算用到的参数少，出字快。但硬件门槛（显存总量）没有下降。
- **报价要点**：MoE 交付的风险主要在"显存刚好够 → 长上下文或并发一上来就 OOM"。所以报价时要么留足显存余量（硬件加钱），要么明确写清楚"上下文和并发上限"。
- **别承诺**：不要说"MoE 的某个专家专门处理你这类业务"，无法验证，属于虚假宣称。要说的是"整体模型能力"和"实测效果"。

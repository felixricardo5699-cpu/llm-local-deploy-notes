# 采样参数与解码策略

> [!abstract] 一句话讲清楚
> 模型每一步只输出"每个候选词的概率"，**怎么从这堆概率里挑一个词**，就是解码策略。temperature / top_p / top_k 都是在这个"挑"的动作上加约束——参数调对了，同一个模型表现能差出一大截。

## 为什么重要

- 这是**最便宜的效果调优**：不换模型、不加显卡、不改代码，只改三个参数，客户满意度可能就上来了。
- 交付里高频的"玄学"问题，一半以上出在这里：
  - "回答太死板，像机器人"→ 采样太保守；
  - "回答开始胡说、术语乱造"→ 采样太激进；
  - "让它输出 JSON，老是多个逗号或多句废话"→ 该用低温度 + 严格格式约束；
  - "同样的问题每次答案都不一样，客服不认"→ 这是参数导致的不确定性，要固定或降低。
- 解释清楚这些参数，你就从"会装环境的人"变成"会调系统的人"。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 逻辑值 | Logits | 模型给词表里每个候选词打的"原始分"，还没变成概率。 | 分数不是概率，要过 softmax。 |
| 概率分布 | Probability Distribution | 所有候选词的概率，加起来等于 1。 | 大模型每步都要做一次这个选择。 |
| 温度 | temperature | 控制"随机程度"的旋钮：低=保守选最可能的，高=敢选冷门词。 | 不是"创造力开关"这么简单，太高会开始胡编。 |
| 核采样 | top_p / nucleus sampling | 只从"累计概率达到 p 的那一小撮词"里挑。 | 和 top_k 不同：top_p 是动态数量，top_k 是固定数量。 |
| 最大 k 采样 | top_k | 只保留概率最高的 k 个词，其余丢弃。 | k 太大会把太离谱的词放回来。 |
| 重复惩罚 | repeat_penalty / presence penalty | 压一压"已经说过的话"，防止复读。 | 调太高会导致句子不连贯、逻辑断裂。 |
| 频率惩罚 | frequency_penalty | 按词出现次数惩罚，越常用越压。 | 和存在惩罚不同：存在惩罚只看"出现过没有"。 |
| 贪心解码 | Greedy Decoding | 每步都选概率最高的一个词，完全不随机。 | 结果稳定但容易重复、死板。 |
| 束搜索 | Beam Search | 同时保留几条候选路径，最后选整体概率最高的。 | 翻译类常用；聊天类现在很少用，太慢太"稳"。 |
| 随机采样 | Sampling | 按概率随机抽，temperature/top_p 都是在调这个。 | 聊天默认方式。 |
| 投机解码 | Speculative Decoding | 用小模型"抢答"多个词，大模型批量验证，速度提升明显。 | 不改变输出分布（理论上），属于提速技术。 |
| 停止符 | Stop / EOS | 告诉模型"到这儿别说了"的特殊标记。 | 输出被截断经常是 max_tokens 到顶，不是模型出错。 |

## 原理与机制

### 每一步都在做选择题

模型前向一次，得到词表里**每个 token 的分数**（logits，几万到十几万个候选）。然后：

1. 分数 ÷ temperature → 调整"陡峭程度"；
2. 只看 top_k 或 top_p 圈定的候选；
3. 剩下的重新归一化成概率；
4. 按概率抽一个词；
5. 这个词接回输入，重复。

**关键直觉**：

- temperature 调的是"概率分布有多平"：低 → 尖（几乎只选第一），高 → 平（冷门也有机会）。
- top_p / top_k 调的是"候选范围有多大"：砍掉长尾。
- 两者叠加：**范围先砍，再在范围内按温度抽**。

### temperature 到底怎么起作用

| temperature | 效果 | 适用 |
|---|---|---|
| 接近 0 | 几乎等于贪心，结果稳定、可复现 | 抽取、分类、格式化输出、代码 |
| 0.3~0.7 | 稳中带一点变化 | 客服问答、RAG 回答、大多数业务 |
| 0.7~1.0 | 明显多样 | 创意写作、头脑风暴 |
| 大于 1 | 高风险随机 | 一般不要，容易胡言乱语 |

> [!warning] 常见误解
> "temperature 越高模型越聪明"——不对。它只是让模型更愿意选低概率词。**能力上限是模型本身，温度只改变"采样风格"。**

### top_p 和 top_k 怎么配合

- **top_p = 0.9**：把候选按概率从高到低排，累计到 90% 就截断。候选数量**随分布变化**（模型很确定时只有几个词，不确定时几十个）。
- **top_k = 40**：永远只留概率最高的 40 个。候选数量**固定**。

实践建议：

- **一般只调一个**，另一个设成"不限制"（常见做法是 top_k=0 或很大，top_p=0.9 左右）。
- 两个都收得很紧 → 回答会很死板，甚至重复。
- 两个都放得很开 + 高温度 → 容易跑偏。

### 重复惩罚：别调过头

模型有时候会陷入复读（"这个方案很好，这个方案很好，这个方案很好"）。

- **repeat_penalty**（llama.cpp/Ollama 常用）：对已经出现过的 token 的概率直接除以惩罚系数。1.0 是不惩罚，1.1~1.2 是常用范围。
- **presence_penalty / frequency_penalty**（OpenAI 风格）：前者看"出现过没有"，后者看"出现多少次"。

调过头的表现：**句子开始前言不搭后语、专有名词被换掉、代码变量名被乱改**。这是新手最容易踩的坑——为了"不重复"把惩罚拉到 1.5，结果模型连人名都说不全了。

### 贪心、束搜索、采样：三种挑法

| 策略 | 怎么做 | 优点 | 缺点 | 用在哪 |
|---|---|---|---|---|
| 贪心 | 每步选概率最高的 | 快、稳定 | 死板、易重复 | 抽取、格式化、确定性任务 |
| 束搜索 | 同时保留 N 条路径，最后选总概率最高的 | 整体更优、稳 | 慢、N 倍显存、聊天显得"套路" | 翻译、摘要（传统方案） |
| 采样 | 按概率抽 | 自然、多样 | 不确定、可能跑偏 | 聊天、写作、Agent |

现在的主流是**采样**，聊天/Agent 场景极少用束搜索，因为它慢而且答案"太平均"。

### 投机解码：用"抢答"提速

思路很聪明：

1. 一个**小模型**（草稿模型）先快速猜出后面 5~8 个词；
2. **大模型**一次性并行验证这几个词；
3. 猜对的部分直接采纳，猜错的位置从那里开始重来。

收益：

- 大模型原本要跑 8 次，现在可能只要 1~2 次 → 出字速度明显提升；
- 理论上输出分布不变（质量不掉），所以是"纯赚"的提速手段；
- 代价：要额外加载一个小模型（多占显存），且小模型和大模型"风格"越接近收益越大。

这也是"为什么有的服务出字特别快"的技术来源之一，见 [[推理性能指标与调优]]。

## 分类与对比

### 任务 → 参数组合（经验值）

| 任务类型 | temperature | top_p | 说明 |
|---|---|---|---|
| 数据抽取 / 分类 | 0~0.2 | 0.8~1.0 | 要稳定可复现，几乎别随机 |
| JSON / 结构化输出 | 0~0.3 | 0.9 | 配格式约束，低温最稳 |
| 代码生成 | 0.1~0.3 | 0.9~0.95 | 稍高一点可以多思路，但别太高 |
| RAG 问答 | 0.2~0.5 | 0.9 | 要贴合资料，不要自由发挥 |
| 客服 / 业务对话 | 0.5~0.7 | 0.9 | 自然又不跑偏 |
| 创意写作 | 0.8~1.0 | 0.95 | 追求多样 |
| 头脑风暴 | 0.9~1.1 | 0.95~1.0 | 允许发散，但要人工筛 |

> 以上是起点，不是标准答案。**必须用业务样例题实测**，不同模型对温度的敏感度差别很大。

### "确定性"的两个档位

| 想要的效果 | 做法 | 代价 |
|---|---|---|
| 尽量可复现 | temperature=0、固定 seed（引擎支持的话） | 永远同一句回答，没有变化 |
| 可复现但允许少量多样 | temperature 0.2~0.3 + 固定 prompt | 仍然有随机性，但幅度小 |

交付里如果客户说"每次回答不一样不行"，给他 temperature=0 或低温度方案，并说明"完全固定会牺牲自然度"。

## 决策点

- **岔路口 1：回答不稳定 / 每次差异太大**
  - 判断依据：任务是否要求可复现。
  - 推荐选择：**降低 temperature（0.2 左右）+ 收紧 top_p（0.8~0.9）**，固定提示词和参数。
  - 代价：回答变"标准化"，可能显得机械。

- **岔路口 2：输出格式不听话（JSON 缺括号、多解释）**
  - 判断依据：只是格式问题，还是内容理解问题。
  - 推荐选择：**temperature 降到 0~0.2** + 明确"只输出 JSON、不要解释" + 用引擎的结构化输出/JSON mode（支持的话）。
  - 代价：低温偶尔会让复杂推理变弱，必要时拆成两步（先推理再格式化）。

- **岔路口 3：回答开始胡说、术语乱造**
  - 判断依据：看 temperature 和 repeat_penalty 是不是被调高了。
  - 推荐选择：**先降 temperature 到 0.5 以下**；repeat_penalty 回落到 1.1 左右；还不稳考虑升量化档位或换大模型。
  - 代价：多样性下降。

- **岔路口 4：客户嫌慢，想提速**
  - 判断依据：是首字慢还是吐字慢。
  - 推荐选择：吐字慢 → 考虑投机解码、更小模型、更低量化；首字慢 → 压缩提示词、开 Prompt Caching。别盲目调采样参数，它对速度几乎没帮助。
  - 代价：投机解码要多占显存。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| temperature | 随机程度 | 调大 → 多样、易跑偏；调小 → 稳定、易死板 | 0~1.0，业务常用 0.3~0.7 |
| top_p | 候选累计概率范围 | 调小 → 候选少、保守；调大 → 候选多、发散 | 0.8~0.95 |
| top_k | 固定保留前 k 个 | 调小 → 保守；调大 → 放回长尾怪词 | 0（不限制）或 20~50 |
| repeat_penalty | 惩罚已出现的词 | 调大 → 少复读但可能不连贯 | 1.0~1.2 |
| presence_penalty | 惩罚"出现过"的词 | 调大 → 更愿意换话题 | 0~1.0，常用 0~0.5 |
| frequency_penalty | 按出现次数惩罚 | 调大 → 更少重复用词 | 0~1.0，常用 0~0.3 |
| max_tokens | 最多生成多少 token | 调大 → 更完整但更慢更贵 | 按任务定，如 512~4096 |
| stop | 停止符列表 | 命中就停 | 自定义结束标记，如 `"\n\n"` |
| seed | 随机种子 | 固定后可复现 | 引擎支持时固定 |
| min_p（部分引擎） | 按最高概率的比例过滤 | 比 top_p 更稳的一种过滤 | 0.05~0.1 量级 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 把 temperature 拉到 1.5 想要"更聪明" | 高温只是更随机，不是更强 | 回到 0.5~0.8；能力问题换模型或上 RAG |
| 同时收 top_p 和 top_k，回答变得死板 | 两重限制叠加，候选被砍太狠 | 只留一个限制，另一个放开 |
| 为了不复读，repeat_penalty 拉到 1.5+ | 惩罚过强，破坏连贯性 | 回到 1.1 左右，必要时换模型 |
| 输出 JSON 老是不完整 | 温度高 + 没做格式约束 | 降温 + 明确指令 + 结构化输出 |
| 以为调参数能提升事实准确率 | 采样参数不改变知识 | 事实问题靠 RAG/提示词/换模型 |
| 同一 prompt 每次结果不同，就怀疑模型坏了 | 采样本身就是随机的 | 说明机制，固定 temperature/seed 达成可复现 |
| 用束搜索做聊天 | 慢、答案套路化 | 聊天用采样；束搜索留给翻译类 |
| 输出被截断，以为是模型问题 | 是 max_tokens 到上限 | 调大 max_tokens 或让回答更简洁 |

## 自检问题参考答案

> [!success]- 1. temperature 调大到底改变了什么，又不能改变什么？
> 它是在 softmax 之前给分数做一次除法：温度低，分布变"尖"，模型几乎只挑概率最高的词；温度高，分布变"平"，冷门词也有机会被选中。所以它改变的是**随机程度和采样风格**。
> 它**改变不了能力上限**：模型本来不知道的事实、本来不会的推理，调温度也变不出来；温度太高反而开始胡编乱造。
> 所以别指望"拉高温让它变聪明"，能力问题要靠 RAG、提示词或换模型解决，温度只负责表达风格。

> [!success]- 2. top_p 和 top_k 的区别是什么？
> **top_p** 是按概率从高到低累加，累计到 p（比如 0.9）就截断，候选数量是**动态**的：模型很确定时只剩几个词，不确定时能留几十个。
> **top_k** 是永远只保留概率最高的 k 个（比如 40），候选数量**固定**，不随分布变化。
> 实践上一般只调一个、另一个放开：常见做法是 `top_k=0`（不限制）配 `top_p=0.9` 左右；两个都收得很紧，回答会死板甚至重复。

> [!success]- 3. "抽取任务"和"创意写作"分别给什么参数？
> 抽取、分类这类任务要稳定可复现：temperature 0~0.2，top_p 0.8~1.0；JSON/结构化输出用 0~0.3，再配明确的格式约束或结构化输出模式。
> 创意写作要多样：temperature 0.8~1.0，top_p 0.95；头脑风暴可以到 0.9~1.1，但要人工筛。
> RAG 问答和客服对话落在中间，大致 0.2~0.7。这些只是**起点**，不同模型对温度敏感度差别很大，必须拿业务样例题实测。

> [!success]- 4. repeat_penalty 调过头会有什么症状？
> 1.0 是不惩罚，常用范围 1.1~1.2。拉到 1.5 以上，惩罚过强，模型会开始"为了不重复而绕开必要的词"。
> 表现是：句子前言不搭后语、专有名词被换成同义词、代码里的变量名被乱改，人名地名都说不全。
> 对策是回落到 1.1 左右；如果还是复读，优先考虑换模型或改提示词，别继续加惩罚。

> [!success]- 5. 贪心、束搜索、采样三种策略各适合什么？
> **贪心**每步选概率最高的那个词：快、稳定，但死板、容易重复，适合抽取、格式化和要求确定性的任务。
> **束搜索**同时保留 N 条候选路径，最后选整体概率最高的：整体更优更稳，但慢、要 N 倍显存，聊天会显得套路化，传统上用于翻译、摘要。
> **采样**按概率随机抽：自然、多样，但不确定、可能跑偏，是聊天、写作、Agent 的主流选择。现在聊天场景极少用束搜索。

> [!success]- 6. 投机解码为什么能提速，代价是什么？
> 思路是"小模型抢答、大模型批改"：先用一个小的草稿模型快速猜出后面 5~8 个词，再让大模型一次性并行验证这几个词，猜对的直接采纳，猜错的位置从那里重来。
> 大模型原本要跑 8 次前向，现在可能只要 1~2 次，所以出字速度明显提升；理论上输出分布不变、质量不掉，属于"纯赚"的提速手段。
> 代价是要额外加载一个小模型、多占显存，而且草稿模型和大模型的"风格"越接近，命中率越高、收益越大。

> [!success]- 7. 客户要求"每次回答一样"，怎么配、代价是什么？
> 配 `temperature=0`（或 0~0.2 的低温度），能固定 seed 的引擎再把 seed 固定，同时固定提示词和所有采样参数。
> 代价是**完全固定就没有变化**，永远同一句回答，遇到表述稍变的问题也可能答得很机械；想要"可复现但允许少量多样"，可以用 0.2~0.3，仍会有小幅随机。
> 跟客户要把这句话讲明白："完全可复现和自然表达是有取舍的"，然后把最终参数写进交付文档。

> [!success]- 8. 怎么判断"回答不好"是采样问题还是模型/提示词问题？
> 先看症状：回答死板、重复 → 采样太保守（温度低、top 收太紧、惩罚过头）；胡说、术语乱造 → 采样太激进或惩罚太高；JSON 不完整 → 温度偏高且没做格式约束；同一问题答案飘 → 采样本身随机。
> 但**事实错误、知识不足、推理错误**不是采样问题——采样参数不改变知识，这类只能靠 RAG、提示词组织或换模型解决。
> 判断方法是拿同一批问题、固定提示词，只改参数跑对比：参数能改善的是表达稳定性，改不动就别在参数上继续折腾。

## 交付视角（对客户怎么讲）

- **客户问"为什么同样的问题答案不一样"**：用"**模型是按概率抽词，不是查表；温度调低就会稳定，调到 0 几乎每次都一样**"来解释。别用"AI 有随机性"这种空话。
- **客户要"稳、准、少废话"**：给一组具体的默认值（比如 temperature 0.3、top_p 0.9），并说明这是给他们场景调的，写进交付文档。比"我调好了"有说服力。
- **客户要"有创意"**：明确告知代价——"**温度调高会更发散，但事实准确性会下降**，建议只在营销文案这类场景用"。
- **报价相关**：参数调优包含在"服务调优"工时里，通常半天到一天。**不要把它说成"随便点两下"**，它需要拿业务样本跑对比、定基线，这是专业价值。
- **别承诺**：不要说"调这几个参数准确率能到 99%"。参数只能改善表达风格和稳定性，事实准确性来自资料、提示词和模型能力。

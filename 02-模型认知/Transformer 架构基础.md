# Transformer 架构基础

> [!abstract] 一句话讲清楚
> 今天几乎所有大模型都是"同一种工厂流水线"：把文字切成 token，变成向量，过几十层"注意力 + 前馈网络"，最后算出下一个 token 的概率。理解这条流水线，才知道显存花在哪、速度卡在哪。

## 为什么重要

- 这是**整层的地基**：[[Attention 与 KV Cache]]、[[Dense 与 MoE 架构]]、[[参数量与显存估算]] 全部建立在它之上。跳过这篇直接看显存公式，你只会背数不会推导。
- 不知道它，你就解释不了两个最常见的现象：
  - 为什么模型**输出是一个字一个字蹦出来的**（自回归生成）——这决定了"生成慢"是天生结构造成的，不全是显卡不行。
  - 为什么**输入提示词越长、回答越慢**——这跟注意力机制和 KV Cache 直接相关。
- 交付场景：客户嫌"回答太慢"，你得能分清是**首 token 慢**（提示词处理，prefill）还是**吐字慢**（解码，decode）。这两个的优化方向完全相反，见 [[推理性能指标与调优]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| Token | Token | 模型眼里的"字块"。可能是一个词、半个词、一个标点，中文里经常一个字或两个字。 | 不是"字"也不是"单词"；1 个 token 大约 0.6~0.75 个英文单词、1~1.5 个汉字，以实际分词器为准。 |
| 分词器 | Tokenizer / BPE | 把人类文字切成 token 的规则表。不同模型的表不一样，切法也不一样。 | 换模型就要换分词器，token 数量会变，"同样的文本不同模型算的上下文不一样长"。 |
| 词嵌入 | Embedding | 把每个 token 变成一串数字（向量），让模型能计算。 | 这里的 Embedding 是模型内部的，别和 [[Embedding 与向量数据库]] 里做检索的 embedding 混为一谈。 |
| 隐层维度 | d_model / hidden size | 向量有多"宽"，比如 4096 维。宽度决定模型的表达能力。 | 不是参数量本身；宽度、层数、FFN 倍数一起决定参数量。 |
| 层 | Layer / Block | 一层 = 一次注意力 + 一次前馈网络。模型"深度"就是叠加了多少层。 | "层数多"不等于"效果一定好"，但通常更贵、更慢。 |
| 注意力 | Attention / Self-Attention | 让每个 token 去看它前面所有 token，决定"该关注谁"。 | 全称细节见 [[Attention 与 KV Cache]]；它不是"注意力资源分配"这种玄学。 |
| 前馈网络 | FFN / MLP | 每层里那个"变宽再变窄"的小网络，负责对信息做加工。 | 它占模型参数量的**大头**（常在一半以上），MoE 就是把这里拆成多个专家。 |
| 残差连接 | Residual | 每层算完的东西"加到"原来输入上，而不是替换它。 | 没有残差，几十层根本训不动；它保证了信息有一条"高速公路"直通。 |
| 层归一化 | LayerNorm / RMSNorm | 每层前后把数值范围"捋平"，防止越算越离谱。 | 现代模型多用 RMSNorm（更省算力）。别和 BatchNorm 混。 |
| 自回归 | Autoregressive | 一次只生成一个 token，然后把它接到输入末尾，再生成下一个。 | 这是"吐字慢"的根源：N 个 token 就要跑 N 次前向。 |
| 逻辑值 | Logits | 模型对词表里每个 token 打的"原始分数"，还没变成概率。 | 要过 softmax 才是概率；采样参数就是在处理 logits，见 [[采样参数与解码策略]]。 |
| 预训练 / 微调 | Pre-train / Fine-tune | 预训练是"读海量文本学语言"，微调是"在预训练基础上针对任务再训一点"。 | 不是同一种训练，成本差好几个数量级，见 [[微调决策与 RAG 取舍]]。 |

## 原理与机制

### 第一步：把文字切成 token

模型不认识汉字，只认识 token ID。分词器负责这层翻译。

- **直觉**：像把一句话拆成乐高积木，每块积木有编号。
- **后果**：**同样的文本，不同模型 token 数不同**。算上下文、算显存、算 API 费用时，单位都是 token，不是字数。这是新手最容易踩的隐性成本。

### 第二步：每层都干两件事——通讯和计算

把一层想象成一个部门：

1. **注意力（通讯）**：每个 token 向前面所有 token "打电话"，汇总信息。谁相关就多听谁的。
2. **前馈网络（计算）**：拿到汇总信息后，每个 token 自己"闷头加工"一遍，变成一个更"懂事"的向量。

两者都套着**残差连接**（加工结果加到原输入上）和**层归一化**（把数值捋平）。所以公式长这样：

```
x = x + Attention(Norm(x))
x = x + FFN(Norm(x))
```

这两行就是所有现代大模型的骨架。重复 N 层，就得到"读懂上下文"的向量表示。

> [!tip] 为什么这么设计
> 注意力负责"横向串联信息"，FFN 负责"纵向抽象加工"。分工明确，而且两个模块都能高度并行计算——这正是 Transformer 能吃掉 GPU 算力的原因。

### 第三步：自回归生成——一次一个 token

模型不是"想好了一整段再吐出来"，而是：

```mermaid
flowchart LR
  A["输入：今天天气"] --> B["模型前向一次"]
  B --> C["算出下一个 token：真"]
  C --> D["拼回输入：今天天气真"]
  D --> E["再前向一次"]
  E --> F["算出：好"]
  F --> G["循环直到结束符"]
```

**关键结论**：

- 生成 500 个 token，就要做 500 次前向计算。**输出长度直接决定耗时**。
- 每次前向都要带着"之前的全部上下文"再算一遍——除非用 KV Cache 把算过的中间结果缓存起来，这就是 [[Attention 与 KV Cache]] 存在的原因。
- 生成是**严格串行**的，GPU 利用率其实不高。这就是为什么"聊天式生成"比"一次性处理一堆文本"慢得多。

### 第四步：训练和推理是两回事

| 维度 | 训练（Training） | 推理（Inference） |
|---|---|---|
| 目标 | 调整参数，让它学会预测下一个 token | 参数固定，只做预测 |
| 数据类型 | 一次要算一批序列，双向并行 | 一次一个 token 往后蹦 |
| 显存花在哪 | 权重 + 梯度 + 优化器状态 + 激活（**大头是后三项**） | 权重 + KV Cache + 少量激活 |
| 显存倍率 | 粗算约为权重的 **4~8 倍**（全参微调） | 粗算约为权重的 **1.2~1.5 倍**（不含长上下文） |
| 谁能干 | 需要 A100/H100 级别和大钱 | 消费级显卡就能跑 |

> [!warning] 这是交付里最容易说错的一句话
> "这个模型 7B，显存 14G 就够"——这说的是**推理**。如果客户问"我能不能自己微调"，答案要另算，见 [[LoRA 与 QLoRA 原理]]。

## 分类与对比

按结构分三类，但今天主流是同一类：

| 类型 | 代表 | 擅长 | 现状 |
|---|---|---|---|
| Encoder-only | BERT 那一代 | 理解类任务（分类、抽取、向量） | 大模型时代基本退出主舞台，但 [[Embedding 与向量数据库]] 还在用它 |
| Encoder-Decoder | T5 那一代 | 翻译、摘要 | 部分场景仍在用 |
| **Decoder-only** | 今天几乎所有开源/闭源大模型 | 生成、对话、推理 | **事实标准** |

为什么 Decoder-only 赢了：

1. 训练目标统一：都是"预测下一个词"，数据可以无限堆。
2. 做成了"通用接口"：所有任务都能转成续写问题。
3. 工程效率高：结构单一，易于扩展和优化。

按规模分（量级，不是精确值）：

| 量级 | 参数量级 | 典型用途 | 单卡可行？ |
|---|---|---|---|
| 小 | 1B~4B | 分类、改写、端侧、草稿模型 | 8G~12G 可以 |
| 中 | 7B~14B | 通用对话、RAG 主力 | 12G~24G 可以 |
| 大 | 30B~40B（含 MoE） | 复杂任务、接近闭源体验 | 24G 勉强、48G 舒服 |
| 超大 | 70B 以上 | 高难度推理 | 需要多卡或量化+大显存 |

具体选型见 [[模型谱系 Qwen]]、[[模型谱系 DeepSeek]]。

## 决策点

- **岔路口 1：这篇讲的结构对我有用吗？**
  - 判断依据：你是"部署交付"而不是"训练模型"。
  - 推荐选择：**只看"输入怎么变 token、输出怎么吐字、显存花在哪"这三件事**，公式和反向传播细节可以跳过。
  - 代价：不深究也能交付，但遇到"为什么长上下文慢"会解释不清。

- **岔路口 2：要不要关心层数和宽度的具体数字？**
  - 判断依据：你要不要自己估算显存 / 解释模型卡。
  - 推荐选择：**只要会看模型卡上的 hidden size / layers / heads，够用**。
  - 代价：不记具体数字，估算是粗估，但已经比拍脑袋准一个数量级。

- **岔路口 3：客户问"为什么回答这么慢"，先查哪？**
  - 判断依据：看是首字慢还是吐字慢。
  - 推荐选择：首字慢 → 查 prefill（提示词长度、是否走了长上下文）；吐字慢 → 查解码（模型大小、量化、KV Cache、并发）。工具和指标见 [[推理性能指标与调优]]。
  - 代价：搞反方向就会去换显卡，钱花了问题还在。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| hidden size（d_model） | 向量宽度 | 调大 → 表达力强、显存和算力涨得快；调小 → 便宜但学不动复杂模式 | 几千量级（如 2048 / 4096 级别） |
| num_layers | 层数 | 调大 → 更深、更慢；调小 → 快但浅 | 20~80 层量级 |
| num_heads | 注意力头数 | 影响"并行看几个角度"；头数必须能整除 hidden size | 8~64 |
| FFN 倍数 | 前馈网络中间层的宽度倍数 | 决定 FFN 参数量；现代模型常用 gated 结构 | 通常 2~4 倍量级（不同结构不同） |
| vocab size | 词表大小 | 调大 → 词嵌入参数变多、多语言更好；调小 → 省显存 | 十几万量级 |
| max context | 原生上下文长度 | 调大 → 训练成本暴涨；直接影响 KV Cache | 8K / 32K / 128K，量级差异极大 |
| 位置编码 | 让模型知道"谁在前谁在后" | 决定能不能做长度外推 | 现在基本都是 RoPE，见 [[上下文窗口与位置编码]] |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 以为"参数量 = 显存"，买了个 7B 以为 7G 就能跑 | 7B 是参数量，fp16 每参数 2 字节，权重就约 14G；还有 KV Cache 和框架开销 | 记住公式"参数量 × 每参数字节数"，留 1.5 倍余量，见 [[参数量与显存估算]] |
| 用字数估算 API 费用，结果差 30% | 计费单位是 token，不是字数，中文尤其不等于 1:1 | 用对应模型的分词器或在线 tokenizer 估 |
| 以为模型"记住了"之前的对话 | 模型本身无状态，是多轮对话把历史**重新拼进提示词**再发一遍 | 对话越长越贵越慢，需要裁剪/摘要策略 |
| 以为生成长度只影响费用 | 生成长度直接决定耗时，是线性叠加的 | 限制 max_tokens，能短则短 |
| 把"上下文窗口"当成"它真能理解那么长" | 窗口是"塞得进"，理解质量受训练数据分布影响 | 关键信息放前面、压缩输入，见 [[上下文窗口与位置编码]] |
| 以为换更大模型一定解决效果问题 | 很多问题是提示词、检索、采样参数造成的 | 先调 [[采样参数与解码策略]] 和 RAG 链路，再考虑换模型 |

## 案例拆解：一句话进来，一句话出去

用一个具体例子把前面几步串起来。假设用户输入"帮我写一句生日祝福"，模型最终回答"愿你的每一天都有惊喜"。中间是这么走的：

1. **切 token**：输入被切成若干 token（可能就是"帮我""写""一句生日祝福"这样的片段），每个 token 查表变成一串数字，这就是 embedding。
2. **过层**：这串向量依次穿过 N 层，每层里做两件事——先做"注意力通讯"（token 之间交换信息），再做"FFN 计算"（每个 token 各自加工），每一步都套残差和归一化。
3. **压成分数**：最后一层的向量过输出层，变成词表里每个候选词的一个分数（logit）。
4. **挑一个词**：按解码策略从分数里选出下一个 token，比如先出"愿"。
5. **接上再来一遍**："帮我写一句生日祝福 愿"作为新输入重新走一遍，出"你"，如此循环，直到出现结束标记或碰到长度上限。

从这里能直接看出三件事：

- **推理是"字字循环"**，不是一次性吐出整句。这也是为什么输出长度直接决定延迟。
- **每一轮都要把前面所有 token 的 K、V 存下来复用**，不然每次都要重算——这就是 [[Attention 与 KV Cache]] 里说的 KV Cache。
- **模型看不到"没生成的字"**，所以它本质上是在一个概率分布上不断做选择，见 [[采样参数与解码策略]]。

## 架构决定的三条工程事实

把结构和工程现象对上号，比背名词有用：

| 架构部位 | 它靠什么变大 | 主要花在哪 | 工程上的直觉 |
|---|---|---|---|
| 层数 × 每层参数 | 参数量线性涨 | 权重显存、单 token 计算量 | 层越多越"深"，延迟越高 |
| 注意力 | 序列长度平方涨（训练）/ 线性涨缓存（推理） | KV Cache、长文本延迟 | 上下文一长，先爆的是显存 |
| FFN | 参数量占大头（通常占一多半） | 权重显存 | 模型的"知识"主要存在这里 |
| 残差 + 归一化 | 不涨参数，只保稳定 | 几乎不占资源 | 没有它们，深层根本训不动 |

记住一句话：**参数主要买"知道多少"，上下文主要买"一次能看多少"，两者都要拿显存结账**。具体怎么算，去 [[参数量与显存估算]]。

## 自检问题参考答案

> [!success]- 1. token 是什么，为什么"字数 ≠ token 数"？
> token 是模型眼里的"字块"，由分词器按固定规则切出来，可能是一个词、半个词、一个标点，中文里经常是一到两个字。
> 因为切法由模型自己的分词器决定，同一段文字在不同模型里切出的 token 数不一样，所以上下文长度、显存、计费都得按 token 算，而不是按字数算。
> 量级上，1 个 token 大约 0.6~0.75 个英文单词、1~1.5 个汉字，具体以实际分词器为准；用字数估费用常常差出三成。

> [!success]- 2. 一层 Transformer 里，注意力和前馈网络各干什么？
> 把一个层想成一个部门：**注意力是"通讯"**，每个 token 向前面所有 token 打电话、按相关性汇总信息；**前馈网络是"计算"**，每个 token 拿着汇总结果自己闷头加工一遍。
> 两者外面都套着残差连接和层归一化，写成 `x = x + Attention(Norm(x))`、`x = x + FFN(Norm(x))`，重复 N 层就是整条流水线。
> 分工的好处是两种计算都适合并行，这正是 Transformer 能吃满 GPU 算力的原因；另外 FFN 占参数量的大头，MoE 就是把这里拆成多个专家。

> [!success]- 3. 为什么大模型是"一个字一个字吐"的，这对速度意味着什么？
> 因为它是**自回归**生成：每次前向只算出下一个 token，把它接回输入末尾，再跑一次前向算下一个，直到出现结束符或到长度上限。
> 这意味着生成 500 个 token 就要做约 500 次前向，而且严格串行，GPU 其实一直没吃饱；所以**输出长度直接决定耗时**，限 max_tokens 是最直接的提速手段。
> 每次前向还要带着全部历史上下文，才需要 KV Cache 把算过的中间结果缓存下来复用，否则每次重算会慢到不可用。

> [!success]- 4. 训练显存和推理显存为什么差好几倍？
> 训练时除了权重，还要存梯度、优化器状态和大量中间激活，全参微调粗算约为权重的 **4~8 倍**；推理时参数固定，只要权重 + KV Cache + 少量激活，粗算约为权重的 **1.2~1.5 倍**（不含长上下文）。
> 所以"7B 模型 fp16 约 14G 就够"只在推理口径下成立；客户问"我能不能自己微调"要另算，个人和小团队能做的是 LoRA 类轻量微调。
> 交付时最忌讳把两个口径混着说，一句话答错，后面报价和硬件方案全歪。

> [!success]- 5. encoder-only 和 decoder-only 有什么区别，为什么后者成了主流？
> encoder-only（BERT 那一代）是"双向读完整段再理解"，擅长分类、抽取、向量化这类理解任务，本身不擅长做生成。
> decoder-only 只做一件事：预测下一个 token，并且只看前面（因果）。它赢在三处——训练目标统一、数据可以无限堆；所有任务都能改写成"续写"；结构单一，工程上最好扩展和优化。
> 现在几乎所有主流大模型都是 decoder-only，但做检索向量时还常遇到 encoder-only 的老模型，见「Embedding 与向量数据库」。

> [!success]- 6. 拿到模型卡，hidden size / layers / heads 分别说明什么？
> `hidden size` 是向量有多宽（几千量级），`num_layers` 是叠了多少层（20~80 层量级），`num_heads` 是一次注意力并行看几个角度（8~64，且必须能整除 hidden size）。
> 这三个数加上 FFN 倍数、词表大小，一起决定参数量；层数与宽度也直接决定显存和单 token 的计算量，所以看这几个数能大致判断"这模型多贵"。
> 具体数值不同模型差异很大，估算时用模型卡上的数字粗算即可，别背死数。

> [!success]- 7. 客户说"回答太慢"，怎么分"首字慢"和"吐字慢"两条路？
> 先看体感：**第一个字出来得慢**，问题在 prefill——提示词太长、走了长上下文、或者输入本身巨大，优化方向是压缩输入、裁剪历史、换更快的引擎。
> **字出来得慢（一个字一个字磨）**，问题在 decode——模型太大、量化太重、KV Cache 占满显存、并发太高，优化方向是换小模型、换量化档、限并发。
> 搞反方向就会去换显卡，钱花了问题还在；具体指标和工具去「推理性能指标与调优」看。

> [!success]- 8. 残差连接和归一化到底在保什么？
> **残差连接**是每层算完的结果"加到"原输入上，而不是替换掉它，等于给信息留了一条高速公路直通后面；没有它，几十层堆起来根本训不动。
> **层归一化**（现代模型多用 RMSNorm）是每层前后把数值范围捋平，防止越算越离谱、梯度爆掉。
> 这两样本身几乎不增加参数和显存，但决定了"深模型能不能训出来"，属于典型的小零件大作用。

## 交付视角（对客户怎么讲）

- **客户问"你这模型多大"**：别说参数量就说"7B"，要说"**7B 参数量、fp16 大约 14G 权重显存、你这张 12G 的卡跑不动，得用 4bit 量化，质量会掉一点点**"。数字 + 后果一起给，客户才信。
- **客户问"为什么它回话慢"**：用"**它是一字一字往外挤的，不是一口气生成整段**"来解释，比讲架构有用。然后给出可操作项：缩短回答长度、换更小模型、升显卡。
- **客户问"能不能自己再训练"**：区分"微调"和"预训练"。个人/小企业能做的是 LoRA 微调，成本在几百到几千量级；**从零预训练不是这个预算能干的事**，直接说明，别硬接。
- **报价相关**：模型越大量级、上下文越长，硬件和交付工时都要往上走。用 [[参数量与显存估算]] 的速查表当场报档位，比"我回去算算"更专业。

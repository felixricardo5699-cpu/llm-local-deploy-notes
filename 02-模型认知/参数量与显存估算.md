# 参数量与显存估算

> [!abstract] 一句话讲清楚
> 跑一个模型要的显存 = **权重 + KV Cache + 激活 + 框架开销**四项。权重按"参数量 × 每参数字节数"算，KV Cache 按"上下文长度 × 并发"算——**权重是起步价，KV Cache 才是长上下文的真正杀手**。

## 为什么重要

- 这是**接单交付时第一个会被问到的问题**："我这台机器能跑多大的模型？"答错了，后面全错——客户买错卡、你报错价、部署当天 OOM。
- 90% 的"模型跑不起来"不是引擎问题，是显存账没算清：
  - 只算了权重，忘了 KV Cache，开长上下文直接崩；
  - 只算了单请求，忘了并发，一上人就崩；
  - 没算框架开销（CUDA 上下文、引擎自身、碎片），刚好卡在边界上，实际差 1~2G。
- 学会这一篇，你可以在**纸上 30 秒**报出一个靠谱的档位。剩下的细节让引擎去试。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 参数量 | Parameters | 模型里可训练数字的个数，单位 B = 十亿。 | 是"个数"不是"字节数"；同一个 7B，fp16 和 4bit 占的显存差 4 倍。 |
| 每参数字节数 | Bytes per Parameter | 每个参数用几个字节存，由精度决定。 | fp16/bf16 = 2，fp8/int8 = 1，int4 理论 0.5，实际常 0.55~0.65。 |
| 权重显存 | Weight VRAM | 模型参数本身占的显存，跑起来必须全程驻留。 | 这是"起步价"，只要模型在，就一直占着。 |
| KV Cache | KV 缓存 | 缓存每一层算过的 K/V，避免重复计算。 | **随长度和并发线性增长**，是长上下文的主要成本。 |
| 激活 | Activation | 计算过程中的临时中间结果。 | 推理时很小，**训练/超长 prefill 时才会变大**；别拿训练的 8 倍率吓自己。 |
| 框架开销 | Framework Overhead | 引擎本身、CUDA 上下文、显存碎片、缓冲区占的部分。 | 通常 1~2G 起步，**必须预留**，否则"算得刚好"必然崩。 |
| 显存余量 | Headroom | 故意留出的安全垫。 | 经验值 10%~20%，或者至少 1~2G。 |
| 量化 | Quantization | 用更低精度存权重，把显存压下来。 | 有质量损失，不是免费的，见 [[量化技术]]。 |
| 上下文长度 | Context Length | 一次能塞进去的 token 数。 | 直接影响 KV Cache，是显存的**乘数**。 |
| 并发 | Concurrency / Batch | 同时处理几个请求。 | 每个请求一份 KV Cache，并发是显存的**另一个乘数**。 |
| 预填充 | Prefill | 一次性处理整段输入的阶段。 | 这一步会临时用到较多激活，输入特别长时要注意。 |
| 显存带宽 | Memory Bandwidth | 显存读写速度。 | 决定解码速度的上限；它和"显存容量"是两回事，见 [[硬件基础与 GPU 生态]]。 |

## 原理与机制

### 总公式：四项拆解

```
需要显存 ≈ 权重 + KV Cache + 激活 + 框架开销
最终还要 ×(1 + 余量)，余量通常 10%~20%
```

下面逐项拆。

### 第一项：权重——最确定的一项

```
权重显存 ≈ 参数量 × 每参数字节数
```

记住这张"字节数表"就够了：

| 精度 | 每参数字节数 | 7B 模型权重量级 | 说明 |
|---|---|---|---|
| FP32 | 4 | 约 28G | 部署几乎不用，太贵 |
| FP16 / BF16 | 2 | 约 14G | **质量基准线**，能跑就跑这个 |
| FP8 | 1 | 约 7G | 新卡支持，质量接近 fp16 |
| INT8 | 1 | 约 7G | 通用，质量损失小 |
| INT4 | 0.5（实际 0.55~0.65） | 约 4G | 消费级主力，质量有可见损失 |

> [!tip] 为什么 int4 不是精确的 0.5
> 因为实际文件里不是所有参数都压到 4bit：embedding、输出层、归一化层通常保留更高精度，还有量化系数、元数据。所以 `参数量 × 0.6` 是更靠谱的心算系数。GGUF 的 Q4_K_M 大约就是这个量级。

**速算口诀**：7B 的 fp16 ≈ 14G，int8 ≈ 7G，int4 ≈ 4G。其他规模按比例缩放。

### 第二项：KV Cache——长上下文的真正杀手

```
KV Cache ≈ 2 × 层数 × 序列长度 × KV头数 × 每头维度 × 每元素字节数
```

心算简化版：

```
每 1K token 的 KV ≈ 层数 × hidden_size × 2 × 每元素字节数 ÷ GQA 分组倍数
```

> [!warning] 这一段是全篇最该记住的
> 很多人算完权重就说"能跑"，然后开 32K 上下文、2 个并发，直接 OOM。原因是：
> - KV Cache 和**上下文长度成正比**；
> - KV Cache 和**并发数成正比**；
> - 它不量化的时候是 fp16，占得很实在。
> 一个 7B 级别模型在长上下文下，**KV Cache 完全可能超过权重本身**。

粗略的量级感受（数字是量级，不同模型差很多，以模型卡为准）：

| 上下文 | 7B 级 Dense（GQA，fp16 KV） | 说明 |
|---|---|---|
| 4K | 几百 MB ~ 1G 级 | 日常聊天基本无感 |
| 16K | 1~3G 级 | RAG 长文档开始要留余量 |
| 32K | 2~6G 级 | 24G 卡开 32K + 并发要小心 |
| 128K | 10G 以上级 | 通常必须量化 KV 或降并发 |

**能省 KV Cache 的手段**（按性价比排序）：

1. **换 GQA 结构的模型**（KV 头数少，天然省几倍）；
2. **别默认拉满上下文**，按需开；
3. **KV Cache 量化**（fp16 → int8/fp8，近似减半）；
4. **限制并发数**（最直接）；
5. 用 PagedAttention 类引擎减少碎片浪费（见 [[vLLM]]）。

### 第三项：激活——推理时别自己吓自己

激活是计算过程中的临时张量。两个场景差别巨大：

- **推理（平时部署）**：激活很小，通常几百 MB 到一两 G 量级，跟权重比是零头。
- **训练 / 超长输入的 prefill**：激活会明显变大，极端情况下能吃掉几个 G。全参微调时激活是显存大头之一，见 [[LoRA 与 QLoRA 原理]]。

**结论**：做推理估算时，把激活当成"预留 0.5~2G"就够了；但客户如果要做微调，必须另外算。

### 第四项：框架开销——那个总被忘掉的 1~2G

这部分不体现在任何模型文件里，但真实存在：

| 来源 | 大概量级 | 说明 |
|---|---|---|
| CUDA 上下文 / 驱动运行时 | 几百 MB | 每个进程一份，跑起来就有 |
| 推理引擎自身缓冲 | 几百 MB ~ 1G+ | 不同引擎差别大 |
| 显存碎片 | 几百 MB | 长期运行、频繁换上下文更明显 |
| 多卡通信缓冲 | 视规模 | 多卡部署要单独留 |

所以：**算出来刚好等于显存，等于跑不起来。**必须留余量。

### 心算四步法（现场报档位用）

```
① 权重 = 参数量(B) × 字节数        例：14B × 2 = 28G（fp16）
② KV   = 长度和并发带来的量级       例：14B + 8K + 1 并发 ≈ 1~2G
③ 激活 = 预留 0.5~1G
④ 开销 = 预留 1~2G
⑤ 合计 × 1.1~1.2  → 和显卡显存比
```

**举例**：客户要 14B 模型、fp16、8K 上下文、单并发。

- 权重：14 × 2 = 28G
- KV：1~2G
- 激活 + 开销：约 2G
- 合计约 31~32G → 24G 卡**跑不了 fp16**，要么上 48G 卡，要么降到 int8（14G + 约 4G ≈ 18G，24G 卡舒服）。

这就是 30 秒内能给客户的答案。

## 显存档位速查表（8G / 12G / 16G / 24G / 48G）

> [!important] 怎么用这张表
> 表中"能跑的量级"指的是**单并发、常用上下文（4K~8K）、留了余量**的舒适档位。量化档位统一按 GGUF 的 Q4_K_M / int4 量级估算。实际差异很大，最终以实测为准。

| 显存 | 舒适区（稳） | 可尝试（紧） | 基本别想 | 典型场景 |
|---|---|---|---|---|
| **8G** | 7B~8B 的 int4（约 4~5G）+ 4K 上下文 | 14B 的 int4（约 8G+），几乎没余量，上下文得压到很小 | 14B 以上、任何 MoE 大模型 | 轻量对话、分类、改写、端侧/笔记本 |
| **12G** | 7B~8B 的 int8 或更高；14B 的 int4 + 8K 上下文 | 24B 的 int4（约 13G+）——上下文必须很小 | 32B 以上、70B | 通用对话、个人 RAG、编码助手 |
| **16G** | 14B 的 int4 舒适，或 14B 的 Q5/Q6；24B 的 int4 + 8K | 32B 的 int4（约 18G+）——容易 OOM | 70B、多数 MoE 大模型 | 中等 RAG、多模态小模型、图像工作流并行 |
| **24G** | 14B 的 int8；32B 的 int4（约 18G）+ 8K 上下文 | 30B 级 MoE 的小型号；70B 的 int4（约 40G）**不行**，除非 2 张卡 | 70B 以上单卡、大 MoE | 主力交付档位：RAG、Agent、多模态 |
| **48G** | 32B 的 int8 / fp16 紧；70B 的 int4（约 35~42G）+ 短上下文 | 70B 的 int4 + 16K 上下文 + 单并发 | 100B+ 稠密（fp16 就不可能） | 单机高配：70B 级、长上下文、较重并发 |

补充说明：

- **MoE 按总参数看**：表里不单列，因为决定能不能跑的是总参数。看到"总参数 100B+"的 MoE，即使激活只有 10B 级，也先按 100B 去算权重。（见 [[Dense 与 MoE 架构]]）
- **Apple 统一内存**：内存和显存共享，能"装下"更大模型，但带宽有限、出字速度明显更慢，见 [[MLX 与 Apple 芯片推理]]。
- **多卡不是简单叠加**：两张 24G 不等于一张 48G，模型并行有通信开销，体验会打折。
- **"紧"档位意味着**：上下文要压、并发要限、长会话要重启。能跑 ≠ 好交付。

### 上下文和并发怎么把"能跑"变成"跑不动"

以 24G 卡 + 32B int4（权重约 18G）为例，剩余约 6G：

- 4K 上下文 + 1 并发：舒服。
- 8K 上下文 + 2 并发：开始紧张（KV 翻倍）。
- 32K 上下文 + 4 并发：大概率 OOM。

所以报价时**必须写清交付边界**："支持 8K 上下文、2 并发"——这是工程承诺，不是能力贬低。

## 分类与对比：三种估算精度

| 估算方式 | 用时 | 误差 | 适用场合 |
|---|---|---|---|
| 纯心算（参数量 × 系数 + 2G） | 10 秒 | 几 G 级 | 电话里、微信里先给个档位 |
| 公式 + 上下文/并发代入 | 2 分钟 | 0.5~2G | 报价、写方案、确认硬件 |
| 实机 `/nvidia-smi` + 引擎日志压测 | 半小时 | 很小 | 最终验收、交付前定参数 |

三者不冲突：**先用第一档给方向，第二档定方案，第三档验收**。

## 决策点

- **岔路口 1：客户显存刚好装下权重（比如 24G 装 20G 权重）——能接吗？**
  - 判断依据：剩余显存 - KV - 激活 - 开销 是否为负。
  - 推荐选择：**不接，或明确降配**（降量化、降上下文、限并发）。剩余不到 2~3G 的单子基本都会在验收时出事。
  - 代价：拒绝一单，或者标清楚边界后接下来，都好过交付翻车。

- **岔路口 2：显存不够，是换小模型 / 降量化 / 加卡，还是降上下文？**
  - 判断依据：先看业务最在意什么（效果 / 速度 / 长度 / 并发）。
  - 推荐选择：**效果优先 → 保模型、降上下文和并发；速度优先 → 降量化；长度优先 → 换 GQA 模型 + 量化 KV；全都要 → 加卡**。
  - 代价：每种都有明确损失，要跟客户说清是哪一种。

- **岔路口 3：要不要给客户上 MoE？**
  - 判断依据：总参数折算的权重显存是否有 30% 以上余量。
  - 推荐选择：余量够 → MoE 性价比高（速度快）；余量不够 → 换 Dense。
  - 代价：MoE 对上下文和并发更敏感，余量不足会非常难用。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| 量化档位（Q4_K_M / int8 / fp16） | 决定权重显存 | 越低越省显存、质量损失越大 | 消费级首选 Q4_K_M；有质量要求选 int8 |
| 上下文长度上限 | 决定 KV Cache 上限 | 翻倍就多一份 KV | 按业务定，别默认拉满 |
| max_num_seqs / 最大并发 | 决定 KV Cache 总数 | 每加一个并发多一份 KV | 显存紧张时 1~2 |
| KV Cache 精度 | KV 用 fp16 还是 int8/fp8 | 降精度近似减半 | 长上下文时值得开 |
| gpu_memory_utilization | 引擎允许占用的显存比例 | 调高塞更多请求，太高易 OOM | 留 10% 余量附近 |
| max_model_len | 引擎里限制的单请求长度 | 限制失控的长请求 | 按业务上限定 |
| swap / CPU offload | 把部分层放到内存 | 能"跑起来"但速度暴跌 | 仅应急，不做交付方案 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 24G 卡跑 7B fp16 还以为很宽裕 | 14G 权重 + 长上下文 KV + 开销，实际上余量远没有想象的大 | 加 KV 和开销一起算；开长上下文要重新算 |
| 按"参数量 = 显存 GB"估算 | 混淆了个数和字节（fp16 是 2 字节） | 背住：7B fp16≈14G、int4≈4G |
| 算出来和显存一模一样，结果 OOM | 没算框架开销和碎片 | 至少留 1~2G 或 10%~20% |
| 用 int4 的显存去承诺 int8 的效果 | 量化有质量损失，尤其小模型 | 交付前用业务数据实测；话术上说清"有损" |
| 单并发测试通过就交付，客户一上多人就崩 | 每个并发一份 KV Cache | 按客户真实并发数压测，写进验收标准 |
| 以为"上下文越长越强" | KV 涨、速度降、注意力质量也可能下降 | 只在需要时开长上下文；优先 RAG 替代 |
| 把 MoE 的激活参数当参数量算 | 权重必须按总参数装 | 显存一律用总参数算 |
| 用多卡显存简单相加来估 | 模型并行有通信和复制开销 | 预留 10%~20%，并接受速度打折 |
| 忽略 embedding 层的额外占用 | 词表大的模型 embedding 占比不低 | 用官方模型文件实际大小校准一次 |

## 自检问题参考答案

> [!success]- 1. 四项拆解分别是什么，每项大概怎么算？
> **权重**＝参数量 × 每参数字节数（fp16 2 字节、int8 1 字节、int4 约 0.55~0.65 字节），这是跑起来必须全程驻留的起步价。
> **KV Cache**＝2 × 层数 × 序列长度 × KV 头数 × 每头维度 × 每元素字节，心算版是 `层数 × hidden_size × 2 × 字节数 ÷ GQA 分组倍数`，和上下文长度、并发成正比。
> **激活**：推理时很小，预留 0.5~2G 就够；超长 prefill 或训练时会明显变大。
> **框架开销**：CUDA 上下文、引擎缓冲、显存碎片，固定预留 1~2G；最后整体再乘 1.1~1.2 的余量。

> [!success]- 2. 14B 模型在 fp16 / int8 / int4 下各要多少权重显存？
> 按 `参数量 × 每参数字节数`：14B × 2 ≈ 28G，14B × 1 ≈ 14G，14B × 0.5~0.6 ≈ 7~8G。
> 注意这只是**权重**。加上 KV Cache、激活、框架开销和余量，14B 的 int4 塞进 8G 卡仍然吃力，12G 才比较从容，16G 就舒服了。
> 现场报价就按这个口径说，别只报"14B"，要报"14B + 量化档 + 显存档位"三件套。

> [!success]- 3. 为什么说"KV Cache 是长上下文的真正杀手"？
> 权重是固定的、可预期的；KV Cache 是**变量**，随上下文长度和并发数一起涨，而且没量化时按 fp16 实打实占显存。
> 一个 7B 级模型在长上下文下，KV Cache 完全可能超过权重本身；开到 128K 就是 10G 以上级别。
> 所以"权重装得下"只代表能启动，不代表能开长上下文、能上并发。交付前必须把 KV 那笔账单独算一遍。

> [!success]- 4. KV Cache 和哪两个因素成正比，各有什么应对手段？
> 和**上下文长度**成正比：对策是按业务需要开上下文、别默认拉满，大多数 RAG 场景 8K~16K 就够。
> 和**并发数**成正比：每个请求都有独立一份缓存，对策是限制并发上限，按客户真实并发数压测。
> 另外还有两个杠杆：KV Cache 量化（fp16 → int8/fp8，近似减半）和换 GQA 模型（KV 头数天然少几倍），性价比都很高。

> [!success]- 5. 现场给 8G / 16G / 24G / 48G 各报一个舒适档位。
> **8G**：7B~8B 的 int4，4K 上下文，轻量对话和分类改写。
> **16G**：14B 的 int4 舒适，或 24B 的 int4 配 8K；再高就紧了。
> **24G**：14B 的 int8，或 32B 的 int4 配 8K 上下文，这是主流交付档位。
> **48G**：70B 的 int4 配短上下文，或 32B 的 int8。
> 这些都是"单并发、常用上下文、留了余量"的舒适档；压到"可尝试"档意味着上下文要压、并发要限，能跑不等于好交付。

> [!success]- 6. 为什么"算得刚好等于显存"实际上跑不起来？
> 因为账面之外还有框架开销：CUDA 上下文和驱动运行时几百 MB、引擎自身缓冲区几百 MB 到 1G 以上、显存碎片几百 MB，多卡还有通信缓冲。
> 这些不体现在任何模型文件里，但真实存在。算得刚好就等于**没有安全垫**，一开长上下文、一上并发、或者跑久了有碎片，立刻 OOM。
> 所以经验上至少留 1~2G 或 10%~20% 的余量，"刚好"就是"跑不起来"的另一种说法。

> [!success]- 7. 推理估算和训练估算为什么差好几倍？
> 训练时除了权重，还要存梯度、优化器状态和大量中间激活，全参微调粗算约为权重的 **4~8 倍**。
> 推理时参数固定，只需要权重 + KV Cache + 少量激活，粗算约为权重的 1.2~1.5 倍（不含长上下文）。
> 所以"7B 模型 14G 够"只在推理口径下成立。客户一说"我想自己训练/微调"，必须切换口径重算，个人和小团队能接的是 LoRA 类轻量微调。

> [!success]- 8. 为什么 MoE 必须按总参数算显存？
> 因为路由可能把任何一个 token 分给任何一个专家，**所有专家权重都必须加载进显存**，缺一个就会出错。激活参数只决定"这次算哪几个专家"，不决定"要装多少"。
> 所以模型卡上"总参数 100B、激活 12B"的 MoE，权重显存和 100B 稠密模型差不多，24G 卡一样跑不动。
> 正确姿势是：显存按总参数算，速度按激活参数估；余量不足 30% 就别上 MoE，长上下文会非常难受。

## 交付视角（对客户怎么讲）

- **客户问"我这台机器能跑什么模型"**：先问三个数——**显存多大、要多长上下文、几个人同时用**。然后按四步法当场报档位。只报模型名不报边界，等于埋雷。
- **客户问"为什么别人说 24G 能跑 70B"**：解释那是 int4 极限档 + 极短上下文 + 单并发，属于"能跑起来"而不是"能交付使用"。把"能跑"和"好用"分开讲，客户会立刻理解。
- **写进方案的标准表述**：建议在交付文档里固定写清：`模型 + 量化档位 + 最大上下文 + 最大并发 + 显存占用实测值`。这五项写清楚，验收和售后都省事。
- **报价关联**：显存档位直接决定硬件档位和报价。8G/12G 是入门单，16G/24G 是主流单，48G 以上是高配单。用这张速查表把"硬件 → 能力 → 价格"串起来，谈单会顺很多。
- **别承诺**："这个模型肯定能跑满 128K"这种话不要出口。说"按你的业务实测，我们先压测再定上限"，专业且安全。

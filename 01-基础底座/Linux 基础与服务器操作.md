# Linux 基础与服务器操作

> [!abstract] 一句话讲清楚
> 本地大模型部署绝大多数跑在 Linux 服务器上。这篇讲"登录服务器之后你真正要会的那几件事"：文件在哪、谁能改、服务怎么跑、日志去哪看、磁盘为什么满。目标不是背命令，而是看懂一台机器的状态。

## 为什么重要

- **位置**：上游是 [[硬件基础与 GPU 生态]]（机器长什么样），下游是 [[Shell 与命令行基础]]（命令怎么组合）和 [[Docker 与容器化基础]]（怎么打包交付）。
- **现实约束**：[[vLLM]] 基本只在 Linux 上有完整支持；[[Ollama]] 虽然全平台，但生产环境还是放 Linux。客户给的机器、云上租的机器，几乎都是 Linux。
- **不懂会怎样**：服务起不来只看到 `permission denied`；端口被占只会重启；磁盘写满后所有服务一起挂；客户问「日志呢」你答不上来。这些都不是模型问题，是操作系统问题。
- **真实场景**：客户给一台带 4090 的工作站，只给了 SSH 账号和密码。你要在 10 分钟内搞清楚：系统版本、显卡驱动、磁盘分布、已占用的端口、有没有别的服务在跑——然后才决定装在哪、用哪个端口。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 发行版 | Distribution / Distro | 把 Linux 内核 + 软件包管理 + 一堆工具打包成的"整套系统"，比如 Ubuntu、Debian | 内核都一样，区别在包管理器和软件新旧，选哪个直接影响你装驱动顺不顺 |
| shell | Shell | 你敲命令、它翻译给系统执行的那个程序，常见 bash | 它不是"系统本身"，只是操作系统的遥控器；换个 shell 不影响服务 |
| root | root / superuser | 系统最高权限账号，什么都能改、也什么都能删 | 日常别用 root 跑服务；权限太大意味着误操作代价不可逆 |
| sudo | superuser do | 普通用户临时"借用"root 权限执行一条命令 | 它只是提权工具，不等于你就是 root；sudo 后产生文件的属主往往变成 root，是后面权限坑的来源 |
| 家目录 | home / `~` | 每个用户自己的文件夹，比如 `/home/ubuntu` | 用 `~` 写的路径只对当前用户成立；换用户跑服务后路径就找不到文件了 |
| 挂载 | mount / 挂载点 | 把一块硬盘、一个分区"接到"目录树上某个位置，之后往这个目录读写就是往那块盘读写 | 目录看着是空的不代表磁盘空；数据盘没挂载时，往挂载点写其实是写进系统盘 |
| 文件权限 | rwx / 755 / 644 | 谁能读、写、执行一个文件，分属主、同组、其他人三类 | `644` 是文件常见值，`755` 常给目录/可执行文件；`777` 等于谁都能改，等于没权限管理 |
| chown | change owner | 改文件的主人（属主和属组） | 它和 chmod 不是一回事：chmod 改"能干什么"，chown 改"归谁" |
| 进程 | process / PID | 正在运行的程序，每个有唯一编号 PID | 同名进程可能有好几个；只靠名字 kill 容易杀错，先看 PID |
| 信号 | signal / SIGTERM / SIGKILL | 给进程发的一条"消息"，最常见是让它正常退出或强行杀掉 | 先 SIGTERM（给人收拾的时间），不行才 SIGKILL（直接击毙，进程没机会存盘） |
| 守护进程 | daemon / 后台服务 | 脱离终端、在后台长期运行的进程 | 前端跑的服务 SSH 一断就死，这就是很多"服务莫名其妙挂了"的原因 |
| systemd | systemd / unit | Linux 的服务管家：定义服务怎么启动、崩了要不要重启、开机要不要自启 | 它管的服务和你在终端里手动跑的是两套东西，混着用最容易出现"两个实例抢端口" |
| 日志 | log / journald | 系统和服务的运行记录，看故障第一现场 | 分两套：systemd 的 `journalctl` 和传统 `/var/log` 下的文件，服务是哪种装法决定去哪看 |
| 包管理器 | apt / dnf / pacman | 系统的"应用商店"，负责装、升级、卸载系统软件 | 它管的是系统软件，不是 Python 的 pip；两套系统别混着装同一个东西 |
| 软链接 | symlink | 给文件/目录起个别名，指向真正的位置 | 删软链接只删别名；但用 `cp`、备份时可能跟进去复制真文件，行为容易误判 |
| inode | inode | 文件在磁盘上的"身份证"，记着权限、大小、数据块位置 | 磁盘报满有两种：空间满了，或者 inode 用完了（大量小文件），同一个报错两种原因 |

## 目录树速查：文件都放在哪

Linux 没有 C/D 盘，只有一棵从 `/` 开始的树。部署时你会反复碰到的位置就这些：

| 路径 | 放什么 | 部署时和它的关系 |
|---|---|---|
| `/etc` | 系统和服务配置 | 改服务配置、防火墙、用户组都在这里 |
| `/var/log` | 传统程序的日志 | 磁盘被日志吃满时来这找 |
| `/var/lib` | 服务运行数据 | 数据库、Docker 数据常在这附近（视发行版） |
| `/home/用户名` | 用户家目录 | 默认环境变量的坑源，服务别依赖这里 |
| `/opt` | 手动安装的大型软件 | 部分推理工具会装在这 |
| `/usr/local` | 手动编译安装的软件 | 自装的 Python/CUDA 常在这，注意 PATH |
| `/mnt` `/media` | 临时挂载点 | 数据盘一般挂这或 `/data` |
| `/data` | 约定的数据盘目录 | **推荐所有模型放这**（通常要自己建） |
| `/tmp` | 临时文件 | 可能被系统清理，别放模型和产出 |
| `/proc` `/dev` | 内核/设备信息的虚拟目录 | 容器 GPU 直通就是往容器里暴露 `/dev/nvidia*` |
| `/root` | root 的家目录 | 别用它跑服务、放模型 |

> 一句话记法：**配置找 `/etc`，日志找 `/var/log`，数据自己建一个目录放**。

## 原理与机制

### 直觉版

Linux 服务器像一栋写字楼：**目录树是楼层号**（所有东西挂在一棵树上，没有 C 盘 D 盘的概念），**权限是门禁**（谁能进哪间房），**进程是正在房间里干活的人**，**systemd 是物业**（负责让该上班的人一直上班），**日志是监控录像**。

### 拆解版

1. **单根目录树 + 挂载**：所有路径都从 `/` 开始。硬盘接进来不会自动出现一个 E 盘，而是"挂"到某个目录上。同一个 `/data` 目录，挂载前后读写的是完全不同的盘。
2. **权限三件套**：每个文件都记着"属主 / 属组 / 其他人"分别能读（r）、写（w）、执行（x）。root 是例外，它无视大部分限制——所以用 root 跑服务，一旦被攻破损失最大。
3. **进程有父子关系**：你在终端里敲的命令是 shell 的子进程。SSH 断开时，系统会给这个终端下挂的进程发"挂断信号"（SIGHUP），它们默认就退出了。这就是前台跑服务一断开就死的原因。
4. **systemd 托管**：把启动方式写成一个 unit 文件，systemd 就接管了它——崩了按策略拉起、开机自启、日志统一收走。正式服务必须这么跑。
5. **日志分两处**：systemd 托管服务的日志进 journal，`journalctl -u 服务名` 看；传统程序自己写文件到 `/var/log`。报错首先要判断"我该去哪看"。

### 后果

- 为什么正式服务不能挂在前台终端：SSH 一断就死，而且没人负责重启。
- 为什么不要用 root 跑应用：权限过大和文件属主混乱，后面全是坑。
- 为什么磁盘规划要先做：模型动辄几十 GB，日志和镜像也长肉，全塞系统盘迟早写满，写满后连登录都可能失败。

## 三种让服务"活下去"的方式

| 方式 | 断线后还活着 | 崩了自动重启 | 开机自启 | 适合场景 | 代价 |
|---|---|---|---|---|---|
| `nohup 命令 &` | 是 | 否 | 否 | 一次性的长任务、下载、批处理 | 输出默认进文件，容易占盘 |
| `tmux` / `screen` | 是（会话在服务端） | 否 | 否 | 交互式调试、需要随时回看的任务 | 它不保证服务活着，只保证终端还在 |
| systemd unit | 是 | 是（按策略） | 是 | 正式服务、客户机器上的服务 | 要写配置，改了要 reload |
| 容器 + 重启策略 | 是 | 是 | 是 | 交付、要求可复现 | 多一层，排错要先看容器 |

- 判断顺序：**临时任务 → nohup/tmux；正式服务 → systemd；要交给客户 → 容器**。
- 别用"挂在 tmux 里"糊弄客户：那不是服务方案，客户那边没人会去 `attach` 会话。

### systemd unit 最少要写这几行

一个服务能被 systemd 托管，unit 里至少要有：怎么启动、用哪个用户、崩了怎么办。关键字段如下（路径/用户按实际改）：

```ini
[Service]
ExecStart=/opt/app/start.sh
User=deploy
Restart=always
Environment="CUDA_VISIBLE_DEVICES=0"
```

- `ExecStart` 必须是**前台运行**的启动方式（不能带 `&`），否则 systemd 会认为进程启动后立刻退出。
- `Restart=always` 让服务崩溃后自动拉起；`Environment` 是服务级环境变量，它不会读你的 `.bashrc`。

### 碰到问题进程时怎么安全地处理

- 先确认是不是自己的进程：`ps -ef | grep 关键字`，看清 PID、启动用户、启动时间。
- 优先让进程自己退：`kill PID`（发 SIGTERM），等几秒看日志确认它收尾。
- 实在不退再强杀：`kill -9 PID`（SIGKILL），代价是没机会存盘，资源要等系统回收。
- 别用宽匹配：`pkill -f python` 会把机器上所有 Python 进程一起杀，共享机器上尤其危险。

## 分类与对比：发行版怎么选

| 维度 | Ubuntu LTS | Debian | RHEL 系（Rocky / Alma 等） | Arch 系 |
|---|---|---|---|---|
| 包管理器 | apt | apt | dnf / yum | pacman |
| 软件新旧 | 较新、稳定 | 偏保守 | 保守、企业认证 | 最新 |
| NVIDIA 驱动/CUDA 支持 | 官方支持最好、文档最多 | 可行，文档略少 | 有官方渠道，但琐碎 | 手动配置多 |
| 适合场景 | **部署默认选择** | 追求稳定、预算一般 | 客户已有企业环境 | 折腾、学习 |
| 新手坑 | 版本太新反而要跟驱动对版本 | 软件旧，可能需要自己加源 | 包名/命令和 Ubuntu 不一样 | 滚动更新容易把驱动搞崩 |

> 推荐：**接单部署默认用 Ubuntu LTS**，生态和教程最全；客户已有 RHEL 系就跟随客户，别为了自己顺手给客户换系统。

## 用户与用户组：为什么部署常新建一个用户

- **权限隔离**：服务只能碰自己该碰的目录，出问题影响面小。
- **归属清晰**：`ls -l` 一眼看出哪些文件是哪个服务产生的，备份和清理不容易误删。
- **组协作**：把模型目录的属组设成专门的组，多个服务用户都能读，但都改不了别的东西。
- **交接友好**：客户运维更容易接受"有一个 deploy 用户专跑服务"，而不是"所有东西都塞 root"。

## 完整流程：接手一台陌生 Linux 服务器的 8 步盘点

### 第 1 步：登录，确认"我是谁、这是哪台"

```bash
ssh 用户名@服务器IP
whoami && hostname && cat /etc/os-release
```

- **为什么**：先建立身份和系统版本的基本盘；很多后续命令和包名跟发行版强相关。
- **输出是**：当前用户、机器名、系统版本。
- **失败表现**：连不上——先查网络/端口/账号（见 [[网络基础与内网穿透]]）。

### 第 2 步：摸硬件和显卡

```bash
nproc && free -h && df -h && nvidia-smi
```

- **为什么**：CPU 核数影响模型加载和前处理，内存影响能否做 CPU 推理，磁盘决定模型往哪放，`nvidia-smi` 决定这台机器到底有没有可用的卡。
- **验收**：四个数字都看到了，且没有满盘告警。
- **失败表现**：`nvidia-smi` 显示 `command not found` 或 "No devices were found"——先别慌，可能是驱动没装（见 [[驱动-CUDA-框架版本兼容]]）。

### 第 3 步：看磁盘分布，决定模型放哪

```bash
lsblk && df -hT
```

- **为什么**：模型、镜像、日志会持续长肉。系统盘通常不大，数据盘可能还没挂载。
- **输出是**：磁盘列表和挂载点，找到大容量且已挂载的目录（常见是 `/data`、`/home`）。
- **失败表现**：只有一块盘且快满了——先规划，不然后面一定会写满。

### 第 4 步：看端口占用

```bash
ss -tlnp
```

- **为什么**：知道 8000/8080/11434 这些常用端口有没有被占，决定自己服务用哪个端口。
- **验收**：能说出"谁在监听哪个端口"。

### 第 5 步：看已有服务

```bash
systemctl list-units --type=service --state=running
```

- **为什么**：避免重复部署、避免两个服务抢显卡或抢端口。
- **输出是**：正在跑的服务清单。

### 第 6 步：看日志有没有历史报错

```bash
journalctl -p err -b --no-pager | tail -n 50
```

- **为什么**：这台机器最近有没有硬件错误、驱动报错、磁盘异常，先扫一眼能避开很多"接手就爆炸"。
- **验收**：没有持续的硬件/文件系统错误。

### 第 7 步：决定安装位置和方式

- 驱动层用系统包管理器装、应用层用独立环境或容器装，两套不要混。
- **为什么**：系统软件升级可能影响显卡驱动，应用依赖装在系统里会越装越乱（见 [[Python 环境与依赖管理]]、[[Docker 与容器化基础]]）。

### 第 8 步：先跑一个最小验证，再上模型

- 先用最简方式验证"卡能用、网络通、磁盘能写"，再上正式部署。
- **验收**：`nvidia-smi` 正常、能下载或拷贝模型、服务端口能从本机访问。
- **失败表现**：跳过这步直接上大模型，出问题时无法区分是环境问题还是模型问题。

## 排错顺序：从现象定位到层

部署出问题别急着重装。按层往下走，每一层只回答一个问题：

| 层 | 先看什么 | 说明什么 | 继续排查 |
|---|---|---|---|
| 硬件/驱动 | `nvidia-smi` | 卡在不在、驱动正不正常 | 异常 → [[驱动-CUDA-框架版本兼容]] |
| 网络/端口 | `ss -tlnp`、本机 `curl` | 服务有没有在听、端口对不对 | 本机通外部不通 → [[网络基础与内网穿透]] |
| 服务托管 | `systemctl status`、容器状态 | 进程起没起、重启了几次 | 反复重启 → 看 journal 最后几十行 |
| 磁盘/内存 | `df -h`、`free -h` | 有没有写满、有没有 OOM | 满盘 → 先清理再重启服务 |
| 应用/框架 | 应用日志、框架报错 | 上面都正常才轮到这一层 | 依赖问题 → [[Python 环境与依赖管理]] |

> 核心原则：**先确认"东西在不在"，再确认"能不能通"，最后才怀疑"代码/模型有问题"**。顺序反了会浪费大量时间。

## 决策点

- **岔路口 1：用哪个发行版？** 条件——客户已有系统就跟随；新机器自建就选 Ubuntu LTS。判断依据——驱动和容器的资料量。代价——选偏门发行版，遇到问题自己啃。
- **岔路口 2：服务用 systemd 还是 Docker？** 要开机自启、要长期稳定、要交付给客户 → 用 systemd 或容器编排（推荐容器，见 [[Docker 与容器化基础]]）；临时试验 → `tmux` 里跑。代价——容器多一层，排查要多看一步。
- **岔路口 3：日常用 root 还是 sudo？** 一律建普通用户 + sudo。判断依据——误删和权限污染的风险。代价——每次多敲几个字。
- **岔路口 4：驱动用系统源还是 NVIDIA 官方仓库？** 推荐官方仓库或发行版推荐方式，装/卸干净、能回滚；不建议新手用 `.run` 手工安装，卸载容易留残留。代价——官方仓库版本可能偏旧，但稳定。
- **岔路口 5：模型放系统盘还是数据盘？** 一律数据盘 + 明确目录（如 `/data/models`）。代价——要提前配好目录和权限。
- **岔路口 6：磁盘满了清什么？** 顺序：Docker 镜像/日志 → journal → 旧模型 → 缓存。别直接 `rm` 正在写的日志文件。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| `chmod` 数字位 | 一次性设置属主/组/其他人的权限 | 数字越大权限越宽，`777` 等于谁都能改 | 目录 `755`、普通文件 `644`、密钥 `600` |
| `systemctl start` / `enable` | 前者是"现在启动"，后者是"开机自启" | 只 start 不 enable，重启机器后服务就没了 | 两个都设 |
| `systemctl status` | 看服务状态和最近日志 | 只看状态不够，还要看下面的错误行 | 排查第一站 |
| `journalctl -u 服务 -f` | 跟踪某个服务的实时日志 | 加 `--since "10 min ago"` 缩小范围 | 排错常用 |
| `df -h` / `du -sh 目录` | 看磁盘剩余 / 看某目录占多大 | 两者结合定位"谁把盘写满了" | 接手第一件事 |
| `ss -tlnp` | 列监听端口和对应进程 | 只查端口不够，要看到 PID | 端口冲突排查 |
| `ulimit -n` | 单进程可打开的文件数上限 | 并发高时太小会报 "too many open files" | 按需调高（如 65535 量级） |
| `free -h` / swap | 内存与交换分区 | swap 太小会在内存紧张时直接 OOM | 视机器内存 |
| `nproc` | 可用 CPU 核数 | 影响加载和 CPU 推理线程数 | 按核心数设 |
| `0.0.0.0` vs `127.0.0.1` | 服务监听的地址 | 只听本机 → 外网连不上；听所有网卡 → 要配防火墙 | 对外服务用 `0.0.0.0` + 防火墙 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| SSH 一断开，服务就停了 | 服务挂在终端会话下，终端退出时收到挂断信号 | 正式服务用 systemd 托管或放进容器；临时任务用 `tmux`（见 [[Shell 与命令行基础]]） |
| 本机 `curl` 能通，客户电脑打不开 | 服务监听在 `127.0.0.1`，或防火墙/安全组没放行 | 改监听 `0.0.0.0`，逐一排查本机防火墙和云安全组（见 [[网络基础与内网穿透]]） |
| 服务区磁盘突然写满，所有服务一起挂 | 模型、镜像、日志全在系统盘；Docker 日志不轮转 | `df -h` + `du -sh` 定位；把模型/日志迁到数据盘并配轮转 |
| 启动报 "Address already in use" | 旧进程没退干净，或另一个服务占了端口 | `ss -tlnp` 找到 PID 再处理，别盲目重启整机 |
| `rm` 删了大日志文件，磁盘空间没释放 | 进程还拿着文件句柄，空间要等进程关闭才释放 | 用 `truncate -s 0 文件` 清空，或重启该服务；别直接删正在写的日志 |
| 换用户跑服务后读不到模型文件 | 文件属主是上一个用户，权限没给到新用户 | `chown` 改属主或用组权限；先 `ls -l` 看清是谁的文件 |
| 改了 `~/.bashrc` 的环境变量，服务里却不生效 | systemd 和容器不读用户 shell 配置 | 写进 unit 的 `Environment=` 或容器的环境变量 |
| `nvidia-smi` 说驱动有问题，改了半天框架 | 根因在驱动层，不在应用层 | 按 [[驱动-CUDA-框架版本兼容]] 的顺序自上而下查，别先动框架 |
| 全盘 `find` / `du` 搜模型文件，整机卡住 | 大量小文件把磁盘 IO 打满，同机服务跟着变慢 | 限定目录搜索（在 `/data` 下按项目找），避开业务时段 |

## 服务器安全最低基线

- **SSH**：改掉默认端口、尽量禁用密码登录改密钥（交付前先确认客户运维能接受）。
- **防火墙**：只放行真正要用的端口；数据库和推理服务默认不要直接暴露公网。
- **用户**：一个服务一个普通用户，别全用 root 跑。
- **权限**：密钥文件 `600`，配置目录别图省事给 `777`。
- **更新**：内核/驱动升级前先确认能回滚，客户生产机上尤其要谨慎。
- **留档**：把 unit 文件、compose 文件、配置改动清单留在客户机器上，同时自己留一份，下次维护不用从头猜。

## 交付视角（对客户怎么讲）

- 客户问「服务器为什么不能直接用 root」：一句话——权限太大，一次误操作就能把整台机器搞坏，而且出事时谁也说不清是谁改的。
- 客户问「服务为什么不能就开个窗口跑着」：讲清断线会死、不会自动重启、日志容易丢；正规做法是托管成系统服务或容器。
- 客户问「为什么要单独买数据盘」：模型和日志会持续占空间，写满系统盘会导致整机故障，数据盘是隔离风险。
- 报价/交付时把「环境盘点 + 服务托管 + 日志与磁盘规划」单独写进交付清单，这是客户能感知到的专业度。
- 客户说「我这台机器平时也有人用」：强调资源隔离和权限隔离，说明会新建用户、限端口、限显存，不影响别人办公。

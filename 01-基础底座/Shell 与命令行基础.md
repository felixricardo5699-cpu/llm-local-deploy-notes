# Shell 与命令行基础

> [!abstract] 一句话讲清楚
> Shell 是"把一堆小工具串起来干大事"的那层胶水。这篇讲清楚管道、重定向、环境变量、后台任务这四件事——它们决定了你部署时能不能把长任务挂住、能不能把日志留住、能不能搞明白"为什么同样的命令在客户机器上就失败"。

## 为什么重要

- **位置**：上游是 [[Linux 基础与服务器操作]]（知道文件和进程是什么），下游是 [[Python 环境与依赖管理]]（用命令装依赖、跑脚本）和 [[Docker 与容器化基础]]（容器操作全靠命令）。
- **部署的每一步都是命令**：装驱动、拉模型、起服务、看日志、拷数据，没有一步能绕开命令行。
- **不懂会怎样**：服务挂后台结果 SSH 一断就死；重定向用错把重要日志覆盖；`PATH` 里有两个 python 却一直用的是错的那个；在 Windows 上复制 Linux 命令直接报错。
- **真实场景**：客户要你把几十 GB 的模型从一台机器搬到另一台，下载要半小时以上，中途你的网络可能断。这时候你要会：后台跑、写日志、断线后回来接着看、确认它到底还在不在。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| shell | Shell | 你敲命令、它负责翻译并交给系统执行的程序 | 它只是"遥控器"，不是系统本身；换 shell 不影响服务 |
| bash / zsh / sh | Bash / Zsh / POSIX sh | 不同品牌的 shell，语法大体一样、细节有差 | 网上抄的脚本可能只在 bash 下能跑，`sh` 不认某些写法 |
| PowerShell | PowerShell | Windows 上的现代 shell，能传"对象"而不只是文本 | 和 bash 语法不兼容，不能直接互抄命令 |
| 标准输入 | stdin / fd 0 | 程序默认从这读数据（一般是键盘） | 管道会把上游输出接到这里，程序不用改代码 |
| 标准输出 | stdout / fd 1 | 程序正常结果的出口（一般是屏幕） | 日志和结果混在一起时，要分开重定向 |
| 标准错误 | stderr / fd 2 | 程序报错的出口，和 stdout 是两条道 | 只重定向 stdout 时，错误还是打到屏幕上，容易漏看 |
| 管道 | pipe / `\|` | 把前一条命令的输出，直接喂给后一条命令 | 只传文本流，不传文件；上游失败不一定让整条链失败 |
| 重定向 | redirection / `>` `>>` | 把输出改道写进文件 | `>` 是覆盖，`>>` 是追加；用错一次就能毁掉日志 |
| 文件描述符 | fd / 0 1 2 | 上面三个"口"的编号 | `2>&1` 写得越靠后越正确，顺序错了等于没写 |
| 环境变量 | environment variable | 给程序看的一张张小纸条，比如"模型路径在哪" | 不加 `export` 只对当前 shell 有效，子进程根本看不到 |
| PATH | PATH | 系统找命令时依次搜索的目录列表 | 排在前面的优先；多版本工具冲突大多出在这里 |
| 通配符 | glob / `*` `?` | 由 shell 先把文件名展开，再交给命令 | 它不是正则表达式；带空格的文件名会被拆开 |
| 引号 | single / double quotes | 单引号"原样照抄"，双引号允许变量替换 | 路径有空格、变量要展开时，引号写错是最常见的坑 |
| 命令替换 | `$(命令)` | 把一条命令的结果塞进另一条命令里 | 嵌套时用 `$()` 比反引号清楚；反引号容易和单引号混 |
| 退出码 | exit code / `$?` | 命令结束后留下的数字，`0` 表示成功 | 0 才是成功，非 0 是失败——和直觉相反，容易记反 |
| 作业控制 | job control / `&` `jobs` `fg` | 把命令丢到后台跑、再叫回前台 | 后台任务仍属于当前会话，SSH 断开照样死 |
| tmux / screen | 终端复用器 | 会话留在服务器上，你断开网络也不影响它 | 它保的是"终端会话"，不是"服务自动重启" |
| nohup | no hang up | 让命令忽略"挂断信号"，断线后继续跑 | 不负责崩溃重启，也不负责开机自启 |
| 换行符 | CRLF / LF | Windows 和 Linux 的换行编码不一样 | 从 Windows 传上去的脚本常报 `bad interpreter: ^M` |

## 原理与机制

### 直觉版

命令行像一条**流水线**：每个小工具只干一件小事，上一个的出口接下一个的入口。Shell 是站在产线边上的调度员，它先按规则把"变量、通配符、命令替换"展开成真正的命令，再启动程序、接好管道。

### 拆解版

1. **每个程序都有三个流**：stdin（进）、stdout（正常出）、stderr（出错出）。重定向和管道的本质，就是给这三个流重新接线。
2. **管道的方向**：上游的 stdout → 下游的 stdin。文字流式传输，所以适合 `grep`、`head`、`tail` 这类小工具；但中间的报错走 stderr，不会自动进管道。
3. **重定向的细节**：`>` 覆盖、`>>` 追加；`2>&1` 是"把 stderr 指到 stdout 当前指向的地方"，所以它必须写在 `>` 后面，顺序反了就指向屏幕。
4. **先展开，后执行**：变量 `$X`、命令替换 `$(...)`、通配符 `*`、花括号 `{a,b}` 都是 shell 在执行前替换好的。引号的作用就是阻止某几种展开：单引号全阻止，双引号只阻止一部分。
5. **环境变量与 PATH**：程序启动时从父进程继承环境变量。`PATH` 是一串目录，系统按顺序找你要的命令——这就是为什么"我明明装了新版本，跑起来还是旧的"。
6. **作业与信号**：`&` 把任务放后台，但它和终端在同一个会话里；终端断开时系统发 SIGHUP，这些进程默认就退出了。`nohup` 让进程忽略它，`tmux` 让会话本身活在服务器上。
7. **退出码是自动化的基础**：`0` 成功，非 0 失败。`&&`（前面成功才执行后面）、`||`（失败才执行）和脚本里的 `set -e` 都靠它。

### 后果

- 同一个任务，用错挂后台的方式 → SSH 一断，任务白跑。
- 重定向写成 `>` → 每次重启都把上一次的日志覆盖，出问题时没有现场。
- PATH 顺序不清楚 → 你以为在用虚拟环境里的 python，其实在用系统的，装了一堆却控制不到。
- 不检查退出码 → 脚本里某一步失败了没被发现，一路跑下去产出错的东西。

## 分类与对比：Bash / PowerShell / cmd

| 维度 | Bash（Linux） | PowerShell（Windows） | cmd（Windows 老壳） |
|---|---|---|---|
| 管道传什么 | 文本 | 对象（能直接取属性） | 文本 |
| 设环境变量 | `export KEY=值` | `$env:KEY = "值"` | `set KEY=值` |
| 引用变量 | `$KEY` / `${KEY}` | `$env:KEY` | `%KEY%` |
| 成功后才执行 | `&&` | `&&`（新版支持） | `&&`（部分版本） |
| 后台运行 | `命令 &` 或 `nohup` | `Start-Process` | `start /b` |
| 路径分隔符 | `/` | `\`（也支持 `/`） | `\` |
| 脚本换行 | LF | CRLF | CRLF |
| 适合场景 | 服务器部署、容器 | Windows 日常管理、装 Docker | 老工具兼容 |

> 结论：**服务器上的东西一律按 Linux/Bash 学**；自己 Windows 电脑上装环境用 PowerShell + WSL2，别指望两套命令能互抄。

## 完整流程：把一条手动命令变成"离开你也能跑"的任务

### 第 1 步：先在当前会话里把命令跑通

- **做什么**：小参数、小数据量先验证命令本身没问题。
- **为什么**：后面挂后台再出错，排查成本高得多。
- **验收**：命令在前台能正常结束，退出码为 0。

### 第 2 步：把输出落到日志文件

```bash
python infer.py > run.log 2>&1 &
```

- 这段在干嘛：让程序在后台跑，把正常输出和错误都写进 `run.log`。
- 关键点：`2>&1` 必须放在 `>` 后面；`&` 表示放后台。

- **为什么**：断线后你唯一能看的就是日志，没有日志等于瞎。
- **验收**：`tail -f run.log` 能看到持续输出。

### 第 3 步：选择托管方式

| 任务性质 | 推荐方式 | 理由 |
|---|---|---|
| 一次性批处理、下载、导出 | `nohup 命令 &` 或 `tmux` | 简单够用，任务结束就完事 |
| 需要边跑边交互、随时回看 | `tmux` | 会话在服务端，断线重连可继续 |
| 要长期稳定、要自动重启 | systemd unit 或容器 | 有重启策略、能开机自启 |
| 要交接给客户 | 容器 + compose | 环境可复现，操作有文档 |

### 第 4 步：确认它"真的在跑"

```bash
tmux new -s llm    # 新建会话
tmux attach -t llm # 断线后回来
```

- 这段在干嘛：在服务器上开一个持久会话，按 `Ctrl-b d` 可以暂时离开。
- 关键点：断开的是客户端，会话还在服务器上。

- **为什么**：很多人以为挂后台了，其实进程早退出了，只是没看日志。
- **验收**：用 `ps` 或 `jobs` 看到进程；日志在持续增长。
- **失败表现**：日志停在某一行不动、进程列表里查无此进程。

### 第 5 步：模拟断线，再回来验证

- **做什么**：主动断开 SSH 再连上，回来确认任务还在。
- **为什么**：这是唯一可靠的验证方式，别靠"应该没事"。
- **验收**：任务仍在运行，日志继续增长。

### 第 6 步：把命令固化下来

- **做什么**：命令写进 `run.sh`、写进 systemd unit、或写进 compose 文件，并在交付文档里说明怎么启动/停止/看日志。
- **为什么**：交付物是"客户能自己重启的东西"，不是你记得住的一条命令。
- **验收**：另一个人照文档能在 5 分钟内把服务拉起来。

## 管道实战：三个排查组合

### 组合 1：找"谁在占端口"

```bash
ss -tlnp | grep 8000
```

- 这段在干嘛：列出所有监听端口，再筛出 8000 那条。
- 关键点：管道把 `ss` 的输出直接交给 `grep`，不用先存成文件。

### 组合 2：边看边存日志

```bash
command 2>&1 | tee run.log
```

- 这段在干嘛：命令的输出同时显示在屏幕上、并写进 `run.log`。
- 关键点：适合"我要盯着进度，也得留证据"的场景。

### 组合 3：确认命令真的成功

```bash
命令 && echo OK || echo FAIL
```

- 这段在干嘛：按退出码决定打印 OK 还是 FAIL。
- 关键点：`&&` 前面成功才走，`||` 前面失败才走；脚本里批量执行时很有用。

> 注意：管道默认只看最后一环的退出码，中间某环失败可能被吞掉。重要脚本开头加 `set -o pipefail`。

## 决策点

- **岔路口 1：长任务怎么挂？** 一次性 → `nohup`；要交互 → `tmux`；正式服务 → systemd/容器（推荐）。代价：越正式，配置越多，但换来的可靠性对交付是必须的。
- **岔路口 2：覆盖还是追加？** 日志用 `>>` 追加；一次性结果文件用 `>` 覆盖但要确认路径没写错。推荐：日志一律追加 + 配轮转。
- **岔路口 3：单引号还是双引号？** 需要变量展开用双引号；要原样传给远程或正则用单引号。不确定时先用单引号试，避免意外的变量替换。
- **岔路口 4：Windows 上到底用哪套命令？** 涉及 Linux 工具链（Docker、CUDA、Shell 脚本）→ 用 WSL2；纯 Windows 管理（服务、注册表、磁盘）→ PowerShell。代价：WSL2 多一层文件系统，跨系统读写大文件会慢。
- **岔路口 5：变量写在哪？** 只在当前会话用 → `export`；只对自己生效 → `~/.bashrc`；要对所有用户/服务生效 → `/etc/environment`；systemd 服务 → 写进 unit 的 `Environment=`。选错就会出现"我明明设了但不生效"。
- **岔路口 6：要不要写成脚本？** 步骤超过 3 条、需要重复执行、或要交给客户 → 写脚本。代价：脚本本身也需要维护和测试。

- **岔路口 7：要不要上 WSL2？** 需要 Docker/Linux 工具链/复现服务器环境 → 上；只是偶尔传文件、看日志 → 用 SSH 客户端就够。代价：WSL2 占内存、跨系统大文件读写慢。

## 环境变量到底写在哪

| 写在哪 | 生效范围 | 什么时候被读取 | 常见坑 |
|---|---|---|---|
| 当前终端 `export` | 当前会话 | 每次开终端 | 关掉终端就没了 |
| `~/.bashrc` | 当前用户 | 交互式 shell 启动时 | systemd 服务、非交互脚本不读它 |
| `~/.bash_profile` | 当前用户 | 登录时 | 和 `.bashrc` 的加载时机不同，容易设了不生效 |
| `/etc/environment` | 所有用户 | 登录时 | 不执行 shell 语法，只能写 `KEY=值` |
| systemd unit `Environment=` | 该服务 | 服务启动时 | 不读任何 shell 配置，服务变量必须写这 |
| 容器 `-e` / compose `environment` | 该容器 | 容器启动时 | 和宿主机环境完全隔离，要在 compose 里显式传 |

> 判断口诀：**人是交互的 → 写 shell 配置；服务是托管的 → 写 unit 或容器配置**。混着写就会出现"我明明加了却不生效"。

## 参数与配置说明

| 参数 / 写法 | 作用 | 说明 | 常见用法 |
|---|---|---|---|
| `set -euo pipefail` | 让脚本"出错就停、未定义变量报错、管道中任一环失败就失败" | 不开容易带病继续跑 | 脚本开头常驻 |
| `>` / `>>` | 覆盖 / 追加输出 | 日志用 `>>` | `>> app.log` |
| `2>&1` | 把错误输出并入正常输出 | 顺序必须对 | `> app.log 2>&1` |
| `&` | 放后台 | 断线仍会死 | `命令 &` |
| `nohup` | 忽略挂断信号 | 输出默认进 `nohup.out` | `nohup 命令 > run.log 2>&1 &` |
| `tee` | 输出同时"写文件 + 显示" | 适合既要看又要存 | `... \| tee run.log` |
| `tail -f` | 实时跟踪文件末尾 | 配合 `-n 100` 先看最近 100 行 | `tail -f run.log` |
| `timeout` | 给命令加超时 | 防止脚本挂死 | `timeout 600 命令` |
| `-n` / `nproc` | 控制并行度 | 并行过高会抢 CPU/内存 | 视机器核数 |
| `$?` | 上一条命令退出码 | 0 成功 | 判断依据 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 重启后日志里只有最新一次记录 | 用 `>` 覆盖写 | 日志统一用 `>>`，或交给日志轮转管理 |
| 双引号里的变量正常，改成单引号后"值没了" | 单引号不展开变量 | 要展开就用双引号；要原样传就用单引号 |
| `nohup.out` 越来越大，最后磁盘写满 | 没指定输出文件，全堆在默认文件里 | 重定向到指定日志并配清理/轮转 |
| 在 `.bashrc` 里设了变量，systemd 服务里不生效 | 服务和登录 shell 是两套环境 | 写进 unit 的 `Environment=` 或容器环境变量 |
| Windows 上编辑的脚本传到 Linux 报 `bad interpreter: ^M` | 换行符是 CRLF | 改成 LF（编辑器或 `dos2unix`） |
| `rm -rf $DIR` 变量为空，结果删错目录 | 变量没定义，命令变成 `rm -rf` | 先 `echo` 确认路径；写法上加引号并判空 |
| 管道前半段报错，整条命令却"成功" | 默认只检查最后一环的退出码 | 用 `set -o pipefail` |
| 前台命令按 `Ctrl+Z` 后以为停了，其实在后台挂着 | `Ctrl+Z` 是暂停（SIGSTOP），不是结束 | 用 `jobs` 查看，`kill` 真正结束它 |
| 复制命令时带上换行/提示符，执行报错 | 多粘贴了 `$`、`#` 或换行 | 只复制命令本身；粘贴后先看一眼 |

## 交付视角（对客户怎么讲）

- 客户问「为什么要在服务器上敲命令」：一句话——图形界面只是包装，底层还是这些命令；远程服务器带宽有限，用命令行最快也最稳。
- 客户问「服务会不会我下班它就停了」：讲清楚托管方式，说明会用系统服务或容器托管，断线、重启都不影响。
- 客户问「你怎么保证操作不误删东西」：说明会先看再动、关键操作用备份和确认、不直接 `rm -rf` 变量路径。
- 交付时把启动/停止/看日志三条命令写进文档，客户能自助操作，你的售后压力会小很多。

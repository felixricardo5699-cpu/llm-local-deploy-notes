# 网络基础与内网穿透

> [!abstract] 一句话讲清楚
> 你的模型服务"能不能被外面访问"，只取决于三件事同时成立：程序监听对了地址、防火墙放行了、网络路径通了；内网穿透就是给没有公网 IP 的机器临时修一条路。

## 为什么重要

- 本地部署几乎一定会遇到"模型跑起来了，但同事/客户打不开"的问题，九成以上是这三要素里缺了一个。
- 客户现场常在内网、没有公网 IP、甚至不允许开端口；你要么做内网可达方案，要么做穿透，否则交付完等于没交付。
- 很多"框架 bug"其实是网络问题：流式输出卡住、上传大文件失败、连接被重置，都和代理、缓冲、超时有关。
- 你后面要学的服务化、API 鉴权、远程运维，全部建立在这一层认知上。
- 接单视角：能快速判断"是程序问题还是网络问题"，是交付时最省时间的一项能力。

## 核心名词全解

| 名词 | 英文/缩写 | 大白话解释 | 容易混淆/注意 |
|---|---|---|---|
| IP 地址 | IP | 网络里一台机器的门牌号 | 公网 IP 和内网 IP 是两套世界 |
| 公网 IP / 内网 IP | Public / Private IP | 公网 IP 全世界能找到；内网 IP 只在局域网里有效 | 家里的宽带多数没有固定公网 IP |
| 网络地址转换 | NAT | 路由器帮你把内网请求转出去，回来再转回来 | 出去的能回来，外面主动进来很难 |
| 端口 | Port | 一台机器上不同服务的门牌号，如 8000 | 服务只能占一个端口，冲突就起不来 |
| 监听地址 | Bind address | 服务在哪张"网卡/地址"上等请求 | `127.0.0.1` 只给自己，`0.0.0.0` 给所有网卡 |
| 域名解析 | DNS | 把域名翻译成 IP 的通讯录 | 改了解析要等缓存过期 |
| hosts | hosts | 本机私有的"域名→IP"对照表 | 只对这台机器生效，排错时能救命 |
| HTTP / HTTPS | HTTP(S) | 网页和 API 用的传输协议，HTTPS 是加密版 | 本地服务默认是 HTTP，浏览器会提示不安全 |
| 反向代理 | Reverse proxy | 站在服务前面的门卫，统一收请求再转给后端 | 和"正向代理"方向相反，别记混 |
| 防火墙 | Firewall | 决定哪些端口可以进出的关卡 | 系统防火墙和云安全组是两道关 |
| 安全组 | Security group | 云服务器控制台上配的端口白名单 | 常常是"本机通了、外面不通"的元凶 |
| 端口转发 | Port forwarding | 把 A 端口的请求转到 B 端口 | Docker 的 `-p` 就是端口转发 |
| SSH 隧道 | SSH tunnel | 借 SSH 连接把端口"搬"到另一台机器上 | 轻量、临时，断了就没了 |
| 内网穿透 | NAT traversal | 让没有公网 IP 的机器被外面访问到 | 工具很多，原理都是"内网主动向外连" |
| WebSocket / SSE | WebSocket / SSE | 长连接；SSE 是单向的流式推送，大模型输出常用 | 中间有代理缓冲时，流式会"憋着不出来" |
| 带宽 / 延迟 | Bandwidth / Latency | 一次能搬多少数据 / 数据多久到 | 流式体验主要卡延迟，下载模型主要卡带宽 |

## 原理与机制

### 直觉版

- 把网络想成寄快递：IP 是收件地址，端口是房间号，域名是好记的昵称。
- 你从内网寄出去，路由器（NAT）帮你换成对外的地址寄走，回件也能按记录送回你手上。
- 但外面的人想主动给你寄件，路由器不知道你是谁，就退回了。
- 内网穿透就是"你的机器主动挂一个快递员在外面等着，有件他再转给你"。

```mermaid
flowchart LR
    A["客户端浏览器"] --> B["DNS 域名解析"]
    B --> C["防火墙 / 云安全组"]
    C --> D["反向代理"]
    D --> E["模型服务 :8000"]
```

- 请求按箭头顺序走，任何一环没放行，用户看到的现象都是"打不开"或"一直转圈"。
- 所以排查时照着箭头从头到尾逐段验证，比东一榔头西一棒子快得多。

### 拆解版

**1. 一次请求在服务端经历了什么**

- 客户端发请求到 `IP:端口` → 到达宿主机的网卡 → 被防火墙检查 → 交给监听该端口的进程。
- 进程如果是反向代理（如 Nginx），它再把请求转给后端真正干活的端口。
- 后端返回 → 原路返回给客户端。
- 任何一环断了，表现都是"连不上"或"超时"，所以必须按链路顺序查。

**2. 能不能被访问，只看三件事**

- 监听地址对不对：服务必须监听 `0.0.0.0`（或宿主机网卡 IP），只听 `127.0.0.1` 时外部永远进不来。
- 防火墙放没放行：系统防火墙（如 ufw、firewalld）和云厂商安全组，两道都要开。
- 网络路径通不通：同一个局域网能通，不代表外网能通；没有公网 IP 就必须穿透。

**3. NAT 带来的后果**

- 家里宽带和公司内网通常都是 NAT 后面的内网地址。
- 内网机器主动向外请求是通的（比如下载模型、调用外部 API）。
- 外部主动连内网机器基本不通，除非在路由器上做过端口映射。
- 所以部署在内网的服务，默认只有同一个局域网内的人能用。

**4. 反向代理为什么几乎是必需品**

- 统一入口：对外只开一个端口（通常是 443），内部多少服务都藏在后面。
- 统一加密：HTTPS 证书只装在一处，后端还是明文 HTTP。
- 统一鉴权：加一层访问控制，多个服务共用。
- 统一缓冲与超时设置：这既是好东西（保护后端）也是坑（把流式输出憋住）。

**5. 流式输出为什么怕缓冲**

- 大模型输出是一个 token 一个 token 推给前端的，中间任何一层开启缓冲，都会攒一批才转发。
- 用户看到的现象是"转圈半天，然后整段答案突然出现"。
- 涉及的三层都要检查：应用本身是否 flush、反向代理是否关闭缓冲、客户端是否用 SSE/流式读取。
- 很多"模型很慢"的投诉，其实是代理缓冲导致的假慢。

### 后果

- 服务只听 `127.0.0.1` → 本机测试全绿，一交给别人就"打不开"。
- 只开系统防火墙、没开云安全组 → 你在服务器上怎么测都通，客户浏览器就是连不上。
- 直接暴露端口到公网、不做鉴权 → 几小时内就会被扫描器找到，轻则被白嫖算力，重则被塞东西。
- 反向代理默认缓冲不关 → 流式接口体验极差，客户以为模型性能不行。

## 分类与对比

### 内网穿透三种常见方案

| 方案 | 原理 | 成本 | 安全 | 延迟 | 适合谁 |
|---|---|---|---|---|---|
| SSH 隧道 | 借 SSH 连接把端口转到公网机器 | 需要一台有公网 IP 的中转机 | 较高，走 SSH 加密 | 低 | 临时调试、远程运维 |
| frp 类工具 | 内网客户端主动连公网服务端，建立反向隧道 | 需要公网服务器或服务 | 中等，需自己配鉴权 | 低 | 长期稳定对外提供服务 |
| 基于虚拟组网的方案 | 把多台机器组进同一个虚拟局域网 | 通常有免费额度，商业版付费 | 较高，控制面加密 | 视线路而定 | 自己多台机器互访、团队协作 |

### 对外暴露的三种姿态

| 姿态 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 端口直连 | 防火墙开放 `IP:端口` | 最简单、最快 | 无加密、无鉴权、容易被扫 |
| 域名 + 反向代理 | 域名指向代理，代理转后端 | 可上 HTTPS、可鉴权、可统一管理 | 多一层配置，可能引入缓冲问题 |
| 虚拟专用网络 | 先把人拉进同一内网再访问 | 不对外暴露端口，最安全 | 每个使用者都要装客户端并授权；对“只要一个网页”的客户来讲门槛偏高 |

## 完整流程：从"本机能用"到"外面能用"

### 第 1 步：本机自己先通

- **做什么**：在服务器上执行 `curl -v http://127.0.0.1:8000/`。
- **为什么**：先排除服务本身的问题，把变量降到最少。
- **验收标准**：返回正常响应，查看命令输出可达。
- **失败表现**：本机就报连接被拒，说明服务没起或端口不对，与网络无关。

### 第 2 步：确认监听地址

- **做什么**：用 `ss -tlnp` 看监听地址是 `127.0.0.1:8000` 还是 `0.0.0.0:8000`。
- **为什么**：这是"外面打不开"最最常见的原因。
- **验收标准**：显示 `0.0.0.0:8000` 或 `*:8000`，而不是 `127.0.0.1`。
- **失败表现**：本机通、局域网内其他机器不通 → 基本可以断定只听回环地址。

### 第 3 步：局域网内再试一次

- **做什么**：用同一局域网另一台机器访问 `http://服务器内网IP:8000/`。
- **为什么**：验证防火墙是否放行，把"服务"和"网络"分开判断。
- **验收标准**：局域网能通。
- **失败表现**：局域网不通 → 查系统防火墙和端口占用。

### 第 4 步：决定要不要对外暴露

- **做什么**：和客户确认：只有内网用、还是要公网访问；给多少人用；能不能接受装客户端。
- **为什么**：这决定你用反代、穿透还是虚拟组网，别自己先动手。
- **验收标准**：写下一句话方案，客户确认。
- **失败表现**：先做公网暴露，结果客户安全要求不允许 → 白干。

### 第 5 步：放行防火墙 / 安全组

- **做什么**：系统防火墙放行端口，云控制台安全组加一条入站规则。
- **为什么**：这两道关是独立生效的，少一道都不通。
- **验收标准**：`curl` 从公网能连上（或穿透后能连上）。
- **失败表现**：安全组只放了 22 端口，服务端口怎么都不通。

### 第 6 步：套反向代理 + 鉴权 + HTTPS

- **做什么**：域名解析到服务器 → 反向代理转发到后端端口 → 配 HTTPS → 加访问控制。
- **为什么**：对外服务必须考虑加密和鉴权，裸端口等于把门敞着。
- **验收标准**：浏览器显示安全连接，未授权访问被拦截，流式输出正常。
- **失败表现**：HTTPS 能开但流式输出变成"整段弹出" → 代理缓冲没关。

### 第 7 步：收尾：关掉多余端口、留存访问记录

- **做什么**：只保留必要端口，记录谁在用、访问日志在哪、限流规则是什么。
- **为什么**：暴露面越小越安全，出问题也更容易定位。
- **验收标准**：端口扫描只剩预期端口，日志可查。
- **失败表现**：调试时开的临时端口忘了关，后面成了被扫描的入口。

## 决策点

- **岔路口 1：要不要暴露公网？** 使用者都在内网 → 不暴露；有外部客户 → 先用虚拟组网，不行再穿透 + 反代。代价：不暴露最安全但协作受限。
- **岔路口 2：端口直连还是域名 + 反向代理？** 推荐域名 + 反向代理。代价：多一层配置，还要处理缓冲和超时问题。
- **岔路口 3：穿透选哪种？** 临时调试、已有一台公网机器 → SSH 隧道；长期对外服务 → frp 类反向代理；多台机器互访、团队使用 → 虚拟组网。代价：越稳定越需要额外资源或费用。
- **岔路口 4：证书怎么来？** 有域名 → 用自动签发；纯内网 → 自签证书或直接内网 HTTP。代价：自签证书浏览器会警告，客户体验差。
- **岔路口 5：要不要加访问鉴权？** 只要不是纯内网 → 必须加。最低配是反向代理层加账号密码或令牌。代价：多一步分发凭证。
- **岔路口 6：流式接口被缓冲怎么办？** 先关反向代理缓冲，再看应用层是否 flush，最后查客户端读取方式。推荐按这个顺序。
- **岔路口 7：能不能用动态域名 + 端口映射替代穿透？** 有公网 IP 可以；没有公网 IP 就不行，只能在路由器上折腾也没用。代价：动态 IP 还要处理地址变化。

## 参数与配置说明

| 命令 / 配置 | 作用 | 关键点 |
|---|---|---|
| `ss -tlnp` | 看谁在监听哪些端口 | 重点看监听地址与进程 |
| `curl -v 地址` | 带细节发请求 | 连不上还是返回慢，一眼能分清 |
| `curl -N` | 关闭 curl 自己的缓冲 | 测流式输出必须加 |
| `proxy_buffering off` | 反向代理关闭缓冲 | 流式接口必须配 |
| `proxy_read_timeout` | 后端多久没响应算超时 | 长任务要调大 |
| `client_max_body_size` | 允许的上传大小 | 上传文件报 413 就是它 |
| `proxy_set_header` | 把客户端信息透传给后端 | 少了后端拿到的都是代理 IP |
| `serverAddr` / `serverPort`（frp 客户端） | 穿透服务端地址 | 用域名或固定 IP |
| `localPort` / `remotePort`（frp 客户端） | 本地端口 / 公网映射端口 | 一对一映射，别写反 |
| `ssh -L 本地:目标:端口` | 本地端口转发 | 把远端服务搬到本地访问 |
| `ssh -R 远端:目标:端口` | 远程端口转发 | 把本地服务暴露到远端机器 |
| `ufw allow 端口` | 放行端口 | 改完记得确认生效 |
| `0.0.0.0` | 监听所有网卡 | 服务启动参数的常见默认值坑 |
| `TZ` / `LANG` | 时区与编码 | 影响日志时间和中文显示 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 本机能访问，别人访问不了 | 服务只监听 `127.0.0.1` | 启动参数改成 `0.0.0.0` |
| 局域网通、公网不通 | 云安全组没放行端口 | 控制台加入站规则，再测 |
| 端口明明没被占，服务起不来 | 进程需要更高权限的端口，或绑定地址冲突 | 换端口，或用非特权端口 |
| 流式输出变成"卡很久后一次性出现" | 反向代理开启缓冲 | 关闭缓冲，检查应用层 flush |
| 上传大文件失败 | 代理或框架的请求体上限太小 | 调大 `client_max_body_size` 等上限 |
| 从外网访问自己的公网地址不通 | NAT 回环未支持 | 用内网地址测，或换穿透方案 |
| HTTPS 配好后接口报错 | 后端还在用 HTTP 且代理配置不匹配 | 统一协议与端口，检查转发头 |
| 临时穿透能用，过几天失效 | 使用的是临时地址或会话过期 | 长期服务要固定方案 + 监控 |
| 服务突然被陌生 IP 高频访问 | 裸端口暴露被扫描 | 关闭端口、加鉴权、加强制证书 |

## 自检问题参考答案

> [!success]- 1. 能被访问的三个必要条件
> 三件事同时成立才行：**监听地址对**（服务监听 `0.0.0.0` 或宿主机网卡 IP，不能只听 `127.0.0.1`）、**防火墙放行**（系统防火墙和云厂商安全组两道关，少一道都不通）、**网络路径通**（同一局域网能通不代表外网能通，没有公网 IP 就必须做穿透）。任何一条不满足，用户看到的现象都是"打不开"或超时，所以排查时按这三条逐条验证最快。

> [!success]- 2. `127.0.0.1` 和 `0.0.0.0` 的区别
> `127.0.0.1` 是回环地址，只有这台机器自己能访问；`0.0.0.0` 表示监听所有网卡，局域网和其他机器才能连进来。最典型的坑：服务默认只听回环，你在服务器上 `curl 127.0.0.1:8000` 全绿，一交给别人就"打不开"。所以部署完要用 `ss -tlnp` 确认监听地址是 `0.0.0.0:8000`，改完再用防火墙把访问范围收窄，别裸着。

> [!success]- 3. 没有公网 IP 为什么外部连不进来
> 这类机器在内网 NAT 后面，用的是内网地址：它主动向外发请求是通的（下载模型、调外部 API 都没问题），但外面的人主动连它时，路由器不知道这个请求该转给谁，就进不来。除非在路由器上做端口映射，否则内网服务默认只有同一个局域网内的人能用。要对外，就得靠内网主动向外建立的通道（穿透）或虚拟组网。

> [!success]- 4. 反向代理还能解决什么
> 除了转发，它主要干四件事：统一入口（对外只开一个端口，内部多少服务都藏在后面）、统一加密（HTTPS 证书只装一处，后端仍是明文 HTTP）、统一鉴权（多个服务共用一层访问控制）、统一缓冲与超时（保护后端，但也可能把流式输出憋住）。还能把客户端信息透传给后端，否则后端看到的都是代理 IP。

> [!success]- 5. 流式输出卡住的排查顺序
> 先看应用自己有没有 flush、客户端是不是用 SSE/流式方式读，可以用 `curl -N` 关掉客户端缓冲来测；再查反向代理是不是开了缓冲，流式接口必须配 `proxy_buffering off`；最后看长任务的超时设置够不够。典型现象是"转圈半天，然后整段答案突然出现"，很多"模型很慢"的投诉其实是代理缓冲造成的假慢。

> [!success]- 6. SSH 隧道与 frp 分别适用什么场景
> SSH 隧道是借一条 SSH 连接把端口搬过去，轻量、临时、断了就没了，适合临时调试和远程运维，但需要一台有公网 IP 的中转机。frp 这类工具是内网客户端主动连公网服务端、建立反向隧道，适合长期稳定对外提供服务，代价是要自己准备公网服务器并配好鉴权。多台机器互访、团队协作则更适合虚拟组网方案。

> [!success]- 7. 对外暴露为什么必须鉴权和加密
> 直接暴露裸端口，几小时内就会被扫描器找到：轻则被白嫖算力，重则被塞东西、被当成跳板。所以只要不是纯内网，就必须加访问控制——最低配是在反向代理层加账号密码或令牌，同时套 HTTPS 保护传输。再配合只保留必要端口、记录访问日志、设置限流，暴露面越小越安全。

## 交付视角

- 对客户怎么讲："服务只在我们约定的端口上对外提供，有加密和访问控制，其他端口一律关闭。"
- 客户 IT 会问"要不要开放公网"：先问清楚使用者范围；能内网就内网，必须公网就只开一个入口 + 鉴权。
- 客户常问"为什么内网能用、他们回家就打不开"：用大白话说清公网/内网和穿透的区别，别讲术语。
- 客户问"流式输出是不是很重要"：要，尤其对话类场景；这是体验分水岭，部署验收时要专门测一遍。
- 报价时把"网络接入方案 + 安全加固"单独列项，并写清是内网方案还是公网方案、谁提供域名和服务器。

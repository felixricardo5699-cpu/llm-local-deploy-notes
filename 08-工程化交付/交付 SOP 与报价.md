# 交付 SOP 与报价

> [!abstract] 一句话讲清楚
> 把"上门装个模型"这件事拆成有先后顺序、有交付物、有验收标准、有价格依据的流程：需求评估 → 方案与报价 → 实施 → 验收 → 售后。

## 为什么重要

- **报价不是拍脑袋**：同样的"部署一个本地大模型"，客户场景不同，工作量能差五倍。没有评估表，你要么报高了丢单，要么报低了白干。
- **工期估算错是亏钱主因**：技术活往往 1~2 天，但等客户批网络、装驱动、给数据、走验收流程，能拖两周。工期内不含"客户配合周期"，必亏。
- **验收标准不写清，尾款收不到**：客户一句"效果不太好"就能卡住。必须把"达标"变成可测的条目。
- **预期管理是口碑**：客户以为本地模型等于线上大模型，第一句话就会失望。事前讲清楚边界，事后才不会有纠纷。

上游是这一层其他所有笔记（技术能力决定报价项），下游是 [[项目阶梯与实战清单]] 和 [[高频咨询问题与话术]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| SOP | Standard Operating Procedure | 标准作业流程，固定步骤和交付物 | 不是文档摆设，是防止漏项的检查表 |
| 需求评估 | Requirement Assessment | 把客户"我想要个 AI"翻译成机器、模型、功能 | 评估表填不出来就不要报价 |
| 显存预算 | VRAM Budget | 这台机器能装下多大的模型、多长的上下文 | 不是"能加载就行"，要留出 KV Cache 和并发余量 |
| 工作量拆解 | WBS | 把项目拆成可估时的小块 | 拆到 4 小时粒度才估得准 |
| 工期 | Lead Time | 从开工到交付的总时间 | 分"实际工时"和"日历周期"，二者差很多 |
| 交付物 | Deliverable | 交付时能点交的东西（能跑的服务、文档、镜像） | 只交"服务"最吃亏，文档和镜像也是交付物 |
| 验收标准 | Acceptance Criteria | 判定"做完了"的可测条件 | 主观描述（效果好）不算标准 |
| 尾款 | Final Payment | 验收通过后付的部分 | 尾款比例和验收条件必须挂钩 |
| 售后 | After-sales | 交付后的问题处理与维护 | 分质保期（免费修 bug）和运维期（付费服务） |
| 变更 | Change Request | 交付过程中新增的需求 | 一定要书面确认，口头加需求是亏损源头 |
| 预期管理 | Expectation Management | 事前把能力边界说清楚 | 越早说越值钱，越晚说越像找借口 |
| 报价锚点 | Price Anchor | 让客户有对比的报价单位（按功能/按服务/按人天） | 不同锚点适合不同客户，选错很难谈 |

## 原理与机制

### 直觉：报价 = 交付物 × 难度 × 风险

不要按"我花了几天"报价，客户不关心你的工时。按**客户得到什么**报价：

- 一个能用的问答服务 vs 一个接入他们 OA 系统的问答服务 —— 后者贵在集成和联调，不贵在模型。
- 一台机器上的服务 vs 三十个人在用的服务 —— 后者贵在权限、稳定性和运维。

**给客户看的报价单应该只有"交付物"和"价格"，工时是你的内部成本，不出现在客户面前。**

### 关键机制：显存决定模型，场景决定显存需求

需求评估的第一个大坑是"客户要 671B 效果，只有一张 4090"。评估表的作用就是把这个矛盾在报价前暴露出来。

粗略的判断链条（具体数字以模型卡和实测为准）：

| 机器量级 | 适合的模型量级 | 适合的场景 | 需要提醒的限制 |
|---|---|---|---|
| 8G 显存（消费卡/笔记本） | 小参数量 + 量化 | 个人助手、文本处理、简单问答 | 长文档吃不下，速度一般 |
| 16~24G 显存（单张 4090/4080 级） | 中等参数 + 量化，或小参数全精度 | 部门级知识库问答、写作辅助 | 并发个位数，长上下文受限 |
| 48~80G 显存（专业卡/多卡） | 中等参数全精度或较大参数量化 | 多人使用、复杂 RAG、代码助手 | 并发仍有限，需要批处理优化 |
| 多卡（多张 80G 级） | 大参数模型 | 高质量问答、复杂推理 | 成本高，多卡通信有额外开销 |

**关键提醒**：显存不是"模型大小 ≤ 显存"就行。要留出：KV Cache（随上下文和并发涨）、框架开销、显存碎片余量。经验上给模型本身留出显存的 60%~70%，其余留给运行时。

### 关键机制：工期 = 技术工时 + 客户配合周期 + 缓冲

新手只算第一项，所以永远超期。

- **技术工时**：环境适配、部署、调优、测试、写文档。
- **客户配合周期**：等机器到位、等网络开通、等数据脱敏、等 IT 审批、等验收排期。这一项经常比技术工时还长，且不受你控制。
- **缓冲**：不可预期问题的余量。

**报价和排期都要基于"日历周期"，而不是"我埋头干几天"。** 给客户的交付日期要给客户配合留出明确的前置条件："收到机器和网络权限后 N 个工作日内完成"，而不是"下周给你"。

### 关键机制：验收标准要写成"可执行的检查"

坏标准：效果好、速度快、能用。
好标准：

- 用客户提供的 20 条真实问题测试，回答"内容相关且无明显幻觉"的比例达到约定值（由客户判定）；
- 单请求首字延迟在客户场景下不超过约定值；
- 服务在客户机器上重启后能自动恢复；
- 文档齐全，客户能按文档独立重启服务并取日志。

**验收标准要在报价前就跟客户确认，写进合同附件。** 事后补标准，客户只会往严了定。

## 完整流程

`输入 → 动作 → 输出 → 验收标准`

### 阶段一：需求评估（1~3 天）

**输入**：客户的场景描述、机器情况、预算范围。

**动作**：填需求评估表。

| 评估项 | 要问的 | 影响什么 |
|---|---|---|
| 使用场景 | 问答/知识库/写作/代码/多模态 | 决定模型类型与引擎 |
| 使用者数量 | 几个人、并发峰值 | 决定显存预算与是否要排队 |
| 数据形态 | 文档/表格/图片/音视频、多少量 | 决定要不要 RAG、解析工作量 |
| 机器现状 | 显卡型号数量、内存、磁盘、系统、是否有网 | 决定可行性、是否需要建议采购 |
| 网络环境 | 内网/公网、是否允许远程 | 决定交付方式（见 [[远程交付与远程运维]]） |
| 数据合规 | 能否出内网、有无行业要求 | 决定鉴权、日志、模型选型（见 [[安全与合规]]） |
| 现有系统 | 要不要对接 OA/CRM/网站 | 决定集成工作量（最容易低估） |
| 预算与期望 | 预算区间、上线时间、谁拍板 | 决定方案档位与报价锚点 |
| 谁验收 | 业务方还是 IT | 决定验收标准怎么写 |

**输出**：一份"可行性 + 方案档位 + 报价区间"的一页纸。

**验收标准**：客户能在这份纸上指出"我要的是这个档位"，且双方对"不做什么"有共识。

### 阶段二：方案与报价（1~2 天）

**动作**：给 2~3 个档位，而不是一个价。

- 基础档：能跑起来、能用、有文档。
- 标准档：基础 + 集成 + 性能达标 + 监控。
- 增强档：标准 + 安全加固 + 定期运维 + 培训。

**为什么给多档**：客户不一定选最便宜的，但一定要有对比。只报一个价，客户只会砍价；给三档，客户在选"要哪些"，不是在选"便宜多少"。

**输出**：报价单 + 方案说明 + 工期（含前置条件）。

### 阶段三：实施（按规模 3~15 个工作日）

按顺序做，每一步有产出：

1. 环境确认：拿到机器、驱动版本、网络权限（**这一步经常卡住**）。
2. 基础部署：引擎起来、模型加载、API 通。（见 [[本地部署全流程]]）
3. 容器化/固化：做成镜像和 compose，开机自启。（见 [[容器化部署]]）
4. 功能联调：接客户端/业务系统/RAG。
5. 性能达标：按 [[性能调优清单]] 调到约定指标。
6. 安全加固：鉴权、限流、日志策略。（见 [[安全与合规]]）
7. 监控与文档：健康检查、自检脚本、运维文档。（见 [[监控与日志]]）

**每一阶段结束给客户一个一句话进展**，不要失联。失联是客户焦虑和加需求的源头。

### 阶段四：验收（1~3 天）

**动作**：

1. 按合同里的验收条目逐条过，客户方签字或邮件确认。
2. 做一次"客户独立操作"演练：客户自己重启服务、取日志、跑测试用例。
3. 交付全部交付物，做交付清单确认。
4. 开一次 30 分钟培训（操作 + 排错 + 找谁）。

**输出**：验收单 + 交付物清单签收。

**验收标准**：合同条目全过 + 客户能独立完成基本操作 + 尾款条件达成。

### 阶段五：售后（按约定周期）

- **质保期**（通常几周到几个月）：交付内容本身的缺陷免费修。
- **运维期**（付费）：监控、巡检、响应、版本升级、模型切换。
- **边界**：客户改坏了、换了硬件、加了新需求，都算变更，另计。

## 决策点

- **岔路口 1：客户机器不够，接不接**
  - 推荐：**不硬接**。给两个选项：降需求（小模型/短上下文/少并发）或建议采购（你可以代配或只出建议，不赚硬件钱）。
  - 代价：丢单风险；但硬接的结果是验收不过、口碑受损。

- **岔路口 2：报价按项目还是按人天**
  - 小项目/需求清晰 → 按项目（客户喜欢确定价）。
  - 需求模糊/长期合作 → 按人天或按阶段。
  - 推荐：**对外按项目报，对内按人天核算**。客户看到人天会开始算"你一天值多少钱"。
  - 代价：按项目报要自己承担超期风险，所以评估要保守。

- **岔路口 3：接不接"效果类"验收**
  - 客户要求"准确率 90%"这类主观指标时要小心。
  - 推荐：**把主观指标转成可测流程**（客户出题、客户判定、约定比例），并约定"未达标的处理方式"（调优轮次 / 换模型 / 退部分款）。
  - 代价：测起来麻烦，但不这样做，验收就是无底洞。

- **岔路口 4：要不要免费加"顺便做"的需求**
  - 推荐：**一律走变更单**，小额可以赠送但要明确说"这次送你的"。
  - 代价：短期显得不好说话；长期能避免项目烂尾。

- **岔路口 5：售后包月怎么定价**
  - 推荐：按"是否含响应时间承诺"分档。含 SLA 的贵，不含的便宜。
  - 代价：含 SLA 意味着你要随时能响应，要有余量。

## 参数与配置说明

> 这一节的"参数"是报价与合同要素。

| 要素 | 作用 | 调高/调低的影响 | 常见做法 |
|---|---|---|---|
| 预付款比例 | 启动资金与客户诚意 | 太高客户犹豫，太低你没保障 | 三到五成，按项目规模 |
| 尾款比例 | 验收后的约束力 | 太低客户不着急验收 | 不低于三成 |
| 质保期 | 免费修缺陷的时长 | 太长成本高，太短客户不放心 | 按项目复杂度定，写清范围 |
| 响应时间（SLA） | 出问题多久响应 | 承诺越短成本越高 | 分级：紧急/一般/咨询 |
| 变更单价 | 新增需求的计价基准 | 没有基准就会扯皮 | 提前约定人天单价 |
| 验收测试样本数 | 用多少条真实问题测 | 太少不具代表性，太多测不完 | 20~50 条客户真实问题 |
| 工期缓冲 | 应对意外的余量 | 不给缓冲必然超期 | 技术工时的 30% 起 |

## 交付物清单（模板）

- [ ] 可运行的服务（含镜像或安装包）
- [ ] 启动/停止脚本与开机自启配置
- [ ] 配置文件（参数有注释，不是裸 YAML）
- [ ] 模型文件位置说明与替换方法
- [ ] API 文档（地址、鉴权方式、请求示例、错误码）
- [ ] 运维手册（启停、日志位置、自检命令、常见问题）
- [ ] 监控与告警说明（如包含）
- [ ] 安全材料（数据流图、权限清单、日志策略、模型授权说明）
- [ ] 验收测试记录（测试用例与结果）
- [ ] 培训录屏或培训提纲
- [ ] 交接清单（账号回收、通道关闭）

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 报完价客户就没消息了 | 报的是"工时"不是"价值"，客户无法比较 | 给多档方案，每档写清客户能得到什么 |
| 项目做到一半发现机器不够 | 需求评估跳过了机器确认 | 评估表第一项就填显卡和驱动版本 |
| 验收拖了一个月收不到尾款 | 验收标准是主观描述 | 报价前把验收条目写成可测项并双方确认 |
| 客户不停加小需求，越做越亏 | 没有变更机制，碍于情面全接 | 所有新增走变更单；小额赠送要明确说出口 |
| 工期承诺了却一直等客户 | 工期没区分"工时"和"日历周期" | 交付日期写"收到前置条件后 N 个工作日内" |
| 客户拿线上大模型的效果做对比 | 预期没管理 | 第一次沟通就演示本地模型的实际表现和限制 |
| 售后半年白干 | 质保期没写范围，"有问题"全包 | 质保只覆盖交付内容缺陷；新需求/误操作/硬件故障另计 |
| 交付完客户不知道能干什么 | 没有培训和使用场景引导 | 交一次培训 + 一份"怎么用"的一页纸，比堆功能有用 |

> [!warning] 一条经验
> 项目亏损的最大来源不是报价低，是**范围不清**。报价低但范围清楚的项目能赚钱；报价高但范围模糊的项目一定亏。

## 自检问题参考答案

> [!success]- 1. 需求评估表里哪一项最容易漏、漏了最致命？
> 机器与驱动确认最容易漏。只问"想要什么效果"，没问显卡型号、显存、驱动版本，实施时才发现装不下，只能临时降需求或建议采购，报价和口碑都受伤。
> 这张表第一项就该填显卡和驱动版本，填不出来先别报价。

> [!success]- 2. 为什么"显存够装模型"不等于"能交付"？还要留哪些余量？
> 模型权重只是显存账单的一部分。运行时还要留 KV Cache（随上下文和并发上涨）、框架开销、显存碎片余量。
> 经验上给模型本身留 60%~70%，其余给运行时；判据要按"峰值 + 并发"算，不是"能加载就行"。

> [!success]- 3. 工期为什么必须区分工时和日历周期？
> 技术工时是埋头干的天数；客户配合周期是等机器、等网络开通、等数据脱敏、等审批、等验收排期，常常比技术工时还长，而且不受你控制。
> 所以对客户承诺要写"收到前置条件后 N 个工作日内完成"，不要写"下周给你"。

> [!success]- 4. 为什么给三档方案比报一个价更好谈？
> 只报一个价，客户能做的动作只有砍价；给基础档、标准档、增强档三档，客户是在选"要哪些交付物"，谈的是范围而不是折扣。
> 三档的区别要写清：能跑起来能用、加上集成与性能达标、再加安全加固与运维，客户自己就能对上号。

> [!success]- 5. 验收标准怎么写才算"可测"？举一个把主观变客观的例子。
> 可测＝双方能当面或书面判定的条目。比如把"效果好"改成：用客户提供的 20~50 条真实问题测试，"内容相关且无明显幻觉"的比例达到约定值、由客户判定。
> 再配"首字延迟不超约定值""重启后能自动恢复""客户能按文档独立启停取日志"，并约定未达标怎么处理（调优轮次/换模型/退部分款）。

> [!success]- 6. 变更单解决什么问题？为什么不能靠"这次先帮你做"。
> 变更单把"新增需求另计"变成书面依据，防止口头"顺便做"累积成无底洞；没有它，范围越做越大，亏损和扯皮都从这里开始。
> 小额需求可以送，但要明确说"这次送你的"，否则客户会当成常态，下次不送反而不高兴。

> [!success]- 7. 质保期和运维期的边界在哪？
> 质保期免费修的是"交付内容本身的缺陷"，按项目复杂度定，写清范围；运维期是付费服务，含监控、巡检、响应、版本升级、模型切换，按是否含响应时间承诺分档定价。
> 边界外的事——客户误操作、换硬件、加新需求、断电断网——都按变更或工单另计。

> [!success]- 8. 你认为交付里最容易被低估的工作量是哪一块？
> 是集成联调和客户配合周期。评估表里"现有系统要不要对接"最容易被低估，对接 OA/CRM/网站往往比部署本身费时间；而等机器、等审批、等验收排期更是不可控。
> 技术部署本身常常 1~2 天就完，报价和排期要把这两块单列出来，别都压进"部署"里。

## 交付视角（对客户怎么讲）

- **客户问"多少钱"**：先反问场景和机器，再给区间。"同样叫本地大模型，8G 显存跑个小模型和双卡跑知识库，工作量差好几倍，我先确认一下您的场景。"
- **客户问"为什么比买软件贵"**：软件是标准品，您买的是"适配您的机器、您的数据、您的流程"，还包括出问题有人管。
- **客户问"能不能便宜点"**：降价要换范围，不要直接让价。"可以去掉 XX 和 YY 两项，价格能到 Z。"
- **报价口径**：按"基础部署 / 集成联调 / 性能达标 / 安全加固 / 运维服务"分项，客户能自己勾选，也知道钱花在哪。
- **必须提前说的限制**：效果受机器和数据质量限制；本地模型不等于线上旗舰模型；不承诺"什么都能问"；数据安全靠配置保证而非口头承诺。
- **尾款策略**：尾款与验收挂钩，验收与可测条目挂钩。三句话写进合同，后面省很多事。

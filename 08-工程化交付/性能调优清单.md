# 性能调优清单

> [!abstract] 一句话讲清楚
> 客户说"太慢了"，不要立刻换模型或换卡。按"便宜的、影响大的先查"这个顺序走一遍，八成的问题在硬件和参数层就能解决，剩下的才轮到量化、批处理和投机解码。

## 为什么重要

- **调优待办最容易做反**：新手一上来就折腾投机解码、换量化格式，花两天提升 10%；而真正的问题可能是 PCIe 插错槽、显存被别的东西占着、或者应用层在串行等待。
- **每一条调优都有代价**：量化换速度但掉质量，批处理换吞吐但如果延迟飙升，KV Cache 优化吃显存。不知道代价就会"调完更快了，但客户说效果变差了"。
- **这是报价的分水岭**：基础部署是一个价，"性能不达标要优化"是另一件事。有这套清单，你能界定"达标/不达标"的边界，而不是无限期免费调优。

上游是 [[推理性能指标与调优]]（指标定义与前缀/解码两阶段），横向是 [[参数量与显存估算]] 和 [[量化技术]]。这份清单是**工程侧的操作顺序**，不是原理讲解。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 首 token 延迟 | TTFT（Time To First Token） | 从发出请求到吐出第一个字的时间 | 决定了"感觉快不快"；长上下文时它才是主要瓶颈 |
| 解码速度 | TPOT / ITL（每 token 时间） | 之后每个字吐出来的间隔 | 决定"读得顺不顺"；和人阅读速度比，通常 10~30 token/s 就够看 |
| 吞吐 | Throughput（tokens/s） | 整机每秒能产出多少 token | 决定"能服务多少人"；和延迟经常互相矛盾 |
| 并发 | Concurrency | 同时处理多少个请求 | 不是越大越好，超过显存承载会直接 OOM 或排队 |
| 批处理 | Batching | 把多个请求合成一批一起算 | 静态批 vs 连续批（continuous batching）差别很大 |
| 连续批 | Continuous Batching | 请求一个个进、一个个出，不等整批做完 | vLLM/SGLang 的核心能力之一；Ollama 早期版本没有 |
| KV Cache | KV 缓存 | 存已算过 token 的中间结果，避免重复算 | 上下文越长占得越多，显存不够时先压缩它 |
| 量化 | Quantization | 把权重从 16 位压成 8/4 位，省显存换速度 | 省的是显存和带宽，掉的是质量，4 位以下要重点验质量 |
| 投机解码 | Speculative Decoding | 用小模型先猜几个字，大模型批量验证 | 有加速比但依赖"猜得准"；写代码/专业文本保持率低就白搭 |
| 显存碎片 | Memory Fragmentation | 显存总量够但连续块不够，导致分配失败 | 表现为"重启就好、跑一会就 OOM"，见 [[故障案例库]] |
| 前缀缓存 | Prefix Caching | 相同开头（系统提示词、长文档）复用计算结果 | 对固定系统提示词的场景收益极大，对闲聊几乎无用 |
| PCIe 通道 | PCIe Lanes | CPU 和显卡之间的通道数 | 插错槽或通道减半会让模型加载和多卡通信变慢 |

## 原理与机制

### 直觉：一次推理分两段，瓶颈不同

- **预填充（prefill）**：把整段输入一次性算完，产出第一个 token。这一步是**算力密集**，并行度高。
- **解码（decode）**：一个 token 一个 token 往外吐，每步都要读一遍模型权重。这一步是**显存带宽密集**，并行度低。

所以：

- 客户说"第一个字等很久" → 看预填充，通常是长上下文、大 prompt、或 CPU 在忙别的。
- 客户说"吐字很慢" → 看解码，通常是显存带宽、量化格式、batch 内竞争。
- 客户说"人一多就卡" → 看 batch 与调度策略，不是单请求速度问题。

**先用一句话分清是哪种"慢"，再动手。** 分不清就开始调参数，等于蒙。

### 关键机制：为什么顺序是"从下往上"

越底层的问题，影响越全局、修复越一次性：

- 硬件/驱动层不对 → 后面所有参数都白调；
- 引擎参数不对 → 再好的卡也跑不出该有的速度；
- 量化/批处理 → 中等影响，有明确 trade-off；
- 投机解码/KV 优化 → 边际收益，容易引入新问题。

**经验法则**：如果实际速度只有理论预期的 1/3 以下，先怀疑底层（驱动、显存占用、PCIe、CPU 绑定），不要怀疑参数。

### 关键机制：显存带宽才是解码速度的天花板

解码每生成一个 token，都要把模型权重从显存读一遍。所以单请求速度大致受 **显存带宽 ÷ 模型大小** 限制。

这解释了两件事：

1. 同一张卡，4 bit 量化的模型解码明显快于 16 bit（读的数据少了）；
2. 两个程序抢一张卡时，速度不是简单减半，而是互相把对方等的带宽抢走——所以"先清干净显存"经常比任何参数调优都有效。

## 完整流程

按顺序做，每一档先测基线再改动，改动后再测。**没测过基线就不要调参**。

### 第 0 档：先把基线测出来

`输入 → 动作 → 输出 → 验收标准`

- 输入：同一段固定 prompt（长度接近客户真实场景），固定输出长度。
- 动作：连续请求若干次，记录 TTFT 和 tokens/s；同时开一个并发测试。
- 输出：一张"当前状态"的表（见文末模板）。
- 验收：能复现出稳定的数字，波动不超过合理范围。

> 没有基线，所有"变快了"都是错觉。

### 第 1 档：硬件与驱动（先清场）

**要查什么**

- 卡是不是满血工作：`nvidia-smi` 看功耗上限、当前功耗、温度、显存占用、是否有其他进程。
- 是否被别的东西占着：同一个 `nvidia-smi` 列表里的其他进程，尤其是一堆小 python 残留。
- 电源模式：笔记本/工作站可能跑在节能模式；服务器可能限了功率。
- 温度墙/功耗墙：长时间跑后频率下降，速度会掉——这是"跑一会儿变慢"的典型原因。
- PCIe 通道：多卡或加载慢时值得看一眼是不是 x16/x8 减半。
- CPU 是否拖后腿：如果是 llama.cpp 混合推理（CPU+GPU），CPU 核数/内存带宽才是瓶颈。

**预期收益**：清掉僵尸进程通常立刻恢复；解除功耗/温度限制可能提升一档。
**风险**：几乎没有。**这一档永远是第一步。**

### 第 2 档：驱动与 CUDA 栈一致性

**要查什么**

- 宿主机驱动版本 vs 框架要求的 CUDA 版本是否匹配（见 [[驱动-CUDA-框架版本兼容]]）。
- 是不是跑在 CPU 上了（日志里找设备信息，`torch.cuda.is_available()` 之类）。
- 多卡时是否只用了 1 张卡、或者卡间通信走了慢路径（P2P/PCIe 拓扑）。
- 容器里是否漏了驱动能力（`NVIDIA_DRIVER_CAPABILITIES`）。

**预期收益**：如果踩了不匹配，收益是"从不可用到可用"级别。
**风险**：升级驱动有把别的服务搞挂的风险，**动之前记录原版本、准备回滚**。

### 第 3 档：引擎参数（收益最大的一档）

按影响排序：

1. **上下文长度上限（max model len）**：设得远大于实际需求会白白吃显存、拉低并发。按客户真实文档长度设，通常比模型上限小很多。
2. **最大并发/批大小**：靠压测找到拐点。显存没满但吞吐上不去，是并发给小了；延迟飙升是给大了。
3. **gpu memory utilization / 显存占比**：常见默认 0.9 左右，多服务共存时必须调小，否则互相 OOM。
4. **数据类型**：某些引擎可强制半精度/自动混合精度，注意别把本该 fp16 的跑成 fp32。
5. **线程数 / 并行度**：llama.cpp 的 `-t` 不是越大越好，超过物理核数会互相抢。
6. **是否开启连续批处理/前缀缓存**：对多轮、固定提示词场景收益很大。

**预期收益**：这一档经常就能拿到数倍提升。
**风险**：参数之间会互相影响（并发调高 + 上下文调长 = 显存爆），**一次只改一个**。

### 第 4 档：量化

- 16 bit → 8 bit：质量损失通常很小，省一半显存、速度快一档。
- 8 bit → 4 bit：显存省得明显，速度看引擎实现；**质量必须用客户真实数据验证**。
- 4 bit 以下 / 混合精度量化：只在极低显存场景考虑，质量风险要写进交付文档。

**预期收益**：显存翻倍级，速度显著。
**风险**：**质量下降是隐性的**——自测时读起来没问题，客户用两天发现"回答变笨了"。量化前留一份全精度的对照输出。

### 第 5 档：批处理与调度

- 静态批 → 连续批：吞吐提升明显，是 vLLM 这类引擎的默认优势。
- 请求排队策略：长请求会把短请求堵住，客户端侧可按长度分流。
- 流式输出：不提升总吞吐，但**感知延迟**大幅下降，成本最低的"变快"手段。

**预期收益**：吞吐通常能提升到原来的数倍（视负载形态）。
**风险**：批越大单请求延迟越高；流式输出要改客户端，属于集成层工作。

### 第 6 档：KV Cache 与显存优化

- 压缩 KV Cache 精度（fp8 KV cache 等）：省显存、提并发，质量影响较小但需验证。
- PagedAttention 之类分页管理：减少碎片，提升承载上限。
- 前缀缓存的命中率：多轮对话、固定系统提示词场景要确认真的命中了。
- 限制单请求上下文：比任何 cache 技巧都有效。

**预期收益**：并发承载能力提升，长上下文场景明显。
**风险**：参数组合多，容易配出"能跑但很慢"的中间态；改完必须重测。

### 第 7 档：投机解码 / 高级技巧

- 草稿模型（draft model）投机解码：需要额外一份小模型占用显存。
- 多卡并行策略（张量并行 vs 流水线并行）：通信开销与收益要实测。
- 图编译/算子融合：一次性投入大，版本升级易失效。

**预期收益**：通常是个位数到几十个百分点，**不是数量级**。
**风险**：最容易被高估的一档。客户文本越专业（代码、法律、医疗），草稿命中率越低，加速比越差，甚至变慢。

## 决策点

- **岔路口 1：客户说慢，先问哪个"慢"**
  - 条件：等第一个字久 / 吐字慢 / 人多了卡。
  - 推荐：先按这三类分清，再决定查预填充、解码还是调度。**别直接开始调参数**。
  - 代价：多花 10 分钟问清楚，省两天瞎调。

- **岔路口 2：优化还是加钱换硬件**
  - 条件：调优后仍不达标，且差得很远。
  - 推荐：**先跑第 1~3 档，把软件层的空间榨干**，再给客户"硬件升级"和"降低需求"两个选项。
  - 代价：硬件升级要花客户的钱，降需求要客户改业务，两条都得客户点头。

- **岔路口 3：量化换性能值不值**
  - 条件：显存吃紧、客户对回答质量敏感度高。
  - 推荐：**先降上下文和并发，再考虑量化**；必须量化时优先 8 bit，4 bit 要做 A/B 对照。
  - 代价：量化验证要客户参与，工期要算进去。

- **岔路口 4：加并发还是加流式**
  - 条件：客户抱怨"卡"但其实单请求不慢。
  - 推荐：**先上流式输出**（改客户端，成本最低，感知提升最大），再看真实并发。
  - 代价：客户端要改，有的客户系统改不动。

- **岔路口 5：要不要上投机解码**
  - 条件：前三档已优化到位，仍有提升诉求，且输出内容可预测。
  - 推荐：**大多数交付场景不需要**。收益小、复杂度高、版本敏感。
  - 代价：多一份显存、多一层配置，以后升级引擎容易出兼容问题。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| `max-model-len` / `num_ctx` | 上下文上限 | 调大：能吃长文但占显存、降并发；调小：省显存但截断 | 按客户真实长度 ×1.5 余量 |
| `max-num-seqs` / 并发批大小 | 同时处理的请求数 | 调大：吞吐升、延迟升、显存升 | 压测找拐点，别拍脑袋 |
| `gpu-memory-utilization` | 引擎可用的显存比例 | 调大：能装但别服务抢不过；调小：留不住 | 单服务 `0.85~0.9`，多服务分 |
| 线程数 `-t`（llama.cpp） | CPU 线程 | 超过物理核数反而慢 | 物理核数附近，实测 |
| `batch size` / `max batch` | 单批大小 | 同并发 | 从 1 开始压到拐点 |
| KV cache 精度 | KV 缓存位宽 | 降精度：省显存、可能掉质量 | 精度敏感场景先验证 |
| `temperature` / `top_p` | 采样参数 | 与速度无关，但影响"看起来是否流畅" | 见 [[采样参数与解码策略]] |
| 并发上限（应用层） | 客户端限制 | 太低浪费算力，太高全排队 | 略低于压测拐点 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 调了半天参数没变化 | 基线没测，或者改的参数根本没生效（配置文件读的不是这份） | 每次改完从日志确认实际生效值；一次只改一个变量 |
| 跑一会儿就变慢 | 温度墙/功耗墙降频，或显存碎片越跑越多 | 看频率曲线；定期重启或上分页管理；改善散热 |
| 单请求很快，多请求就崩 | 并发超过显存承载，KV Cache 撑爆 | 压测找拐点，应用层限流；不要"能起就让它全上" |
| 量化后速度没涨 | 瓶颈不在显存带宽而在别处（CPU、网络、应用串行） | 回到第 1 档重新定位；量化只解决带宽/容量问题 |
| "换了更大的卡还是慢" | 新卡插在 x8 通道、或驱动没换、或多卡并行策略选错 | 查 PCIe 链路、驱动版本、并行配置 |
| 测试数字和客户体验不一致 | 测的是短 prompt 短输出，客户场景是长文档长回答 | 压测数据必须贴近真实场景分布 |
| 流式输出开了但没感觉变快 | 客户端把所有 token 收完才渲染 | 前端要真的边收边显示；检查中间层有没有缓冲 |
| 上了投机解码偶尔输出乱码 | 草稿模型和主模型 tokenizer/版本不匹配 | 用同族配套模型；不一致就别用 |

> [!tip] 一条省时间的规则
> 每次优化前先写下"我预期提升多少"。调完如果没达到预期的一半，说明判断错了方向，**立刻回退**，别在错误方向上继续叠参数。

## 自检问题参考答案

> [!success]- 1. 三种慢分别对应哪个阶段？
> 等第一个字久是预填充（算力密集，看长文档、大 prompt、CPU 在忙别的）；吐字慢是解码（显存带宽密集，看量化格式和带宽竞争）；人一多就卡是调度与批处理（不是单请求速度问题）。先用一句话分清哪种慢，再动手，分不清就开始调参数等于蒙。

> [!success]- 2. 为什么解码卡在显存带宽上？
> 解码每生成一个 token 都要把模型权重从显存完整读一遍，算力用不满，时间花在"搬数据"上，所以单请求速度大致受显存带宽除以模型大小限制。这解释了两件事：4 bit 量化解码明显快（读的数据少了），两个程序抢一张卡时速度不是减半，而是互相抢带宽。

> [!success]- 3. 拿到慢的反馈第一步做什么？
> 测基线。固定一段接近客户真实场景的 prompt、固定输出长度，连续请求若干次，记录 TTFT 和 tokens/s，再跑一组并发测试。没有基线，所有"变快了"都是错觉；改了参数也说不清是哪个起了作用，更没法判断有没有达标。

> [!success]- 4. 为什么按从下往上的顺序调？
> 越底层的问题影响越全局、修复越一次性：硬件或驱动不对，后面所有参数白调；引擎参数不对，再好的卡也跑不出该有的速度；量化、批处理有明确 trade-off；投机解码和 KV 优化是边际收益，还容易引入新问题。实际速度低于理论预期三分之一时，先怀疑底层。

> [!success]- 5. 量化换速度的代价怎么验证？
> 代价是隐性的质量下降：16 到 8 bit 通常损失小，8 到 4 bit 在复杂推理、固定格式、多步任务上明显，小模型更敏感。验证靠量化前留一份全精度对照输出，用客户真实任务同题 A/B，看正确率、格式合规、多步推理有没有退化；4 bit 以下把质量边界写进交付文档。

> [!success]- 6. 什么时候该建议加硬件？
> 第 1 到 3 档都榨干了、离目标还差得远的时候。给客户两个选项：加钱换硬件，或降需求（缩短上下文、降并发、接受更大延迟）。继续在软件层调，边际收益已经很低，还会白耗工期；把选项摆给客户选，比你自己硬扛更专业。

> [!success]- 7. 流式输出提升的是哪个指标？
> 提升的是感知延迟：首字更快出现、边收边看，体验明显变好。总吞吐不变，因为算的 token 总数没变。它是最便宜的"变快"手段，但客户端必须真的边收边渲染，中间层有缓冲就会把效果吃掉。

> [!success]- 8. 怎么证明优化真的达标了？
> 用同一套方法测：固定 prompt 与输出长度、固定并发、贴近客户真实场景分布，优化前后各测一次 TTFT、tokens/s、P95 延迟，并把测试环境、方法、输入长度、并发数写进文档。客户感觉和数字不一致时，先比对测试场景与真实场景差在哪（短 prompt 对上长文档）。

## 交付视角（对客户怎么讲）

- **客户问"能不能再快一倍"**：先问清楚现在的瓶颈在哪。多数情况下"快一倍"要么靠减需求（上下文变短、并发变低），要么靠加硬件，纯软件调优有上限。把三档选项摆出来让客户选。
- **客户问"为什么别人家说能到很快"**：别人的数字通常是在短输入、单请求、高配卡上测的。用客户的真实文档和真实并发测一遍，差距就出来了。
- **报价口径**：基础部署含"按标准参数配置 + 一次基线测试"；**性能调优单独计价**，按"目标指标 + 调优轮次"报价，写明"达到目标即结束，未达标按轮次计费或转硬件方案"。
- **一定要写进文档**：测试环境、测试方法、输入长度、并发数、得出的指标。以后扯皮时这就是依据。
- **别承诺绝对数字**：说"按你的场景实测下来是这个量级"，不说"保证 50 tokens/s"。

# 故障案例库

> [!abstract] 一句话讲清楚
> 18 个真实高频故障的"病历档案"：环境、现象（原样报错特征）、根因、解决、预防。遇到报错先按症状查表，再按案例对号入座。

## 怎么用这本手册

1. **先看下面的速查表**，按"现象关键词"找到最像的案例；
2. 进案例看"现象"是否和你的一致（尤其是报错特征）；
3. 按"解决"执行，按"预防"改交付文档；
4. 对不上？退回 [[排错方法论]] 的分层模型，先定层再查。

> [!tip] 读案例的正确姿势
> 不要只看"解决"那一栏。**看"根因"才能学会判断，看"预防"才能不再犯。** 同一个根因往往会在别的场景以别的报错出现。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 故障 | Fault / Failure | 系统没有按预期工作的状态 | "故障"是状态，"报错"只是它的一种表现 |
| 症状 | Symptom | 你观察到的现象：报错、慢、乱码、没反应 | 症状不是原因；同一个症状可能来自不同层 |
| 根因 | Root Cause | 真正导致故障的那一个变量 | 找到"改回去就坏、改过来就好"的才算根因 |
| 原样报错 | Raw Error | 未经转述的完整报错文本 | 排错最重要的输入，转述一次信息就丢一半 |
| 显存碎片 | VRAM Fragmentation | 显存总量够但没有连续的大块可用 | 典型表现是"重启就好、跑一阵又 OOM" |
| 显存溢出 | OOM | 申请显存失败，进程被终止 | 要区分"装不下"和"碎片/泄漏"两种 OOM |
| 上下文超限 | Context Overflow | 输入加输出超过模型能处理的最大长度 | 引擎可能静默截断，不一定报错 |
| 温度墙 / 功耗墙 | Thermal / Power Limit | 太热或太费电时 GPU 自动降频 | 表现为"跑一会儿变慢"，不是软件 bug |
| 精度损失 | Precision Loss | 量化压缩带来的质量下降 | 简单问答看不出来，复杂任务才暴露 |
| 端口占用 | Port Conflict | 启动时端口已被别的进程用了 | 有时不报错，而是把请求打到了别的服务上 |
| 编码不一致 | Encoding Mismatch | 同一段中文在不同环节被按不同编码解释 | 乱码的根源几乎都在"转码"这个动作上 |
| 级联失效 | Cascading Failure | 底层出问题，上层报了一个看起来无关的错 | 排错要看最底层的原始错误 |
| 回归 | Regression | 修好一个问题，弄坏了另一个 | 修复后必须跑一遍关键路径 |

## 原理与机制

### 故障的三种时间形态（决定了排查方式）

| 形态 | 表现 | 排查重点 |
|---|---|---|
| 启动即失败 | 服务根本起不来，有明确报错 | 看启动日志，从下往上扫（驱动→框架→模型文件） |
| 运行中退化 | 能跑，但越来越慢 / 越来越占显存 | 看趋势曲线，查泄漏、碎片、降频、磁盘 |
| 间歇性失败 | 偶发失败，难以复现 | 加日志和监控，抓现场；查并发、超时、资源竞争 |

**先判断属于哪种形态**，再决定是"看日志"还是"看曲线"还是"加观测点"。判断错了，后面全是白费。

### 为什么现场故障大多是"配置与环境"问题

交付现场和实验室的区别：

- 客户机器的驱动、系统、Docker 版本、端口占用、防火墙，全都不受你控制；
- 客户的操作习惯（重启、改配置、装别的软件）会不断改变环境；
- 同一份"能跑"的配置，换一台机器就要重新确认一遍。

所以这本手册里 18 个案例，真正属于"模型/算法"问题的很少，绝大多数是环境、版本、配置、编码、资源这几类。**这也是为什么排错的第一反应应该是"环境有什么不一样"，而不是"模型是不是不行"。**

### 为什么要有"预防"这一栏

故障会重复。同一个根因，在这台机器上表现为 OOM，在另一台机器上表现为服务起不来。

- **解决**只对这一次有效；
- **预防**（写进检查清单、写进文档、加进监控、固化进镜像）才对下一次有效。

这也是为什么本手册每条案例都有"预防"——它是把一次事故变成一次流程改进的接口。

## ① 硬件层

### 案例 12：跑一会儿就变慢，频率掉下来

- **环境**：工作站，单张高端消费卡，长时间连续推理；机房通风一般。
- **现象**：刚开始速度正常，跑十几分钟后 tokens/s 明显下降；重启服务后短暂恢复；`nvidia-smi` 里温度接近上限、当前频率低于标称，功耗顶在限制值附近。
- **根因**：撞温度墙或功耗墙，GPU 自动降频保护。不是模型问题，也不是参数问题。
- **解决**：改善散热（机箱风道、风扇曲线、清理灰尘、环境温度）；确认电源功率余量足够；必要时在引擎侧限制持续负载，避免长时间满载。
- **预防**：交付前做一次"连续跑 30 分钟"的稳定性测试；把温度和频率写进监控（见 [[监控与日志]]）；在交付文档里写明"这是物理限制，不是软件 bug"。

### 案例 17：写到一半报错、日志写不进

- **环境**：Linux，模型目录和数据目录都在系统盘；长期运行。
- **现象**：运行几天后服务异常，日志停止增长；写文件时报 `No space left on device`；`df -h` 显示某个分区 100%。
- **根因**：模型文件（几十 G）+ 日志无限追加 + 缓存文件堆积，把磁盘写满。也可能是 Docker 数据目录默认在系统盘。
- **解决**：清理日志和缓存；把模型、Docker 数据目录、日志目录迁到大容量分区；配置日志轮转。
- **预防**：交付前查磁盘余量并写进检查清单；日志轮转必须在交付时就配好；监控磁盘使用率（阈值设在明显提前的位置）。

## ② 驱动层

### 案例 05：容器里看不到 GPU

- **环境**：Linux + NVIDIA 卡，用 Docker 部署推理服务。
- **现象**：宿主机 `nvidia-smi` 正常；容器内执行 `nvidia-smi` 报 `could not select device driver "" with capabilities: [[gpu]]`，或提示找不到 `libcuda.so`；不加 `--gpus` 时容器能起但只能用 CPU。
- **根因**：宿主机装了显卡驱动，但没装 NVIDIA Container Toolkit，或装了之后 Docker 服务没重启，导致运行时没有 GPU 支持。
- **解决**：安装容器工具包，重启 Docker 服务；用最小命令先验证 GPU 能被"接"进容器，再回到完整 compose 配置。
- **预防**：把"GPU 直通验证"作为容器化交付的第一步（见 [[容器化部署]]），不要等全配完再测；验收清单里加一条"容器内能看到卡"。

### 案例 06：CUDA 版本链条对不上

- **环境**：宿主机驱动版本偏旧；镜像/环境里的 CUDA 运行时较新。
- **现象**：启动时或第一次推理时报 `CUDA driver version is insufficient for CUDA runtime version`，或框架报 `no kernel image is available for execution on the device`；也可能表现为加载即崩。
- **根因**：驱动支持的最高 CUDA 版本低于运行时需要的版本。注意 `nvidia-smi` 右上角显示的是"驱动支持的最高 CUDA 版本"，不是"已安装版本"，很多人在这里看错。
- **解决**：两条路——升级宿主机驱动（推荐，一次解决），或把镜像/框架的 CUDA 版本降到驱动支持范围内。不要试图只降框架版本蒙过去。
- **预防**：交付前记录"驱动版本 → 支持的 CUDA 上限 → 框架要求"这条链（见 [[驱动-CUDA-框架版本兼容]]）；镜像里锁定版本，不用 `latest`；升级驱动前留回滚方案。

## ③ 框架层

### 案例 01：启动就 CUDA OOM

- **环境**：单卡 24G 级，跑中等参数量模型的量化版；引擎按默认参数启动。
- **现象**：启动过程最后阶段报 `CUDA out of memory. Tried to allocate ...`；`nvidia-smi` 显示显存被占了一部分后崩掉；换更小的模型能起。
- **根因**：模型权重 + KV Cache 预留 + 引擎预分配（很多引擎按 `gpu-memory-utilization` 预占显存）+ 框架开销，加起来超过可用显存。常见触发点是上下文长度上限或最大并发设得远大于实际需求。
- **解决**：按顺序降——先降上下文长度上限到客户真实需求，再降最大并发/批大小，再降显存预占比例；仍然不够就换更小的量化版本。启动前确认卡上没有别的进程。
- **预防**：交付前用 [[参数量与显存估算]] 先算账，按"模型占六到七成、其余留给运行时"的余量配置；首次启动永远从小参数开始往上加，而不是从默认值往下减。

### 案例 02：跑一段时间才 OOM，重启就好

- **环境**：长期运行的服务，请求长度差异很大（有长文档、有短问答）。
- **现象**：刚启动一切正常；几小时或几天后突然 OOM，重启后立刻恢复；`nvidia-smi` 显存曲线缓慢上升，不是阶跃。
- **根因**：显存碎片（长短请求交替导致空闲块不连续）或 KV Cache 未及时释放；也可能是某类超长请求把显存推过阈值后没回落。
- **解决**：启用支持分页/碎片管理的引擎能力；限制单请求最大长度；限制并发；配置定期重启策略作为兜底（并记录日志便于定位诱因）。
- **预防**：监控显存曲线（看趋势不看瞬时值）；压测时混合长短请求，而不是只测单一长度；交付文档里写明"建议的最大单请求长度"。

### 案例 03：模型加载失败，报文件错误

- **环境**：从网盘/内网拷贝的模型文件，多分片的大模型。
- **现象**：加载时报找不到某个分片、`safetensors` 解析失败、`unexpected end of file`、或文件大小明显小于预期；有时报“shape mismatch”。
- **根因**：下载/拷贝中断导致文件不完整；分片少了一片；或者把不同量化版本的配置文件混用了。
- **解决**：核对每个文件大小与模型卡上的清单；重新传输缺失文件；确认配置文件（config、tokenizer 相关文件）和权重版本一致。
- **预防**：模型搬运后用校验和逐个核对（见 [[模型获取与离线搬运]]）；交付包里附一份"文件清单 + 校验值"；内网拷贝优先用支持断点续传/校验的方式。

### 案例 04：模型格式和引擎不匹配

- **环境**：Ollama / llama.cpp / vLLM 混着用，模型来源杂。
- **现象**：报 `not a valid GGUF file`、`unsupported model architecture`、`Invalid file format`；或者加载成功但输出全是乱码/重复。
- **根因**：GGUF 格式给 llama.cpp/Ollama 用，safetensors 给 vLLM/Transformers 用，拿错格式就会报格式错；另一种情况是引擎版本太老，不认识新模型的架构。
- **解决**：按引擎要求选格式；升级引擎到支持该架构的版本；转换格式用官方脚本，不要手工拼。
- **预防**：交付文档里写清"本服务使用哪个引擎 + 支持哪些模型格式"；客户要换模型时先确认格式，别让客户自己试。

### 案例 11：突然变慢，GPU 利用率却不高

- **环境**：同一台机器上之前装过别的 AI 工具；服务重启过几次。
- **现象**：请求变慢很多，`nvidia-smi` 里 GPU 利用率很低甚至个位数，但显存里能看到多个 python 进程；日志显示模型确实加载在 GPU 上。
- **根因**：多个残留进程分走了显存和带宽；或者是框架悄悄退回 CPU 推理（日志里设备信息显示 CPU）；也可能是容器只分到了一张卡但配置里写了多卡。
- **解决**：清掉残留进程后重测；确认框架日志里的设备是 GPU；确认容器/进程拿到的卡编号与实际一致。
- **预防**：交付时用独立容器隔离；启动脚本里先检查有没有旧进程；把"设备确认"写进启动日志（版本 + 模型 + 设备）。

## ④ 参数层

### 案例 08：输出重复、胡言乱语、乱码

- **环境**：自建服务，客户端自己传采样参数。
- **现象**：输出大段重复同一句、或者字符乱跳、或者答非所问；同一模型换官方客户端就正常；有时中英混杂。
- **根因**：采样参数不对（温度过高/过低、重复惩罚过强、top_p 过小）；客户端传参格式不对（字符串传给数值）；tokenizer 与模型不匹配（尤其自己转换格式后）；或者流式解析时把多字节字符切断了。
- **解决**：先用默认参数 + 短输入复现；换官方客户端对照；确认 tokenizer 文件来自同一模型；流式输出端按字节安全地拼接。
- **预防**：在 API 文档里给出推荐参数和取值范围；服务端对参数做校验和钳制；交付时做一次"标准客户端 + 客户客户端"对照测试。

### 案例 13：量化之后"变笨了"

- **环境**：为了省显存，把全精度模型换成低比特量化版本。
- **现象**：能跑、速度也上去了，但客户反馈"答得不如以前准""格式经常不对""多步推理容易断"；简单问答看不出来，复杂任务明显。
- **根因**：量化本身有精度损失，低比特对小模型、复杂推理、结构化输出影响更大；另外可能同时换了量化格式但没有配对应的模板/提示词。
- **解决**：优先换回更高比特（如 8 bit）；或换更大的模型但保持较高比特；确认模型的对话模板与量化版本匹配；把客户真实任务做成测试集做 A/B 对照。
- **预防**：量化前留存一份全精度版本的对照输出；交付前用客户真实数据做质量抽检，不要只测"能不能出字"；在报价与方案里写明"低比特量化的质量边界"。

### 案例 14：长文档问答只答一半 / 报上下文错误

- **环境**：客户上传几十页文档做问答，模型上下文窗口有限。
- **现象**：超过一定长度后报 `context length exceeded` / `maximum context length` 相关错误；或者不报错但回答只覆盖文档前半段；或者回答明显在"编"（因为后半段根本没进去）。
- **根因**：输入总长度超过模型或引擎配置的上下文上限；部分是引擎层面 `max-model-len` 单独设了小值；RAG 场景下是检索塞进去的片段太多。
- **解决**：按真实需求把上下文上限调到合适值（不是越大越好，吃显存）；超长文档走切分 + 检索（见 [[文档解析与切分策略]]）；在应用层做长度预检并给出明确提示，而不是静默截断。
- **预防**：明确写出"单次最大输入长度"；应用层加长度校验与友好报错；长文档场景默认走 RAG 而不是硬塞。

## ⑤ 应用层

### 案例 07：中文乱码

- **环境**：Windows 上跑脚本/服务，或 Linux 上通过管道处理中文。
- **现象**：控制台输出中文变问号、方块、或 `????`；日志文件打开是乱码；从 Windows 拷到 Linux 后文本异常。
- **根因**：编码不一致。Windows 控制台默认代码页不是 UTF-8；脚本文件保存成了 GBK；Python 输出流编码与终端不一致；文件传输时被转码；写文件没指定编码。
- **解决**：统一全链路 UTF-8：脚本/配置保存为 UTF-8；程序里显式指定读写编码；Windows 控制台切到 UTF-8 代码页；跨平台传输用二进制方式。
- **预防**：交付时统一规定编码并在文档里写明；启动脚本里显式设置编码；避免用 shell 重定向写中文内容（这也是本库要求用工具写文件的原因）。

### 案例 09：本机能访问，别的机器连不上

- **环境**：Linux 服务器，服务用默认配置启动。
- **现象**：服务器上 `curl localhost:端口` 正常返回；同一局域网另一台机器访问超时或拒绝连接；`netstat` 发现服务监听在 `127.0.0.1`。
- **根因**：服务默认只绑定回环地址；或防火墙没放开端口；或容器端口映射写错（映射到了别的容器/别的端口）。
- **解决**：把监听地址改为 `0.0.0.0`（注意这等于对内网开放，配合鉴权）；确认防火墙规则；确认容器端口映射；跨网段还要看路由和网段隔离。
- **预防**：交付文档里写明"监听地址 + 端口 + 谁能访问"；上线前从另一台机器做一次访问验证；把这条写进部署检查清单（见 [[部署检查清单]]）。

### 案例 10：端口被占用

- **环境**：机器上之前装过同类服务（比如已经有一个 Ollama 或别的 Web 服务）。
- **现象**：启动报 `address already in use` / `bind: Only one usage of each socket address`；或者启动"成功"但访问到的是另一个不相干的服务。
- **根因**：默认端口被占用；客户机器上已经跑着同类服务；上次的进程没退干净。
- **解决**：确认占用者是谁再决定（换端口最安全，杀进程要看是不是客户在用的服务）；换端口后同步改客户端配置和文档。
- **预防**：交付前扫一遍已占用端口；端口写进配置而不是硬编码；文档里写明"如需改端口改哪里"。

### 案例 15：RAG 答非所问，被误判成"模型不行"

- **环境**：本地模型 + 知识库问答，文档是 PDF 扫描件或格式复杂的表格。
- **现象**：模型回答看起来"不知道"或"编造"，客户认为是模型能力差；同样的模型直接问通用问题表现正常；检索出来的片段和问题无关。
- **根因**：问题在检索层——文档没解析好（扫描件没 OCR、表格被压成一行）、切分粒度不合适、embedding 模型与语言不匹配、检索数量太少或 rerank 没做。
- **解决**：先单独验证检索：手工看前几条召回内容对不对；不对就修解析和切分；检索对了再调生成。
- **预防**：交付 RAG 项目必须做"检索评估"和"生成评估"两段（见 [[RAG 评估与调优]]）；给客户演示时先展示"检索到了什么"，避免把检索问题归到模型头上。

### 案例 16：机器重启后服务没了

- **环境**：客户机房/办公室机器，可能被断电或例行重启。
- **现象**：交付时一切正常；客户重启机器后访问不了；登录上去发现服务进程不存在；手动启动后又正常。
- **根因**：没有配置开机自启（裸进程启动）；容器没配重启策略；或者用了需要登录会话才能启动的方式（比如在某用户桌面会话里开窗口）。
- **解决**：服务化（systemd）或容器化 + `restart: unless-stopped`；确保服务不依赖桌面登录；重启验证一次。
- **预防**：把"重启验证"作为交付验收的固定项；启动脚本 + 自启配置 + 文档三件套一起交付（见 [[容器化部署]]、[[远程交付与远程运维]]）。

### 案例 18：鉴权与跨域问题

- **环境**：给业务系统提供 API，前端页面直接调用；客户自己管账号。
- **现象**：用工具请求正常，网页调用报跨域错误（CORS）；或所有请求返回 `401`/`403`；或某个客户端一切正常、另一个客户端 401；偶尔报 `429 too many requests`。
- **根因**：`401` = 没带/带错 API Key；`403` = Key 有但没权限（或 IP 白名单）；CORS = 浏览器限制，服务端没配允许来源；`429` = 触发限流。
- **解决**：对齐 Key 的传递方式（Header 还是 Query）；按人发 Key；正确配置允许的来源或走同源反向代理；确认限流阈值与客户业务量匹配。
- **预防**：交付 API 文档里写清"Key 放哪、示例请求、错误码含义"；交付时用客户真实客户端联调一次；限流阈值留余量并写进文档（见 [[安全与合规]]）。

## 案例之外的通用经验

- **90% 的故障和最近一次变更有关**。先问"刚才改了什么"，比看代码快。
- **报错要看第一现场**：应用层报"请求失败"时，真正的错误在上面几层的日志里。
- **同一个症状，先排除最便宜的**：显存被占、端口被占、Key 错了、跑在 CPU 上——这四件事能解决一大半"玄学问题"。
- **能复现就成功一半**。不能复现时，先加日志和监控，等它再出现（见 [[监控与日志]]）。
- **每次排错都写记录**。写够 20 条，你会发现自己有一套稳定的判断路径，这就是经验。

## 决策点

- **岔路口 1：先重启恢复，还是先取证**
  - 条件：客户是否在等、故障是否复现过。
  - 推荐：**第一次出现先取证再重启**；客户业务中断且已经复现过，先恢复再补分析。
  - 代价：取证要几分钟；但反复出现的故障，只有取证才可能断根（见 [[排错方法论]]）。
- **岔路口 2：查案例对号入座，还是从头分层定位**
  - 条件：报错是否有明确关键词。
  - 推荐：**有原样报错就在手册里搜关键词**，对得上就按案例走；对不上就走分层模型。
  - 代价：硬套案例容易只修表面（同一个症状多个根因）。
- **岔路口 3：修当前机器，还是改交付流程**
  - 条件：同一个问题是否已在不同客户处出现过。
  - 推荐：**第二次出现就必须改进流程**（加检查项、加监控、固化镜像），否则会第三次、第四次。
  - 代价：改流程要额外时间，当期项目可能来不及，可以排到下一个项目。
- **岔路口 4：降级运行还是停下来等修好**
  - 条件：客户是否接受"能力下降但可用"。
  - 推荐：**优先给降级方案**（小模型/少并发/短上下文 + 明确告知限制），先保住业务，再修根因。
  - 代价：降级期间客户体验差，要有书面说明。
- **岔路口 5：客户自己的环境问题，修不修**
  - 条件：根因在客户环境（断电、网络、误操作、装冲突软件）。
  - 推荐：**按变更/工单处理**，先恢复再谈费用；交付文档里提前界定范围。
  - 代价：当期可能得罪客户，长期避免无限免费售后。

## 参数与配置说明

> 这里的"参数"是**判断用的阈值**，不是引擎参数。交付时把这些阈值写进文档，客户和你都用同一套标准。

| 判断项 | 看什么 | 危险信号 | 建议动作 |
|---|---|---|---|
| 显存占用 | 长期曲线 | 持续上涨不回落 | 查泄漏与碎片；限制单请求长度 |
| 显存余量 | 峰值时剩余量 | 余量太小 | 降上下文/并发，或换更小的量化 |
| 温度 | 满载持续温度 | 接近温度上限 | 改善散热；限制持续负载 |
| 频率 | 满载频率 | 明显低于标称 | 查降频原因（温度/功耗） |
| 磁盘 | 剩余空间 | 快满 | 清理日志/缓存，迁数据目录 |
| 延迟 | P95/P99 | 明显高于基线 | 查并发、排队、上下文长度 |
| 错误率 | 单位时间错误数 | 上升或出现新错误类型 | 看日志第一现场 |
| 模型加载时长 | 每次启动耗时 | 突然变长很多 | 查磁盘、文件完整性、卡占用 |
| 重启后状态 | 能否自动恢复 | 需要人工介入 | 补自启与服务化 |

## 常见坑与误区（用案例库时）

| 现象 | 原因 | 对策 |
|---|---|---|
| 照着案例解决却没用 | 症状像但层级不同（同一个报错可能多个根因） | 用案例缩小范围，再用 [[排错方法论]] 验证 |
| 案例看多了更乱 | 只记"解决方案"，没记"判断依据" | 记住每个案例的根因特征和验证动作 |
| 客户描述和案例对不上 | 客户转述丢了关键信息 | 用六段模板重新收集一次信息 |
| 修好一个又来一个 | 只做了点状修复，没改流程 | 把每个案例的"预防"落到交付文档和检查清单 |
| 重启后不复现就不管了 | 把"偶发"当"解决" | 记下来并加监控，等它再出现时抓现场 |
| 同样的报错在另一个客户处又出现 | 没把根因和预防固化进交付流程 | 把该案例的"预防"加进 [[部署检查清单]] |

## 交付视角（对客户怎么讲）

- **客户问"会不会老出问题"**：不会不出问题，但有准备。我们交付时埋了监控和自检脚本，常见问题有手册，多数情况能远程处理。
- **客户报障只说"用不了"**：把速查表里的关键词发给他（"是报错、是慢、还是连不上"），比反复问更高效。
- **客户自己乱试之后**：先问清"试过什么、改过什么"，很多"新故障"是客户自己改配置造成的，先恢复再排查。
- **报价口径**：故障处理按"是否属于交付内容缺陷"区分——是我们配错的免费修，是客户环境/误操作/新需求的按工单或运维服务计。
- **承诺要谨慎**：不承诺"所有问题都能远程解决"，有些故障必须到现场（硬件、网络、断电）。

# 监控与日志

> [!abstract] 一句话讲清楚
> 给交付出去的服务装上"体温计"和"黑匣子"：体温计让你在客户打电话之前就知道它不舒服，黑匣子让你在出事之后能还原现场。

## 为什么重要

- 没有监控的交付，等于把自己变成 7×24 客服：客户半夜发现挂了，你第二天才知道，而且现场已经没了。
- 没有日志的排错，等于蒙眼睛修车：客户只会转述"报错了"，你连哪一层都不知道。
- **监控本身也是交付物和议价点**：能提供监控面板和健康周报的交付方，自然能收运维费；只交付一个能跑的进程，就只能拼价格。
- 客户越大越在意这个：他们的 IT 会问"你们怎么发现故障""日志保留多久""有没有告警"。

上游是 [[性能调优清单]]（先知道指标含义才能监控），下游接 [[远程交付与远程运维]]（监控是远程运维的前提）和 [[交付 SOP 与报价]]（售后服务的依据）。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 指标 | Metric | 随时间变化的数字，如显存占用 23G | 指标是"趋势"，不记录单次事件 |
| 日志 | Log | 一条条带时间戳的文字记录 | 日志是"细节"，适合还原单次事故 |
| 追踪 | Trace | 一个请求经过哪些环节、各花多久 | 排查"慢在哪一步"靠它，不靠猜 |
| 采集 | Scrape / Agent | 定时去抓指标，或装在机器上的小程序 | 拉模式（Prometheus 抓）和推模式（agent 推）要选一个 |
| 面板 | Dashboard | 把指标画成图，一眼看趋势 | 面板不是给自己看的，是给"不懂技术的人"看的 |
| 告警 | Alert | 指标越界时主动通知 | 告警疲劳比没告警更糟：天天响就没人看了 |
| 黄金指标 | Latency / Traffic / Errors / Saturation | 延迟、流量、错误、饱和度 | 四个够了，别一开始就上上百个指标 |
| 抖动 | Jitter | 延迟忽高忽低 | 平均值会掩盖抖动，要看分位数 |
| 分位数 | P50 / P95 / P99 | 把延迟排序后取第 50/95/99 百分位 | **P99 才是客户投诉的来源**，平均值骗人 |
| 轮转 | Log Rotation | 日志按大小/时间切分并清理 | 不配轮转，跑几个月把磁盘写满，服务直接挂 |
| 结构化日志 | Structured Log | JSON 这类机器可读格式 | 排错效率高，但人读起来丑，可双写 |
| 心跳 | Heartbeat | 定期上报"我还活着" | 心跳在 ≠ 服务能用；要和健康检查区分 |

## 原理与机制

### 直觉：监控分三层，别混在一起

1. **机器层**：GPU 状态、温度、功耗、磁盘、内存、网络。回答"这台机器健康吗"。
2. **服务层**：进程活着吗、端口通吗、模型加载完了吗、健康检查过不过。回答"服务能用吗"。
3. **业务层**：延迟、QPS、错误率、输出长度、用户是谁。回答"用户用得好吗"。

**分层的好处**：一条告警出来，你知道先看哪一层。混在一起的监控面板，看的人自己都糊涂。

### 关键机制：为什么 GPU 监控比 CPU 监控麻烦

- CPU 监控基本是"百分比"，GPU 不是：**显存占用高不等于忙**（模型常驻显存），**利用率 100% 也不一定在干有效活**。
- GPU 的关键指标是**一组**，要一起看才判断得对：

| 指标 | 正常状态 | 异常含义 |
|---|---|---|
| 显存占用 | 加载后稳定在一个水平 | 持续上涨 = 泄漏；突然归零 = 进程挂了 |
| GPU 利用率 | 推理时有明显负载 | 长期 0 但服务在 = 跑在 CPU 上；长期 100% 但很慢 = 到瓶颈了 |
| 温度 | 稳态区间内 | 撞温度墙会降频，速度莫名变慢 |
| 功耗 | 在功耗上限内波动 | 长期顶格 = 满负荷；远低于上限却慢 = 有别的瓶颈 |
| 频率 | 接近标称 | 频率掉了 = 降频，通常是散热或功耗限制 |
| 错误计数 | 无 | XID 报错、ECC 错误 = 硬件/驱动问题，要认真看 |

> [!warning] 记住这句话
> **显存占用高不是问题，显存持续上涨才是问题；利用率高不是问题，利用率高但吞吐低才是问题。**

### 关键机制：日志要有"三层信息"才可排错

一条能用的日志，至少要能回答三个问题：

1. **什么时候、在哪个环节**（时间戳 + 组件名）；
2. **发生了什么、严重不严重**（级别 + 一句话）；
3. **现场是什么样**（关键参数、请求 id、异常栈）。

最常见的烂日志是只写第 2 条：`Error: failed`。这种日志等于没有。



好日志的对照：

```
# 差：出问题时完全看不出上下文
ERROR: request failed

# 好：一眼知道哪个请求、哪个环节、什么错误
2026-10-28 14:03:11 ERROR [api] req=8f2a model=qwen len=18200 decode failed: context length exceeded (max=16384)
```

### 关键机制：告警的价值在于"可行动"

告警不是"通知"，是"叫你去做什么"。判断一条告警该不该存在，问一句：**收到之后我具体要做什么？** 答不上来就删掉。

- 有用：显存连续 10 分钟上涨 → 可能泄漏，去看进程。
- 有用：服务健康检查连续失败 → 去重启并查日志。
- 没用：GPU 利用率 95% → 说明在正常工作，通知你干嘛？
- 没用：磁盘使用率 60% → 还早。

### 概念级：Prometheus + Grafana 是什么关系

- **Prometheus**：负责"存指标 + 按规则算告警"。它定时去你的服务抓一个 `/metrics` 页面（文本格式的指标清单），存成时间序列。
- **Grafana**：负责"画图"。连上 Prometheus，把指标画成面板，给客户看。
- **Exporter**：负责"把没有指标的东西变成有指标"。比如 `node_exporter` 管机器、`dcgm-exporter` 管 NVIDIA GPU。

**要不要上这套**：单机交付、就服务一个部门 → 一个轻量脚本写日志 + 一个简单健康检查页就够了。多机、客户有 IT 团队、要接他们现有监控 → 上标准栈。**别为了显得专业给小项目上重装备**，客户维护不动反而是负担。

## 完整流程

`输入 → 动作 → 输出 → 验收标准`

### 1. 输入：先确定"谁看监控、看什么"

| 角色 | 关心什么 | 怎么看 |
|---|---|---|
| 客户业务人员 | 能不能用、快不快 | 一个页面：绿/黄/红 + 最近错误 |
| 客户 IT | 机器负载、磁盘、有没有异常 | 标准面板或接入他们现有系统 |
| 你（交付方） | 全量指标 + 日志 + 告警 | 远程访问面板 + 日志文件 |

**先定这三个，再决定装什么。** 反过来做（先装一套再想给谁看）通常白装。

### 2. 动作：埋最小可用监控（单机版）

不做重装备，也能有 80% 的效果：

- 一个 `/health` 接口：返回服务状态、模型名、已加载时长。
- 一个 `/metrics` 接口（或定时任务）：把显存、温度、QPS、错误数写进日志。
- 一个定时脚本每分钟跑一次 `nvidia-smi` 关键字段，追加到 `gpu.log`。
- 一个日志轮转配置，避免写满磁盘。

这套东西的价值：客户说"变慢了"，你远程看日志就能定位到"显存满了"还是"没人用"。

### 3. 动作：定日志规范

写进交付文档，让后续接手的人也能看懂：

- **目录**：固定为 `logs/`，按服务名分文件。
- **滚动**：按天或按大小，保留 N 天（合规场景另定）。
- **级别**：`ERROR` 必须带上下文；`INFO` 记录请求摘要；`DEBUG` 只在排障时开。
- **必带字段**：时间戳、级别、组件、请求 id、耗时、关键参数（模型名、输入长度）。
- **禁止**：把完整 prompt 和客户数据原样打进日志（这是数据泄露，见 [[安全与合规]]）。

### 4. 动作：定告警

按"严重程度 × 可行动性"来：

| 级别 | 触发 | 通知谁 | 动作 |
|---|---|---|---|
| P0 挂了 | 健康检查连续失败 | 你 + 客户 IT | 立刻查，重启或回滚 |
| P1 快挂了 | 显存持续上涨、温度撞墙、磁盘将满 | 你 | 当天处理，必要时提前换服务 |
| P2 不达标 | P99 延迟超阈值、错误率升高 | 你（周报） | 分析原因，纳入下周优化 |
| P3 信息 | 版本变更、重启、模型切换 | 记录 | 不用通知，留痕 |

**初期规则**：只对 P0 做即时通知，其余做日报。上来就全量即时通知，一周内所有人都会屏蔽你。

### 5. 输出与验收标准

| 交付物 | 验收方式 |
|---|---|
| 健康检查接口 | 客户浏览器打开能看到状态 |
| 日志目录与规范说明 | 客户能按文档找到最近一次报错 |
| 监控面板（如提供） | 客户 IT 能看懂三个数：是否在跑、快不快、出没出错 |
| 告警配置说明 | 写明告警发给谁、什么条件下发、怎么关 |
| 数据保留策略 | 日志/指标保留多久，磁盘怎么清理 |

验收标准：**服务挂掉后，客户或你能在 10 分钟内知道，并且能找到日志里对应的那次事故。**

## 决策点

- **岔路口 1：要不要上 Prometheus + Grafana**
  - 条件：机器数量、客户是否有 IT 团队、是否要接客户已有系统。
  - 推荐：**单机单服务不上**，用日志 + 健康检查页；多机或客户有 IT 就上标准栈。
  - 代价：标准栈要多维护两三个服务，客户机器资源也要占一点。

- **岔路口 2：监控数据放客户机器还是传出来**
  - 推荐：**默认留在客户机器**，你远程看。客户数据不出域是硬约束（见 [[安全与合规]]）。
  - 代价：你没法主动看，需要"客户开着通道"或客户帮你看。

- **岔路口 3：日志要不要记录 prompt 和输出**
  - 推荐：**默认不记全文**，记长度、hash、耗时、错误类型。排障确需时临时开启并告知客户。
  - 代价：有些问题（质量类）没有原文很难查，需要客户配合复现。

- **岔路口 4：告警发给自己还是发给客户**
  - 推荐：**P0 双发**（你 + 客户 IT），P1/P2 只给你。客户只想知道"能不能用"，不想看技术细节。
  - 代价：双发会让客户 IT 有依赖，反而增加沟通。

- **岔路口 5：实时面板 vs 定时巡检报告**
  - 推荐：**客户看周报，你看实时面板**。客户看实时面板容易过度解读（"刚才那个尖峰怎么回事"）。
  - 代价：要花时间做报告，但这部分可以包装成运维服务收费。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| 采集间隔 | 多久抓一次指标 | 太密浪费资源，太疏看不到尖峰 | 机器指标 15~60 秒 |
| 日志级别 | 记录详细程度 | `DEBUG` 会写爆磁盘 | 生产 `INFO`，排障临时 `DEBUG` |
| 日志保留天数 | 存多久 | 太短查不到旧事故，太长占磁盘 | 30 天起 |
| 日志轮转大小 | 单文件多大切换 | 太大不好打开，太小文件太多 | 100~500MB |
| 告警连续次数 | 连续几次越界才告警 | 太小误报刷屏，太大反应慢 | 3~5 次 |
| 延迟阈值 | P99 超过多少告警 | 按客户可接受度定，不是拍脑袋 | 用基线 ×2 左右 |
| 显存告警阈值 | 超过多少算危险 | 太敏感常有误报 | 留 10% 以上余量 |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| 磁盘突然满了，服务挂了 | 日志没轮转，一直追加 | 配轮转；监控磁盘；大日志文件定期清理 |
| 告警天天响，最后没人看 | 阈值太敏感或告警不可行动 | 只对可行动的留即时告警；其余转日报；定期清理告警规则 |
| 服务挂了但监控显示正常 | 只监控了进程（`docker ps` 在），没监控"能否出字" | 健康检查要做一次真实推理或轻量请求 |
| 客户说慢，你看指标一切正常 | 只看平均值，没看分位数；或者监控没覆盖应用层 | 加 P95/P99；把"端到端耗时"从客户端侧也测 |
| 日志里看不出问题 | 级别用错（全 INFO/全 ERROR）、缺上下文、缺请求 id | 定日志规范，ERROR 必须带上下文（见上文样例） |
| 显存监控曲线一直一条直线 | 采的是"分配总量"不是"使用量"，或指标取错了字段 | 核对指标定义；用 `nvidia-smi` 交叉验证 |
| 客户 IT 拒绝装监控 agent | 安全合规不允许 | 降级为"日志 + 客户自检脚本"，把限制写进交付文档 |
| 换人接手后看不懂面板 | 面板没文档、指标没命名规范、没人讲过一次 | 交付时做一次 15 分钟讲解 + 一页纸说明 |

> [!tip] 别忽视"日志写得好"的商业价值
> 客户出问题时，你能说"我看一下日志"然后 5 分钟给出结论，和"你帮我敲几个命令把输出发我"再猜半小时，客户感受完全不同。日志规范是低成本的信任来源。

## 自检问题参考答案

> [!success]- 1. 监控三层各回答什么问题？
> 机器层（GPU、温度、功耗、磁盘、内存、网络）回答"这台机器健康吗"；服务层（进程、端口、模型加载完没、健康检查）回答"服务能用吗"；业务层（延迟、QPS、错误率、输出长度）回答"用户用得好吗"。分层的好处是告警一出来，你知道先看哪一层。

> [!success]- 2. 显存高没事、持续上涨为啥有事？
> 模型本来就要常驻显存，占用高说明加载好了，是正常状态；持续上涨才说明有东西在累积——显存泄漏、碎片、KV Cache 没释放、超长请求过后没回落。判据是看趋势曲线而不是瞬时值；显存突然归零则说明进程挂了。

> [!success]- 3. 利用率 100% 但吞吐低是为什么？
> 可能是真到瓶颈了，更常见的是"在干无效活"：多个进程抢同一张卡互相等带宽、模型其实跑在 CPU 上、PCIe 通道减半、CPU 或内存拖住 GPU、请求在应用层串行排队。利用率高不等于有效吞吐高，要结合分位数延迟和请求日志一起看。

> [!success]- 4. 可排错的日志要有哪三类信息？
> 一是什么时候在哪个环节（时间戳加组件名），二是发生了什么、严重不严重（级别加一句话），三是现场什么样（关键参数、请求 id、异常栈）。只有一句 `Error: failed` 的日志等于没有，因为看不出任何上下文，也没法关联到具体请求。

> [!success]- 5. 哪些告警应该直接删掉？
> 判断标准只有一句：收到这条告警我具体要做什么，答不上来就删。GPU 利用率 95% 说明正常工作、磁盘使用率 60% 还早，通知你都没有行动可做；显存连续 10 分钟上涨、健康检查连续失败才是可行动的。告警疲劳比没告警更糟。

> [!success]- 6. Prometheus 与 Grafana 分工？
> Prometheus 负责存指标并按规则算告警，它定时去服务的 `/metrics` 抓文本格式的指标清单；Grafana 负责画图，把指标做成面板给客户看；Exporter 负责把本来没有指标的东西变成有指标（机器用 `node_exporter`，GPU 用 `dcgm-exporter`）。单机单服务不需要这套。

> [!success]- 7. 日志里为什么不能记原文？
> 记全文等于把客户数据又存了一份副本，还没人管：日志可能被打包带走、被越权查看，本地部署"数据不出域"的卖点就崩了。默认只记请求 id、长度、耗时、错误类型；质量类问题用客户脱敏后的样本复现，确需原文时单独目录、单独权限、明确保留期并告知客户。

> [!success]- 8. 服务挂了多久内必须知道？
> 目标是不超过 10 分钟。做法是健康检查连续失败触发 P0 告警、双发给你和客户 IT，再加一个定时巡检脚本每几分钟把关键指标写一行日志。别只监控进程存活，`docker ps` 里还在但模型已经不能出字，同样算挂，健康检查要做一次真实或轻量推理。

## 交付视角（对客户怎么讲）

- **客户问"我怎么能知道它挂了"**：给他一个健康页面 + 一句"挂了我会先知道"。别承诺 7×24 值守，除非真的有运维团队，那要另算钱。
- **客户问"日志里会不会有我们的资料"**：明确回答"默认只记长度和耗时，不记内容"，并把这条写进交付文档。
- **客户问"能不能接我们公司的监控系统"**：能，但要确认他们用什么（Prometheus/Zabbix/云监控），适配是额外工作量，单独计价。
- **报价口径**：监控和日志分两档——"基础（健康检查 + 日志 + 一页纸说明）"包含在部署里；"进阶（面板 + 告警 + 周报）"作为运维服务按月收。
- **限制说清**：监控数据留在客户机器上，你不主动向外传；要不要外传、传什么，由客户书面确认。

# 容器化部署

> [!abstract] 一句话讲清楚
> 把"能跑通的推理服务"连同它依赖的 Python、CUDA、系统库一起打包成镜像，让它在客户机器上和在你机器上表现一致；顺便解决 GPU 直通、模型文件怎么进去、开机怎么自动起来这三个问题。

## 为什么重要

- **交付翻车的第一大原因是环境不一致**：你机器上装过一堆东西，客户机器是干净的；源码拷过去就开始缺库、版本冲突。
- **容器是"交付标准件"**：镜像 = 环境说明书 + 可执行文件。写清楚镜像版本，等于写清楚"这套东西在哪都能复现"。
- **它把责任边界变清晰**：镜像内是交付方的事，镜像外（数据、配置、GPU 驱动）是客户环境的事。验收时这条边界特别有用。
- 典型场景：客户有一台 4090 工作站，要求"装好之后开机自动起、断网也能用、以后换机器能搬过去"。没有容器化，这三条几乎都做不到。

上游是 [[Docker 与容器化基础]] 和 [[驱动-CUDA-框架版本兼容]]，下游直接接 [[远程交付与远程运维]] 和 [[监控与日志]]。

## 核心名词全解

| 名词 | 英文 / 缩写 | 大白话解释 | 容易混淆 / 注意 |
|---|---|---|---|
| 镜像 | Image | 一个打包好的"只读模板"，里面是 Python、CUDA 库、你的代码 | 镜像是死的，跑起来才叫容器；镜像是分层的，改一层只重传那一层 |
| 容器 | Container | 镜像跑起来的一个实例，有自己的文件系统和进程空间 | 容器删了里面的数据就没了，数据必须放在卷/挂载里 |
| Dockerfile | Dockerfile | 描述"怎么从基础镜像一步步装出你的镜像"的脚本 | 不是安装脚本，每行生成一层；层数多不等于慢，乱序缓存失效才慢 |
| GPU 直通 | GPU Passthrough | 让容器里的程序直接看到宿主机的显卡 | 不是虚拟化切分，容器里看到的就是整卡；多卡要指定哪几张 |
| NVIDIA Container Toolkit | nvidia-container-toolkit | 让 Docker 能把 GPU 设备"接"进容器的官方组件 | 只装显卡驱动不够，缺它 `--gpus` 会直接报错或看不到卡 |
| 基础镜像 | Base Image | 你的镜像从哪来（如 `nvidia/cuda`、`pytorch/pytorch`） | 起点决定上限：基础镜像的 CUDA 版本决定了能装什么版本的框架 |
| 卷 / 挂载 | Volume / Bind Mount | 把宿主机的一个目录"接"到容器里 | 模型文件、数据、日志都该走挂载，不该打进镜像 |
| 镜像体积 | Image Size | 打包出来多大 | 体积大 → 传输慢、客户磁盘吃紧、离线交付拷 U 盘时间翻倍 |
| compose | Docker Compose | 用一个 YAML 描述"起哪些容器、怎么连、挂什么卷" | 单机多容器编排，不是集群方案；客户机器上只要一个 compose 文件 |
| 离线镜像包 | Offline Image Tar | 用 `docker save` 导出成 tar，拿到无网环境 `docker load` | 客户内网没网时唯一可靠的交付方式，见 [[模型获取与离线搬运]] |
| 健康检查 | Healthcheck | 容器自己报告"我还活着吗" | 只能证明进程在，不等于模型加载完了、能出字了 |

> [!warning] 最容易被搞混的一对
> **`docker exec` 进去能跑** ≠ **服务健康**。很多"容器起来了但 API 不通"的情况，是模型还在加载（大模型加载 1~3 分钟很正常），健康检查写得太乐观。

## 原理与机制

### 直觉：容器不是虚拟机

虚拟机是"模拟一台电脑"，里面有完整的操作系统；容器是"给进程加个隔离的视野"，共用宿主机内核，只是看不到别人的东西。

所以：

- 容器**启动快**（秒级），但**不能装自己的内核**——内核版本跟着宿主机走。
- 容器**不能真的隔离 GPU**：GPU 是设备节点，容器只是被允许访问 `/dev/nvidia*`。
- 容器**不是安全边界**：客户让你"用容器隔离租户"，那是做不到的，别承诺。

### 关键机制一：GPU 是怎么进容器的

宿主机上装了 NVIDIA 驱动后，会出现一组设备节点（`/dev/nvidia0`、`/dev/nvidiactl`、`/dev/nvidia-uvm` 等）。NVIDIA Container Toolkit 负责在启动容器时：

1. 把需要的设备节点映射进容器；
2. 把宿主机的驱动库（`libcuda.so` 这一类）挂进容器；
3. 注入 `NVIDIA_VISIBLE_DEVICES`、`NVIDIA_DRIVER_CAPABILITIES` 这些环境变量。

**后果**：容器里的 CUDA 用户态库是你镜像里带的（可以和宿主机驱动版本不完全一致），但**驱动是宿主机的**。这就解释了最经典的一条规则——

> 宿主机驱动版本必须 ≥ 镜像里 CUDA 运行时的要求。反过来说，镜像里的 CUDA 版本可以比宿主机的老，但不能比它新太多。

这也解释了为什么"我 CUDA 装的是 12.x，为什么 nvidia-smi 显示的是 12.y"——`nvidia-smi` 右上角那个是**驱动支持的最高 CUDA 版本**，不是"你装了 12.y"。

### 关键机制二：模型文件为什么不该打进镜像

模型动辄几个 G 到几十 G。打进镜像会带来：

- 镜像分层缓存全废：改一行代码也要重传整个模型层；
- 客户想换模型就得换镜像；
- 离线交付时 tar 包大到无法拷。

正确做法是**代码进镜像，模型走挂载**。容器启动时把宿主机的模型目录挂到约定路径，引擎按路径加载。

例外：如果你要交付一个"开机即用、不许客户乱改"的黑盒，把模型打进去反而更省心——但要在 SOP 里写清楚"换模型需重新交付镜像"。

### 关键机制三：为什么需要 compose 而不是一堆 `docker run`

`docker run` 的参数会散在聊天记录、文档、你的记忆里。客户重启机器、或者换个运维接手，参数就丢了。

compose 文件本质是**把启动参数固化成一个可版本控制的文件**：端口、卷、GPU、环境变量、重启策略、健康检查全在里面。交付时这一个文件就是"服务定义说明书"。

## 完整流程

`输入 → 动作 → 输出 → 验收标准`

### 1. 输入：确认三件事

- **客户机器**：显卡型号与数量、驱动版本、磁盘剩余、是否有网。
- **服务形态**：只要 API 还是要带界面？单模型还是多模型？
- **运维要求**：开机自启？谁来启动？日志放哪？出问题找谁？

> 这一步没确认就开做，后面 80% 的返工来自这里。

### 2. 选基础镜像（决定成败的一步）

按链条倒推：**客户驱动版本 → 允许的 CUDA 版本 → 框架版本 → 基础镜像**。

建议优先选官方维护的镜像（`nvidia/cuda`、`pytorch/pytorch` 的带 cuda 标签版本），不要自己从 Ubuntu 裸装 CUDA——那是给自己挖坑。

### 3. 写 Dockerfile：只做三件事

```dockerfile
# 只保留关键行：基础镜像锁定、依赖安装、启动命令
FROM nvidia/cuda:<按官方文档选定>-runtime-ubuntu22.04
RUN pip install --no-cache-dir -r requirements.txt
CMD ["python", "-m", "your_server", "--port", "8000"]
```

- **锁定基础镜像版本**，不要用 `latest`（`latest` 今天能跑，下个月就变）。
- 依赖装完清缓存（`--no-cache-dir`），否则镜像白白大几百 MB。
- 启动命令放最后一行，方便改。

### 4. 构建并本地验证（本机 GPU 上）

```bash
docker build -t llm-svc:1.0 .
docker run --gpus all -p 8000:8000 -v /data/models:/models llm-svc:1.0
```

验证顺序不要跳：**容器能起 → 能看到 GPU → 模型能加载 → API 能出字**。每步失败对应不同的排查方向（见 [[排错方法论]]）。

### 5. 写 compose，固化启动方式

```yaml
# 关键项：GPU 预留、模型挂载、重启策略
services:
  llm:
    image: llm-svc:1.0
    ports: ["8000:8000"]
    volumes: ["/data/models:/models:ro"]
    deploy: { resources: { reservations: { devices: [{ driver: nvidia, count: all, capabilities: [gpu] }] } } }
    restart: unless-stopped
```

- 模型目录挂载加 `:ro`（只读），防止程序误删客户模型。
- `restart: unless-stopped` 让机器重启后服务自己回来。
- 多卡机器用 `count: 1` + `device_ids` 精确指定，别用 `all` 让引擎抢占全部显存。

### 6. 离线交付准备

客户内网没网时：

```bash
docker save llm-svc:1.0 -o llm-svc-1.0.tar
# 客户机上：docker load -i llm-svc-1.0.tar
```

顺序是：**先在客户机器上确认基础镜像/工具链有没有**，再传你的镜像。别忘了 compose 文件、配置模板、模型文件、启动脚本要一起打包。

### 7. 输出与验收标准

| 交付物 | 验收方式 |
|---|---|
| 镜像 tar（或镜像仓库地址） | 客户机上 `docker load` 成功、`docker images` 能看到 |
| compose 文件 + 启动脚本 | 客户自己按文档执行一次能起来 |
| 模型目录说明 | 挂载路径、换模型怎么改，写在文档里 |
| 冒烟测试脚本 | 一行 curl 能返回一段文字，非空且是中文/英文正常文本 |
| 运维说明 | 启停命令、日志位置、常见自检命令 |

验收的硬标准只有一条：**在客户操作的机器上，按你写的文档，客户能自己把服务起来并打通一次请求。**

## 决策点

- **岔路口 1：模型打包进镜像 vs 挂载**
  - 条件：模型是否会换、镜像多大能接受、客户是否允许碰模型目录。
  - 推荐：**默认挂载**。只有"黑盒交付、客户完全不管"的场景才打包进去。
  - 代价：挂载多一个配置项，客户装错路径会加载失败；打包则换模型必须重新交付。

- **岔路口 2：自己写 Dockerfile vs 用官方镜像 + 改启动参数**
  - 条件：引擎是否官方有镜像（vLLM、Ollama 一般都有）。
  - 推荐：**能用官方镜像就先用**，只加一层配置。等参数复杂到官方镜像盖不住，再自己写。
  - 代价：官方镜像通常体积偏大，且默认参数不一定适合你的卡。

- **岔路口 3：单容器 vs compose 多容器**
  - 条件：是否要一起起 Web UI、反向代理、监控 agent。
  - 推荐：**API + UI + 反代 用 compose**；只有单个推理服务时，一个 compose 也比 `docker run` 好。
  - 代价：compose 有学习成本，客户运维要看懂 YAML。

- **岔路口 4：交付镜像 tar vs 交付 Dockerfile + 构建**
  - 条件：客户有网且愿意自己构建 → Dockerfile；无网或不想让客户构建 → tar。
  - 推荐：**默认交付 tar + 保留 Dockerfile 作为文档**。客户构建出来的东西和你的不完全一样，出问题难界定责任。
  - 代价：tar 体积大，传输费时间；镜像仓库方案需要客户有内网 registry。

- **岔路口 5：`--network host` vs 端口映射**
  - 条件：客户是否只允许固定端口、是否有容器网络问题。
  - 推荐：**默认端口映射**（`-p`），只在容器内需要访问宿主机服务且映射麻烦时才用 host 网络。
  - 代价：host 网络丢失端口隔离，多个服务抢端口时很难查。

## 参数与配置说明

| 参数 | 作用 | 调大/调小的影响 | 常见取值 |
|---|---|---|---|
| `--gpus` | 指定容器能看到哪些卡 | 给少了模型放不下，给多了会抢占显存 | `all` / `'"device=0,1"'` |
| `NVIDIA_VISIBLE_DEVICES` | 环境变量形式的 GPU 指定 | 同上；在 compose 里更常用 | `all` / `0` / `0,1` |
| `NVIDIA_DRIVER_CAPABILITIES` | 容器需要驱动的哪些能力 | 默认 `utility,compute`；要用视频编解码才加 `video` | `compute,utility` |
| `shm-size` | 容器内共享内存大小 | 太小会导致多进程/大 batch 直接崩 | 按内存的 1/4 给，如 `8g` |
| `restart` | 重启策略 | `always` 会无限重启刷日志；`no` 挂了就挂着 | `unless-stopped` |
| `volumes :ro` | 只读挂载 | 防止误删；但程序要写缓存时得另开可写目录 | 模型 `:ro`，日志可写 |
| `healthcheck.interval` | 健康检查间隔 | 太短会让大模型加载期一直被判定不健康 | 加载慢的服务给 `30s~60s`，`start_period` 给足 |
| `deploy.resources.reservations` | compose 里的 GPU 预留 | 只在 compose 规范下生效，写错会被忽略且不报错 | 必须写 `capabilities: [gpu]` |

## 常见坑与误区

| 现象 | 原因 | 对策 |
|---|---|---|
| Docker 里 `nvidia-smi` 报 `could not select device driver` | 宿主机没装 NVIDIA Container Toolkit，或装了没重启 docker | 装 toolkit 后 `systemctl restart docker`；先用 `--gpus all` 跑一个最小验证 |
| 容器里能看到卡，但跑模型报 `CUDA driver version is insufficient` | 镜像里的 CUDA 运行时比宿主机驱动支持的版本新 | 降基础镜像 CUDA 版本，或升级宿主机驱动；别去降框架版本 |
| 镜像动辄二三十 G，拷 U 盘要一小时 | 把模型打进了镜像层，或 `pip` 缓存没清 | 模型改挂载；`--no-cache-dir`；用多阶段构建把编译依赖丢在中间层 |
| `docker load` 后服务起来但 API 一直超时 | 模型还在加载，健康检查太乐观；或端口映射到了别的进程 | 看容器日志等加载完成；`start_period` 给足；`netstat` 确认端口归属 |
| 改了代码重新 build，但跑起来还是老行为 | Docker 层缓存复用了旧层，或 `docker run` 用了旧 tag | 确认 `docker images` 的 tag 和时间；关键位置加 `--no-cache`；用版本号 tag 不用 `latest` |
| 客户机器上容器起不来，报 `no space left on device` | Docker 默认数据目录在系统盘，客户系统盘只剩几 G | 交付前查 `df -h`；把 Docker data-root 或模型目录挪到大盘 |
| 加了 `--gpus all` 后另一个服务变慢 | 两个容器都在抢同一张卡的显存，互相挤 | 每个服务显式指定 `device_ids`；用 `nvidia-smi` 看谁占着 |
| 宿主机重启后服务没起来 | 用了 `docker run` 没写 `--restart`，或客户环境 Docker 服务没设开机自启 | 用 compose + `restart: unless-stopped`；把"开机自启"写进验收清单 |

> [!warning] 一个不写在文档里迟早会踩的坑
> 客户机器上往往已经有一个"别的部门装的 Docker"，数据目录、端口、甚至 Docker 版本都和你预期不同。**交付前一定先在客户机器上跑一遍 `docker info`**，别假设。

## 交付视角（对客户怎么讲）

- **客户问"为什么要用 Docker，直接装不行吗"**：直接装也行，但下次换机器、换系统、升级，环境要重来一遍。打包成镜像相当于把这套环境"刻成光盘"，换机器直接放进去就能跑，也方便以后回滚。
- **客户问"镜像多大/要多久"**：取决于模型大小和依赖，通常几百 MB 到十几 G。模型文件单独放，不占镜像传输时间。
- **客户问"数据放在容器里安全吗"**：数据不在容器里，在客户自己的目录，容器只是"读"它。容器删了数据还在。
- **报价口径**：容器化的工作量不在于写 Dockerfile，而在于**适配客户的显卡/驱动/网络**和**写运维文档**。按"环境适配 + 打包 + 文档 + 验收陪跑"拆开报，比笼统报"部署费"更容易被接受。
- **限制要提前说**：容器不隔离 GPU、不隔离租户；客户多部门共用一台机器时，需要额外做端口和账号隔离方案，这部分单独算。
